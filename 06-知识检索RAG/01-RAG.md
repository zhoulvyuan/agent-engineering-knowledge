# RAG / 检索增强生成

> **状态**：🟢 已理解 ｜ **深度**：A 深入掌握 ｜ **更新**：2026-09-15
> **上级**：[06-知识检索RAG](README.md) ｜ **依赖**：Embedding、Context Engineering

## 一句话定义

> RAG（Retrieval-Augmented Generation，检索增强生成）是在生成前先从外部知识源检索出相关文本片段，并将其作为上下文一起喂给大模型，让模型基于"检索到的证据"而非仅凭参数记忆来作答的技术范式。

## 解决的问题

> 在 RAG 出现之前，大模型只能依赖训练时固化在参数里的知识，由此带来一连串麻烦：
>
> - **知识过时**：模型有训练截止时间，无法回答之后发生的事，更新知识必须重新训练，成本高、周期长。
> - **幻觉**：面对参数里没有的事实，模型会"一本正经地编造"，且无法溯源。
> - **私域/长尾知识缺失**：企业内部文档、个人资料、冷门领域不在公开训练语料中，模型根本不知道。
> - **无法引用来源**：答案不可验证、不可审计，难以在企业场景落地。
> - **上下文窗口有限**：无法把整个知识库直接塞进 prompt，需要一种"按需取用"的机制。

### RAG 解决什么问题

RAG 本质上解决的是"让模型使用它参数里没有、或不可靠的知识"这一问题，具体包括：

- **知识时效性**：把易变、需频繁更新的知识外置到可随时增删改的知识库，更新知识不再需要重训模型。
- **事实可靠性与可溯源**：答案建立在检索到的文档片段上，可以附带引用来源，便于验证和审计，显著降低幻觉。
- **私域知识接入**：无需把企业机密数据写进模型权重，就能让模型"读懂"内部文档。
- **成本可控**：相比微调或重训，维护一个向量索引的边际成本极低。

一句话：RAG 把"记忆"和"推理"解耦——模型负责理解与组织语言，知识库负责提供事实。

### 为什么不能只依赖模型参数

- **参数是有损、压缩的记忆**：训练把海量语料压进有限参数，细节（具体数字、长尾实体、罕见事实）容易丢失或被"脑补"。
- **知识冻结在训练截止点**：参数无法感知之后发生的变化，而现实知识持续更新。
- **无法区分"知道"与"猜测"**：模型对参数化知识没有置信度边界，不知道的也会流畅输出，造成幻觉。
- **更新代价高**：改动参数里的某条事实需要微调甚至重训，无法做到像数据库一样增删改查。
- **不可审计**：参数是黑箱，答案无法指向具体出处，不满足合规和可信要求。

因此工程上更稳妥的做法是：事实类、易变类、私域类知识放外部检索；语言能力、推理模式、通用常识留在参数里。

### RAG 基本流程（切分 / 索引 / 检索 / 重排 / 注入）

典型流程分为**离线构建**与**在线查询**两个阶段：

| 阶段 | 步骤 | 说明 |
| --- | --- | --- |
| 离线 | 切分 Chunking | 把文档按语义/长度切成片段，权衡：太大则噪声多、检索不精准，太小则语义不完整。常用重叠切分、按标题/段落切分。 |
| 离线 | 索引 Indexing | 对每个 chunk 用 Embedding 模型生成向量，存入向量数据库（如 FAISS、Milvus、pgvector）；也常同时建倒排/BM25 索引支持关键词检索。 |
| 在线 | 检索 Retrieval | 把 query 向量化，用向量相似度（+ 关键词）召回 Top-K 候选片段；常用混合检索（dense + sparse）提升召回。 |
| 在线 | 重排 Rerank | 用更强的 Cross-Encoder 对召回的候选做精排，把最相关的几条排到前面，解决"召回高但排序差"的问题。 |
| 在线 | 注入 Augmentation | 把精排后的片段拼进 prompt 模板（通常附带来源/指令约束），连同原始问题一起交给 LLM 生成答案。 |

关键点：检索召回侧重"宁多勿漏"，重排侧重"去粗取精"，注入侧重"组织上下文 + 约束模型只依据证据作答"。

### RAG 与微调的取舍

两者解决的问题不同，常常互补而非互斥：

| 维度 | RAG | 微调 Fine-tuning |
| --- | --- | --- |
| 适合解决 | 注入**事实/知识**，尤其易变、私域、需溯源 | 调整**行为/风格/格式**，教会特定任务范式 |
| 知识更新 | 改库即可，实时、低成本 | 需重新训练，慢、贵 |
| 可溯源 | 可附来源 | 不可溯源 |
| 幻觉 | 显著降低（有证据约束） | 不一定降低，甚至可能固化错误 |
| 推理延迟 | 增加（检索 + 更长上下文） | 不增加 |
| 典型场景 | 问答、知识库助手、文档检索 | 领域语气、特定输出结构、指令遵循 |

经验法则：**"模型不知道的事实"用 RAG，"模型不会做的任务/风格"用微调**。两者可叠加（微调一个擅长用检索上下文作答的模型）。

### RAG 的失效模式（检索不到 / 检索到但不相关 / 上下文冲突）

- **检索不到（召回失败）**：知识本身不在库里，或切分/向量化导致语义丢失、query 与文档表述差异大（词汇鸿沟）。对策：混合检索、查询改写/扩展（HyDE、Multi-Query）、更好的切分与 Embedding。
- **检索到但不相关（精排失败）**：Top-K 里混入噪声片段，稀释了真正相关的内容。对策：Rerank 精排、调小 K、相关性阈值过滤。
- **上下文冲突**：检索片段之间互相矛盾，或与模型参数化知识冲突，模型可能选错或折中出错。对策：注明来源优先级、时间戳去旧、提示模型"仅依据给定材料并指出冲突"。
- **"迷失在中间"（Lost in the Middle）**：上下文过长时模型忽略中间位置的信息。对策：精排后只放少量高质量片段，重要内容放首尾。
- **忠实性失败**：即使检索正确，模型仍脱离证据自由发挥。对策：强约束 prompt、要求逐句引用、加事实核查/评测（如 RAGAS 的 faithfulness 指标）。

## 核心内容

- **两阶段架构**：离线建索引（切分 → Embedding → 入向量库），在线查询（检索 → 重排 → 注入 → 生成）。
- **切分 Chunking**：决定检索粒度，是效果上限的关键，需按语义边界切并控制重叠。
- **Embedding + 向量检索**：把语义相似转化为向量空间的近邻搜索（ANN），是 dense retrieval 的核心。
- **混合检索（Hybrid）**：dense（语义）+ sparse（BM25/关键词）互补，兼顾语义与精确匹配。
- **重排 Rerank**：用 Cross-Encoder 对候选精排，大幅提升 Top-N 相关性。
- **查询增强**：查询改写、Multi-Query、HyDE、Step-back 等提升召回质量。
- **上下文注入与 Prompt 约束**：组织证据、附来源、约束模型"只依据材料作答"。
- **评测**：召回率/命中率（检索侧）、faithfulness/answer relevancy（生成侧），工具如 RAGAS。
- **进阶形态**：GraphRAG（结合知识图谱）、Agentic RAG（多轮/工具式检索）、Self-RAG（模型自判是否需检索）。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | Embedding / 向量检索 | RAG 的召回依赖 Embedding 把文本映射到向量空间，并用 ANN 做近邻搜索；Embedding 质量直接决定检索上限。 |
| 下游 | Context Engineering / Prompt 工程 | 检索到的片段最终要通过上下文组织与 prompt 约束注入模型，RAG 的"最后一公里"是上下文工程。 |
| 易混淆 | 微调（Fine-tuning）/ 长上下文（Long Context） | 微调改的是模型行为与参数化知识，RAG 注入的是外部事实；长上下文是"直接塞更多文本"，RAG 是"按需检索少量相关文本"，两者可结合但不等价。 |

## 典型工程场景

- **企业知识库问答**：基于内部文档、Wiki、规章制度的智能客服与员工助手。
- **文档/合同/研报分析**：对私有长文档做问答、摘要、要点抽取并给出出处。
- **客服与技术支持**：结合产品手册、工单历史回答用户问题，降低幻觉。
- **代码库助手**：检索相关代码片段、API 文档辅助代码生成与答疑。
- **搜索增强型应用**：在搜索结果上做生成式摘要与直答。
- **垂直领域助手**：医疗/法律/金融等需要可溯源、强时效的专业问答（注意合规，不替代专业意见）。

## 适用边界

**适合使用**

- 知识**易变、需频繁更新**，不适合固化进参数。
- 需要**可溯源、可审计**的答案（企业、合规场景）。
- **私域/长尾知识**，不在公开训练语料中。
- 知识量大、无法全部塞进上下文窗口，需要按需取用。
- 对**降低幻觉**有强需求的事实型问答。

**不适合使用**

- 任务是改变模型**行为、风格、输出格式**，而非补充事实——该用微调。
- 问题依赖**全局推理/多跳综合**，单纯片段检索难以覆盖（需 GraphRAG 或 agentic 检索）。
- 知识库本身**质量差、噪声大**，检索只会放大错误（垃圾进垃圾出）。
- 对**延迟极度敏感**且知识稳定的场景，检索开销不划算。
- 知识**极小且稳定**，直接写进 prompt 或系统提示更简单。

## 常见误区

- **"接上向量库就万事大吉"**：切分、Embedding、重排、评测任一环节差都会拖垮效果，RAG 是系统工程而非插件。
- **"RAG 能消除幻觉"**：只能显著降低，模型仍可能脱离证据自由发挥，需忠实性约束与评测。
- **"检索 Top-K 越大越好"**：K 过大引入噪声、稀释相关信息并触发"迷失在中间"，通常配合重排取少量高质量片段。
- **"RAG 和微调二选一"**：两者解决不同问题，常常互补叠加。
- **"相似度高就等于相关"**：向量相似 ≠ 真正能回答问题，需要重排和相关性判断。
- **"切分只是技术细节"**：切分策略往往是效果差异的最大来源之一。
- **"有了长上下文就不需要 RAG"**：长上下文成本高、仍有"迷失在中间"问题，且无法替代对海量知识库的按需检索与溯源。

## 我的结论

> **何时该用**：当问题的瓶颈是"模型缺少某些事实知识"——尤其是私域的、易变的、长尾的、需要溯源的知识，且这些知识量大到无法直接塞进上下文时，RAG 是首选且性价比最高的方案。它让知识更新从"重训模型"降维成"维护数据库"。
>
> **何时不该用**：当瓶颈是"模型不会做某种任务、不符合某种风格或格式"时，RAG 无能为力，应选微调；当知识极少且稳定时，直接写进 prompt 更简单；当问题需要跨文档全局推理时，普通 RAG 不够，要上 GraphRAG/Agentic RAG。
>
> **判断底线**：把 RAG 当成一套检索—重排—注入—评测的系统工程来做，而不是"接个向量库"。效果的天花板由切分质量、Embedding、重排和忠实性约束共同决定；缺乏评测的 RAG 等于盲飞。
