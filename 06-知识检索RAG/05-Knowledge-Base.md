# Knowledge Base / 知识库

## 一句话定义

> 知识库是把企业分散的文档、数据与经验，经过采集、清洗、切分、标注和向量化后，统一存储并提供检索接口的结构化知识资产集合，供人或 AI 应用（如 RAG）按需查询。

## 解决的问题

> 在知识库出现之前，组织的知识散落在 Wiki、网盘、工单系统、代码仓库、邮件和员工个人经验里，存在三类麻烦：一是"找不到"——信息孤岛导致同一问题反复被问、答案难以定位；二是"信不过"——同一主题存在多个过期或冲突版本，无法确定哪个是权威答案；三是"用不上"——大模型本身知识有截止日期且不了解企业内部私有信息，直接问会产生幻觉。知识库通过集中治理与统一检索，为人工检索和 LLM 应用提供一个可信、可更新、可追溯的知识来源。

### Knowledge Base 与 RAG 的关系

- 知识库是"数据资产 + 存储检索能力"，RAG 是"把检索结果注入 LLM 生成"的应用范式；二者是被依赖与依赖的关系，而非同一层概念。
- 在 RAG 流水线里，知识库承担"检索"（Retrieval）环节的后端：负责内容的入库、索引、过滤和召回；RAG 再做重排、拼接 Prompt、交给 LLM 生成（Generation）。
- 一个高质量知识库可以服务多种消费方：RAG 问答、Agent 工具调用、传统全文搜索、BI 报表，并不绑定 LLM。
- 工程直觉：RAG 效果的上限往往由知识库的数据质量和召回质量决定，而非仅由模型大小决定——"garbage in, garbage out"。

### 企业知识库的基本架构

典型分层如下：

| 层 | 职责 | 关键组件/技术 |
| --- | --- | --- |
| 接入/采集层 | 从多数据源抽取内容 | 连接器（Confluence、SharePoint、Git、数据库）、增量同步、OCR |
| 处理/加工层 | 清洗、切分(chunking)、抽取元数据、Embedding | 文档解析、分块策略、向量化模型、元数据/标签 |
| 存储/索引层 | 持久化并建立可检索索引 | 向量库(如 Faiss/Milvus/pgvector)、倒排索引(ES/OpenSearch)、原文对象存储 |
| 检索/服务层 | 对外提供召回与过滤接口 | 向量检索 + 关键词检索(混合检索)、重排、权限过滤、API/SDK |
| 治理/运维层 | 版本、权限、监控、评估 | 血缘、审计日志、召回评测、数据新鲜度监控 |

- 实践中常用"混合检索"（向量语义检索 + BM25 关键词检索 + 重排模型）兼顾语义泛化与精确匹配。
- 元数据（来源、时间、部门、密级、标签）是实现过滤、权限和失效治理的关键，不是可选项。

### 知识的更新、版本与失效处理

- 更新方式：全量重建成本高、延迟大；生产上更常用增量同步（基于源系统的变更事件/时间戳/哈希比对），仅对变化文档重新切分和向量化。
- 版本管理：对文档保留版本号与生效时间；更新时不是盲目覆盖，而是替换对应 chunk 的向量并同步元数据，避免旧 chunk 残留导致"幽灵答案"。
- 失效处理：为知识设置时效元数据（如 valid_until、last_reviewed），检索时过滤或降权过期内容；对已删除源文档要级联清理索引，防止检索到已不存在的内容。
- 一致性难点：Embedding 模型升级会使新旧向量不可比，通常需要对全库重新向量化（re-embedding），这是一次有成本的迁移，应纳入版本规划。
- 建议建立"数据新鲜度"监控指标与定期复审机制，而非只在出错后被动修复。

### 权限与多租户隔离

- 核心原则：检索结果必须经过与源系统一致的权限校验，杜绝"越权召回"——用户不应通过问答看到其无权访问的原文。
- 常见做法：
  - 行级/文档级权限：在每个 chunk 的元数据中记录 ACL（允许的用户/角色/部门），检索时按当前用户身份做 metadata 过滤。
  - 多租户隔离：按 tenant_id 做物理分库/分集合（强隔离）或逻辑分区 + 强制过滤（弱隔离）；SaaS 场景优先考虑强隔离以防数据串租。
  - 密级分层：按公开/内部/机密分级，结合用户 clearance 控制可见范围。
- 工程陷阱：权限过滤若放在"召回之后"做后过滤，可能导致 top-k 被无权内容占满、有权内容被挤出；更稳妥是把权限作为检索的前置过滤条件。
- 审计：记录"谁、何时、检索到哪些文档"，满足合规与可追溯要求。

## 核心内容

- 本质：知识库 = 内容(原文) + 结构(元数据/标签/关系) + 索引(向量+关键词) + 检索服务 + 治理。
- 数据生命周期：采集 → 解析清洗 → 分块(chunking) → 向量化 → 入库建索引 → 检索召回 → 更新/失效。
- 分块(chunking)是质量关键：块太大召回噪声多、太小丢失上下文；常用按语义/标题结构切分并设重叠(overlap)。
- 检索范式：纯向量语义检索、纯关键词检索、混合检索 + 重排(reranker)，生产多采用混合检索。
- 元数据驱动：过滤、权限、时效、来源溯源都依赖规范的元数据。
- 质量评估：以召回率/命中率、MRR/NDCG、答案可溯源性、新鲜度等指标持续评测，而非一次性建好即止。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | Embedding 模型、文档解析/分块、向量数据库 | 知识库的构建依赖向量化模型把文本转为向量、依赖解析与分块把原文切成可检索单元、依赖向量库/倒排索引做持久化与检索。 |
| 下游 | RAG、Agent、问答/搜索应用 | 知识库作为检索后端被 RAG 和 Agent 消费，为 LLM 生成提供事实依据，也可直接服务企业搜索。 |
| 易混淆 | 向量数据库、知识图谱 | 向量数据库只是知识库的存储/索引组件之一，不等于知识库；知识图谱强调实体与关系的结构化表达，知识库范畴更广且常以非结构化文档为主，二者可结合（GraphRAG）。 |

## 典型工程场景

- 企业内部智能问答/客服助手：员工或客户用自然语言查询政策、产品手册、FAQ。
- 开发者文档助手：对 API 文档、代码仓库、设计文档做语义检索，辅助编码与排障。
- 法务/合规/金融知识检索：对合同、法规、研报做可溯源问答，要求权限与时效严格。
- 运维知识沉淀：把历史工单、故障复盘、Runbook 结构化，辅助故障定位。
- 多部门/多租户 SaaS 平台：为不同客户隔离各自的私有知识并提供问答能力。

## 适用边界

**适合使用**

- 知识量大、分散、更新频繁，人工检索成本高的场景。
- 需要让 LLM 基于私有/内部/实时数据作答，降低幻觉并支持溯源。
- 对答案可追溯、可审计、可控权限有要求的企业级应用。

**不适合使用**

- 知识极少或几乎不变（如几页固定文案），直接写进 Prompt 或静态页面更简单。
- 需要精确计算、事务一致性或复杂关系推理的场景，应用数据库/知识图谱/专用引擎而非文本检索。
- 对强实时（毫秒级最新）要求极高且数据变化剧烈时，检索的更新延迟可能无法满足。

## 常见误区

- 把"向量数据库"等同于"知识库"：向量库只是索引组件，知识库还包含治理、权限、更新、评估等能力。
- 认为"塞进去就能用"：忽视分块策略、元数据和数据清洗，导致召回质量差、答案不可用。
- 只用向量检索：对专有名词、编号、精确匹配场景，纯语义检索常漏召，需混合检索。
- 忽视权限与时效：直接把全部文档向量化并开放检索，造成越权泄露或引用过期内容。
- 建好即不管：不做召回评测和新鲜度监控，知识库会随时间腐化。
- 升级 Embedding 模型却不重建索引：新旧向量不可比，检索质量悄然下降。

## 我的结论

> 当知识规模大、更新频繁、需要让 LLM 基于私有数据可溯源作答，并有权限/合规要求时，应当建设知识库——它是 RAG 效果的真正地基，投入应优先放在数据质量、分块、混合检索与治理上，而不是只盯着换更大的模型。
> 反之，若知识量很小且基本不变、或任务本质是精确计算与强关系推理，就不该用知识库：直接写进 Prompt、用传统数据库或知识图谱会更简单可靠。一句话判断——"知识是否多到人找不动、又重要到不能让模型瞎编"，是则用，否则不用。
