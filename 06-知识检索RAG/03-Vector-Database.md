## 一句话定义

> 向量数据库是以高维向量（embedding）为一等公民的存储系统，通过近似最近邻（ANN）索引对"语义相似度"做高效检索，而非对字段做精确匹配。

## 解决的问题

> 在它出现之前，相似度检索要么用关系库/全文检索做关键词精确或布尔匹配，无法表达"语义相近"；要么把全部向量加载进内存做暴力线性扫描（brute-force），在百万级以上数据量时延迟和内存都不可接受。工程上还缺少对向量的持久化、分片、增量更新、过滤（元数据）与一致性管理，开发者只能自己拼装 FAISS + 存储 + 服务层。向量数据库把"ANN 索引 + 持久化 + 元数据过滤 + 水平扩展 + 服务化 API"打包成一个系统，降低了语义检索落地的工程成本。

### 向量数据库与关系数据库的区别

| 维度 | 关系数据库 | 向量数据库 |
| --- | --- | --- |
| 查询语义 | 精确匹配 / 范围 / JOIN，结果确定 | 相似度 Top-K，结果是**近似**的 |
| 核心数据 | 结构化行列 | 高维浮点向量 + 元数据 |
| 索引 | B-Tree / Hash，面向等值与区间 | HNSW / IVF / PQ 等 ANN 索引 |
| 相似度度量 | 无内建语义距离 | 余弦 / 内积 / 欧氏距离 |
| 一致性 | 强调 ACID、强一致 | 多偏向最终一致，侧重召回与吞吐 |

关键差异在于：关系库回答"哪些行满足条件"，向量库回答"哪些向量在语义上最接近查询向量"，后者为了性能主动用召回率换取延迟，结果不保证 100% 精确。注意两者并非对立——pgvector 就是在关系库里增加向量能力。

### 向量索引的基本类型与取舍

- **Flat / Brute-force**：全量线性扫描，召回率 100%，但 O(N) 延迟，仅适合小规模（几万条内）或作为召回基准。
- **IVF（倒排文件 / 聚类）**：先用 k-means 把向量分桶，查询时只扫描最近的 nprobe 个桶。省内存、构建快，但召回受分桶边界影响，nprobe 越大越准越慢。
- **HNSW（分层可导航小世界图）**：基于图的索引，查询延迟低、召回高，是目前多数场景默认。代价是内存占用高、构建较慢，参数 M / efConstruction / efSearch 影响质量与速度。
- **PQ / OPQ（乘积量化）**：对向量压缩编码，大幅降低内存与存储，常与 IVF 组合（IVF-PQ）用于超大规模，代价是精度损失。
- **DiskANN**：面向磁盘的图索引，用 SSD 承载超大规模向量，内存成本低。

取舍核心是"召回率 ×（延迟 + 内存 + 成本）"三角：小数据用 Flat；追求低延迟高召回用 HNSW；数据量极大且要控内存用 IVF-PQ / DiskANN。

### 主流选型（pgvector / Milvus / Qdrant / Chroma）的差异

| 产品 | 形态 | 适合场景 | 特点 / 取舍 |
| --- | --- | --- | --- |
| **pgvector** | PostgreSQL 扩展 | 已有 PG、数据量中等、要和业务数据一起事务与过滤 | 复用 PG 运维/备份/SQL，支持 HNSW/IVFFlat；超大规模与极致 ANN 性能不如专用库 |
| **Milvus** | 分布式专用库 | 亿级以上、需水平扩展与多索引 | 存算分离、多种索引、生态成熟；架构重、运维复杂 |
| **Qdrant** | 专用库（Rust） | 中大规模、强元数据过滤 | 过滤与 payload 能力强、性能好、部署相对轻；生态较 Milvus 新 |
| **Chroma** | 嵌入式 / 轻量 | 原型、本地开发、小规模 RAG | 上手快、Python 友好；不面向大规模高并发生产 |

一句话经验：原型用 Chroma，已有 Postgres 就先上 pgvector，需要强过滤选 Qdrant，真的到亿级规模再上 Milvus。具体版本的最新性能数据会变化，选型前应以当前官方 benchmark 为准（见待解决问题）。

### 什么时候不需要向量数据库

- 数据量很小（几万条以内）：直接用 FAISS/numpy 内存索引甚至暴力计算即可，无需独立系统。
- 已有 Postgres 且规模中等：pgvector 足够，不必单独运维专用向量库。
- 检索本质是关键词/精确匹配：用 BM25、全文检索（ES / PG 全文）更合适，语义向量反而可能降低精确度。
- 向量基本静态、离线构建一次：可用预构建索引文件 + 对象存储，不需要在线写入与分片。
- 结构化过滤为主、语义相似度为辅：优先用关系库，向量只作补充。

## 核心内容

- **数据模型**：每条记录 = 向量（固定维度浮点）+ 原始 ID + 元数据（payload），元数据用于过滤与回显。
- **距离度量**：余弦相似度、内积（dot product）、欧氏距离（L2）；需与 embedding 模型训练时的度量保持一致。
- **ANN 索引**：HNSW / IVF / PQ / DiskANN 等，用近似换性能，核心指标是召回率 vs. 延迟 vs. 内存。
- **写入与更新**：支持增量 upsert、删除、重建索引；部分系统写入后需 flush/compaction 才可检索。
- **过滤检索（filtered search）**：在相似度检索基础上叠加元数据条件（如 tenant、时间、标签），pre-filter 与 post-filter 策略影响召回与性能。
- **分片与扩展**：按向量分片、多副本保证吞吐与可用性，分布式系统存算分离。
- **工程指标**：QPS、P99 延迟、召回率@K、内存/磁盘占用、构建时间。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | Embedding 模型 | 向量库存的是 embedding 的输出；向量维度、度量方式、语义质量都由上游模型决定，模型换了索引通常要重建 |
| 下游 | RAG 检索管线 / 检索器（Retriever） | 向量库作为召回层，为 LLM 提供上下文；常与 Rerank、混合检索组合，影响最终答案质量 |
| 易混淆 | 全文检索（ES/BM25）与 FAISS 库 | 全文检索做关键词匹配而非语义；FAISS 是索引算法库而非带持久化/服务化/过滤的完整数据库 |

## 典型工程场景

- RAG 知识库问答：文档切块 → embedding → 入库 → 语义召回喂给 LLM。
- 语义搜索 / 相似推荐：相似商品、相似文章、以图搜图、相似代码片段。
- 去重与聚类：近重复内容检测、用户/实体画像聚类。
- 多模态检索：文本-图像-音频统一到向量空间做跨模态搜索。
- 长期记忆 / Agent memory：把对话或事件向量化存储，供 Agent 后续按语义召回。
- 异常检测：用向量距离识别离群点。

## 适用边界

**适合使用**

- 需要"语义相似"而非精确匹配的检索（RAG、语义搜索、推荐）。
- 数据量大到暴力扫描不可行（百万级以上），需要 ANN 加速。
- 需要在线增量写入、元数据过滤、水平扩展与服务化 API。
- 多模态或非结构化内容需要统一到向量空间检索。

**不适合使用**

- 以精确匹配、范围查询、复杂 JOIN 为主的结构化业务查询。
- 数据量很小，内存索引或暴力计算已足够。
- 要求结果 100% 精确可复现（ANN 本质是近似）。
- 需要强事务一致性且写读强保证的核心交易场景。

## 常见误区

- **"向量库能取代关系库/搜索引擎"**：它只擅长相似度召回，精确过滤、聚合、事务仍需关系库，关键词场景 BM25 常更好；生产多用混合检索。
- **"结果一定准确"**：ANN 是近似，召回率 <100%，调参（efSearch、nprobe）是在精度和延迟间折中。
- **"随便换 embedding 模型即可"**：换模型意味着向量空间变了，必须全量重建索引，且度量方式要匹配。
- **"维度越高越好"**：维度升高带来存储、内存、延迟成本，还有"维度灾难"，应按模型与效果权衡。
- **"没有向量库就做不了语义检索"**：小规模用 FAISS/numpy 即可，不必过早引入独立系统。
- **"选型只看 QPS"**：忽略召回率、过滤能力、运维成本、与现有栈的契合度，往往是更大的坑。

## 我的结论

> 当检索需求是"语义相近"而非"精确匹配"、且数据规模大到暴力扫描扛不住、同时需要在线写入与元数据过滤时，才值得引入向量数据库；这是 RAG 和语义搜索的标准召回层。
> 反过来，若数据量小（几万以内）、以关键词/结构化查询为主、或已有 Postgres 且规模中等，就不该为了"时髦"单独上一套向量库——优先用 FAISS 内存索引或 pgvector。选型遵循"原型 Chroma → 已有 PG 用 pgvector → 需强过滤用 Qdrant → 到亿级再上 Milvus"，并始终记住：ANN 是用召回率换性能，调参和混合检索（向量 + BM25 + Rerank）往往比盲目换数据库更能提升效果。
