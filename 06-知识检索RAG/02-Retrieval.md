# Retrieval / 检索

## 一句话定义

> 检索（Retrieval）是在 RAG 流程中，根据用户查询从外部知识库里找出少量最相关文本片段、并把它们提供给大模型作为生成依据的过程。

## 解决的问题

> 大模型的知识被冻结在训练数据截止时刻，无法覆盖私有数据、实时数据和长尾细节；直接把全部资料塞进上下文又受窗口长度、成本和"大海捞针"注意力衰减的限制。检索出现之前，人们只能靠反复微调（成本高、更新慢）或人工复制粘贴资料到提示词里（无法规模化、易过时）。检索让模型在推理时"按需"获取最相关的少量证据，从而回答训练时没见过的问题，并支持引用溯源、降低幻觉。

### 文档切分策略如何选择

切分（chunking）决定了检索的最小粒度，直接影响召回质量和上下文利用率。核心权衡是：块太大则噪声多、向量语义被稀释、浪费上下文；块太小则语义不完整、容易丢失跨句信息。

- **固定长度切分**：按 token/字符数（如 256~512 token）切，带 10%~20% 重叠（overlap）防止句子被截断。实现简单，是最常用的基线。
- **按结构切分**：沿标题、段落、列表、Markdown/HTML 标签等自然边界切，保持语义完整性，适合结构化文档。
- **语义切分（semantic chunking）**：用句向量相似度检测语义断点，相邻句子相似度骤降处切块，效果好但计算成本高。
- **父子/多粒度切分**：检索时用小块命中（精准），返回时给大块或其父文档（上下文完整），如 small-to-big、parent-document retriever。

选择原则：先看数据形态（FAQ 短文本可整条成块，长技术文档宜按结构 + 重叠），再结合下游 embedding 模型的最佳输入长度，最后用检索评测集调参，没有万能值。

### 向量检索 / 关键词检索 / 混合检索的取舍

| 方式 | 原理 | 擅长 | 短板 |
| --- | --- | --- | --- |
| 向量检索（稠密） | query 与 chunk 编码为向量，按余弦/内积找近邻 | 语义相似、同义改写、跨语言 | 精确术语、专有名词、ID、长尾词易漏；可解释性差 |
| 关键词检索（稀疏，BM25/倒排） | 词项匹配 + TF-IDF 权重 | 精确匹配、专有名词、代码、低频关键词 | 词形/同义不匹配时召回为零，无语义泛化 |
| 混合检索 | 并行跑两路，用 RRF 或加权融合结果 | 兼顾语义与精确匹配，鲁棒性最好 | 工程更复杂，需调融合权重、维护两套索引 |

取舍建议：通用问答和语义性强的场景优先向量；强术语/代码/合规类场景不能只靠向量，需加关键词；生产系统推荐默认混合检索 + 重排序（reranker），这是当前最稳的组合。资源受限或语料极小时可退回单一方式。

### 查询改写（query rewriting）的作用

用户的原始查询常常口语化、含指代、过短或措辞与文档不一致，直接检索召回差。查询改写在检索前对 query 做变换以提升命中率：

- **多查询生成（multi-query）**：用 LLM 生成多个措辞不同的等价查询，分别检索后合并，覆盖更多表达方式。
- **指代消解/上下文补全**：在多轮对话中把"它""这个方案"还原成具体实体，使独立检索可用。
- **HyDE（假设性文档）**：先让 LLM 生成一个假想答案，再用答案而非问题去检索，缩小 query 与 doc 的语义鸿沟。
- **查询分解**：把复杂多跳问题拆成子问题分别检索，适合需要多条证据的推理。
- **术语/同义扩展**：补充专业术语、缩写全称，弥补用户用词与语料的差异。

代价是增加一次或多次 LLM 调用，带来延迟和成本，且改写错误会放大噪声，需要评测验证收益。

### 召回率与准确率的权衡

这是检索系统调参的核心张力。召回率（recall）关注"相关文档有没有被取回"，准确率/精确率（precision）关注"取回的文档里有多少真相关"。

- 增大 top-k、放宽相似度阈值、启用混合检索 → 召回率升，但引入更多噪声块，精确率降，还会挤占上下文、增加成本和幻觉风险。
- 收紧阈值、减小 top-k、加重排序 → 精确率升，但可能漏掉边缘相关证据，召回率降。
- **工程常用解法**：先用高召回的粗检索取回较多候选（如 top-50），再用 cross-encoder reranker 做精排，取精排后的 top-3~5 送入模型——即"宽召回 + 强精排"，兼顾两端。
- 评估要用贴近业务的检索评测集（标注 query-doc 相关性），常看 Recall@k、Precision@k、MRR、nDCG，并最终以端到端答案质量为准，而非孤立优化单一指标。

## 核心内容

- **索引阶段（离线）**：加载 → 清洗 → 切分（chunking）→ 向量化（embedding）/建倒排索引 → 写入向量库/搜索引擎。
- **检索阶段（在线）**：查询改写 → 向量化 → 近邻搜索（ANN，如 HNSW/IVF）与/或关键词检索 → 结果融合（RRF/加权）→ 重排序（reranker）→ 截断为 top-k 片段。
- **三类召回信号**：稠密向量（语义）、稀疏向量/BM25（词项）、元数据过滤（时间、来源、权限）。
- **重排序（rerank）**：用 cross-encoder 对 query-chunk 对精细打分，纠正粗检索的排序误差，是提升精确率的关键一环。
- **上下文装配**：对命中块做去重、按相关性排序、拼接引用来源，控制总 token 预算后交给生成模型。
- **评估闭环**：离线用 Recall@k/nDCG 等指标，在线看点击/答案采纳率，持续迭代切分、embedding 与融合策略。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | Embedding 模型、向量数据库、文档切分 | 检索依赖高质量向量表示、可扩展的 ANN 索引和合理的 chunk 粒度；上游质量直接决定召回天花板 |
| 下游 | 生成（Generation）、Reranking、Prompt 装配 | 检索结果经重排后拼入提示词，供 LLM 生成带引用的答案；检索召回的证据质量决定生成的可信度 |
| 易混淆 | 微调（Fine-tuning）、全文搜索、推荐系统召回 | 微调是改模型参数、检索是外挂知识不改参数；传统全文搜索只有词项匹配而无语义向量；推荐召回面向物品排序而非问答证据 |

## 典型工程场景

- 企业内部知识库问答（制度、产品手册、工单历史）。
- 技术文档 / API 文档助手与代码库问答。
- 客服/售后机器人，基于 FAQ 和历史对话给出带来源的回答。
- 法律、医疗、金融等需要引用溯源、合规可追溯的专业问答。
- Agent 的长期记忆与工具知识注入，让 Agent 在推理时检索历史与外部资料。
- 搜索增强的研报、文献综述、尽调等信息聚合类任务。

## 适用边界

**适合使用**

- 知识量大、更新频繁、无法全部放进上下文窗口的场景。
- 需要引用来源、可溯源、可审计的问答。
- 私有/领域数据，无法或不值得通过微调注入模型。
- 对事实准确性要求高、需要降低幻觉的任务。

**不适合使用**

- 纯推理、创作、翻译等不依赖外部事实的任务（检索反而引入噪声）。
- 知识极少且稳定，直接写进系统提示词即可，无需建索引。
- 对延迟极度敏感且无法容忍检索开销的场景。
- 需要全局汇总/统计类问题（如"文档里一共有多少条规则"），单纯语义检索难以胜任，需结构化查询或 GraphRAG 等补充。

## 常见误区

- 以为"接了向量库就等于做好了 RAG"，忽视切分、重排、评估等关键环节。
- 盲目追求大 top-k，认为取回越多越好，实际会稀释信号、增加幻觉和成本。
- 只用向量检索，忽略专有名词/代码/ID 场景下关键词检索不可替代。
- 把 embedding 相似度当作"相关性"真值，相似度高未必语义相关，缺少 reranker 把关。
- 忽视元数据过滤与权限控制，导致检索到越权或过期内容。
- 不建评测集，仅凭个别 case 主观调参，无法量化改进。

## 我的结论

> 当问题的答案依赖大量、私有或高频更新的外部事实，且需要可溯源、低幻觉时，就应该用检索——它比微调更新快、成本低，比塞满上下文更省、更准。反之，纯创作/推理/翻译类任务，或知识极少且稳定、可直接写进提示词的场景，就不该用检索，否则只会引入噪声和延迟。真正的生产级检索不是"接个向量库"，而是"合理切分 + 混合召回 + 强重排 + 评测闭环"的工程体系；其中最该投入的是重排序和评估集，这两者对最终答案质量的边际收益往往高于更换 embedding 模型。
