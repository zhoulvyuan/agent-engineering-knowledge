# Reranking / 重排

> **状态**：🟢 已理解 ｜ **深度**：B 能够应用 ｜ **更新**：2026-09-15
> **上级**：[06-知识检索RAG](README.md) ｜ **依赖**：Retrieval

## 一句话定义

> Reranking 是在第一轮召回出候选文档之后，用一个精度更高（但更慢）的模型对这批候选逐一打分并重新排序，把最相关的结果顶到前面的二次排序阶段。

## 解决的问题

> 在 Reranking 出现之前，RAG/搜索系统往往直接把向量检索（或 BM25）的 Top-K 原样喂给大模型或用户。这类第一阶段检索为了低延迟做了强压缩与近似：稠密向量把一整段话压成单个向量，丢失细粒度语义；稀疏检索只看词面匹配，无法理解语义。结果是"召回还行、排序不准"——真正最相关的那条经常排在第 8、第 15 位，而被截断的 Top-5 里塞满了形似神不似的噪声。把这些噪声直接送进上下文窗口，既浪费 token，又会把 LLM 带偏、诱发幻觉。

### Reranking 解决什么问题

它解决的是第一阶段检索"召回够、排序不够准"的问题，核心价值是**提升结果列表顶部的相关性精度（Precision@K / nDCG）**。

- 第一阶段（向量/BM25）为了在百万级库里做到毫秒级响应，牺牲了排序精度，只保证"相关的大概率落在 Top-50/Top-100 里"。
- Reranking 对这个较小的候选集做精细比较，把真正相关的文档重新顶到前几位，让下游只需要很小的 K（如 Top-3）就能拿到高质量上下文。
- 直接收益：减少送入 LLM 的噪声片段 → 降低幻觉、减少 token 消耗、提升回答准确率；在纯搜索场景则直接改善用户点击的头部体验。

### 为什么检索之后还需要重排

关键在于两阶段的**精度/成本是互斥的**，必须分工：

| 维度 | 第一阶段检索（召回） | 重排（Rerank） |
| --- | --- | --- |
| 交互方式 | 双塔（bi-encoder），query 与 doc 独立编码 | 交叉编码（cross-encoder），query+doc 拼接共同编码 |
| 能否离线预算 | 文档向量可离线建索引 | 必须在线实时计算，无法预存 |
| 规模 | 对全库（百万~十亿）做 ANN 近似 | 只对 Top-N（几十~几百）候选精算 |
| 精度 | 较低，丢失词级交互 | 高，能捕捉词与词的细粒度匹配 |

双塔模型里 query 和 doc 从不"见面"，只能靠向量点积近似，天然损失信息；cross-encoder 让 query 和每个 doc 做全程注意力交互，能判断"这段话是否真的回答了这个问题"。但 cross-encoder 对每个候选都要跑一次完整前向，无法像向量那样预先建索引，所以**只能、也只需**作用在第一阶段缩小后的候选集上。这就是"先召回、再重排"级联结构的根本原因。

### 重排的延迟与成本代价

重排是用延迟和算力换精度，代价集中在在线推理环节：

- **延迟与候选数线性相关**：N 个候选就要 N 次前向。本地小型 cross-encoder（如 bge-reranker-base）对 Top-50 通常增加几十毫秒；候选越多、模型越大，延迟越高。
- **候选长度二次放大**：cross-encoder 把 query+doc 拼接后过 attention，长文档（attention 对序列长度近似 O(L²)）会显著变慢，因此常需截断或分块。
- **GPU/服务成本**：自建需要常驻 GPU；用托管 API（Cohere Rerank、Jina Reranker、Voyage 等）按请求和文档数计费，高 QPS 下成本可观。
- **常见权衡手段**：减小候选 N、用蒸馏/量化的小 reranker、对长文截断、加缓存、或改用延迟更低的 late-interaction 方案（如 ColBERT）折中。
- 经验法则：第一阶段取 Top-50~100 送入重排、重排后保留 Top-3~5，通常是精度与延迟较优的平衡点。

## 核心内容

- **定位**：检索管线中的第二阶段，介于"召回"与"生成/展示"之间，属于精排（precision-oriented）环节。
- **主流模型形态**：
  - Cross-encoder（交叉编码器）：query 与 doc 拼接后统一编码输出相关性分数，精度最高、最常用（bge-reranker、Cohere Rerank、Jina Reranker）。
  - Late interaction（如 ColBERT）：token 级向量延迟交互，精度接近 cross-encoder 但可部分预计算，延迟更低。
  - LLM-as-reranker：用大模型直接做 pointwise/pairwise/listwise 判断相关性，灵活但贵且慢。
- **打分范式**：pointwise（逐条打分）、pairwise（两两比较）、listwise（整体排序）；工程中 cross-encoder 多为 pointwise。
- **典型流程**：query → 第一阶段召回 Top-N（向量/BM25/混合）→ reranker 对 (query, doc_i) 逐一打分 → 按分数降序 → 截取 Top-K → 送入 LLM 或返回用户。
- **常与混合检索配合**：BM25 + 向量先各自召回并合并（或 RRF 融合），再统一交给 reranker 做最终排序。
- **评估指标**：nDCG@K、MRR、Precision@K、Recall@K（召回在第一阶段看，精度在重排后看）。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | Retrieval / 向量检索 / 混合检索（BM25+Dense、RRF） | 重排不自己召回，依赖第一阶段提供的 Top-N 候选集；候选质量决定重排上限（召回里没有的文档永远排不出来）。 |
| 下游 | 上下文组装 / Prompt 构造 / LLM 生成 | 重排后的 Top-K 作为高质量上下文送入生成环节，直接影响答案准确性与 token 开销。 |
| 易混淆 | 向量检索的相似度排序 / Embedding 模型 | 向量检索用的是双塔离线相似度（粗排），reranker 用的是在线 cross-encoder（精排）；二者模型结构、是否可建索引、精度/延迟定位完全不同，不能相互替代。 |

## 典型工程场景

- **企业 RAG 知识问答**：从知识库召回 Top-50 后重排取 Top-3~5，减少噪声、降低幻觉。
- **电商/站内搜索**：向量+BM25 召回商品后重排，优化头部结果的点击与转化。
- **客服/工单检索**：对相似历史工单或 FAQ 做精排，提升一次命中率。
- **代码检索与代码助手**：对召回的代码片段按与需求的真实相关性重排。
- **多路召回融合后统一排序**：多个数据源/多种检索策略结果合并后，用 reranker 做统一裁决。
- **长文档问答**：文档分块召回大量 chunk 后，重排挑出真正相关的少数块。

## 适用边界

**适合使用**

- 第一阶段召回明显"召回高但排序差"，Top-K 噪声多、答案常排在靠后。
- 对回答/结果精度敏感，愿意为准确率付出几十毫秒级延迟。
- 候选集可控（Top-N 在几十到几百量级），有 GPU 或可接入 reranker API。
- 多路/混合召回需要一个统一、语义感知的最终排序。

**不适合使用**

- 极致低延迟、每毫秒都敏感的场景（如大规模实时广告排序前端），且精度要求不高。
- 第一阶段召回本身就很准、Top-3 已足够好，重排收益不明显。
- 候选集过大又不先裁剪（直接对全库重排不可行，成本爆炸）。
- 真正问题出在"召回根本没召到"——此时应先优化 embedding/分块/混合检索，重排救不了召回缺失。

## 常见误区

- **"重排能提升召回率"**：错。重排只重新排序给定候选，无法把第一阶段漏掉的文档找回来；召回天花板由第一阶段决定。
- **"用更好的 embedding 就不需要重排"**：双塔模型结构上就损失词级交互，再好的 embedding 也难达到 cross-encoder 的精排精度，两者互补而非替代。
- **"直接对全库重排最准"**：cross-encoder 无法建索引，全库逐条打分成本不可接受，必须先召回再重排。
- **"重排分数是绝对相关性概率"**：多数 reranker 输出的是相对排序分，跨 query 不可直接比较，拿它做硬阈值过滤需谨慎校准。
- **"候选 N 越大越好"**：N 增大线性抬高延迟成本，收益递减，需按场景调优而非一味加大。
- **"reranker 和 embedding 模型可以混用同一个"**：二者训练目标和结构不同，不能把 embedding 模型当 reranker 用。

## 我的结论

> 当第一阶段检索出现"相关文档召回到了、但没排到前面"的症状，且业务对结果精度敏感、能接受几十毫秒级额外延迟时，就应该上 Reranking——它是用在线算力换头部相关性的高性价比手段，尤其在 RAG 中能显著减少噪声上下文、降低幻觉和 token 消耗。
> 反之，如果瓶颈在召回（想要的根本没召到）、延迟预算极紧、或 Top-3 已经足够准，就不该先碰重排：此时该去优化分块、embedding 和混合检索。一句话——**重排是精排不是召回，先保证召到，再谈排好；它永远作用在被裁剪过的候选集上，而非全库。**
