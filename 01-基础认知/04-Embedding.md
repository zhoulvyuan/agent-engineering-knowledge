## 一句话定义

> Embedding 是把文本（或图片、音频等）映射成一个固定长度的实数向量的表示方法，让"语义相近"在数学上表现为"向量相近",从而可以用数值计算来比较语义。

## 解决的问题

> 计算机本身只会处理数字，而文本是离散符号；传统做法（one-hot、关键词匹配）只能看"字面是否相同",无法理解"番茄"和"西红柿""汽车"和"轿车"是同一个意思。
> 这导致语义检索、相似度比较、聚类分类等任务都卡在"字面不等于语义"上。Embedding 把语义装进连续向量空间，让机器第一次能用距离/角度来衡量"意思有多接近",而不是只比字符。

### Embedding 是什么

Embedding 就是一段内容的"语义坐标"：一个固定维度（如 384、768、1536 维）的实数向量。模型把输入编码成这个向量，使得**语义相近的内容在向量空间里彼此靠近，语义无关的彼此远离**。它是对内容含义的稠密（dense）数值表示，不同于只记录"有没有某个词"的稀疏表示。

### 为什么可以把文本转换成向量

因为语义是可以从"上下文共现"中学出来的——分布假说：**意思相近的词出现在相似的语境里**。
- 早期（Word2Vec/GloVe）通过"预测上下文词"训练出词向量，就观察到 `国王 - 男人 + 女人 ≈ 王后` 这种语义代数关系。
- 现代句向量模型（如 BERT 系、OpenAI/BGE 等 embedding 模型）在海量文本上训练，用对比学习等目标让"相关句子向量靠近、无关的推远"。
- 本质上，向量的每个维度是模型学出来的某种"隐含语义特征",训练让这些维度共同编码了含义，所以文本能被压成一个有意义的坐标点。

### Embedding 与语义检索、RAG 的关系

Embedding 是语义检索和 RAG 的**底层引擎**：
1. **离线建库**：把文档切块（chunk）→ 每块算 embedding → 存进向量数据库。
2. **在线检索**：用户 query 也算成 embedding → 在向量库里找**最近邻**（相似度最高的若干块）。
3. **RAG**：把检索到的相关块拼进 context，交给 LLM 基于这些事实作答。
所以 RAG 中"检索"这一步，靠的就是 embedding 的语义相似度，而不是关键词匹配——这让它能召回"意思对但用词不同"的内容。

### Embedding 的相似度度量方式

- **余弦相似度（cosine similarity）**：比较两个向量的**夹角**，只看方向不看长度，是文本检索最常用的度量；值域 [-1,1]，越接近 1 越相似。
- **点积（dot product）**：方向和模长都算进去；当向量已归一化时，点积与余弦等价（很多系统因此先做归一化）。
- **欧氏距离（L2）**：比较空间直线距离，越小越近；归一化后与余弦单调相关。
- 实务上：文本语义检索默认用余弦；用哪种要和模型训练/库的约定一致（比如 OpenAI embedding 推荐余弦）。真正大规模检索会用 ANN（近似最近邻，如 HNSW/IVF）来加速。

## 核心内容

- **稠密 vs 稀疏**：embedding 是稠密向量（每维都有值，编码语义）；关键词/TF-IDF 是稀疏向量（编码字面）。实际系统常把二者混合（hybrid search）。
- **维度**：维度越高表达力越强但越占存储/计算，常见 384~3072。
- **归一化**：很多模型输出需先 L2 归一化，之后点积=余弦，便于统一度量。
- **模型选择**：不同 embedding 模型针对不同语言/任务，中文检索应选中文或多语模型；query 和 doc 必须用**同一个**模型编码才可比。
- **向量数据库 + ANN**：Faiss、Milvus、pgvector 等负责存向量并用 HNSW/IVF 等近似算法快速找最近邻。
- **局限**：embedding 捕捉的是整体语义相似，不擅长精确匹配（如 ID、专有名词、否定、数字），所以常配合关键词检索与重排序（rerank）。

## 典型工程场景

> - 语义检索 / RAG：按意思召回相关文档块。
> - 相似度/去重：找相似问题、重复内容、相关推荐。
> - 聚类与分类：对文本做无监督分组或零样本分类。
> - 推荐系统：用户/物品向量匹配。
> - 异常/意图识别：用距离判断是否偏离已知语义。

## 适用边界

**适合使用**

- 需要按"语义"而非"字面"检索、比较、分组时
- 召回"意思相同但用词不同"的内容
- 大规模文本的相似度计算（配向量库 + ANN）

**不适合使用**

- 需要精确匹配（ID、代码、专有名词、精确数字）——用关键词检索更稳
- 对否定、细微逻辑差异敏感的判断（embedding 容易把"能退款"和"不能退款"算得很近）
- 对可解释性要求高的场景（向量维度不可直接解读）
- 直接拿来做生成/推理（那是 LLM 的事）

## 常见误区

- 以为 embedding 能理解精确含义——它只给"大致语义相近",对否定/数字/实体不敏感。
- query 和文档用不同模型编码还去比相似度——必须同一模型、同一空间。
- 忘记归一化就混用点积/余弦，导致度量不一致。
- 以为语义检索能完全取代关键词检索——精确匹配场景仍需 BM25，常用 hybrid。
- 认为维度越高越好——要权衡存储、速度与收益，并常加 rerank 提升精度。

## 我的结论

> Embedding 是"语义的坐标系":它把含义变成可计算的向量，让机器第一次能按"意思像不像"而不是"字一不一样"来检索和比较。
> - **该用它**：做语义检索、RAG、相似推荐、聚类——凡是"按意思找"的任务。
> - **不该单独用它**：需要精确匹配、处理否定/数字/实体，或要求可解释时，必须配关键词检索和重排序。
> 工程要点：query 与 doc 用同一模型、先归一化再用余弦、大规模用 ANN、精度不够加 rerank/hybrid。心智模型：embedding 负责"粗召回语义相近",精确性和排序交给后续环节补齐。
