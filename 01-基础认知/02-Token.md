## 一句话定义

> Token 是 LLM 处理文本的最小单位——一段文本经分词器（tokenizer）切分后得到的"子词片段"，模型的输入、输出、计费、上下文长度都以它为单位。

## 解决的问题

> 直接用"字符"或"整词"喂给模型都有缺陷：按字符切，序列太长、学不到语义；按整词切，词表会爆炸（几十万词 + 永远有没见过的新词/拼写错误/多语言）。
> 子词切分（BPE / WordPiece / SentencePiece 等）在二者间折中：常见词保留为一个 token，生僻词拆成若干子词片段，用一个几万大小的固定词表就能覆盖任意文本（包括没见过的词），既控制了序列长度又避免了 OOV（未登录词）问题。

### Token 是什么

Token 是分词器把文本切出来的最小片段，通常是"子词"级别：可能是一个完整单词、一个词的一部分、一个标点、一个空格，甚至是组成一个汉字/emoji 的多个字节。模型内部并不直接看文本，而是把每个 token 映射成一个整数 ID，再查成向量（embedding）进行计算。所谓"模型逐 token 生成"，就是在这个固定词表上一个个预测 ID。

### Token 与文本的关系

- 文本 ↔ token 是通过分词器**双向可逆**转换的（encode / decode）。
- **不是一一对应**：切分粒度取决于语言和分词器。经验值（以 OpenAI 系为例）：
  - 英文：约 1 个 token ≈ 0.75 个单词，1000 token ≈ 750 词。
  - 中文：常见字约 1～2 个 token / 字，比英文更"费 token"。
  - 空格、换行、标点都会单独占 token；相同含义不同写法 token 数可能不同。
- 不同模型用不同分词器，同一段文本的 token 数会不一样，不能跨模型直接套用。

### Token 与上下文窗口的关系

- **上下文窗口（context window）= 模型一次能处理的 token 总数上限**，且是"输入 + 输出"**共享**这个预算。
- 超出窗口的内容会被截断或报错；窗口越大，能塞进的资料/历史越多，但注意力成本随之上升，还可能出现"迷失在中间"。
- 工程含义：prompt、对话历史、检索内容、模型回答全都在抢同一个 token 预算，必须做裁剪、摘要、滑动窗口等管理。

### Token 与成本、性能的关系

- **成本**：API 按 token 计费，通常输入和输出**分别定价**（输出往往更贵）。省钱的本质就是省 token——精简 prompt、压缩历史、限制 max_tokens。
- **性能/延迟**：生成是自回归的，输出每多一个 token 就多一次前向计算，**延迟主要由输出 token 数决定**；输入长也会增加首 token 延迟（prefill）。
- 一句话：token 既是"钱的单位"也是"时间的单位"，优化 LLM 应用在很大程度上就是优化 token 用量。

## 核心内容

- **分词算法**：主流是 BPE（GPT 系）、WordPiece（BERT 系）、SentencePiece/Unigram（多语言、T5/LLaMA 系）。核心思想都是"从数据里统计出高频子词组合，构建固定词表"。
- **词表（vocabulary）**：一般几万量级（如 GPT-4 的 cl100k 约 10 万）。词表越大，单 token 承载信息越多、序列越短，但 embedding 矩阵更大。
- **ID 化与 embedding**：token → 整数 ID → 向量，才进入 Transformer 计算；输出端再把概率最高的 ID → token → 文本。
- **可逆与边界**：encode/decode 可逆，但 token 边界不等于语义/词边界，这也是模型"数不清字母个数""不会精确反转字符串"等现象的根源之一。
- **实用工具**：OpenAI 的 tiktoken、HuggingFace tokenizers 可用来实际数 token、估算成本和窗口占用。

## 典型工程场景

> - 成本预算与计费：估算一次调用/一个功能的 token 消耗与费用。
> - 上下文管理：对话历史裁剪、RAG 片段拼接、长文档分块（chunking）。
> - 限流与配额：按 TPM（tokens per minute）做速率控制。
> - 输出控制：用 max_tokens 约束长度、延迟和成本。
> - 分块检索：把长文本切成合适 token 大小的 chunk 做向量化。

## 适用边界

**适合使用**

- 任何需要估算 LLM 成本、延迟、窗口占用的场景
- 长文本处理前的分块、截断、摘要决策
- 需要跨组件（输入/历史/检索/输出）分配 token 预算时

**不适合使用**

- 需要精确字符/字数统计时（token ≠ 字符数，应直接按字符数）
- 跨模型直接套用某一分词器的 token 数（分词器不同，结果不同）
- 对用户展示"长度"时用 token 当单位（用户理解的是字/词）

## 常见误区

- 以为 1 token = 1 个单词或 1 个字——实际是子词，比例随语言和分词器变化。
- 以为上下文窗口只限制输入——输入和输出共享同一预算。
- 以为中英文 token 消耗一样——中文通常更费 token。
- 忽略空格、标点、换行也占 token。
- 用某模型的 token 数去估另一个模型的成本——分词器不同，不可直接套用。

## 我的结论

> Token 是 LLM 工程里的"计量基本单位"：窗口、钱、延迟全都用它衡量，所以优化应用 ≈ 优化 token 用量。
> - **该关注它**：做成本预算、上下文裁剪、长文分块、限流配额时，必须按真实 token 计算（用 tiktoken 等实测，而非拍脑袋按字数）。
> - **不该用它**：给用户看长度、做精确字符统计时别用 token。
> 心智模型：把 token 当成"模型世界里的货币 + 时间单位",所有资源分配都围绕这个预算展开。
