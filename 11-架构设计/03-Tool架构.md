# Tool 架构

> **上级**：[11-架构设计](README.md) ｜ **依赖**：Agent 架构

## 一句话定义

> Tool 架构是指 Agent 系统中"工具"从定义、注册、发现、调用到结果回传这一整套可扩展的工程机制——它把外部能力（API、函数、脚本、检索、代码执行等）封装成模型可理解、可安全调用的标准化接口，让 LLM 能跳出纯文本生成去真正操作外部世界。

## 解决的问题

> 在没有工具机制之前，LLM 只能基于训练语料生成文本，存在三类硬伤：
> 1. **知识封闭且过期**——无法获取训练截止日期之后的信息，也拿不到私有/实时数据。
> 2. **不能执行动作**——只能"说"不能"做"，无法下单、查库、改文件、运行代码。
> 3. **不擅长精确计算与确定性逻辑**——算术、日期、结构化查询等任务靠概率生成极易出错。
>
> 工具机制让模型把这类任务"外包"给确定性的程序，自己只负责判断"何时调用、传什么参数、如何解释结果"，从而把概率语言模型变成能可靠完成实际工作的系统。

### 工具注册、发现与版本管理

- **注册（Registration）**：每个工具需要向系统声明一份机器可读的"契约"，通常包含名称、自然语言描述、参数 schema（多用 JSON Schema）、返回结构、权限要求等。这份契约既供运行时校验参数，也会被序列化进 prompt 让模型理解工具用途。
- **发现（Discovery）**：当工具数量增长到几十上百个时，把全部工具塞进上下文会浪费 token 并降低选择准确率。常见做法是**按需检索**——用向量检索/关键词/分类过滤先召回与当前任务相关的少量工具，再喂给模型（如 RAG-for-tools、工具路由器）。MCP 这类协议还把发现标准化为 `tools/list` 这样的运行时查询。
- **版本管理**：工具的参数、语义会演进。工程上建议：接口做**语义化版本**（如 `search_v2`）、对破坏性变更保持旧版本并行一段时间、在描述里标注 deprecated、用契约测试锁定输入输出，避免模型调用习惯被悄悄改坏。
- **要点**：注册契约是"模型侧文档"也是"运行时校验源"，两者应来自同一份定义（single source of truth），避免描述与实现漂移。

### 工具执行的沙箱与权限层

| 维度 | 做法 |
| --- | --- |
| 隔离 | 代码/命令类工具放进容器、WASM、子进程或 serverless 沙箱执行，限制文件系统、网络、系统调用 |
| 权限 | 按最小权限原则给工具授权；区分只读工具与写/副作用工具；敏感操作（删库、转账、发邮件）需人类确认（human-in-the-loop） |
| 配额与超时 | 对每个工具设超时、速率限制、资源配额，防止失控循环或恶意输入拖垮系统 |
| 输入校验 | 把 LLM 生成的参数视为**不可信输入**，执行前用 schema 校验、白名单、参数清洗，防止注入/越权 |
| 审计 | 记录每次调用的参数、结果、耗时、调用方，便于回溯、计费与安全审查 |

关键认知：模型的输出是概率性的，可能被 prompt injection 操纵去调用危险工具，因此**权限边界必须由系统（而非模型）强制执行**，不能依赖模型"自觉"。

### 工具结果的规范化

- **结构化返回**：工具结果应回传为稳定、可解析的结构（JSON/固定字段），而不是裸文本，便于后续工具链消费和模型理解。
- **错误规范化**：成功与失败用一致的格式表达（如 `{status, data, error}`），错误要给出模型可据以修正的信息（缺哪个参数、权限不足、超时），支持模型重试或换策略。
- **体积控制**：大结果（长文档、大 JSON、二进制）要截断、摘要或分页，避免撑爆上下文；可返回"句柄/引用 + 摘要"，让模型按需再取。
- **一致性**：同类工具尽量统一字段命名与语义，降低模型学习成本；时间、单位、编码等做标准化，减少歧义。

## 核心内容

- **工具契约（Schema）**：名称 + 描述 + 参数 JSON Schema + 返回结构，是模型理解和系统校验的共同基础。
- **工具调用生命周期**：模型决策调用 → 生成结构化参数 → 系统校验 → 沙箱执行 → 结果规范化回传 → 模型解释并进入下一步（常嵌在 ReAct / function calling 循环里）。
- **选择与路由**：工具多时需检索/路由，先缩小候选集再让模型选择，兼顾准确率与 token 成本。
- **安全层**：隔离沙箱、最小权限、输入校验、人工确认、审计日志、配额超时。
- **标准化协议**：OpenAI function calling / tool calling、Anthropic tool use、以及跨厂商的 MCP（Model Context Protocol）把"工具如何声明与调用"标准化。
- **可观测性**：对调用链路做 tracing、指标与日志，支撑调试、评估与成本治理。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | Agent 架构 / 规划与推理循环（ReAct） | Agent 的决策循环决定"何时、调用哪个工具"，Tool 架构是其执行底座；没有规划层，工具只是被动函数 |
| 下游 | 外部 API / 函数 / 代码执行环境 / 检索系统 | 工具最终落到对这些具体能力的封装与调用，Tool 架构是它们接入 Agent 的统一适配层 |
| 易混淆 | 普通 Function Calling vs. 完整 Tool 架构 | Function calling 只是"模型产出调用意图"的一个接口原语；Tool 架构还包含注册发现、权限沙箱、结果规范化、版本与可观测性等完整工程体系 |

## 典型工程场景

- **企业智能助手/Copilot**：接入内部检索、工单系统、CRM、日历，让 Agent 真正查数据、建工单、排会议。
- **AI 编码工具**：封装文件读写、代码搜索、运行测试、执行 shell 命令等工具，构成编码 Agent 的操作面。
- **数据分析 Agent**：工具包括 SQL 查询、代码解释器（Python 执行）、绘图，完成"自然语言→查询→计算→可视化"。
- **自动化运维/RPA**：把部署、扩容、告警处理封装为受权限约束的工具，由 Agent 编排执行。
- **多工具编排的客服/交易机器人**：查订单、退款、发通知等组合调用，敏感写操作走人工确认。

## 适用边界

**适合使用**

- 任务需要实时/私有数据，或需要执行有副作用的动作。
- 需要确定性计算、结构化查询、精确逻辑（交给程序而非让模型"猜"）。
- 能力需要可扩展、可组合，且希望对调用做统一的权限与审计治理。

**不适合使用**

- 纯文本生成/改写/总结等模型本身就能胜任、无需外部能力的任务——引入工具只增加延迟与复杂度。
- 工具契约无法清晰定义、副作用不可控或不可回滚、又缺乏安全评估的高危操作（宜先人工）。
- 极低延迟要求且工具往返开销不可接受的场景。

## 常见误区

- **把 function calling 等同于 Tool 架构**：接口原语只是起点，缺少注册发现、权限、结果规范化就不是可用的生产架构。
- **工具越多越好**：工具过多会稀释选择准确率、浪费 token，应配检索/路由并精简描述。
- **信任模型生成的参数**：模型输出必须当作不可信输入做校验，权限由系统强制，否则易被 prompt injection 利用。
- **工具描述写得随意**：描述即"模型侧文档"，含糊的描述直接导致误调用；要清晰说明用途、参数、边界。
- **忽视错误与结果规范化**：不规范的错误信息让模型无法自我修正；超大结果不截断会撑爆上下文。
- **忽视可观测性与成本**：不做 tracing/配额，调试困难且容易产生失控调用成本。

## 我的结论

> **何时该用**：当任务需要触达模型内部能力之外的东西——实时/私有数据、确定性计算、对外部系统产生副作用——且这种能力需要被多次、可组合、可治理地复用时，就应该把它建成规范的 Tool 架构，而不只是临时拼一个 function call。衡量标准是：是否需要注册发现、权限隔离、结果规范化和审计这几件事中的任何一件，只要需要，就值得按架构来做。
> **何时不该用**：任务靠模型本身即可完成、无外部依赖、无副作用时，加工具是过度工程；高危且不可回滚、又缺安全评估的操作，优先人工或先做充分的权限与评估设计再上。核心判断是"工具带来的确定性/可执行性收益，是否超过它引入的延迟、复杂度与安全风险"。
