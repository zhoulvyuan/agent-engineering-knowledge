## 一句话定义

> Agent 架构是一套以大模型为决策核心、通过"感知—决策—行动—观察"循环驱动，并借助工具调用、记忆/状态管理和编排控制去自主完成多步任务的软件结构。

## 解决的问题

在 Agent 架构出现之前，LLM 应用大多是"单轮问答"或固定流程的 Prompt 链（Chain），存在几个麻烦：

- 任务被写死成固定步骤，无法根据中间结果动态决定下一步，面对开放式、步数不定的任务（如"排查这个线上故障"）就失效。
- 模型只能生成文本，无法真正"做事"——不能查数据库、调 API、读写文件，只能靠人把结果复制粘贴回去。
- 长任务缺少状态承载：上下文窗口有限，多步之间的中间结论、已尝试过的路径没有地方沉淀，容易重复或遗忘。
- 缺乏错误恢复机制：一步出错整条链就断，没有重试、反思、换路径的能力。

Agent 架构把"让模型自己决定下一步 + 让模型能调用外部能力 + 让状态可持续"三件事结构化，从而支撑自主、多步、可恢复的任务执行。

### Agent 的组件划分

一个工程化 Agent 通常可拆成以下相对正交的组件，解耦后便于替换与测试：

| 组件 | 职责 | 工程落点 |
| --- | --- | --- |
| 模型/推理层 | 作为决策大脑，根据上下文产出"下一步动作"（文本回复或工具调用） | LLM 客户端、Prompt 模板、输出解析 |
| 循环引擎（Orchestrator） | 驱动 感知→决策→行动→观察 的主循环，决定何时继续、何时终止 | 状态机 / ReAct 循环 / 图执行器 |
| 工具层（Tools） | 把外部能力（API、检索、代码执行、文件系统）封装成模型可调用的函数 | 工具注册表 + Schema + 执行沙箱 |
| 记忆/状态层 | 承载短期上下文、长期记忆、任务进度与中间结果 | 对话历史、向量库、KV 存储、scratchpad |
| 规划层（可选） | 把大任务分解为子任务并排序，支持回溯与重规划 | Planner、任务队列、DAG |
| 控制与安全层 | 预算/步数上限、权限校验、人工审批、可观测性 | Guardrails、HITL、日志/trace |

关键原则：决策（模型）与执行（工具）分离，编排（循环）与业务逻辑分离，这样才能单独替换模型、单独测试工具、单独调整终止策略。

### 循环引擎如何设计

循环引擎是 Agent 的心脏，核心是一个"直到满足终止条件才停"的受控循环：

- **基本回合（turn）**：组装上下文 → 调用模型 → 解析输出 → 若是工具调用则执行工具、把观察结果写回上下文 → 回到第一步；若是最终答复则结束。这就是 ReAct（Reason+Act）范式的工程形态。
- **终止条件**：必须显式设计，至少包括"模型给出终结标志（如 final answer / 空工具调用）""达到最大步数""超出 token/时间/成本预算""触发错误阈值"。缺少硬上限是 Agent 失控、烧钱的首要原因。
- **错误处理**：工具异常不应直接中断循环，而是把错误信息作为"观察"回灌给模型，让它决定重试、换工具还是放弃；对确定性失败要有熔断。
- **并发与确定性**：单工具调用串行最简单；需要并行时（如同时查多个数据源）要在引擎层做 fan-out/fan-in，并保证把结果有序写回。
- **可观测性**：每一回合的输入上下文、模型输出、工具入参/返回都应落 trace，否则线上问题无法复现。
- **进阶形态**：从线性 ReAct 发展到图执行（如 LangGraph 的节点+边+条件跳转），把循环显式建模为状态图，便于表达分支、回环与人工介入点。

### 工具注册与调度层如何抽象

工具层要解决"模型如何知道有哪些能力、如何正确调用、调用后如何安全执行"三个问题：

- **注册（声明）**：每个工具用结构化 Schema 描述——名称、用途说明、参数类型与约束（通常用 JSON Schema）。说明文字本身就是给模型看的"文档"，写得准不准直接决定调用准确率。
- **暴露给模型**：把工具 Schema 注入到模型的 function-calling / tool-use 接口，模型据此产出结构化调用请求（函数名+参数 JSON），而不是靠解析自由文本。
- **调度（dispatch）**：引擎按模型选定的工具名路由到对应实现，做参数校验（类型、必填、范围）、鉴权与配额检查，再执行。
- **执行与隔离**：有副作用或危险的工具（代码执行、Shell、写操作）要放进沙箱，并区分只读/写操作，写操作可要求人工确认。
- **返回归一化**：工具结果统一成结构化、可截断、可被模型消费的格式；过大的返回要摘要或分页，避免撑爆上下文。
- **抽象要点**：工具应是无状态纯函数式接口（输入→输出），把状态交给记忆层；工具集可按命名空间/权限分组，并支持动态启停（按任务阶段只开放相关工具，减少选择干扰）。

### 状态存储的位置与形式

Agent 的"状态"是多层的，不同层放在不同位置、用不同形式：

| 状态类型 | 形式 | 存储位置 | 生命周期 |
| --- | --- | --- | --- |
| 短期工作记忆 | 对话消息列表 / scratchpad | 内存中的上下文窗口 | 单次任务/会话 |
| 任务进度状态 | 结构化 state 对象（当前步、计划、已完成子任务） | 内存 + 可持久化到 DB | 跨回合、可恢复 |
| 长期记忆 | 向量嵌入 + 原文 | 向量数据库 / 检索库 | 跨会话、长期 |
| 事实/实体记忆 | KV、关系表、知识图谱 | 关系库 / 图库 / KV | 长期 |
| 产物与中间文件 | 文件、Blob | 文件系统 / 对象存储 | 任务期或长期 |

工程要点：

- 短期上下文受窗口限制，需要摘要、滑动窗口或分层记忆来压缩；不能把所有历史无脑拼进去。
- 要区分"易失状态"（放内存，追求速度）与"需恢复/审计的状态"（持久化为显式 state，便于崩溃重启后续跑、便于回放）。
- 长期记忆检索（RAG）本质是"按需把外部状态拉进短期上下文"，与短期记忆是互补关系。
- 多 Agent 或多会话场景要做状态隔离（按 session/user 分键），避免串台。

## 核心内容

- **决策核心**：LLM 负责在每一步推理"现在该做什么"，是不确定性的来源，也是能力上限。
- **循环驱动**：以 感知(组装上下文)→决策(模型输出)→行动(工具执行)→观察(结果回灌) 的闭环推进，直到终止条件满足。
- **工具调用**：通过结构化 function-calling 把模型与外部世界连接，让"生成文本"变成"产生副作用"。
- **记忆与状态**：短期上下文 + 长期记忆 + 显式任务状态，共同解决"长任务记不住、断了接不上"的问题。
- **规划与反思**：复杂任务先分解（Planning），执行中可自我批评/修正（Reflection），失败后可回溯重规划。
- **编排范式**：从单 Agent 的 ReAct，到图式编排（状态图），再到多 Agent 协作（分工、消息传递、supervisor 调度）。
- **控制面**：预算/步数上限、权限与沙箱、人工介入（HITL）、全链路可观测性，是从 Demo 走向生产的分水岭。

## 典型工程场景

- **AI 编码助手**：读代码库、改文件、跑测试、看报错再修，多步自主完成一个工程任务。
- **智能客服/工单处理**：查订单、调内部 API、按策略决定退款或升级，而非固定脚本。
- **运维/排障 Agent**：根据告警自主查日志、查监控、定位根因并给出修复建议。
- **数据分析助手**：把自然语言需求转成查询，执行、读结果、再追问式深挖。
- **深度检索/研究助手**：多轮搜索—阅读—归纳，自主决定还要查什么。
- **浏览器/桌面自动化**：读页面状态、决定点击/输入，完成跨系统的操作流程。

## 适用边界

**适合使用**

- 任务步数不固定、路径依赖中间结果，无法提前写死流程。
- 需要调用多种外部工具/系统，并根据返回动态决策。
- 容忍一定不确定性，且有验证/回退机制（如可跑测试、可人工审批）。
- 探索性、开放式任务（排障、研究、代码修改）。

**不适合使用**

- 流程确定、步骤固定的任务——用普通 Workflow/Chain 更可靠、更便宜、更可控。
- 对延迟、成本极敏感的高频在线场景——Agent 多轮调用成本和延迟成倍放大。
- 要求结果 100% 确定、可审计、强合规且不容出错的关键路径——模型决策的不确定性是风险源。
- 工具副作用大且难回滚、又无法加人工确认的场景。

## 常见误区

- **"Agent 越自主越好"**：无约束的自主会导致循环失控、烧钱、不可预测；生产中往往是"受约束的 Agent + 确定性骨架"更实用。
- **把 Agent 等同于 ReAct 一种循环**：ReAct 只是最基础形态，图式编排、规划+反思、多 Agent 都是 Agent 架构。
- **忽视终止条件与预算上限**：没有硬上限的循环是线上事故和账单爆炸的常见原因。
- **工具描述随便写**：工具 Schema/说明是模型选择与填参的唯一依据，描述含糊会直接拉低调用准确率。
- **把所有历史都塞进上下文**：以为上下文越多越好，实则噪声多、成本高、还会超窗；需要摘要与检索。
- **用 Agent 解决本该用普通代码/工作流的问题**：为了"显得智能"而过度工程化。
- **缺少可观测性**：不记录每回合 trace，线上问题无法复现和归因。

## 我的结论

Agent 架构的价值在于把"运行时的控制流交给模型"，所以它只在**任务路径不确定、需要动态调用工具、且能容忍并验证不确定性**时才值得用。此时应采用"确定性流程做骨架 + 在不确定节点嵌 Agent"的混合设计，并务必配齐步数/预算上限、工具沙箱与权限、人工介入点和全链路 trace——这些控制面比"更聪明的 prompt"更能决定生产成败。

反过来，当流程固定、对成本/延迟敏感、或要求强确定性与可审计时，就不该用 Agent，而应退回到普通 Workflow/Chain 或纯代码。一句话：**能用确定性流程表达的，就不要交给模型去自由决策**；把 Agent 的自主性用在刀刃上，并用工程约束把它的不确定性圈起来。
