## 一句话定义

> AI 应用架构是指以大语言模型（LLM）为核心推理引擎、通过提示词/上下文、工具调用、知识检索和编排控制等组件把模型能力嵌入真实业务流程的软件系统结构设计。

## 解决的问题

在 LLM 出现之前，业务系统要实现"理解自然语言、推理决策、生成内容"这类能力，需要为每个场景单独训练模型、编写大量规则或堆砌 NLP 流水线，成本高、泛化差、迭代慢。直接把 LLM 当成一个黑盒 API 调用又会遇到新的麻烦：模型会幻觉、知识过期、无法访问私有数据、无法执行真实动作、输出不稳定难以对接下游系统，而且上下文窗口有限、调用成本和延迟都不可忽视。AI 应用架构要解决的正是"如何把一个概率性、无状态、知识固化的语言模型，可靠地嵌入到确定性、有状态、强约束的工程系统里"这一核心矛盾。

### AI 应用的标准分层

业界虽无统一规范，但收敛出一套较为公认的分层。自上而下大致为：

| 层 | 职责 | 典型组件 |
| --- | --- | --- |
| 交互/接入层 | 承接用户输入与多轮会话、鉴权限流、流式输出 | Chat UI、API Gateway、WebSocket/SSE |
| 编排层（Orchestration） | 决定调用顺序、路由、循环、重试，是应用的"控制中枢" | Agent Loop、工作流引擎、Router、状态机 |
| 模型层 | 提供推理能力，可多模型路由与降级 | LLM API、本地推理、Embedding 模型 |
| 上下文/提示层 | 组装 System Prompt、few-shot、记忆、检索结果 | Prompt 模板、Context 拼装、Memory |
| 能力扩展层 | 让模型"看得到数据、做得了事" | RAG/向量库、Tools/Function Calling、MCP |
| 数据与基础设施层 | 持久化、可观测、评测、成本与安全治理 | 向量库、关系库、Tracing、Eval、Guardrails |

要点：编排层是把"无状态模型"变成"有状态应用"的关键；上下文层决定模型每一次推理"看到什么"，往往是质量瓶颈所在。

### LLM 在系统中的位置

LLM 应被定位为"系统中的一个推理/生成单元"，而不是整个系统本身。它处在编排层之下、被编排层调度，核心职责有三类：自然语言理解与意图抽取、基于上下文的推理与规划（如决定调用哪个工具）、以及文本/结构化内容生成。它的本质特征决定了放置方式：无状态（状态由外部记忆维护）、概率性（同输入可能不同输出）、知识有截止日期且不可信（需外部检索校正）、无法直接产生副作用（需通过工具）。因此架构上通常把 LLM 包在一层"适配/防腐层"后面，便于多模型切换、降级和成本控制，避免业务代码与某个具体模型强耦合。

### 哪些部分该由代码控制、哪些交给模型

核心原则：确定性、强约束、可审计、涉及安全与金钱的部分交给代码；需要语义理解、模糊判断、自然语言生成的部分交给模型。

- **交给代码**：权限鉴权、数据读写事务、金额计算、流程的硬性分支与状态转移、工具的实际执行、输入输出校验（schema 校验）、重试与超时、审计日志。
- **交给模型**：意图识别、信息抽取、文本摘要/改写/生成、从候选工具中选择、把自然语言翻译成结构化参数、对检索结果做综合推理。
- **边界经验**：能用规则/代码可靠实现的，就不要交给模型（更便宜、更稳、可测试）；凡让模型做决策，必须用代码在外层做校验与兜底（如参数 schema 校验、白名单、人工确认）。错误成本越高，越应把最终决定权收回代码。

## 核心内容

- **以 LLM 为推理内核**：模型负责理解与生成，但不持有状态、不直接产生副作用。
- **上下文工程（Context Engineering）**：通过 System Prompt、few-shot、记忆、RAG 检索把"模型没有的信息"注入上下文；上下文质量直接决定输出质量。
- **工具调用 / Function Calling**：让模型通过结构化调用访问外部数据和执行动作，是"从聊天到做事"的关键。
- **编排与控制流**：分为固定工作流（Workflow，路径由代码预定义）与自主智能体（Agent，路径由模型动态决定）两种范式，可组合使用。
- **记忆与状态**：短期记忆（会话上下文）与长期记忆（向量/数据库），由应用层显式管理。
- **防腐与治理**：模型适配层、Guardrails（输入输出过滤）、评测（Eval）、可观测性（Tracing/日志）、成本与延迟控制、多模型路由与降级。
- **可靠性机制**：schema 校验、重试、超时、幂等、人工确认（Human-in-the-loop）兜底模型的不确定性。

## 典型工程场景

- 企业知识库问答 / 智能客服（RAG + 多轮会话 + 工单工具调用）。
- AI 编码助手（代码上下文检索 + 工具执行 + Agent 循环）。
- 文档/报告自动生成与审阅（抽取、摘要、结构化生成）。
- 流程自动化助手：把自然语言指令翻译成对内部 API/系统的调用（Function Calling）。
- 数据分析对话（NL2SQL、调用 BI 工具并解读结果）。
- 内容审核与合规辅助（分类、理由生成，配合规则兜底）。

## 适用边界

**适合使用**

- 任务涉及自然语言理解、生成或模糊语义判断，传统规则难以覆盖。
- 需求多变、长尾场景多，难以为每种情况预先编码规则。
- 可以容忍一定概率的错误，或能通过校验/人工确认兜底。
- 有可用的私有数据可通过 RAG/工具注入，提升答案的相关性与时效性。

**不适合使用**

- 要求 100% 确定性、强一致、可完全审计的核心交易逻辑（如记账、扣款）——应由代码实现，模型最多做辅助。
- 简单且规则明确的任务，用代码/正则/传统 ML 更便宜更稳。
- 对延迟或成本极度敏感、调用量巨大且价值密度低的场景。
- 错误代价极高且无法有效兜底的高危场景（如医疗诊断、法律裁决直接输出）。

## 常见误区

- **把 LLM 当成系统本身**：以为"调个大模型 API"就是 AI 应用，忽视上下文工程、编排、评测与兜底，上线后质量不可控。
- **过度 Agent 化**：凡事都让模型自主决策多步循环，导致不可预测、成本高、难调试；很多场景固定 Workflow 更合适。
- **忽视上下文质量**：把问题归咎于"模型不行"，实际是检索召回差、提示词杂乱、上下文超限被截断。
- **缺少校验与兜底**：直接把模型输出接入下游系统，不做 schema 校验、不设白名单与人工确认。
- **没有评测体系**：靠"感觉"调提示词，改一处坏三处，无法量化回归，难以持续迭代。
- **把 RAG 当银弹**：以为接了向量库就不会幻觉，忽视召回质量、切块策略和重排。

## 我的结论

当任务需要自然语言理解或生成、需求长尾多变、且错误可被校验或人工兜底时，就该用以 LLM 为核心的 AI 应用架构，并把重心放在上下文工程、编排控制和评测治理上，而不是只盯着换更强的模型。反过来，当逻辑确定、规则清晰、要求强一致与可审计，或错误代价高且无法兜底时，就不该让模型来做决定——此时应由代码主导，模型至多承担辅助性的理解与生成。一句话：模型负责"理解与表达"，代码负责"决定与执行"，架构的价值在于稳妥地划清这条边界并为模型的不确定性兜底。
