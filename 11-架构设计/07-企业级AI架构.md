## 一句话定义

> 企业级 AI 架构是一套把大模型/Agent 能力作为可复用、可治理的平台能力沉淀下来的系统设计：它把模型接入、数据与知识、Agent 编排、安全合规、可观测与成本治理分层解耦，使多业务线能在统一基座上安全、稳定、低成本地构建 AI 应用。

## 解决的问题

> 在没有统一架构之前，企业内各团队各自对接模型 API、各写一套 RAG 和 Prompt、各存一份密钥，带来一系列麻烦：

- 重复造轮子：每条业务线重复实现模型调用、重试、限流、向量检索、评测，投入高且质量参差。
- 供应商锁定与切换难：Prompt 和调用逻辑与某个厂商强耦合，模型涨价、降智或下线时无法平滑迁移。
- 安全与合规黑洞：密钥散落、敏感数据直接发给外部模型、无审计日志，难以通过安全评审和监管要求。
- 成本不可见：Token 消耗无法按团队/应用归集，预算失控且无法做容量规划。
- 质量不可控：缺少统一的评测、灰度、回滚机制，一次 Prompt 或模型变更可能悄悄劣化线上效果。

### 如何从零设计一个企业级 AI Agent 系统

从零设计应遵循"分层解耦、先平台后应用"的思路，典型分层如下：

| 层 | 职责 | 关键组件 |
| --- | --- | --- |
| 接入/网关层 | 统一入口、鉴权、限流、路由 | API Gateway、AI Gateway、租户隔离 |
| 模型层 | 屏蔽厂商差异、负载均衡、回退 | Model Router、Provider Adapter、缓存 |
| 编排/Agent 层 | 任务规划、工具调用、多 Agent 协作 | Planner、Tool/Function 注册中心、Workflow 引擎 |
| 知识/记忆层 | RAG、向量库、短期/长期记忆 | Embedding、向量检索、知识库、Memory Store |
| 数据层 | 结构化数据、文档、日志 | 数仓/湖、对象存储、消息队列 |
| 治理层（横切） | 安全、合规、评测、可观测、成本 | 审计、PII 脱敏、Eval、Tracing、计量计费 |

落地建议：先打通"模型网关 + 可观测 + 评测"这条最小闭环，再逐步沉淀 RAG、Agent 编排与记忆；用一个真实业务场景驱动平台能力建设，避免过度设计。安全与成本从第一天起就纳入设计，而不是事后补。

### 多业务线如何复用基础设施

复用的核心是把共性能力下沉为平台服务，把差异性留在应用层：

- 平台沉淀共性：模型网关、向量检索、Prompt/工具注册中心、评测与可观测，以服务或 SDK 形式对所有业务线开放。
- 多租户隔离：通过 tenant/project 维度隔离配额、密钥、数据和日志，防止互相串数据与争抢资源。
- 配置化而非编码化：Prompt、模型选择、RAG 参数等用配置 + 版本管理，业务线通过配置自助接入，减少平台团队成为瓶颈。
- 知识库分层：公共知识（制度、FAQ）集中维护并共享，业务私有知识按租户隔离。
- 内部开发者体验：提供统一 SDK、示例和自助控制台，让业务线"几行代码接入"，这是复用能否真正发生的关键。

### 权限、审计、合规

这是企业落地的硬门槛，需系统性设计：

- 身份与权限：接入企业 SSO/OIDC，做到按用户、角色、租户的细粒度授权（谁能调哪个模型、访问哪些知识库、调用哪些工具）。
- 数据安全：敏感数据（PII、密钥、商业机密）在送入外部模型前做脱敏/脱密或走私有化模型；明确数据是否可被厂商用于训练。
- 全链路审计：记录每次请求的用户、输入、输出、所用模型、工具调用与时间戳，支持留痕回溯与责任追溯。
- 内容安全：输入/输出两侧接入内容审核与越狱检测，防止有害内容和 Prompt 注入。
- 合规对齐：按行业与地区对齐监管要求（如数据出境、个人信息保护、金融/医疗行业规定、企业内部数据分级），并保留合规证据。

### 模型接入层如何统一

统一模型接入层（AI Gateway / Model Router）是企业架构的中枢：

- 统一协议：对上暴露一致接口（通常兼容 OpenAI 风格 API），屏蔽各厂商在参数、流式、函数调用上的差异。
- 路由与回退：按场景、成本、延迟、可用性在多模型/多厂商间路由，主模型故障或限流时自动回退到备选。
- 密钥与配额集中管理：密钥只存在网关，业务线不接触；按租户下发配额与速率限制。
- 弹性与韧性：统一实现重试、超时、熔断、限流和语义缓存，降低重复调用成本。
- 可观测内建：在网关层天然采集 Token、延迟、错误率等指标，为计量和治理提供数据源。

工程上可自建网关，也可基于开源方案（如 LiteLLM、各类 AI Gateway）定制，关键是让它成为唯一出口。

### 成本如何分摊与治理

成本治理的前提是"可计量、可归集、可控制"：

- 计量：在网关统一采集每次调用的输入/输出 Token、模型单价，换算成本并打上 tenant/app/user 标签。
- 分摊：按租户/业务线/应用维度做 Chargeback 或 Showback，让各团队为自己的消耗负责。
- 控制：设置预算与配额告警、速率限制，超阈值降级或拒绝；对高频重复请求用语义缓存。
- 优化：按任务难度分级路由（简单任务用小模型/廉价模型，复杂任务才用旗舰模型），控制上下文长度与检索条数，用批处理和缓存降本。
- 持续治理：建立成本看板和定期复盘，把"效果/成本"作为模型选型与 Prompt 迭代的核心指标。

## 核心内容

- 分层架构：接入层、模型层、编排/Agent 层、知识/记忆层、数据层，加上横切的治理层（安全/合规/评测/可观测/成本）。
- 模型网关：统一入口，负责路由、回退、密钥管理、限流熔断、缓存与指标采集，是解耦业务与厂商的关键。
- 平台化与多租户：共性能力下沉为平台服务，按租户隔离配额、数据与密钥，业务线通过配置自助接入。
- 知识与记忆：RAG（向量检索）、公共/私有知识分层、短期与长期记忆，让 Agent 具备企业上下文。
- 安全合规基座：SSO、细粒度授权、PII 脱敏、内容审核、全链路审计贯穿始终。
- 可观测与评测：Tracing、指标、离线/在线 Eval、灰度与回滚，保证质量可控、变更可回退。
- 成本治理：全链路 Token 计量、按租户分摊、预算告警与分级路由优化。

## 典型工程场景

- 大型企业统一 AI 中台：为多个事业部提供统一的模型调用、知识库和 Agent 编排能力。
- 智能客服/知识问答：基于企业私有知识的 RAG 问答，需多租户、权限与审计。
- 研发效能平台：代码助手、测试生成、文档生成等多工具集成，统一接入与计量。
- 金融/医疗等强监管行业：对数据脱敏、审计留痕、合规对齐有硬性要求的 AI 应用。
- 多厂商模型并存与切换：需要在多个模型供应商间做路由、回退与成本优化的场景。

## 适用边界

**适合使用**

- 有多条业务线或多个团队需要共享 AI 能力、避免重复建设。
- 对安全、合规、审计、成本可见性有明确要求的中大型组织。
- 需要在多模型/多厂商间灵活切换、规避锁定与可用性风险。
- AI 已从试点走向规模化生产，需要稳定性、可观测与治理。

**不适合使用**

- 单一应用、单团队的早期 PoC/原型，直接调模型 API 更快，过早平台化是浪费。
- 需求高度不确定、尚在探索价值阶段，重架构会拖慢验证速度。
- 极小团队缺乏平台维护人力，自建网关与治理体系的边际收益低于成本。

## 常见误区

- 把"包一层统一 API"等同于企业级架构，忽视了治理、评测、多租户与可观测这些真正难的部分。
- 先建大而全的平台再找场景，结果平台无人用；应由真实业务驱动、小步沉淀。
- 只关注模型效果，忽视成本、安全与合规，上线后被成本或合规问题反噬。
- 把 MLOps 那套直接套到 LLM 上，忽略 Prompt 版本、评测困难、幻觉与注入等 LLM 特有问题。
- 认为 RAG/Agent 搭好就万事大吉，缺少持续评测与回滚机制，线上效果悄悄劣化却无人察觉。

## 我的结论

当企业的 AI 使用已经从"一个团队做一个 Demo"走向"多团队、多场景、要上生产"时，就应该投入企业级 AI 架构：把模型网关、可观测、评测这条最小闭环先建起来，再逐步沉淀 RAG、Agent 编排、记忆与成本治理，由真实业务驱动而非一次性建大平台。反过来，在单应用、早期验证、价值尚不明确或缺乏平台维护人力的阶段，不该做重架构——直接调 API、快速迭代验证价值更划算。核心判断标准是"复用收益与治理需求是否已经超过平台建设与维护成本"。
