# 知识架构

> **上级**：[11-架构设计](README.md) ｜ **依赖**：RAG

## 一句话定义

> 知识架构是把企业/应用的外部知识，从原始来源到可供模型消费的可检索表示，这一整条链路的组织方式与治理规则——它定义了知识如何接入、切分、索引、更新、融合与授权。

## 解决的问题

> 大模型本身的参数知识是静态、过时且不可控的：训练截止后的新信息它不知道，私有/领域数据它从未见过，而且无法溯源、无法按权限隔离。早期做法是把资料一股脑塞进 Prompt，很快撞上上下文长度、成本、相关性稀释（lost in the middle）等问题。知识架构的出现，是为了系统性地解决"模型需要用但不在参数里的知识"该如何被组织、召回、更新和治理，而不是靠临时拼接。

### 知识接入、切分、索引的流水线

一条典型的知识流水线（offline/ingestion 侧）包含以下阶段，工程上通常做成可重放、可增量的 DAG：

| 阶段 | 做什么 | 工程要点 |
| --- | --- | --- |
| 接入 Load | 从数据源（文件、数据库、API、网页、IM）拉取原始内容 | 统一为中间文档模型；保留 source/uri/权限/版本等元数据 |
| 解析 Parse | PDF/Office/HTML 转为结构化文本 | 保留标题层级、表格、代码块；OCR 处理扫描件 |
| 切分 Chunk | 把长文切成检索单元 | 按语义/标题/固定窗口切分，带 overlap；chunk 内保留标题路径做上下文 |
| 向量化 Embed | 用 embedding 模型把 chunk 编码为向量 | 固定模型版本；换模型需全量重建索引 |
| 索引 Index | 写入向量库 + 倒排/关键词索引 | 同时建稠密（向量）与稀疏（BM25）索引，支持混合检索 |

关键决策点：切分粒度（太大召回不精、太小丢上下文，常见 256~1024 token）、是否做父子分块（小块召回、大块喂模型）、是否抽取结构化字段做元数据过滤。流水线必须支持增量更新与幂等重跑，否则无法应对持续变化的数据源。

### 知识更新与失效

知识不是一次性灌入，而是需要持续同步与过期管理：

- **增量同步**：对数据源做变更检测（时间戳、版本号、内容 hash、CDC/webhook），只重算发生变化的文档，避免全量重建的成本。
- **删除与失效**：源文档删除/下线时，必须同步删除对应向量（软删除打 tombstone 或硬删除），否则会召回"幽灵知识"。给 chunk 带 TTL 或 valid_until 可支持时效性内容自动过期。
- **一致性窗口**：ingestion 与检索是异步的，存在延迟；需明确"数据多久能生效"的 SLA，并避免半更新状态（先删后写、或版本切换原子生效）。
- **重建触发**：embedding 模型升级、切分策略变更、schema 调整都需要全量 reindex，应把索引版本化并支持蓝绿切换。
- **缓存失效**：若对检索结果或答案做了缓存，源更新时要能按文档粒度精确淘汰相关缓存。

核心原则：把"知识的生命周期"当作数据工程问题来治理，而不是把向量库当成只写不删的垃圾桶。

### 多源知识的统一

多源指结构化（数据库、表格）、半结构化（JSON、API）、非结构化（文档、网页）等异构来源的融合，难点在于语义对齐与路由：

- **统一文档模型 + 元数据 schema**：所有来源归一到带 `source / type / tenant / acl / timestamp` 等标准元数据的中间表示，便于过滤与治理。
- **多路检索与路由**：不同来源适合不同检索方式——事实型/数值型走结构化查询（Text2SQL、API 调用），叙述型走向量检索；由 router 根据 query 决定走哪条路或并行后融合。
- **结果融合与去重**：多源召回后用 RRF（Reciprocal Rank Fusion）或 rerank 模型统一排序，并对跨源重复内容去重。
- **冲突消解**：同一事实多源不一致时，需按来源可信度/时效性定优先级，并在答案中标注出处（provenance）。
- **权限统一**：不同源的 ACL 要在检索层统一执行（按 tenant/role 过滤），防止跨源越权泄露。

实务上，知识图谱常作为"多源统一的语义骨架"，把实体对齐后再挂接各源的证据。

## 核心内容

- **四大能力面**：接入与解析、切分与表示、检索与融合、更新与治理。知识架构是这四面的组合设计，而非单一组件。
- **离线/在线双链路**：offline 做 ingestion（解析→切分→embedding→索引），online 做 retrieval（query 改写→检索→rerank→组装 context）。
- **混合检索**：稠密向量（语义）+ 稀疏关键词（BM25，精确匹配）+ 元数据过滤，三者结合显著优于单一向量检索。
- **分块策略**：固定窗口 / 递归按分隔符 / 语义切分 / 父子（small-to-big）/ 带标题路径的上下文增强。
- **重排 Rerank**：用 cross-encoder 对初召回的 topN 精排，提升喂给模型的 context 相关性。
- **元数据与治理**：权限（ACL/多租户）、来源溯源、版本、时效，是生产级知识架构区别于 demo 的关键。
- **评估闭环**：召回率/命中率、答案忠实度（faithfulness）、来源归因准确率，需要有可量化的离线评测集。

| 上游 | Embedding 模型、向量数据库、文档解析/ETL | 知识架构依赖它们把原始数据变成可检索表示并持久化 |
| 下游 | RAG、Agent 的知识工具（retrieval tool）、问答/Copilot 应用 | 它们消费知识架构产出的检索能力来生成有依据的回答 |
| 易混淆 | 知识图谱（Knowledge Graph） | 知识图谱是一种结构化知识表示/一种可选组件；知识架构是更上层的整体链路与治理设计，可以包含也可以不含图谱 |

## 典型工程场景

- 企业内部知识库问答 / 智能客服：把产品手册、工单、FAQ、政策文档接入，支撑有出处的回答。
- 代码助手 / 研发 Copilot：索引代码库、API 文档、设计文档，为生成提供项目上下文。
- 法律、医疗、金融等合规领域：需要强溯源、强权限隔离、可审计的知识供给。
- 多数据源聚合搜索：同时检索 Confluence、数据库、工单系统、网盘并融合排序。
- Agent 长期记忆与知识沉淀：把对话、执行结果结构化入库，形成可复用知识。

## 适用边界

**适合使用**

- 知识量大、更新频繁、无法全部塞进上下文窗口的场景。
- 需要溯源、权限隔离、多租户、可审计的生产系统。
- 知识跨多个异构来源，需要统一检索与融合。
- 领域/私有知识，模型参数里本就没有。

**不适合使用**

- 知识极少且稳定，直接写进 Prompt 或 system message 更简单可靠。
- 任务依赖的是模型的推理/生成能力而非外部事实（如纯创作、翻译）。
- 对延迟极度敏感且无法接受检索开销的实时链路（需权衡或预取）。
- 需要全局聚合/统计类问答（如"一共有多少条"），向量检索天然不擅长，应走结构化查询。

## 常见误区

- **"切好 chunk + 向量库 = 搞定知识架构"**：忽略了更新/失效、权限、融合、评估等治理环节，demo 能跑生产会崩。
- **只用向量检索**：对精确关键词、ID、代码符号召回很差，应配合 BM25 混合检索。
- **chunk 越大越好或越小越好**：粒度是需要按任务与数据实测调参的权衡，没有万能值。
- **向量库只写不删**：源数据删了不同步淘汰，导致召回过期/幽灵知识。
- **换 embedding 模型不重建索引**：不同模型向量空间不可比，必须全量 reindex。
- **忽视权限在检索层的执行**：仅在应用层过滤，容易造成跨租户/越权数据泄露。
- **没有评估集**：靠"看起来还行"调参，无法量化改动带来的收益或回归。

## 我的结论

> 当知识"量大、常变、需溯源、分权限、跨多源"时，就应该把它当成一套知识架构来系统设计——而不是只接一个向量库。它的价值不在 embedding 本身，而在接入、更新、融合、权限、评估这些治理能力的闭环；生产系统的差距几乎都在这里。
> 反过来，如果知识只有几页且稳定，直接写进 Prompt 就够了，上知识架构是过度工程。遇到聚合/统计、精确匹配类需求，不要硬塞给向量检索，该走结构化查询或混合检索。先定清楚"要回答哪类问题、知识怎么变、谁能看"，再决定架构复杂度。
