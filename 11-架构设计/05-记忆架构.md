# 记忆架构

> **状态**：🟢 已理解 ｜ **深度**：B 能够应用 ｜ **更新**：2026-09-15
> **上级**：[11-架构设计](README.md) ｜ **依赖**：Memory

## 一句话定义

> 记忆架构是 Agent 用来在"当前上下文窗口之外"持续存储、组织、检索和淘汰信息的一套机制，让 Agent 能跨轮次、跨会话地记住事实、经验与状态。

## 解决的问题

> 大模型本身是无状态的：每次调用只能看到被塞进上下文窗口的内容，窗口有长度上限且成本随长度增长。没有记忆架构时，Agent 存在三类麻烦：
>
> - **会话失忆**：换一轮对话或超出窗口，之前说过的偏好、约定、结论就丢失，用户被迫反复重复。
> - **上下文爆炸与成本失控**：为了"记住"把全部历史硬塞进 prompt，导致 token 成本高、延迟大，还会触发窗口截断。
> - **缺乏经验沉淀**：Agent 无法把一次任务里学到的教训、用户画像、项目知识累积下来复用，每次都从零开始。

### 短期 / 长期记忆的存储分工

短期记忆（working / short-term memory）承载"当前任务正在用"的信息，长期记忆（long-term memory）承载"需要跨会话保留"的信息，两者在存储介质、生命周期和访问方式上分工明确：

| 维度 | 短期记忆 | 长期记忆 |
| --- | --- | --- |
| 载体 | 上下文窗口、对话 buffer、临时变量/草稿区 | 向量库、KV/文档库、关系库、知识图谱、文件 |
| 生命周期 | 单次任务或单次会话，会话结束即可丢弃 | 跨会话长期保留，显式淘汰才消失 |
| 访问方式 | 直接在 prompt 中可见，无需检索 | 需要检索（语义/关键词/图查询）后再注入 prompt |
| 容量 | 受窗口 token 上限约束 | 近似无限，受存储成本约束 |
| 典型内容 | 当前对话历史、中间推理、刚调用的工具结果 | 用户画像/偏好、历史事实、项目知识、过往经验 |

工程上常再细分长期记忆为：**语义记忆**（事实与知识）、**情景记忆**（发生过的具体事件/交互）、**程序记忆**（如何完成某类任务的技能/流程）。短期记忆更像 CPU 寄存器与缓存，长期记忆更像磁盘，两者通过"检索—注入—回写"形成层级结构。

### 记忆的写入、检索与遗忘

这是记忆架构的三条核心数据通路，每条都需要工程取舍：

- **写入（Write）**：决定"记什么、何时记、以什么粒度记"。常见策略有：原样追加整段对话；用 LLM 做摘要/抽取后再存（事实抽取、要点压缩）；只在满足触发条件（如用户明确偏好、任务里程碑）时写入。要点是避免把噪声全部写进长期记忆，否则检索质量会被稀释。写入还要考虑去重与冲突合并（同一事实多次出现、前后矛盾时如何更新）。
- **检索（Retrieve）**：决定"用什么把相关记忆取出来"。主流是向量语义检索（embedding + ANN），常配合关键词/BM25 做混合检索、按时间衰减或重要度加权重排（re-rank）；结构化记忆则用 SQL/图查询。关键指标是召回相关、过滤无关，并控制注入条数以免挤占窗口。
- **遗忘（Forget / Evict）**：决定"什么该淘汰"。手段包括 TTL 过期、LRU/LFU 淘汰、重要度打分低于阈值即删、周期性摘要压缩（把旧的细节合并成概要）、以及用户显式删除（隐私合规必需）。遗忘不是缺陷而是特性：它控制存储成本、避免过时信息污染决策，并满足"被遗忘权"等合规要求。

### 记忆与上下文的衔接

记忆系统与上下文窗口之间靠一条"检索—编排—注入—回写"的闭环连接，核心是在有限 token 预算内把最相关的记忆放进 prompt：

1. **触发检索**：在构造本轮 prompt 前，用当前 query / 任务状态作为线索去长期记忆检索候选。
2. **预算分配与编排**：对候选做重排、截断、压缩，按优先级分配 token（系统指令 > 关键长期记忆 > 近期对话 > 补充上下文），这属于 Context Engineering 的范畴。
3. **注入**：把选中的记忆以结构化片段（如"已知用户偏好：…"）拼进上下文，必要时标注来源以便模型区分可信度。
4. **回写**：本轮结束后，把新产生的事实/结论/经验按写入策略沉淀回长期记忆，形成下一轮的素材。

衔接的难点在于：窗口有限所以不能全注入；注入过多会分散注意力（lost-in-the-middle）；注入过时或错误记忆会直接导致错误输出。因此记忆架构本质上是在"记得多"和"看得准"之间做工程平衡。

## 核心内容

- **记忆分层**：短期（上下文/工作记忆）与长期（语义/情景/程序记忆）分层存储，并在层间搬运信息。
- **三条数据通路**：写入、检索、遗忘构成记忆的生命周期管理。
- **存储后端多样**：向量库（语义检索）、KV/文档库（结构化事实）、关系库（可查询属性）、知识图谱（实体关系）、文件/对象存储（原始资料），常组合使用。
- **记忆编排层**：负责摘要压缩、重要度打分、重排、冲突合并、token 预算分配，是连接存储与上下文的核心逻辑。
- **检索增强**：与 RAG 共用 embedding/向量检索技术栈，但记忆更强调"随交互动态增长、可写可淘汰"，RAG 更偏"静态外部知识库"。
- **一致性与隐私**：需处理事实更新/冲突、用户级隔离、可删除（合规）等问题。

## 典型工程场景

- **个性化助手/陪伴类产品**：记住用户姓名、偏好、历史目标，跨会话提供连贯体验。
- **客服/CRM Agent**：沉淀用户历史工单、沟通记录、已解决方案，避免重复询问。
- **编码 Agent / 项目助手**：记住代码库约定、架构决策、过往修复经验，跨任务复用项目知识。
- **长程任务 / 多步规划 Agent**：用工作记忆保存中间计划与状态，支撑超出单窗口的任务执行。
- **多 Agent 协作**：用共享记忆作为黑板（blackboard）传递中间产物与共识。
- **自我改进 Agent**：把成功/失败经验写入程序记忆，形成可复用技能。

## 适用边界

**适合使用**

- 需要跨会话/跨轮次保持个性化与连续性的交互型应用。
- 任务上下文超出单个窗口、需要外部化存储中间状态的长程任务。
- 信息会随交互动态增长、需要写入与淘汰（而非只读静态知识）的场景。
- 对用户画像、历史经验沉淀有明确价值的产品。

**不适合使用**

- 单轮、无状态的一次性调用（如一次性翻译/分类），引入记忆只增加复杂度与延迟。
- 全部必需信息都能稳定放进上下文窗口的小任务，直接塞 prompt 更简单可靠。
- 对强一致性/事务性要求极高的权威数据（应放主业务数据库，记忆层只做引用，不做真相源）。
- 隐私高度敏感且无合规删除/隔离能力时，不应长期留存用户数据。

## 常见误区

- **把记忆等同于"无限塞历史"**：真正难点是检索准和遗忘得当，而非存得多；堆砌历史反而降低质量、推高成本。
- **把记忆和 RAG 混为一谈**：记忆强调动态写入、遗忘与用户隔离，RAG 偏静态知识检索，二者技术栈重叠但目标不同。
- **只写不删**：忽视遗忘机制，导致过时/矛盾信息污染决策，并带来存储成本和隐私合规风险。
- **把记忆当真相源**：直接用记忆里的事实做关键决策而不校验，易被过时或错误记忆误导；重要事实应回源核验。
- **忽视注入位置与数量**：检索到就全部塞进 prompt，触发 lost-in-the-middle，模型反而抓不住重点。
- **忽略多用户隔离**：共享记忆空间导致串号、隐私泄露。

## 我的结论

> 记忆架构的价值取决于"信息是否需要跨越上下文窗口而持续存在"。**该用的时候**：产品需要个性化、连续性，或任务跨会话、跨窗口，且信息会动态增长、需要选择性保留——此时记忆架构是刚需。**不该用的时候**：单轮无状态任务，或所有必要信息都能稳定装进窗口——此时直接构造 prompt 更简单可靠，引入记忆只会增加检索延迟、一致性与隐私负担。落地时真正的工程重心不是"存什么"，而是写入策略、检索精度、遗忘与预算编排这几件事，它们决定了记忆是帮手还是噪声源。
