# 多 Agent 架构

> **上级**：[11-架构设计](README.md) ｜ **依赖**：Multi-Agent

## 一句话定义

> 多 Agent 架构是把一个复杂任务拆给多个各有分工、各自持有独立上下文的 LLM Agent，通过显式的通信与编排协议协作完成，而不是让单个 Agent 在一个会话里包揽全部职责。

## 解决的问题

> 单 Agent 在面对复杂任务时会暴露几个结构性麻烦：
> - **上下文膨胀与污染**：一个会话里塞进所有工具结果、历史对话和中间产物，很快撑爆上下文窗口，且无关信息干扰推理质量（俗称"上下文腐烂"）。
> - **职责与提示词耦合**：一个系统提示要同时兼顾规划、检索、编码、审查等相互冲突的目标，难以调优，改一处影响全局。
> - **缺乏并行度**：串行的单 Agent 无法同时推进多个相互独立的子任务，长任务延迟高。
> - **难以专精**：不同子任务需要不同工具集、不同模型、不同约束，单 Agent 很难为每种场景都做到最优。
> 多 Agent 通过"分而治之 + 上下文隔离"来缓解这些问题。

### 多 Agent 的通信拓扑

常见拓扑及其取舍：

| 拓扑 | 结构 | 适用 | 代价 |
| --- | --- | --- | --- |
| 编排者-工作者（Orchestrator-Worker / Supervisor） | 一个中心 Agent 分派任务给多个子 Agent，汇总结果 | 任务可分解、需要统一收口（最常用） | 中心是瓶颈与单点，分派质量决定上限 |
| 层级式（Hierarchical） | 编排者下再挂子编排者，形成多层树 | 超大任务、需要递归分解 | 层级越深，误差与延迟累积越严重 |
| 流水线（Sequential / Pipeline） | A→B→C 顺序传递，各司一环 | 阶段清晰的工作流（如检索→生成→审查） | 前序错误向后传播，无法并行 |
| 群聊/黑板（Group Chat / Blackboard） | 多 Agent 共享消息区自由发言，由调度器选发言人 | 开放式讨论、头脑风暴 | 容易发散、token 成本高、终止条件难定 |
| 去中心化/网状（Peer-to-Peer / Network） | Agent 之间点对点直接通信 | 高自治、动态协作 | 协调复杂，难以调试与追责 |

- 通信载体通常是**结构化消息**（含发送方、接收方、任务、上下文引用），实践中建议走显式消息总线/句柄而非把所有内容塞进同一上下文。
- 工程上**编排者-工作者**是性价比最高、最可控的默认选择；网状/群聊只在确有开放式协作需求时才用。

### 上下文隔离与共享的取舍

- **隔离的好处**：每个子 Agent 只看到与自己子任务相关的最小上下文，避免窗口爆炸、降低干扰、便于独立调优与复用，还能并行执行。
- **隔离的代价**：子 Agent 之间会丢失全局视野，可能重复劳动、产生相互冲突的假设，需要编排者做"信息再汇聚"。
- **共享的方式**：
  - 完全共享同一历史（最简单，但等于退化回单 Agent 的上下文问题）。
  - 共享"摘要/结论"而非原始过程（主流做法：子 Agent 只回传压缩后的结果）。
  - 共享外部状态（黑板、向量库、文件系统、Scratchpad）作为中介，按需读取。
- **工程准则**：默认隔离，按需共享；传递"结果与关键事实"而非"全部过程"；用外部存储承载需要跨 Agent 复用的大块状态，用消息只传指针/摘要。

### 编排者与执行者的职责划分

| 角色 | 职责 | 不该做的事 |
| --- | --- | --- |
| 编排者（Orchestrator / Planner） | 任务分解、分派、调度、结果汇总、冲突裁决、决定终止 | 不亲自做脏活累活、不堆砌领域细节工具 |
| 执行者（Worker / Specialist） | 在受限上下文中完成单一子任务，带专用工具与提示 | 不越权改变全局计划、不擅自调度其他 Agent |

- 编排者应当是"薄"的：擅长规划与路由，而非承载业务逻辑；执行者是"厚"的：专精、工具齐全、提示收敛。
- 关键设计点：**分派粒度**（太细则协调开销大，太粗则失去隔离意义）、**结果契约**（执行者返回的格式/字段要稳定可解析）、**错误处理与重试**（执行者失败时编排者如何降级或重分派）、**终止条件**（避免无限循环）。
- 可引入独立的**审查者/评估者 Agent**（critic/verifier）形成"生成-批判"回路，提升可靠性。

### 相比单 Agent 的收益与成本

**收益**
- 能处理更大、更复杂、可并行的任务；上下文更干净，单步推理质量更高。
- 模块化：各 Agent 可独立迭代、替换、复用，可按子任务选不同模型（强模型做规划、便宜模型做执行）。
- 可观测性更好：职责边界清晰，便于定位是哪一环出错。

**成本**
- **Token/费用成倍增长**：Anthropic 公开数据显示多 Agent 系统 token 消耗可达单次聊天的约 15 倍，分派与汇总本身也烧 token。
- **延迟与复杂度**：多轮协调、消息传递、状态同步带来额外延迟；系统更难调试，错误可能跨 Agent 传播且难归因。
- **一致性风险**：子 Agent 各自假设可能冲突，需要额外机制对齐。
- **工程准则**：先用单 Agent + 好的工具/上下文管理把问题压到极限，只有当任务确实可分解且并行收益明显、或上下文确实装不下时，才升级到多 Agent。不要为了"看起来高级"而上多 Agent。

## 核心内容

- **构成要素**：多个具备独立上下文与工具的 Agent + 通信协议 + 编排/调度逻辑 + 共享状态存储（可选）+ 终止条件。
- **分解-执行-汇聚流程**：编排者分解任务 → 分派给执行者（可并行）→ 执行者在隔离上下文中调用工具产出结果 → 结果回传并由编排者/审查者汇总与裁决 → 必要时迭代重分派 → 满足终止条件后收口。
- **上下文工程**：隔离为默认，消息只传摘要/指针，大状态外置（文件/向量库/黑板）。
- **典型角色**：Planner/Orchestrator、Specialist Worker、Critic/Verifier、Router（路由到合适 Agent）。
- **协作模式**：编排者-工作者、层级、流水线、群聊/黑板、网状。
- **可靠性机制**：结构化消息契约、重试与降级、超时与循环上限、人类在环（HITL）审批点。
- **主流框架**：LangGraph（图/状态机）、AutoGen（对话式多 Agent）、CrewAI（角色分工）、OpenAI Swarm/Agents SDK、MetaGPT 等。

## 典型工程场景

- **深度研究/调研助手**：一个主 Agent 拆成多个子 Agent 并行检索不同来源，再汇总成报告（如 Anthropic 的多 Agent Research 系统）。
- **软件工程 Agent**：规划 Agent 拆任务，编码、测试、代码审查分别由专精 Agent 完成。
- **复杂客服/工单路由**：路由 Agent 把请求分到账单、技术、售后等专精 Agent。
- **数据流水线/ETL + 分析**：抽取、清洗、分析、可视化分阶段由不同 Agent 负责。
- **内容生产线**：选题 → 写作 → 审校 → 配图的角色分工协作。
- **仿真/博弈/多方协商**：模拟多个角色（如谈判双方、辩论正反方）各自决策。

## 适用边界

**适合使用**

- 任务天然可分解为相对独立、可并行的子任务，且并行收益明显（如广度检索、多来源调研）。
- 单任务上下文确实装不下，需要靠隔离来控制窗口与干扰。
- 不同子任务需要显著不同的工具集、约束或模型，专精化收益大。
- 需要"生成-审查"等对抗/校验回路来提升可靠性。

**不适合使用**

- 任务简单或强顺序依赖、无法并行，拆分只会徒增协调开销与延迟。
- 对成本/延迟敏感、token 预算紧张（多 Agent 通常数倍烧钱）。
- 子任务间需要高频紧耦合地共享全部上下文，隔离反而制造信息断层。
- 团队尚无成熟的追踪、评测与调试能力，贸然上多 Agent 会难以维护。

## 常见误区

- **"Agent 越多越聪明"**：数量不等于能力，协调开销与错误传播可能抵消收益，常见反而是单 Agent 调好更划算。
- **把工作流当多 Agent**：确定性步骤编排（固定 DAG）其实是 workflow，不需要每个节点都自治决策。
- **忽视 token 成本**：多 Agent 费用可能是单次对话的十几倍，不做预算治理会失控。
- **共享全部上下文**：把所有历史塞给每个 Agent，等于放弃了隔离的核心价值。
- **没有终止条件/循环上限**：群聊或网状拓扑容易无限对话、发散不收敛。
- **结果契约不稳定**：执行者返回自由文本而非结构化结果，编排者解析失败导致级联错误。
- **错误难归因**：缺乏统一追踪时，跨 Agent 的失败几乎无法定位。

## 我的结论

> 多 Agent 不是默认选项，而是"单 Agent 压不住时"的升级手段。
> - **该用**：当任务可清晰分解为可并行的独立子任务、上下文确实超出单 Agent 承载、或不同子任务需要截然不同的专精与工具，且你已有追踪/评测/成本治理能力时——尤其是广度优先的检索/调研类任务，并行收益最明显。
> - **不该用**：任务强顺序依赖、规模不大、对成本和延迟敏感、或子任务需要紧耦合共享全部上下文时。此时优先把单 Agent 的上下文工程、工具设计和提示调好，往往更快更省更可靠。
> - **落地心法**：默认用编排者-工作者拓扑，默认隔离上下文、只传摘要，设好结果契约、重试、终止条件与可观测性；先证明单 Agent 不够，再加 Agent。
