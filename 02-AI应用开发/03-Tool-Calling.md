# Tool Calling / 工具调用

> **上级**：[02-AI应用开发](README.md) ｜ **依赖**：Structured Output

## 一句话定义

> Tool Calling 是让 LLM 在推理时输出"我要调用某个工具、参数是这些"的结构化请求，由外部程序执行后把结果回传给模型，从而让只会生成文本的模型能够获取外部信息、执行真实动作。

## 解决的问题

> LLM 本身被权重和训练时间冻结：不知道实时信息、算不准数学、访问不了数据库/API、也不能真正"做"任何事（发邮件、下单、查天气）。
> 在 Tool Calling 之前，想让模型做这些只能靠脆弱的文本约定（让它输出一段话再正则解析）。Tool Calling 用标准化的结构化协议把"模型决定用什么工具、给什么参数"规范下来，让模型可以可靠地借助外部能力，从"只会说"升级为"能做事"——这是 Agent 的根基。

### Tool Calling 解决什么问题

补齐 LLM 的四大短板：
- **实时性**：获取训练截止后的最新信息（天气、股价、新闻）。
- **精确性**：把计算、精确查询交给计算器/数据库/代码，避免幻觉。
- **私有数据**：访问企业内部系统、知识库、用户数据。
- **行动能力**：真正执行副作用操作（写文件、发消息、调用业务 API）。
一句话：让模型"知道自己不知道/做不到的事，交给工具"。

### 模型如何决定调用工具

- 你在请求里提供一组**工具定义**（名字、描述、参数 schema）。
- 模型基于用户意图和这些**工具描述**，判断是否需要工具、用哪个、填什么参数——这完全依赖描述写得够不够清楚（工具的 name/description 本质是给模型的提示）。
- 决定调用时，模型不直接执行，而是**输出一个结构化的 tool_call**（工具名 + 参数 JSON）。
- 控制权回到你的程序：你执行工具，把结果作为一条 `tool` 角色消息回传，模型再据此继续（可能再次调用工具，或给出最终答复）。
- 可用参数控制：`tool_choice`（auto/required/指定某工具/none）引导是否及如何调用；模型也支持**并行多工具调用**。

### 工具定义、参数、结果的完整结构

一轮完整的工具调用循环：
1. **工具定义（请求时提供）**：
   - `name`：工具标识。
   - `description`：干什么、何时用（对模型选择至关重要）。
   - `parameters`：JSON Schema，声明参数字段、类型、必填、枚举。
2. **模型输出 tool_call**：`{ id, name, arguments(JSON) }`——这正是一个结构化输出。
3. **程序执行**：解析参数（先 schema 校验）→ 调真实函数/API → 得到结果。
4. **结果回传**：以 `role: tool`（带对应 tool_call_id）把结果 JSON/文本加入 context。
5. **模型续推**：基于工具结果生成下一步（再调用或最终回答）。
整个过程是 assistant↔tool 的多轮消息累积在同一 context 里。

### Tool Calling 与传统 API 调用的区别

| 维度 | 传统 API 调用 | Tool Calling |
| --- | --- | --- |
| 谁决定调用 | 开发者在代码里写死 | 模型在运行时**自主决定**是否/调哪个/传什么参数 |
| 参数来源 | 代码逻辑/用户输入 | 模型从自然语言意图**推断生成** |
| 触发方式 | 确定性控制流 | 概率性决策，可能不调、调错、漏参 |
| 执行者 | 程序直接执行 | 模型只"请求",**仍由程序执行**（模型不碰真实系统） |
| 可靠性 | 确定 | 需校验、重试、权限与安全兜底 |

关键：Tool Calling 不是模型自己去调 API，而是模型**生成调用意图**、程序执行——这层隔离是安全与可控的基础。

### Tool Calling 是 Agent 的基础能力之一

Agent 的本质是"感知—决策—行动"的循环，而**行动**几乎全靠工具调用落地。有了 Tool Calling，模型才能：查信息、用工具、改变环境，并根据结果迭代。再叠加循环控制、记忆、规划，就构成 Agent。可以说没有 Tool Calling 就没有能"做事"的 Agent，它是从"对话"到"自主执行"的分水岭。

## 核心内容

- **本质**：模型输出结构化调用意图（基于 Structured Output），程序执行并回灌结果，形成多轮循环。
- **协议**：OpenAI tools/function calling、Anthropic tool use、以及 MCP 等标准化工具接入方式。
- **描述即接口**：工具 name/description/参数 schema 既是给程序的契约，也是给模型的"说明书",写得好坏直接决定调用准确率。
- **循环控制**：程序负责"执行工具→回传→判断是否结束",并设最大轮数防死循环。
- **安全要点**：模型不直接执行；程序侧必须做参数校验、权限控制、副作用确认（尤其写操作/不可逆操作）、防注入。
- **可靠性工程**：参数校验失败重试、工具报错回灌让模型纠正、幂等设计、超时与降级。

## 典型工程场景

> - 实时信息：天气、股价、搜索。
> - 精确计算/查询：计算器、SQL、数据库检索。
> - 业务动作：下单、发邮件、创建工单、改配置。
> - RAG 检索封装成工具供模型按需调用。
> - 多工具编排的 Agent 任务。

## 适用边界

**适合使用**

- 需要实时/私有数据或精确计算时
- 需要模型执行真实动作（有副作用）时
- 构建能自主决策调用能力的 Agent

**不适合使用**

- 纯文本生成、无需外部能力时（徒增复杂度与延迟）
- 调用路径完全确定、无需模型决策时（直接写代码更可靠）
- 高危不可逆操作缺乏确认/权限控制时（必须先补安全机制）

## 常见误区

- 以为模型自己去执行 API——实际只输出意图，执行在程序侧。
- 工具 description 写得含糊——模型选错/漏调，描述就是接口文档。
- 不校验模型给的参数就执行——可能类型错、越权、注入。
- 对写操作/不可逆操作不加确认——放大错误决策的后果。
- 不设最大调用轮数——可能陷入反复调用的死循环。

## 我的结论

> Tool Calling 是 LLM 从"会说"到"会做"的分水岭：模型负责"决定调什么、传什么参",程序负责"执行",这层分工既扩展了能力又守住了安全边界。
> - **该用它**：需要实时/私有数据、精确计算、真实动作，或要构建 Agent 时。
> - **不该用**：纯文本任务、调用路径确定的场景——别为了用而用。
> - **用它必须做**：参数校验、权限与副作用确认、报错回灌纠正、最大轮数限制。
> 心智模型：把模型当成一个"会填调用单但不能自己动手"的决策者，程序是执行与审核的闸门。
