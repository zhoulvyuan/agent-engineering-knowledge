## 一句话定义

> Prompt Engineering 是通过有意识地设计输入（指令、角色、示例、约束、格式）来引导 LLM 产出想要结果的方法——用自然语言"编程"一个概率模型的行为。

## 解决的问题

> LLM 能力很强但默认行为不可控：同一个问题换个问法，答案的质量、格式、角度可能天差地别；模型还会跑题、过于啰嗦、拒答或瞎编。
> 在没有系统性提示方法之前，用户只能靠运气反复试。Prompt Engineering 把"怎么问"变成一套可复用的技巧，让模型的输出在质量、稳定性和可控性上大幅提升，而且**不需要改模型、不需要训练**。

### 指令设计的基本原则

- **具体明确**：说清任务、对象、范围、输出要求，别留模糊空间（"写摘要" → "用 3 个要点、每点不超过 20 字总结以下文章"）。
- **给上下文**：提供背景、受众、目的，模型才能对准语境。
- **拆解复杂任务**：分步骤或分字段，比一次性要求一大坨更稳（引导 chain-of-thought）。
- **正向指令优先**：说"该做什么"比一堆"不要做什么"更有效。
- **约束前置、关键信息放首尾**：规避 lost in the middle。
- **可迭代**：prompt 要像代码一样测试、固定、版本化，而不是一次写死。

### 角色与约束如何影响输出

- **角色（role/persona）**：用 system prompt 设定身份（"你是资深财务顾问"），会改变用词、专业度、视角和默认假设，相当于把模型拉到某个"语域"。
- **约束（constraints）**：对长度、语气、格式、禁区、必须包含项的限定，能大幅收窄输出空间、提升一致性。
- 二者作用机制相同：都是在 context 里加信息，提高"符合预期的续写"的概率。但注意——角色和约束是**软引导**，不是硬保证，模型仍可能违背（尤其与指令冲突或任务太难时）。

### Few-shot 什么时候有效、什么时候无效

- **有效**：
  - 任务靠文字描述讲不清，但**给例子一看就懂**（特定输出格式、风格、标注规范）。
  - 需要稳定一致的输出模式（分类标签、抽取字段）。
  - 示例能覆盖边界情况、消除歧义。
- **无效/反效果**：
  - 任务本身简单，zero-shot 已够好，加示例只是浪费 token。
  - 示例质量差、不一致、有偏（模型会模仿错误模式和偏置）。
  - 需要真正推理/计算的任务——例子给的是"答案样子",不是"推理能力",此时 chain-of-thought 比堆例子更有用。
  - 示例太长挤占窗口、稀释注意力。
- 经验：先 zero-shot，不行再加 1~3 个高质量、与真实分布一致的示例。

### 输出格式控制的手段与可靠性

按可靠性从低到高：
1. **自然语言要求**（"请用 JSON 返回"）——最简单但最不可靠，模型可能加解释、markdown 包裹、字段漂移。
2. **给格式示例 / 模板**（few-shot 或填空模板）——明显更稳。
3. **明确 schema 描述 + 要求只输出该结构**——进一步收窄。
4. **API 的结构化输出 / JSON mode / function calling**——由解码层约束，**可靠性最高**（见 [Structured Output](02-Structured-Output.md)）。
- 原则：对程序要消费的输出，不要只靠措辞，优先用平台提供的结构化能力，并始终在代码侧做校验与容错。

## 核心内容

- **提示的构成**：指令 + 上下文/背景 + 输入数据 + 输出格式要求（+ 可选示例/角色）。
- **System vs User**：system 设定全局角色与规则（权重更高、更持久），user 给具体任务。
- **关键技巧**：zero-shot / few-shot、chain-of-thought（让模型分步思考）、角色扮演、分隔符分区（用 ``` 或 XML 标签隔开指令与数据，防注入与混淆）、输出模板。
- **迭代工程化**：prompt 应被测试、固定、版本管理，配评测集衡量改动效果。
- **软约束本质**：所有提示都是提高"期望输出"的概率，不是硬保证，关键环节要代码兜底。
- **安全**：警惕 prompt injection——把不可信数据和指令分区，不让数据里的"指令"被当真。

## 典型工程场景

> - 内容生成/改写/摘要/翻译的质量与风格控制。
> - 分类、抽取、打标等任务用提示直接完成（零/少样本）。
> - 固定输出格式供下游程序消费。
> - 设定客服/助手角色与行为边界。
> - 作为 Agent / RAG 系统 prompt 的编写基础。

## 适用边界

**适合使用**

- 调整模型行为、风格、格式而无需训练时
- 任务可用语言或少量示例讲清
- 快速试验、迭代、低成本优化

**不适合使用**

- 需要模型掌握其权重里根本没有的知识/技能（应 RAG 或微调）
- 需要 100% 硬保证的格式/事实（提示是软约束，需结构化输出+代码校验）
- 极长、极复杂的系统级上下文组织（上升为 Context Engineering）

## 常见误区

- 以为提示写得越长越详细越好——冗余会稀释注意力、涨成本。
- 把一堆"不要…"堆上去——正向指令更有效。
- 认为角色/约束是硬保证——它们只是提高概率，仍可能被违背。
- 不做分隔符分区，导致指令被输入数据污染（prompt injection）。
- 只凭感觉改 prompt、不建评测集——无法判断改动是真变好还是碰运气。

## 我的结论

> Prompt Engineering 是"用自然语言给概率模型下指令"的手艺：零成本、起效快，是用好 LLM 的第一道也是最常用的杠杆。
> - **该用它**：想调行为、风格、格式，任务能讲清或能给例子时——永远先试提示。
> - **它的天花板**：提示只能**调用**模型已有能力、是软约束；缺知识要 RAG/微调，要硬保证要结构化输出 + 代码校验。
> 工程心态：把 prompt 当代码——分区、模板化、版本化、配评测集迭代，而不是写一句碰运气。
