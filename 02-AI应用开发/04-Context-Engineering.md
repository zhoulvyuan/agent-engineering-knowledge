## 一句话定义

> Context Engineering 是把"模型每次推理看到的全部输入"当作一个需要系统设计的工程对象，去决定在有限的上下文窗口里放哪些指令、工具、知识、历史和状态，以及如何组织、压缩和更新它们。

## 解决的问题

> 当应用从单轮 prompt 升级为多轮、带工具、带检索、长时运行的 Agent，输入不再是一句话，而是由 system 指令 + 工具定义 + 检索知识 + 对话历史 + 中间状态拼成的一大堆信息，而窗口有限、每个 token 有成本、还会 lost in the middle。
> 只调"怎么写一句话"（Prompt Engineering）已经不够，必须在**系统层面**管理整个上下文的组装、取舍、压缩与流转。Context Engineering 就是为了解决"在有限窗口里让模型每一步都恰好看到该看的信息"这个新问题。

### Context 为什么成为新的工程对象

因为模型此刻的全部认知边界就是这串 context，而现代应用往里塞的东西爆炸式增长：系统指令、几十个工具定义、RAG 检索片段、多轮历史、工具返回、任务状态……它们共抢有限窗口预算，还彼此干扰（无关内容稀释注意力、重要信息被挤到中段被忽略、历史越堆越贵）。于是"往 context 里放什么、怎么放、何时清"成了决定准确率、成本、能否完成长任务的关键变量——它从"写提示的技巧"升格为需要架构设计的**工程对象**。

### 如何组织指令、工具、知识、历史和状态

核心是"每一步只放当前真正需要的，且摆在对的位置":
- **指令（system）**：稳定、精炼的角色与规则，放最前；避免冗长堆砌。
- **工具（tools）**：只挂当前阶段相关的工具；工具多时做分组/检索，避免定义本身撑爆 context。
- **知识（RAG）**：按需检索、只注入 top-k 相关片段，带来源；不要把整个知识库塞进去。
- **历史（history）**：滚动窗口 + 摘要，保留近期原文、远期压成摘要；无关轮次剔除。
- **状态（state）**：把任务进度、中间结论、待办等结构化地显式维护（有时外部化为 memory/文件），需要时再取回。
- **布局**：重要信息放首尾规避 lost in the middle；用分隔符/标签分区，隔离不可信数据防注入。

### Context 与 Prompt Engineering 的关系

二者是**包含与升级**关系，不是对立：
- Prompt Engineering 关注"**怎么把一段话/一个指令写好**"——措辞、角色、示例、格式，粒度是单个提示。
- Context Engineering 关注"**整个输入系统怎么组装**"——指令、工具、知识、历史、状态的选择、顺序、压缩与动态更新，粒度是整次推理乃至整个会话生命周期。
- 一句话：会写 prompt 是 CE 的子技能；CE 是在系统/架构层把包括 prompt 在内的所有上下文成分统一管理起来。单轮小任务 PE 够用，多轮带工具的 Agent 必须上 CE。

### Context 与 Agent 的关系

Context Engineering 几乎是 Agent 的"中枢神经":
- Agent 的每一步决策都只基于当前 context，所以"这一步给它看什么"直接决定行为质量。
- Agent 天然产生大量上下文（多轮工具调用、长历史、检索结果），不管理必然撑爆窗口、涨成本、迷失。
- 规划、记忆、工具选择、子任务隔离（如子 agent 各自独立 context）本质都是上下文管理问题。
- 业界共识：Agent 可靠性的瓶颈，很大程度上是上下文工程做得好不好，而非模型本身。

### 上下文压缩（compact / summarize）的时机与代价

- **时机**：
  - 接近窗口上限 / 达到 token 预算阈值时。
  - 一个阶段/子任务完成、细节不再需要时（把过程压成结论）。
  - 历史中出现大量低价值内容（冗长工具输出、重复对话）时。
- **代价/风险**：
  - **信息丢失**：摘要会丢掉后续可能需要的细节，造成"忘事"或前后不一致。
  - **额外成本/延迟**：压缩本身要再调一次模型。
  - **误差累积**：对摘要再摘要会逐步失真。
- **权衡做法**：分层保留（近期原文 + 远期摘要）、关键事实/决定单独结构化保存（外部 memory）而非只靠摘要、对不可逆信息谨慎压缩、必要时保留原文引用可回溯。

## 核心内容

- **定义域**：context = 指令 + 工具 + 知识 + 历史 + 状态，全部以 token 计、共享窗口。
- **四类操作（可记为 Write/Select/Compress/Isolate）**：写入与外部化（memory/文件）、按需选择注入（检索相关项）、压缩（摘要/裁剪）、隔离（子 agent / 分区）。
- **核心约束**：窗口有限、token 有成本、lost in the middle、注意力稀释、注入风险。
- **与 PE/Tool/SO 的关系**：CE 在系统层统一编排 prompt、工具定义、结构化结果和检索知识。
- **工程化**：把上下文组装做成可配置、可观测、可评测的模块，而不是散落在各处的字符串拼接。
- **安全**：不可信外部内容（检索/工具结果）要分区标注，防止其中的"指令"劫持模型。

## 典型工程场景

> - Agent 多轮任务的历史管理与状态维护。
> - RAG 系统的检索片段选择与注入布局。
> - 多工具应用的工具挂载与按需裁剪。
> - 长对话的滚动摘要与 compact。
> - 多智能体的上下文隔离与信息传递。

## 适用边界

**适合使用**

- 多轮、带工具、带检索、长时运行的 Agent/应用
- 上下文成分复杂、窗口紧张、成本敏感时
- 需要可控、可观测、可评测地管理输入时

**不适合使用**

- 单轮、输入简单的任务（PE 足矣，CE 是过度工程）
- 上下文内容固定不变、无需动态组织时

## 常见误区

- 把 CE 等同于写 prompt——它是系统层的上下文编排，范围大得多。
- 以为窗口大就不用管理——大窗口仍有 lost in the middle、成本和稀释问题。
- 无脑把所有历史/知识塞进去——信息越多不等于越准。
- 压缩不留痕——摘要丢了关键细节导致"失忆"和前后矛盾。
- 不隔离不可信内容——检索/工具结果里的指令劫持模型（注入）。

## 我的结论

> Context Engineering 是 Agent 时代的核心工程能力：模型此刻只认 context，所以"每一步让它恰好看到该看的"比"选哪个模型"往往更决定成败。
> - **该用它**：一旦进入多轮、带工具、带检索、长任务，就必须把上下文当系统对象来设计（选什么、排哪里、何时压、怎么隔离）。
> - **不该过度**：单轮简单任务用好 Prompt Engineering 即可。
> - **关键纪律**：按需注入而非全塞、重要信息置首尾、分层压缩且关键事实外部结构化保存、不可信内容分区防注入、整个组装过程可评测可观测。
> 心智模型：PE 是打磨一句话，CE 是经营模型"工作台上每一刻的信息布局"。
