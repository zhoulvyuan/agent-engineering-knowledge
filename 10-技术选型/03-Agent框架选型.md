# Agent 框架选型

> **上级**：[10-技术选型](README.md) ｜ **依赖**：技术选型方法论、Agent 核心

## 一句话定义

Agent 框架是把"LLM 推理 + 工具调用 + 状态管理 + 多轮循环控制"这套重复工程封装成可复用抽象的开发库，不同框架在"控制权交给开发者还是交给框架"这条轴上定位不同：LangGraph 把 Agent 显式建模为状态图（节点+边+共享状态），追求可控与可观测；OpenAI Agents SDK 以"Agent + Handoffs + Guardrails"为核心，轻量、贴近 OpenAI 生态、强调少概念快上手；Claude Agent SDK（原 Claude Code SDK）面向长时自主任务，内置文件系统/命令执行/子 Agent 与上下文压缩等"操作环境"能力；AutoGen 则以"多个可对话 Agent 之间消息编排"为第一公民，强调对话式多智能体协作。

## 解决的问题

在框架出现之前，开发者要用 LLM 做一个能"自己决定下一步、调用工具、维护记忆、循环直到完成"的 Agent，必须手写一整套胶水代码，典型麻烦包括：

- **循环与终止**：手写 while 循环，自己判断"该继续调工具还是该收尾"，边界条件极易写错导致死循环或过早停止。
- **工具调用协议**：手动拼 function-calling 的 JSON schema、解析模型返回的 tool_call、再把结果塞回对话，样板代码多且易出错。
- **状态与记忆**：对话历史、中间结果、变量在多轮之间如何传递与裁剪，缺乏统一抽象，上下文窗口一超限就崩。
- **多 Agent 协作**：多个角色（规划者/执行者/审查者）之间如何传递任务、如何路由、如何避免互相覆盖状态，全靠自己设计协议。
- **可观测与调试**：Agent 的每一步决策是黑盒，出错难以复现与定位，缺乏 trace / 回放 / 断点能力。
- **可靠性**：重试、超时、人工介入（human-in-the-loop）、断点续跑（持久化）这些生产需求都要重复造轮子。

### 主流 Agent 框架定位差异

四者并非同类竞品，而是在不同抽象层级上解决不同侧重的问题：

| 框架 | 核心抽象 | 定位 | 擅长 | 代价/弱点 |
|---|---|---|---|---|
| **LangGraph** | 状态图（StateGraph：节点、边、共享 State） | 低层、可控的编排引擎 | 复杂分支/循环/条件路由、持久化检查点、human-in-the-loop、可观测 | 概念偏多，上手曲线陡，样板较重 |
| **OpenAI Agents SDK** | Agent + Handoffs + Guardrails + Sessions | 轻量、少概念、生产可用 | 快速搭多 Agent 交接、内置护栏与追踪、贴近 OpenAI 生态 | 概念精简换来灵活性下降，复杂定制需绕路 |
| **Claude Agent SDK** | 自主 Agent + 工具/子Agent + 上下文管理 | 面向长时、自主"干活"的 Agent | 文件读写、命令执行、代码任务、自动上下文压缩、子 Agent | 偏重 Anthropic 模型与特定运行环境 |
| **AutoGen** | 可对话 Agent（ConversableAgent）之间消息编排 | 对话式多智能体协作研究/工程框架 | 多 Agent 群聊、角色分工、代码执行、人类参与 | 对话编排范式对"确定性流程"不够直接 |

一句话区分：**LangGraph 像工作流引擎**（你画图、它跑图）；**OpenAI Agents SDK 像轻量运行时**（少量概念拼出多 Agent）；**Claude Agent SDK 像自主工人**（给目标和环境，它自己干）；**AutoGen 像多人会议**（Agent 之间对话协商）。注意各框架版本演进很快，具体 API 名称以官方最新文档为准（见"待解决问题"）。

### 选型要看哪些维度

建议按以下维度打分，而不是看"谁更火"：

- **控制粒度**：你需要显式控制每一步分支/循环（选 LangGraph 这类图引擎），还是接受框架托管主循环只配置少量规则（OpenAI Agents SDK / Claude Agent SDK）。流程越确定、合规要求越高，越要可控。
- **状态与持久化**：是否需要跨会话记忆、断点续跑（checkpoint）、回放。长任务和需要"暂停等人工审批再继续"的场景，持久化是硬指标。
- **多 Agent 能力**：是单 Agent 够用，还是要多角色协作；若多 Agent，看它是"交接式"（handoff，一次只有一个主导）还是"对话式"（群聊协商），以及路由/终止是否可控。
- **工具与生态集成**：现成工具/连接器（检索、数据库、MCP、向量库）丰富度，与你的模型供应商、可观测平台（如 tracing）、部署栈的契合度。
- **可观测与调试**：是否有 trace、step 回放、可视化，这直接决定生产排障成本。
- **可靠性机制**：重试、超时、护栏（输入/输出校验）、human-in-the-loop 是否内置。
- **模型中立性**：是否绑定单一供应商；跨模型/本地模型需求下，中立框架更稳。
- **上手与团队成本**：概念数量、文档质量、社区活跃度、团队既有技术栈。

实践建议：先定"需求向量"（控制度、是否多 Agent、是否长任务、是否要人工介入），再把候选框架往上套，往往会发现只有一两个真正匹配。

### 什么时候不该用框架（自己写循环）

框架是抽象，抽象有成本。以下情况直接手写"调模型→解析 tool_call→执行→回灌"的循环更划算：

- **流程简单且固定**：只有"问一次模型、调一两个工具、给结果"的线性逻辑，框架的概念负担大于收益。
- **极致可控/可审计需求**：金融、合规场景要求对每个 token、每次调用完全掌控，自写循环最透明。
- **性能/依赖敏感**：想要最小依赖、最低延迟、最小二进制体积（如边缘/嵌入式/Serverless 冷启动敏感）。
- **学习与原型**：想真正理解 Agent 原理，手写一遍 ReAct/工具循环比直接套框架收获大。
- **框架能力不匹配**：你的编排范式与框架的核心抽象冲突，硬套反而要和框架"对抗"。

判断口诀：**当"框架帮你省的样板"少于"你为理解和绕过框架付出的成本"时，就自己写。** 现代模型的原生 function-calling 已经让手写循环比两年前简单很多。

### 框架锁定风险如何规避

- **隔离边界**：把框架调用封装在自己的接口层（Port/Adapter）后面，业务代码不直接依赖框架类型，换框架时只改适配层。
- **模型层解耦**：工具定义、提示词、评测集这些核心资产用框架无关的格式维护（如独立的 schema / prompt 文件），不要让它们只能被某框架读取。
- **拥抱开放标准**：优先选支持开放协议的框架，如工具侧的 **MCP（Model Context Protocol）**、可观测侧的 **OpenTelemetry**，标准化的部分天然可移植。
- **状态可导出**：确认 checkpoint/记忆能导出为通用格式（JSON 等），避免状态被锁死在私有存储里。
- **控制依赖面积**：只用框架的核心能力，少用深度耦合的"魔法"特性；边角功能自己实现。
- **保留退路评估**：选型时就想清楚"如果要迁移，成本在哪"，并写进决策记录（ADR），而不是上线后才发现搬不动。

## 核心内容

**Agent 的本质循环**（所有框架都在包装它）：

```
目标/输入 → LLM 推理（决定下一步）
          → 若需要工具：产出 tool_call → 执行工具 → 结果回灌上下文
          → 回到 LLM 推理 … 循环
          → 满足终止条件（任务完成/达到步数上限/护栏触发）→ 输出
```

**框架在这个循环上加的四层能力**：

1. **编排层（Orchestration）**：决定"下一步走哪个节点/哪个 Agent"。
   - 图式（LangGraph）：显式 node + edge + 条件边，流程即数据。
   - 交接式（OpenAI Agents SDK handoff）：一个 Agent 把控制权移交给另一个。
   - 对话式（AutoGen）：Agent 之间收发消息，由群聊管理器路由。
   - 自主式（Claude Agent SDK）：框架托管主循环，Agent 自行决定调用工具/子 Agent。

2. **状态层（State / Memory）**：共享状态对象、对话历史裁剪、长期记忆、持久化 checkpoint，支撑断点续跑与跨会话记忆。

3. **工具层（Tools）**：统一的工具注册与调用协议，自动生成 schema、解析调用、处理并行工具调用；越来越多框架支持 MCP 以复用生态工具。

4. **治理层（Guardrails / Observability / HITL）**：输入输出校验与护栏、人工介入断点、trace 与回放、重试与超时。

**选型决策流程（简化）**：

```
需要多 Agent 吗? ──否──> 流程复杂/要分支循环吗? ──否──> 自己写循环
      │是                        │是
      ▼                          ▼
对话协商(AutoGen)             图引擎(LangGraph)
或交接(OpenAI SDK)         或自主长任务(Claude Agent SDK)
```

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
|---|---|---|
| 上游 | Agent 核心 / ReAct 范式 / Function Calling | 框架是对"推理-行动循环 + 工具调用"这套底层原理的工程封装；不懂原理会误用框架 |
| 下游 | RAG 工程 / 多 Agent 系统 / Agent 可观测与评测 / 生产部署 | 框架选定后，检索增强、多角色编排、trace 评测、上线运维都在其上展开 |
| 易混淆 | Agent 框架 vs LLM 应用框架（如 LangChain）vs 工作流引擎（如 Temporal/Airflow） | LangChain 偏"组件链/集成库"，Agent 框架偏"自主循环与编排"；传统工作流引擎编排确定性任务、无 LLM 推理决策，三者解决的问题层级不同 |

## 典型工程场景

- **编码/运维自动化 Agent**：读写代码库、跑测试、执行命令完成任务——Claude Agent SDK 这类自主框架或 LangGraph 带持久化的方案适配。
- **客服/业务工单处理**：按意图把对话交接给不同专长 Agent（退款、技术支持、升级人工）——OpenAI Agents SDK 的 handoff + guardrail 很直接。
- **复杂审批/合规流程**：多步分支、条件路由、中途需人工审批再继续——LangGraph 的条件边 + checkpoint + human-in-the-loop。
- **研究型多智能体协作**：规划者/执行者/批评者多角色群聊迭代——AutoGen 的对话式编排。
- **数据分析/报告生成管线**：检索→分析→生成→校验的多阶段流水，需要可观测与重试——图引擎或自主框架 + tracing。
- **带护栏的面向用户助手**：对输入输出做安全/格式校验，防止越权与注入——各框架的 guardrail/校验层。

## 适用边界

**适合使用（选框架）**：

- 需要多步循环、条件分支、多 Agent 协作等非线性复杂编排。
- 长时任务，需要持久化、断点续跑、跨会话记忆。
- 生产系统需要内置的 trace、重试、超时、护栏、人工介入。
- 团队要在统一抽象上协作，降低重复造轮子与维护成本。
- 需要快速复用生态里的工具/连接器（含 MCP）。

**不适合使用（自己写）**：

- 流程简单固定、一两次工具调用即可完成。
- 对延迟、依赖体积、冷启动极度敏感的环境。
- 需要对每一步绝对可控、可审计（强合规）。
- 原型验证或学习目的，想完全掌握底层。
- 现有框架范式与你的编排需求冲突，硬套得不偿失。

## 常见误区

- **"选了框架就不用懂原理"**：框架只是封装，底层仍是 ReAct 循环 + function-calling，不懂原理会在调试和边界场景翻车。
- **"框架越全能越好"**：功能多意味着概念多、耦合深、锁定重；应按需求选最契合的，而非最大的。
- **"LangChain = Agent 框架"**：LangChain 偏组件/集成库，LangGraph 才是其图式编排层；不同层级，别混为一谈。
- **"多 Agent 一定比单 Agent 强"**：多 Agent 带来协调开销、状态冲突、成本上升，很多问题单 Agent + 好工具就够。
- **"框架能替代评测与可观测"**：框架提供 trace 能力，但评测集、回归测试、线上监控仍需自己建设。
- **"换框架很容易"**：若业务代码直接深耦框架 API，迁移成本极高；锁定风险要在选型时就隔离。
- **"框架版本稳定"**：这类框架 API 演进快，照搬旧教程常踩坑，务必对齐官方当前文档。

## 我的结论

**该用框架**：当需求落在"复杂编排（分支/循环/多 Agent）+ 长任务持久化 + 生产级可观测与护栏"中的任意两项以上时，框架省下的工程量远超其抽象成本——此时按"控制粒度/状态/多Agent/生态"四维选型，流程确定且要强控选 LangGraph，轻量交接式多 Agent 选 OpenAI Agents SDK，自主长时干活选 Claude Agent SDK，对话协商式研究选 AutoGen。

**不该用框架**：当逻辑是"调一两次模型 + 少量工具 + 线性输出"，或对可控性/延迟/依赖面极度敏感，或处于学习/原型阶段时，手写循环更透明、更轻、更快。

**无论选哪条路**：都要把框架隔离在适配层后、核心资产（工具 schema、prompt、评测集）保持框架无关、优先拥抱 MCP/OpenTelemetry 等开放标准，以把锁定风险压到最低。选型结论应写进 ADR 并定期随框架演进复审。
