# 模型选型与路由

> **上级**：[10-技术选型](README.md) ｜ **依赖**：技术选型方法论、LLM

## 一句话定义

模型选型与路由，是在「能力—成本—延迟」三角约束下，为每一类任务（甚至每一次请求）挑选最合适的模型，并通过一套可观测、可切换的分流机制把流量导向该模型的工程决策方法。它既是静态的选型（我这条业务线用哪个模型），也是动态的路由（这一次请求交给谁处理）。

## 解决的问题

在它出现之前，团队往往"一个大模型打天下"：所有请求无论难易都丢给同一个最强（也最贵、最慢）的模型。这带来三类麻烦：

- **成本失控**：简单的分类、抽取、改写任务也在烧顶配模型的 token，调用量一上来账单指数级增长。
- **延迟不达标**：实时交互场景（补全、客服首响）被大模型的高首 token 延迟拖垮，用户体验差。
- **选型拍脑袋**：换模型靠"听说某某榜单第一"或"换个新发布的试试"，缺乏针对自己任务的离线评测与灰度验证，升级经常是负优化而不自知。
- **锁定风险**：代码里硬编码了某家 API 的调用方式与 prompt，想切换供应商或降级兜底时牵一发而动全身。

模型选型与路由把"该用哪个模型"从一次性的架构拍板，变成一套可度量、可灰度、可回滚的持续工程实践。

### 能力/成本/延迟三角如何权衡

核心认知：这三者通常是相互制约的，很难同时拿满，工程上要做的是"按业务 SLA 定锚点，然后在剩余两维里优化"。

- **先定硬约束**：哪一维是不可妥协的红线？实时补全类通常锁死延迟（如首 token < 300ms），批量离线分析类通常锁死成本，高风险决策类（医疗、风控）通常锁死能力/准确率。先确定锚点，其余两维才有腾挪空间。
- **用"够用的最小能力"而非"最强能力"**：能力过剩就是在为成本和延迟付冤枉钱。应基于离线评测确定"能稳定通过验收的最低档模型"，而不是默认用旗舰。
- **延迟不只看模型大小**：输出长度、是否流式、是否多轮 Agent、是否带检索/工具调用，往往比模型参数量更影响端到端延迟。缩短输出、启用流式、减少 Agent 轮次常常比换小模型收益更大。
- **成本要算总账**：单价低但需要重试/多轮/长上下文的方案，总成本未必低。应以"每个成功任务的平均成本"而非"每百万 token 单价"来比较。

| 维度 | 典型指标 | 优化手段 | 代价 |
|------|---------|---------|------|
| 能力 | 任务准确率、通过率、人工评分 | 换更强模型、微调、更好 prompt/RAG | 成本↑、延迟↑ |
| 成本 | 每成功任务成本、每百万 token 价 | 换小模型、缓存、蒸馏、路由分流 | 能力可能↓ |
| 延迟 | 首 token 延迟、端到端 P95 | 流式、缩短输出、小模型、本地部署 | 能力可能↓ |

### 何时用小模型、何时大模型、何时微调而非改 Prompt

判断链条建议按"先榨干便宜手段，再上贵手段"的顺序：**Prompt/few-shot → RAG → 路由到合适档位 → 微调 → 换更强基座**。

- **用小模型**：任务定义清晰、输出格式固定、容错较高（分类、意图识别、实体抽取、改写、摘要、简单 SQL）。小模型配合好的 prompt 和少量示例往往够用，且延迟与成本优势显著。
- **用大模型**：需要复杂推理、长链条规划、跨领域知识、处理模糊/开放问题，或作为 Agent 的"大脑"做决策与工具编排。也适合作为"难例兜底"的上层。
- **优先改 Prompt（而非微调）**：问题表现为"模型其实会，但没按要求做"——格式错乱、漏掉约束、风格不符、few-shot 没给够。改 prompt、补示例、加结构化输出约束成本最低、迭代最快。
- **该上微调**：满足以下几条时微调才划算——① 有稳定、量大、同质的任务；② prompt 已优化到瓶颈仍差一截；③ 需要固化特定风格/格式/领域术语；④ 想用小模型达到大模型效果以降本降延迟（蒸馏思路）；⑤ 有足够高质量标注数据（通常数百到数千条起）。微调的代价是数据工程、训练与版本维护成本，且基座升级后可能要重做。

一句话经验：**能力不足找基座/微调，听话不足找 prompt，知识不足找 RAG，别把三者混为一谈。**

### 模型路由（按任务分流）如何设计

路由的本质是"在调用前判断这次请求的难度/类型，分发给成本最优且能胜任的模型"。常见几种策略，可组合：

- **静态规则路由**：按业务线、任务类型、租户等级、输入特征（长度、语言、是否含代码）用规则表直接分流。最简单、可解释、好兜底，是绝大多数系统的基础。
- **分类器路由**：用一个轻量模型/分类器先判断难度或类别，再决定走小模型还是大模型。适合难度分布明显的场景。
- **级联/升级路由（cascade）**：先用便宜模型跑，带置信度或自检；不达标再升级到更强模型。能显著降本，代价是难例延迟变高、需要可靠的"质量判断"信号。
- **模型即路由（LLM-as-router）**：用一个 LLM 判断分发，灵活但增加一跳延迟与成本，适合类目复杂、规则难穷举的场景。

工程落地要点：

- **抽象统一网关层**：所有调用走统一接口（如 OpenAI 兼容协议 + 适配器），业务代码不感知底层是哪家模型，便于切换与灰度。
- **必须有兜底与降级**：主模型超时/限流/报错时自动降级到备用模型或缓存答案，保证可用性。
- **全链路可观测**：按模型维度采集延迟、成本、成功率、路由命中分布，才能持续调优路由表。
- **灰度与回滚**：路由变更按比例灰度，带 A/B 对比指标，可一键回滚。

### 如何评测与持续选型（避免只看榜单）

公开榜单（如综合 benchmark、竞技场排名）只能作为"候选集初筛"，绝不能作为上线依据——榜单任务分布、评测方式与你的真实业务几乎必然不一致，还存在数据污染、过拟合榜单的风险。正确做法：

- **建自己的离线评测集**：从真实流量采样 + 人工构造难例，覆盖主流程、边界与"坑例"。规模从几十条起步也比空谈好，持续扩充。
- **定义任务相关的指标**：分类看准确率/F1，生成看人工评分或 LLM-as-judge，抽取看字段准确率，Agent 看任务完成率/步数/成本。避免只看困惑度之类与业务脱节的指标。
- **离线—灰度—在线三级验证**：离线评测过关 → 小流量灰度看真实指标 → 全量。每一级都带回滚通道。
- **成本/延迟与质量一起评**：选型报告应是"质量×成本×延迟"的综合对比表，而非单看哪个分高。
- **持续回归**：模型供应商会悄悄更新版本、prompt 技巧会迭代、业务数据会漂移。把评测集固化为 CI/定期回归，每次候选模型或 prompt 变更都跑一遍，防止"升级即劣化"。
- **锁定模型版本**：生产优先使用带明确版本号的模型快照，避免"同名模型行为悄悄变化"导致不可复现。

## 核心内容

模型选型与路由可以拆成"选型（离线、慢决策）"与"路由（在线、快决策）"两层，二者由同一套评测与可观测体系贯通。

选型流程（离线、周期性）：

1. **明确任务与 SLA**：任务类型、质量红线、延迟预算、成本预算、合规/部署约束（能否出境、能否本地化）。
2. **圈定候选集**：结合榜单初筛 + 供应商/开源可得性 + 许可证与数据合规，列出 3~6 个候选。
3. **离线评测**：用自建评测集跑质量×成本×延迟三维对比，输出选型矩阵。
4. **灰度验证**：对 Top 候选做小流量 A/B，看真实业务指标。
5. **固化决策**：锁定版本、写入路由表、建立回归评测，纳入定期复盘。

路由机制（在线、每请求）：

```
请求 → 网关/统一接口
        │
        ├─ 预处理：抽取特征（任务类型、长度、语言、租户、难度打分）
        │
        ├─ 路由决策：规则表 / 分类器 / 级联策略
        │        ├─ 简单任务 → 小模型 / 本地模型
        │        ├─ 复杂任务 → 大模型 / 旗舰
        │        └─ 难例升级 → cascade 到更强模型
        │
        ├─ 调用：带超时、重试、限流、缓存
        │
        ├─ 兜底：失败/超时 → 降级模型 or 缓存 or 规则回复
        │
        └─ 观测：记录模型、延迟、token、成本、成功与否 → 反哺选型
```

关键结构要素：

- **统一抽象层**：屏蔽多供应商差异，支持热切换与多活。
- **路由策略层**：规则 / 分类器 / 级联，可配置、可灰度。
- **可靠性层**：超时、重试、限流、熔断、降级兜底、幂等与缓存。
- **评测与观测层**：离线评测集 + 在线指标采集，形成"选型—路由—反馈"闭环。

## 典型工程场景

- **智能客服/助手**：意图识别、FAQ 匹配走小模型，复杂多轮或需推理的问题升级到大模型，兜底转人工。
- **代码补全/辅助编程**：实时补全锁延迟用小/快模型；"解释代码、生成测试、重构"等重任务路由到强模型。
- **文档处理流水线**：抽取、分类、摘要用便宜模型批量跑，审校或复杂推理环节单独路由。
- **多租户 SaaS 平台**：按套餐分流——免费版走小模型，企业版走旗舰，统一网关计费与限流。
- **成本敏感的大规模调用**：级联路由先便宜后升级，加语义缓存命中复用，整体降本显著。
- **多供应商容灾**：主模型限流/故障时自动切备用供应商，保障 SLA。

## 适用边界

适合使用：

- 请求难度/类型分布明显不均，存在大量"简单请求"可下沉到便宜模型。
- 调用量大、成本或延迟是显性约束，优化空间可观。
- 需要多供应商容灾、合规多活或平滑迁移/升级能力。
- 有能力建设离线评测与在线观测，能让路由决策基于数据而非直觉。

不适合使用：

- 调用量很小、成本可忽略，路由带来的工程复杂度得不偿失——直接用一个够用的模型即可。
- 任务高度同质、难度单一，没有分流收益。
- 质量红线极高且难例无法可靠识别（分类器/置信度不靠谱），盲目级联反而引入错误。
- 团队尚无评测与观测基建，上来就做复杂动态路由，容易变成不可解释、不可回滚的黑盒。

## 常见误区

- **只看榜单选型**：榜单任务与你的业务无关，还可能被数据污染/过拟合；不建自评测就上线是最常见的坑。
- **一刀切用旗舰模型**：以为"最强=最优"，忽视成本与延迟，简单任务也在烧顶配。
- **把"不听话"当"能力不足"**：格式/约束问题该改 prompt，却误去微调甚至换基座，南辕北辙。
- **路由只做分发不做兜底**：没有降级与熔断，一旦主模型限流/故障就整体不可用。
- **忽略端到端延迟来源**：盲目换小模型，却没发现延迟主要来自超长输出或多轮 Agent。
- **不锁模型版本**：依赖同名模型，供应商静默更新后行为漂移，线上问题难复现。
- **级联无质量信号**：缺乏可靠的置信度/自检却做 cascade，低质结果被当"通过"放行。

## 我的结论

当业务存在明显的难易分层、调用量大、成本或延迟是硬约束，且团队具备离线评测与在线观测能力时，就应该做模型选型与路由：用"够用的最小模型"承接大流量、强模型兜底难例，配合统一网关、灰度和降级，能在不牺牲质量红线的前提下显著降本提速。

反之，当调用量小、任务同质、成本无压力，或缺乏评测与观测基建时，不该过早引入动态路由——先用一个经离线评测验证"够用"的固定模型，把评测集和统一调用层建起来，等规模和痛点真正出现再演进到路由。核心原则始终是：**先用数据定锚点和候选，再让便宜手段（prompt/RAG/小模型）跑在前面，贵手段（微调/旗舰）兜在后面，任何变更都要可灰度、可回滚。**
