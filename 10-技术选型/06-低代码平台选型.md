# 低代码平台选型

> **状态**：🟢 已理解 ｜ **深度**：C 理解概念 ｜ **更新**：2026-09-15
> **上级**：[10-技术选型](README.md) ｜ **依赖**：技术选型方法论

## 一句话定义

低代码平台选型，是在"用可视化编排/配置快速搭建 AI 应用或自动化流程"与"用代码从零构建"之间做权衡，并在 Dify（LLM 应用编排）、Coze（对话式 Bot/Agent 搭建）、n8n（通用工作流自动化）等代表性平台中，按业务形态、集成需求、可维护性与数据主权匹配出最合适工具的决策过程。

## 解决的问题

在低代码/编排平台出现之前，想做一个"调用大模型 + 检索知识库 + 调外部 API"的应用，团队往往要从零写胶水代码：手动管理 Prompt、拼装 RAG 流程、处理会话状态、对接各家模型 SDK、搭建前端对话界面，还要自己做日志、重试、限流。小改动（换模型、调 Prompt、加一个工具）都要改代码、重新发版，迭代慢、门槛高，产品/运营无法参与。自动化场景同样痛苦：把若干 SaaS 工具（邮件、表格、CRM、消息）串起来，过去要么买重型 iPaaS，要么自己写定时脚本并长期维护。低代码平台把这些重复的"连接、编排、托管"工作沉淀为可视化节点与模板，让非工程角色也能参与、让工程师省掉样板代码。

### Dify/Coze/n8n 各自定位

三者常被放在一起比较，但重心不同：

| 平台 | 核心定位 | 典型产物 | 部署与开源 | 擅长 | 短板 |
|---|---|---|---|---|---|
| **Dify** | 面向开发者的 LLM 应用开发/编排平台（LLMOps） | Chatbot、Agent、工作流、以 API 对外暴露的 AI 后端 | 开源，可自托管（Docker/K8s），也有云版 | RAG 知识库、Prompt 管理、工作流编排、模型可切换、可观测 | 偏 AI 后端，自带前端较朴素；复杂业务逻辑仍需外接代码 |
| **Coze（扣子）** | 面向大众/运营的对话式 Bot 与 Agent 搭建平台 | 聊天机器人、插件化 Agent，可发布到各类社交/IM 渠道 | 以托管 SaaS 为主（国内 coze.cn / 海外 coze.com），开源程度有限 | 上手快、插件生态、多渠道发布、对话体验好 | 自托管/数据主权弱，深度定制与导出受限 |
| **n8n** | 通用工作流自动化（iPaaS 替代），非 AI 专属 | 跨系统的自动化流程、定时/事件触发的集成 | 开源（source-available 许可），强调自托管 | 数百个集成节点、分支/循环/错误处理、可写 Function 节点、也支持 AI 节点 | 不是专门的 LLM 应用框架，RAG/对话体验要自己拼 |

一句话区分：**Dify 做"AI 应用后端"，Coze 做"对话式 Bot/Agent 产品"，n8n 做"系统与系统之间的自动化管道"**。实践中常组合使用，例如 n8n 触发并编排流程、在流程中调用 Dify 暴露的 AI 能力。

### 低代码适合/不适合的场景

适合：需求相对标准、变化快、需要非工程角色参与、以"编排现成能力（模型、API、SaaS）"为主的场景——如内部知识问答、客服 Bot、运营自动化、原型/PoC 快速验证、营销与数据搬运。此时低代码能把交付周期从周级压到天级。

不适合：核心竞争力在于复杂业务逻辑、强性能/高并发、精细的状态与事务控制、严格合规审计、需要深度定制 UI/交互或与大型既有系统深度耦合的场景。平台的抽象在这些地方会变成"卡点"：想做的事超出节点能力，被迫用大量变通（workaround）堆叠，反而比写代码更脆弱、更难维护。

判断口径：**先问"这件事的难点是编排还是逻辑"**。难点在编排/集成——低代码有优势；难点在算法、性能、强一致性、复杂领域建模——该直接写代码。

### 低代码的天花板与何时该转码

天花板主要体现在：复杂控制流（深层循环、复杂条件、并发/事务）表达笨拙；调试与可测试性弱（难做单元测试、难断点、难做 code review 与 diff）；版本管理与协作差（可视化配置不是干净的文本 diff）；性能与成本不透明；超出平台抽象的需求只能靠外接脚本节点或自定义插件打补丁。

应考虑转码（或改为"代码为主、低代码为辅"）的信号：

- 流程里"代码/脚本节点"越来越多，可视化图已经看不懂；
- 频繁遇到"平台做不到，只能绕"的变通，稳定性下降；
- 需要严格的自动化测试、CI/CD、灰度与回滚；
- 性能/成本需要精细优化，或要控制每一次模型调用；
- 多人协作需要真正的代码评审与分支管理。

务实做法是分层：**用低代码快速验证与承载变化快的编排层，把稳定的核心逻辑下沉为代码/服务**，二者通过 API 衔接，而不是非此即彼。

### 数据与锁定风险

数据风险：托管型平台（尤其 SaaS）意味着对话记录、知识库文档、API 密钥等敏感数据流经第三方，需关注数据存储位置、合规（如个人信息保护、跨境）、以及是否被用于模型训练。知识库/向量数据的归属与可导出性尤为关键。

供应商锁定（vendor lock-in）：可视化编排的"资产"是平台私有格式，迁移成本高；平台特有的插件、节点、Prompt 模板难以直接搬到别处；一旦平台调价、改许可或停服，业务被动。

降低风险的做法：优先选可自托管/开源的方案（Dify、n8n）以掌握数据与部署；把 Prompt、知识源、关键逻辑尽量以可导出的形式（文本/代码/标准向量库）保存在自己仓库；在平台与业务之间加一层自有 API 适配，隔离耦合；评估导出/迁移路径作为选型硬指标。Coze 这类强托管平台在便捷性上领先，但在数据主权与可迁移性上要格外审慎评估。

## 核心内容

低代码/编排平台的通用机制可拆成几层：

1. **触发层**：定时、Webhook/事件、对话消息或 API 调用进入流程。
2. **编排层（核心）**：以可视化节点组成有向图（DAG 或带分支/循环的流程），节点类型包括 LLM 调用、知识检索（RAG）、工具/HTTP、条件分支、变量与代码片段节点。
3. **能力层**：模型接入（多厂商可切换）、知识库与向量检索、插件/工具生态、外部 SaaS 连接器。
4. **运行与托管层**：会话状态、队列/重试、限流、密钥管理、日志与可观测（trace、token 消耗）。
5. **对外暴露层**：发布为 Web 应用、嵌入组件、API/SDK，或推送到 IM/社交渠道。

选型时的关键对比维度：

| 维度 | 关注点 |
|---|---|
| 产物形态 | 要 AI 后端 API、对话 Bot，还是跨系统自动化 |
| 部署与数据主权 | 能否自托管、数据在哪、是否开源 |
| 集成广度 | 内置连接器/插件数量与质量 |
| 可维护性 | 版本管理、测试、协作、可观测 |
| 扩展性 | 自定义代码节点/插件能力、逃生出口 |
| 成本模型 | 按调用/席位/算力计费是否透明可控 |
| 生态与社区 | 模板、文档、活跃度 |

## 典型工程场景

- 企业内部知识问答/文档助手：用 Dify 自托管，接内部文档做 RAG，以 API 嵌入办公系统。
- 面向 C 端/社群的客服或陪伴 Bot：用 Coze 快速搭建并一键发布到多个 IM 渠道。
- 运营与增长自动化：用 n8n 把表单、CRM、邮件、消息串成事件驱动流程，自动分发线索。
- 新想法 PoC：产品侧用低代码两三天跑通 Demo，验证后再决定是否投入工程化重写。
- 混合架构：n8n 做调度与系统集成，流程中调用 Dify 暴露的 AI 服务，稳定逻辑用自研微服务承载。

## 适用边界

**适合使用：**
- 以编排/集成现成能力为主、业务逻辑不复杂的场景；
- 需求变化快、需要快速迭代或做原型验证；
- 希望非工程角色（产品、运营）也能参与搭建与调整；
- 可接受（或已自托管解决）数据与锁定方面的权衡。

**不适合使用：**
- 核心价值在复杂算法、强性能/高并发、强一致性与事务；
- 需要严格测试、CI/CD、灰度回滚与规范化代码协作；
- 深度定制 UI/交互或与大型既有系统深度耦合；
- 合规/数据主权要求极高且平台无法满足自托管或导出。

## 常见误区

- 把"低代码"等同于"无需技术"：复杂流程、调试、集成仍需工程思维，运营独立搞定复杂应用往往不现实。
- 认为低代码永远更快：简单场景确实快，但一旦逼近平台天花板，变通成本会反超写代码。
- 忽视可维护性：能跑起来不等于能长期演进；可视化配置的版本管理、测试、评审通常是弱项。
- 把三者当同类替换：Dify、Coze、n8n 定位不同，常是互补组合而非二选一。
- 低估锁定与数据风险：上线前不评估导出/迁移路径与数据合规，后期更换成本极高。
- 以为"开源=无约束"：n8n 等采用的是 source-available 许可，商用需确认许可条款。

## 我的结论

当难点在"编排与集成"、需求多变、要让非工程角色参与、且能通过自托管控制数据时，优先用低代码：AI 应用后端选 Dify（可自托管、RAG 与 LLMOps 完整），对话式 Bot 产品且追求上手速度选 Coze（接受其托管与锁定代价），跨系统自动化选 n8n。当难点在复杂业务逻辑、性能、强一致性、严格测试与合规，或已频繁触到平台天花板、脚本节点泛滥时，就该转码或改为"代码为主、低代码为辅"的分层架构。最稳妥的默认姿势：用低代码承载变化快的编排层做快速验证，把稳定核心沉淀为代码服务，二者以自有 API 解耦，从而兼得速度与可控性。
