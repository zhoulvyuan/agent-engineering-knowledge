# 向量库选型

> **状态**：🟢 已理解 ｜ **深度**：B 能够应用 ｜ **更新**：2026-09-15
> **上级**：[10-技术选型](README.md) ｜ **依赖**：技术选型方法论、Vector Database

## 一句话定义

向量库选型是在给定数据规模、延迟预算、过滤需求、运维能力和既有技术栈的约束下，从 pgvector（PostgreSQL 扩展）、Milvus（分布式专用向量库）、Qdrant（Rust 写的单体/集群向量库）、Chroma（嵌入式轻量库）等候选中，选出"近似最近邻（ANN）检索能力与工程成本最匹配"的那一个的决策过程。

## 解决的问题

在 RAG、语义检索、推荐、去重等场景中，核心操作是"给一个查询向量，在百万到十亿级别的高维向量中找出最相似的 top-k"。传统关系库/倒排索引做不了高效的向量相似度检索，暴力全量计算余弦距离在规模上线后延迟不可接受。向量库出现前，工程师要么自己基于 FAISS/HNSWlib 手写索引、自己管分片与持久化、自己缝合元数据过滤，要么忍受全表扫描。向量库把 ANN 索引（HNSW、IVF、PQ 等）、持久化、元数据过滤、增量更新、横向扩展打包成一个可运维的服务，降低了"把语义检索上生产"的门槛。

### pgvector/Milvus/Qdrant/Chroma 的定位与取舍

四者并非同一层级的替代品，定位差异很大：

| 产品 | 形态 | 典型规模甜区 | 索引 | 过滤 | 运维成本 | 适合人群 |
|------|------|------------|------|------|---------|---------|
| pgvector | PostgreSQL 扩展 | 几万~千万级 | IVFFlat / HNSW | 原生 SQL + WHERE，强 | 极低（复用现有 PG） | 已有 PG、数据量中等、要事务/联表 |
| Chroma | 嵌入式/轻量服务 | 几千~百万级 | HNSW（底层 hnswlib） | 元数据过滤，够用 | 极低（pip 装即用） | 原型、本地开发、单机 RAG demo |
| Qdrant | 独立服务（可集群） | 百万~亿级 | HNSW | 强，payload 过滤 + 可过滤 HNSW | 中（单体易，集群需运维） | 生产级、重过滤、要性能可控 |
| Milvus | 分布式系统 | 千万~百亿级 | IVF/HNSW/DiskANN 等多种 | 支持，表达力中等 | 高（多组件，需 K8s/etcd/对象存储） | 超大规模、多租户、专职团队 |

取舍主线：Chroma 面向"快速起步"，pgvector 面向"少引入新组件"，Qdrant 面向"中大规模生产且过滤复杂"，Milvus 面向"海量数据 + 专职平台团队"。规模越大、团队越专，越往 Qdrant/Milvus 走；栈越想简单、数据越可控，越往 pgvector/Chroma 走。

### 选型维度（规模/延迟/运维/已有栈/过滤能力）

关键评估维度，按工程优先级排列：

- **数据规模与增长**：当前向量条数、维度、预计 12 个月增长。千万级以内，pgvector/Qdrant 单机都能撑；上亿且持续增长要考虑 Milvus 这类分布式。
- **延迟与召回**：ANN 本质是用召回率换速度。要明确 p99 延迟预算和可接受召回（如 recall@10 ≥ 0.95），这直接决定索引参数（HNSW 的 M/ef、IVF 的 nlist/nprobe）。
- **运维能力**：是否有专职团队、是否已有 K8s？Milvus 组件多（proxy、querynode、etcd、对象存储），运维重；pgvector 几乎零新增运维。
- **已有技术栈**：已经重度使用 PostgreSQL，pgvector 能复用备份、监控、权限、事务，边际成本最低。
- **过滤能力**：是否需要"先按元数据过滤再向量检索"（如按租户、时间、权限）。pgvector 用 SQL 最自然；Qdrant 的可过滤 HNSW 在高过滤比下性能较好；朴素实现里"先过滤后 ANN"或"先 ANN 后过滤"都可能导致召回塌陷，需重点验证。
- **其它**：是否要混合检索（向量 + 全文/BM25）、是否多租户隔离、是否要 GPU 加速、license 与成本。

实践上建议用真实数据集 + 真实查询分布做基准测试（benchmark），而不是看厂商宣传数字。

### 什么时候不需要专门向量库（pgvector 够用）

当满足以下大部分条件时，直接用 pgvector（或 Chroma）即可，没必要引入独立向量库：

- 向量总量在百万到千万级以内，增长可预期；
- 已经在用 PostgreSQL，希望减少新组件、复用现有运维/备份/事务；
- 检索需要和结构化字段联表、强过滤、强一致（如电商、SaaS 多租户的权限过滤）；
- 延迟要求不是极端（几十毫秒级可接受），QPS 中等；
- 团队小、不想维护分布式系统。

反过来，当向量上亿、QPS 很高、需要水平扩展与多副本、或需要 GPU/DiskANN 这类高级索引时，pgvector 的单机瓶颈和索引构建开销会凸显，此时才值得上 Qdrant/Milvus。一个常被忽视的点：pgvector 的 HNSW 索引构建和内存占用在大数据量下不可小觑，上线前要实测建索引时间与内存。

### 迁移与锁定风险

向量库的锁定风险相对可控，但仍有成本：

- **数据层**：向量本身是裸浮点数组，可移植；真正的迁移成本在元数据模型、过滤表达式、以及索引需要重建（不同库索引格式不兼容，HNSW 要重新构建）。
- **API 层**：各家 SDK/查询语法不同，若业务代码直接耦合厂商 SDK，迁移要改调用层。缓解办法是在应用内加一层薄抽象（repository/接口），把"插入、检索、过滤"抽象成统一接口。
- **特性锁定**：用了某家独有能力（如 Milvus 的多种索引、Qdrant 的 payload 过滤细节、某云厂商的 serverless 向量服务）后迁移更难。
- **嵌入模型锁定**：比向量库锁定更隐蔽——一旦更换 embedding 模型，所有历史向量都要重新计算并重建索引，这是比换库更大的工程成本，选型时要一并评估。

建议：早期优先选可移植性好、门槛低的方案（pgvector/Qdrant），用抽象层隔离，把"换 embedding 模型"当作一等公民来设计数据管线。

## 核心内容

向量库的关键机制围绕"近似最近邻（ANN）检索"展开：

- **索引类型**：
  - **HNSW（分层可导航小世界图）**：基于图的索引，查询快、召回高，但内存占用大、构建较慢。pgvector、Qdrant、Chroma 默认都用它。关键参数 M（每节点连接数）、ef_construction（建索引质量）、ef_search（查询时搜索宽度，越大越准越慢）。
  - **IVF（倒排文件 + 聚类）**：把向量按聚类分桶，查询时只搜若干近桶（nprobe 个）。内存省、建索引快，召回靠 nprobe 调。常与 PQ（乘积量化）结合压缩内存。
  - **DiskANN**：面向磁盘的大规模索引，用 SSD 存图，内存放不下的超大数据集用它。
- **距离度量**：余弦相似度、内积、欧氏距离（L2）。要和 embedding 模型训练时的度量一致，否则召回异常。向量常需归一化。
- **检索流程**：`查询文本 → embedding 模型 → 查询向量 → ANN 索引召回 top-k 候选 → 元数据过滤 → （可选）重排 rerank → 返回`。
- **过滤与 ANN 的交互**：这是生产难点。"后过滤"（先 ANN 再过滤）可能过滤后不足 k 个；"前过滤"（先缩小集合再搜）在高基数下退化为暴力。Qdrant 的可过滤 HNSW、pgvector 的 SQL 规划器在不同过滤选择率下表现不同，需实测。
- **一致性与更新**：向量数据常需增量插入/删除。关注索引是否支持在线更新、删除是软删还是重建、以及写入后多久可查（可见性延迟）。
- **混合检索**：很多场景需要向量检索 + 关键词（BM25）融合（如 RRF 倒数排名融合），选型时看是否原生支持。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
|------|--------|------|
| 上游 | Embedding / 向量表示 | 向量库存的是 embedding 模型的输出，模型选择、维度、度量方式决定了库里存什么、怎么比，是向量库的前置依赖 |
| 下游 | RAG 检索增强生成 | 向量库是 RAG 中"检索"环节的核心存储与检索引擎，top-k 召回质量直接决定 LLM 生成的事实准确性 |
| 易混淆 | 全文检索引擎（Elasticsearch/OpenSearch） | 全文检索基于倒排索引做关键词匹配，向量库基于 ANN 做语义相似；二者常互补（混合检索），但解决的匹配问题不同，不是替代关系 |

## 典型工程场景

- **RAG 知识库问答**：把文档切块后 embedding 入库，用户提问时检索相关片段喂给 LLM，是当前最主流用途。
- **语义搜索**：电商/文档/代码搜索中补充关键词检索，理解同义与语义意图。
- **推荐与相似物品召回**：基于 item embedding 做"相似商品/相似内容"召回。
- **去重与聚类**：对海量文本/图片做近重复检测、异常检测。
- **多模态检索**：图文跨模态检索（CLIP 类 embedding），以图搜图、以文搜图。
- **Agent 的长期记忆**：把对话/事件 embedding 存入向量库，作为 Agent 的可检索记忆。

## 适用边界

**适合使用（引入专门向量库或 pgvector）**：

- 需要在中大规模向量上做低延迟 top-k 语义检索；
- RAG、语义搜索、推荐召回等以"相似度"为核心的检索；
- 需要向量检索与元数据过滤、混合检索结合；
- 数据持续增量更新、要求可运维可观测的生产服务。

**不适合使用**：

- 向量量极小（几千条以内）且查询不频繁——内存里直接用 numpy/FAISS 暴力算更简单，不必上库；
- 需求本质是精确关键词匹配、结构化查询或聚合统计——该用全文检索或关系库；
- 把向量库当通用数据库用（存大量非检索字段、复杂事务）——向量库不擅长 OLTP/OLAP；
- 对结果要求 100% 精确最近邻且规模大——ANN 是近似的，极端精确需求要重新审视。

## 常见误区

- **"向量库越大牌越好"**：盲目上 Milvus 这类分布式系统，结果运维成本远超收益，小团队被组件拖垮。规模没到就是过度工程。
- **忽视召回率只看延迟**：ANN 用召回换速度，参数没调好时召回可能很低而不自知，RAG 效果差却怪 LLM。要建立召回评测。
- **过滤会"免费"**：以为加个 WHERE 条件不影响性能，实际前/后过滤都可能让召回或延迟塌陷，必须按真实过滤选择率压测。
- **度量不匹配**：embedding 用余弦训练，库里却配成 L2，或忘记归一化，导致结果莫名其妙。
- **低估建索引成本**：pgvector/HNSW 在千万级建索引耗时久、吃内存，上线前不实测，上线时卡死。
- **把换 embedding 模型想得太轻**：换模型意味着全量重算 + 重建索引，比换向量库代价更大。
- **只测厂商 demo 数据**：用厂商基准数字做决策，不用自己的数据分布验证，上线后表现差异巨大。

## 我的结论

默认从简：**已有 PostgreSQL 且向量量在千万级以内、需要强过滤/联表/事务时，首选 pgvector**，复用现有栈、运维成本最低；纯本地原型或单机 demo 用 Chroma 起步最快。**当向量规模进入千万~亿级、QPS 高、过滤复杂、需要独立扩展和可控性能时，选 Qdrant**——性能好、运维相对友好、可移植性佳，是生产级"甜点"。**只有在数据上亿、持续高速增长、有专职平台团队和 K8s 基础设施时，才上 Milvus**。无论选哪个，都要用真实数据和查询分布做基准测试、建立召回评测、用应用内抽象层隔离厂商 API，并把 embedding 模型变更当作最大的迁移风险来提前规划。不该用的情况：向量量极小、需求本质是关键词/结构化查询、或当成通用数据库用时，不要引入向量库。

## 待解决问题

- [ ] 在"高过滤选择率 + 高召回"同时要求下，pgvector、Qdrant、Milvus 的可过滤 ANN 实现各自的性能拐点在哪里，缺乏自己数据集上的权威对比？
- [ ] 混合检索（向量 + BM25）的融合策略（RRF、加权、学习式 rerank）在不同业务上的收益差异如何量化？
