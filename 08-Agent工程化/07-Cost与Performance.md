# Cost & Performance / 成本与性能

> **上级**：[08-Agent工程化](README.md) ｜ **依赖**：Observability

## 一句话定义

> Cost & Performance 是对 Agent/LLM 应用在"花多少钱（Token、调用费、GPU 占用）"和"跑多快（延迟、吞吐）"两个维度做量化、分解、优化和权衡的工程实践。

## 解决的问题

> 在没有系统化成本与性能工程之前，LLM 应用常出现几类麻烦：
> - 账单失控：一次 Agent 多轮推理、长上下文反复重传，Token 消耗呈指数增长，上线后成本远超预估却无法定位是哪一步烧钱。
> - 延迟不可控：用户等待几十秒才出结果，但团队说不清时间花在首 Token（TTFT）、生成（TPOT）还是工具调用上。
> - 盲目选型：要么全程用最贵最大的模型导致浪费，要么全用小模型导致质量不达标，缺乏按场景分工的依据。
> - 吞吐与延迟打架：为了压低单请求延迟牺牲并发，或为了拉高吞吐让单请求排队变慢，没有量化权衡的手段。

### Token 成本如何估算与控制

估算的基本公式：`单次成本 = 输入 Token 数 × 输入单价 + 输出 Token 数 × 输出单价`，Agent 场景还要乘以"轮次数"和"重试率"。

- 先用 tokenizer（如 tiktoken）离线测算典型请求的输入/输出 Token 分布，再乘以调用方的单价得到单位成本，最后乘以 QPS × 时长推出月度账单。
- 关键认知：Agent 多轮对话里，历史消息每轮都会重新作为输入上传，成本随轮数近似线性甚至二次增长，长上下文（System Prompt + 工具定义 + RAG 片段）往往是主要开销。
- 控制手段：裁剪/压缩上下文（摘要化历史、只保留相关 RAG 片段）、限制 `max_tokens` 输出上限、减少不必要的工具定义注入、用更便宜的模型兜底、对重复前缀启用 Prompt Caching。
- 工程上应把 Token 用量作为一级可观测指标（见下游 Observability），按请求/会话/用户维度打点，设预算告警。

### 模型路由（大小模型分工）的收益

模型路由指根据任务难度把请求分发到不同规格的模型，让简单任务走便宜小模型、难任务走昂贵大模型。

- 收益来源：真实流量中大量请求是简单的（分类、抽取、格式化、闲聊），用小模型即可满足；只有少数复杂推理需要旗舰模型。按难度分流通常能把总成本降低数倍，同时平均延迟下降。
- 常见策略：规则路由（按意图/长度/关键词）、分类器路由（小模型先判难度）、级联/升级（先小模型尝试，置信度低或校验失败再升级到大模型）。
- 代价与风险：路由判断本身有成本和延迟；错误路由会把难题丢给小模型导致质量下降，需要用离线评测集校准路由阈值，并监控各路径的质量指标。
- 收益可量化为"质量不显著下降前提下的单位成本降幅"，应与基线（全部走大模型）做 A/B 对比。

### Prompt Caching 的效果

Prompt Caching 把请求中稳定不变的前缀（System Prompt、工具定义、少样本示例、长文档）在服务端缓存其 KV 状态，命中后无需重新计算。

| 维度 | 效果 |
| --- | --- |
| 成本 | 命中的缓存部分通常按远低于常规输入的价格计费（各家折扣不同，常见为输入价的一小部分） |
| 延迟 | 跳过前缀的 prefill 计算，TTFT 显著下降，长 System Prompt 场景收益最明显 |
| 适用前提 | 前缀必须逐字节一致且位于请求开头；缓存有生存期（TTL），冷启动首次仍需全量计算 |

- 最佳实践：把固定内容放在 prompt 最前面、变化内容放后面，最大化可缓存前缀长度；Agent 多轮对话、固定长 System Prompt、RAG 固定指令等场景收益高。
- 注意：具体折扣比例、TTL、是否自动命中因厂商（Anthropic、OpenAI、Google 等）而异，接入前需查当时官方文档并实测。

### 延迟的构成与优化点

端到端延迟可分解为：

- **TTFT（Time To First Token）**：排队 + prefill（处理全部输入）时间，受输入长度、是否命中缓存影响。
- **TPOT / ITL（每输出 Token 时间）**：解码阶段逐 token 生成速度，受模型大小、batch、硬件影响。
- **总生成时间 ≈ TTFT + TPOT × 输出 Token 数**，再加上网络往返和工具调用/RAG 检索等外部耗时。

优化点：缩短/缓存输入降低 TTFT；用流式输出（streaming）改善感知延迟；用更小模型或量化/投机解码（speculative decoding）提升 TPOT；并行化独立的工具调用与检索；减少 Agent 不必要的轮次；就近部署降低网络延迟。衡量时要看 P50/P95/P99 而非平均值。

### 并发与吞吐的权衡

吞吐（throughput，tokens/s 或 req/s）与单请求延迟之间存在根本张力，核心变量是 batch size。

- 增大 batch 提高 GPU 利用率和总吞吐，但单请求排队与解码变慢，延迟上升；减小 batch 降低延迟但浪费算力、吞吐下降。
- 现代推理引擎（vLLM、TGI、TensorRT-LLM）用 continuous batching / PagedAttention 在不显著牺牲延迟的前提下大幅提升吞吐，是缓解该权衡的关键技术。
- 工程决策：面向交互式用户优先保 P95 延迟（小 batch、限并发）；面向批处理/离线任务优先保吞吐（大 batch）。应基于 SLO 做压测，找到满足延迟目标下的最大吞吐点。
- 调用第三方 API 时则主要受限于速率限制（RPM/TPM），需要客户端做并发控制、队列和退避重试。

## 核心内容

- **两条主轴**：成本（Token/调用费/算力）与性能（延迟/吞吐），二者常需权衡，不能只优化一边。
- **成本构成**：输入 Token × 单价 + 输出 Token × 单价，再乘 Agent 轮次与重试；长上下文是主要成本源。
- **延迟分解**：TTFT（排队 + prefill）+ TPOT × 输出长度 + 外部调用耗时；关注分位数而非均值。
- **吞吐杠杆**：batch size 与 continuous batching，决定 GPU 利用率与并发能力。
- **核心优化杠杆**：模型路由（大小模型分工）、Prompt Caching、上下文压缩、流式输出、量化/投机解码、并行工具调用、推理引擎选型。
- **度量先行**：先用可观测性打点量化 Token、延迟、吞吐、成本，再有针对性优化；用离线评测集守住质量底线。

## 典型工程场景

- 面向 C 端的对话/编码助手：需要低 TTFT 和流式输出保证交互体验，同时控制高并发下的单位成本。
- 大规模离线批处理：文档摘要、数据清洗、批量标注，优先吞吐，用大 batch + 小模型 + 缓存压成本。
- 多轮 Agent / 工作流：轮次多、上下文长，需做上下文压缩、Prompt Caching、并行工具调用来同时控成本和延迟。
- RAG 系统：固定指令缓存、检索与生成并行、按查询难度路由模型。
- 成本治理与 FinOps：按用户/功能/租户维度核算 LLM 账单，做预算告警与计费分摊。

## 适用边界

**适合使用**

- 有一定调用量、成本或延迟已成为上线约束的生产系统。
- 流量中任务难度分布不均、存在明显可路由/可缓存结构的场景。
- 有可观测性埋点和评测集，能量化优化收益与质量影响的团队。

**不适合使用**

- 原型/PoC 阶段，调用量极小，过早优化会拖慢迭代（先把功能和质量做对）。
- 任务高度同质且已无可压缩前缀、无难度分层时，路由/缓存收益有限。
- 质量红线极高、任何降级都不可接受的场景，应谨慎用小模型路由。

## 常见误区

- 只盯单价不看总量：忽略 Agent 多轮把历史反复重传，实际账单由 Token 总量和轮次决定。
- 用平均延迟做 SLO：掩盖长尾，应看 P95/P99。
- 以为换小模型一定更便宜更快：若小模型需要更多重试、更长输出或更多轮次纠错，总成本可能反升。
- 把 Prompt Caching 当万能：前缀不一致、放错位置、超过 TTL 都会导致不命中；变化内容放前面会使缓存失效。
- 大 batch 一定更好：对交互式场景会严重拉高 P95 延迟。
- 不做质量兜底就激进降本：路由/量化带来的质量回退未被评测捕获，线上才暴露。

## 我的结论

> 当系统已进入生产、调用量和成本/延迟成为真实约束时，就该系统化做 Cost & Performance：先用可观测性量化 Token、延迟分位和吞吐，再按"模型路由 + Prompt Caching + 上下文压缩 + 流式/并行"这几个高杠杆手段逐项优化，每一步都用离线评测集守住质量。
> 不该用的时机：原型阶段或调用量极小时不要过早优化，先把功能正确性和输出质量做对；在质量零容忍的关键链路上，不要为省钱盲目下沉模型。一句话——先度量、守住质量底线、再在高杠杆点上做权衡优化，而不是凭感觉省钱或提速。
