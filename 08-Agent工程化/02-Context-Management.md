# Context Management / 上下文管理

> **状态**：🟢 已理解 ｜ **深度**：A 深入掌握 ｜ **更新**：2026-09-15
> **上级**：[08-Agent工程化](README.md) ｜ **依赖**：Context Engineering、State Management

## 一句话定义

> 上下文管理是指在 Agent 运行过程中，主动决定"把哪些信息、以什么形态、在什么时机"放进模型有限的上下文窗口，并随对话推进不断增删、压缩、重组这些信息，使模型在每一步都能拿到足够且不过载的输入。

## 解决的问题

> 在它成为显式工程问题之前，人们遇到的麻烦主要有：
>
> - **窗口是硬上限**：LLM 的上下文长度有物理上限，长对话、长文档、多轮工具调用很快把窗口撑满，再往后要么报错，要么静默截断导致关键信息丢失。
> - **"全塞进去"既贵又糟**：把所有历史、所有工具输出原样拼接，不仅 token 成本线性上涨，还会触发"中间遗忘"（lost in the middle）——模型对窗口中部的信息注意力明显下降，准确率反而下降。
> - **多轮累积污染**：失败的尝试、冗长的报错栈、重复的检索结果会不断堆积，稀释有效信号，让后续推理被噪声带偏。
> - **无状态模型的记忆缺口**：模型本身不记忆跨请求的状态，长期任务需要外部机制决定"什么该被记住、什么该被遗忘"，否则 Agent 无法完成跨越多步、多会话的任务。

### 上下文窗口耗尽时怎么办（压缩 / 摘要 / 丢弃）

实践中是三种策略分层组合，而非单选：

| 策略 | 做法 | 适用 | 代价 |
| --- | --- | --- | --- |
| 丢弃（truncation / sliding window） | 直接扔掉最旧的轮次或低优先级消息 | 远期历史与当前任务弱相关时 | 可能丢掉后续才需要的信息，不可逆 |
| 摘要（summarization） | 用一次额外的 LLM 调用把旧历史压成一段结构化摘要，替换原文 | 长对话、长期任务 | 多一次调用的延迟/成本，摘要会丢细节 |
| 压缩（compaction / externalize） | 把原始内容外移到文件/向量库/scratchpad，窗口里只留引用或指针，用时再检索回来 | 大工具输出、代码库、文档 | 需要检索基础设施，存在召回失败风险 |

工程要点：设置触发阈值（如占用达窗口 70~80% 时触发压缩），对最近 N 轮做保真保留、对更早历史做递归摘要（rolling summary），并始终保护系统提示、当前目标、关键约束不被压缩。

### 哪些信息必须保留、哪些可以丢弃

按优先级（高→低）大致分层：

- **必须保留**：系统提示/角色设定、当前任务目标与成功标准、硬约束（安全、格式、权限）、已确认的关键决策与事实、最近几轮交互、未完成的待办状态。
- **可压缩成摘要**：较早的多轮对话、已经得出结论的中间推理过程。
- **可丢弃或外移**：详细的工具原始输出（保留结论即可）、失败且已被纠正的尝试、重复检索到的相同内容、冗长的 stack trace（保留错误类型与关键行）。

判断准则：一条信息"是否影响下一步决策"。影响则留，不影响则压缩或外移；不确定时外移（可召回）优于直接丢弃（不可逆）。

### 子 Agent 的上下文隔离如何设计

核心思想是让每个子 Agent 拥有**独立、最小化**的上下文，避免主 Agent 的噪声互相污染：

- **接口化传递**：父 Agent 只把子任务所需的输入和明确的产出契约传给子 Agent，不下发完整历史。子 Agent 返回的也应是**结果/摘要**，而非它内部的全部过程。
- **窗口隔离**：每个子 Agent 用自己的上下文窗口，彼此不可见，从而实现"并行探索 + 结果汇总"而不互相挤占 token。
- **只回传精华**：子 Agent 完成后，把长推理过程压成结论回传主线程，是控制主 Agent 上下文膨胀最有效的手段之一。
- **共享态走外部**：需要跨子 Agent 共享的状态放到外部存储（文件、黑板/blackboard、数据库），而不是塞进每个人的提示里。

### 工具返回结果过大时如何处理

- **分页 / 截断 + 游标**：工具只返回前 N 条并给出继续游标，由 Agent 决定是否翻页，而不是一次性灌入全部。
- **外移 + 引用**：把完整结果写入文件或存储，窗口里只保留路径/ID 和一句话摘要，后续按需读取（符合"文件系统即上下文"的思路）。
- **先摘要再入窗**：对大段文本/日志先做一次抽取式或生成式摘要，只把与当前目标相关的片段放进上下文。
- **结构化裁剪**：对 JSON/表格只保留需要的字段；对报错只保留错误类型和关键几行。
- **约定工具输出规范**：从工具设计层面就限制默认返回体积（如默认 limit、默认只返回 schema+样例），把"是否要全量"的决定权交给 Agent。

### 如何度量上下文的实际利用率

- **占用率**：当前 token 数 / 窗口上限，是最基本的容量监控指标，用于触发压缩。
- **有效信息密度**：窗口中"真正被下一步决策引用"的内容占比，可通过标注或注意力/引用分析近似评估。
- **压缩前后的任务指标对比**：在同一评测集上比较"压缩/摘要前后"的任务成功率、答案准确率，判断压缩是否损伤了关键信息。
- **成本/延迟指标**：每轮平均 token、每任务总 token、首 token 延迟，反映上下文膨胀的经济代价。
- **位置敏感性测试**：把关键信息放在窗口不同位置做 A/B（探测 lost-in-the-middle 效应），评估布局是否合理。

> 注：业界尚无统一的"上下文利用率"标准指标，多数团队用上述代理指标组合，具体口径见「待解决问题」。

## 核心内容

- **窗口预算管理**：把上下文窗口当成有限预算，为系统提示、历史、工具输出、检索内容分别划定配额，并设触发压缩的阈值。
- **信息分层与优先级**：按"必须保留 / 可摘要 / 可外移丢弃"分层，决定每条信息的去留。
- **压缩机制**：滑动窗口截断、滚动摘要（rolling/recursive summary）、压实（compaction），通常分层叠加使用。
- **外部记忆**：用文件系统、向量库、KV 存储、scratchpad 作为"窗口外的记忆"，窗口内只保留指针与摘要，用时检索回来。
- **上下文布局**：关键信息放在头部和尾部，规避中间遗忘；用明确结构（标签/分节）帮助模型定位。
- **多 Agent 上下文隔离**：子 Agent 独立窗口 + 结果回传，控制主线程膨胀。
- **状态与记忆分离**：短期（本轮窗口）、工作记忆（任务级 scratchpad）、长期记忆（跨会话存储）各司其职。
- **可观测性**：监控 token 占用、成本、压缩触发次数与压缩前后指标，形成闭环调优。

## 典型工程场景

- **长对话客服 / 陪伴助手**：会话持续数十上百轮，需要滚动摘要 + 关键事实长期记忆，避免越聊越贵、越聊越忘。
- **编码 Agent / IDE 助手**：代码库远超窗口，必须靠"读文件→摘要→只保留相关片段"的外移检索，而不是把整个仓库塞进去。
- **深度研究 / 多步调研 Agent**：多轮检索产生海量网页文本，需要边检索边压缩、把中间结论写入 scratchpad。
- **多 Agent 编排（planner + workers）**：主 Agent 分发子任务、子 Agent 独立窗口执行并回传摘要，靠隔离控制总 token。
- **工具密集型工作流（数据分析、运维）**：数据库查询、日志、API 返回体量巨大，需分页、截断、外移处理。
- **跨会话长期任务**：如项目助理记住用户偏好、项目背景，依赖长期记忆的写入与召回策略。

## 适用边界

**适合使用**

- 任务跨越多轮交互、或处理的素材（代码库、文档、日志）远大于窗口。
- 对成本/延迟敏感，需要控制每轮 token 的生产系统。
- 多 Agent / 长期记忆场景，需要显式决定信息去留与共享。
- 工具调用频繁、返回体量大，需要约束输入规模。

**不适合使用**

- 单轮、短输入的简单问答——信息本就能完整放进窗口，额外的压缩/外移只增加复杂度与延迟。
- 对信息完整性零容忍、且素材能完整装入窗口的场景——此时任何有损压缩都是风险，应直接全量传入。
- 原型验证早期——过早引入复杂的压缩/检索基础设施会拖慢迭代；先用简单截断验证，瓶颈出现再优化。

## 常见误区

- **"窗口更大就不用管了"**：窗口变大只是推高上限，中间遗忘、成本上涨、噪声稀释依然存在；大窗口反而更需要主动管理。
- **"全塞进去让模型自己挑"**：无关信息会稀释注意力、降低准确率并增加成本，塞得越多不等于答得越好。
- **把压缩当无损**：摘要和截断都是有损操作，若不保护关键信息、不做压缩前后评测，很容易悄悄丢掉决定性细节。
- **忽视信息位置**：把关键约束埋在长历史中部，模型容易"看不见"；位置布局和内容同样重要。
- **子 Agent 回传全过程**：让子 Agent 把完整推理过程倒回主线程，等于没隔离，主 Agent 照样被撑爆。
- **只截断不外移**：直接丢弃不可逆，很多"暂时没用"的信息后面才需要；可召回的外移往往比直接丢更安全。

## 我的结论

> 上下文管理不是"等窗口报错了再处理"的补救手段，而是任何多轮、长素材、多 Agent 的生产级 Agent 都要从一开始规划的核心工程。
>
> **何时该用**：任务跨多轮、素材超窗口、对成本延迟敏感、或存在多 Agent / 长期记忆时——此时应显式设计窗口预算、分层优先级、压缩阈值与外部记忆，并把工具输出的体积控制在设计阶段就做好。
>
> **何时不该用（或先别上）**：单轮短任务、素材能完整装入窗口、或处于早期原型阶段时，应优先用最简单的"全量 + 必要时截断"，避免过早引入摘要/检索的复杂度与额外延迟。等到 token 成本、准确率下降或窗口溢出成为真实瓶颈，再按"截断 → 摘要 → 外移检索"的顺序逐级增强。核心判断是：**对每条信息问"它是否影响下一步决策"，不确定时选可召回的外移而非不可逆的丢弃。**
