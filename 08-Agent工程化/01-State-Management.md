# State Management / 状态管理

> **上级**：[08-Agent工程化](README.md) ｜ **依赖**：Agent Loop

## 一句话定义

> Agent 状态管理，是在 Agent 的一次或多次运行过程中，对"推进任务所必需的全部可变数据"（目标、历史、中间结果、工具调用轨迹、游标与控制位）进行结构化建模、持久化、恢复与裁剪的工程机制。

## 解决的问题

> 在状态管理被显式工程化之前，Agent 往往把全部运行信息都塞进一个不断追加的对话历史里，带来一系列麻烦：
>
> - 进程一旦崩溃或被中断，所有中间进展（已完成哪几步、工具返回了什么）全部丢失，只能从头重跑，既浪费 Token 又无法保证幂等。
> - 长任务的历史无限增长，很快撞上上下文窗口上限，模型开始"忘记"早期关键信息。
> - 多步任务缺乏可观测的进度，无法做人工介入（human-in-the-loop）、暂停/恢复、回滚到某一步。
> - 并发或多 Agent 协作时，没有清晰的状态边界，彼此的中间结果互相污染。

### Agent 的状态包含哪些内容

Agent 的状态通常是一个结构化对象，而不仅仅是一段对话文本。典型包含以下几类：

| 类别 | 内容 | 示例 |
| --- | --- | --- |
| 任务层 | 用户原始目标、分解出的子任务、计划/待办列表 | goal、plan、todo 列表 |
| 历史层 | 消息序列、工具调用与返回、思考轨迹 | messages、tool_calls、observations |
| 中间产物 | 已检索的文档、生成的代码片段、变量绑定 | scratchpad、artifacts、变量表 |
| 控制层 | 当前步数、循环游标、重试计数、是否等待人工 | step、cursor、retry、pending_approval |
| 环境引用 | 工作目录、文件句柄、会话 ID、外部资源指针 | session_id、cwd、resource handles |

关键区分：真正的"状态"是推进任务**必需且会变化**的数据；只读的配置、系统提示词不算状态。工程上常把状态建模为一个带 schema 的字典（如 LangGraph 的 State），用归约函数（reducer）定义每个字段如何被各节点更新。

### 状态与 Context、Memory 的区别

三者高度相关但职责不同，容易混为一谈：

- **State（状态）**：面向**单次任务执行**的、结构化的、短生命周期的运行时数据。任务结束通常即可丢弃或归档。它是"这次任务跑到哪了"。
- **Context（上下文）**：面向**模型单次推理**的、实际喂给 LLM 的那段窗口内容。它是从 State/Memory 中**投影/裁剪**出来的子集，受窗口大小约束。它是"这一步让模型看到什么"。
- **Memory（记忆）**：面向**跨任务、跨会话**的长期知识，常落在向量库/数据库，按需检索。它是"以前学到/记住的东西"。

一句话串联：Memory 和 State 是数据来源，Context 是每一步从中选取、拼装后真正送进模型的那部分。State 是运行账本，Context 是运行时视图，Memory 是长期档案。

### 状态如何持久化（checkpoint / 快照）

核心思路是把状态对象序列化后写入持久存储，并在关键节点打快照：

1. **序列化**：将 State 转为可存储格式（JSON、MessagePack、Pickle 等），注意工具句柄、文件描述符等不可序列化对象要替换为可重建的引用。
2. **Checkpointer**：在 Agent Loop 的每一步（或每个节点）后写入一次检查点，记录 `(thread_id, step, state_snapshot)`。LangGraph 的 Checkpointer、Temporal 的事件历史都是此模式。
3. **存储后端**：短期用内存/SQLite，生产用 Postgres、Redis、对象存储等；按 `thread_id`（会话/任务线程）组织，便于按线程恢复。
4. **粒度权衡**：全量快照实现简单但写放大大；增量/事件日志（append-only event log + 重放）更省空间，但恢复需要重放。
5. **版本与 schema**：状态 schema 会演进，持久化时应带版本号，避免旧快照无法反序列化。

### 断点续跑与失败恢复如何实现

依赖"持久化检查点 + 可重入的执行引擎"两件事：

- **续跑**：恢复时按 `thread_id` 读取最近一次成功的 checkpoint，重建 State，从 `cursor/step` 指向的下一步继续，而非从头开始。
- **幂等性**：工具调用要尽量幂等或带去重键（idempotency key），否则重放会产生重复副作用（重复下单、重复写文件）。对非幂等操作，记录"已执行"标记并在恢复时跳过。
- **两种恢复语义**：事件溯源（event sourcing）通过重放事件日志重建状态，确定性要求高；快照恢复直接加载状态对象，更快但可能丢失最后一次未落盘的进展。
- **失败分类**：瞬时错误（网络抖动）走重试+退避；逻辑错误走回滚到上一个检查点并可能触发人工介入；致命错误则终止并保留现场供排查。
- **人工介入**：把状态标记为 `pending_approval` 并落盘，等待外部信号后再从该点恢复，这正是 human-in-the-loop 的实现基础。

### 长任务的状态如何避免无限膨胀

膨胀主要来自历史消息和中间产物的无限累积，常用手段：

- **滑动窗口 / 截断**：只保留最近 N 轮，丢弃或归档更早的历史。
- **摘要压缩（compaction）**：周期性地把旧历史用 LLM 总结成一段摘要，替换掉原始明细；DSH 等 Harness 的"上下文压缩"即此思路。
- **外部化中间产物**：大文件、长文本、检索结果不放进状态本体，而是写到外部存储，状态里只存引用/指针，用时再加载。
- **结构化状态替代流水账**：用字段化的 State（当前计划、已完成步骤、关键结论）取代逐字追加的对话，天然限制体积。
- **分层记忆**：热数据留在 State，冷数据下沉到 Memory（向量库），按需召回。
- **定期裁剪无关字段**：子任务完成后清理其专属的 scratchpad，避免长期占用。

## 核心内容

- **状态模型**：以带 schema 的结构化对象建模，字段分为任务层/历史层/中间产物/控制层/环境引用；每个字段配归约函数定义更新语义。
- **状态机 / 图执行**：现代框架（LangGraph、状态机式编排）把 Agent 流程建模为节点+边，节点读写共享 State，边决定下一步走向，使状态流转可控、可观测。
- **持久化机制**：Checkpointer 在每步后序列化状态到后端存储，按 `thread_id` 组织，支持快照与增量两种粒度。
- **恢复机制**：续跑依赖"读取最近检查点 + 从游标继续 + 工具幂等"；区分快照恢复与事件溯源重放两种语义。
- **膨胀治理**：截断、摘要压缩、中间产物外部化、分层记忆共同控制状态体积。
- **一致性与并发**：多 Agent/并发写入需定义合并策略（reducer）、锁或乐观并发控制，避免状态竞争。
- **可观测性**：状态应可导出、可视化（当前步、历史轨迹），这是调试与审计的基础。

## 典型工程场景

- 多步编码 Agent：跨多轮读文件、改代码、跑测试，需要记录已改哪些文件、测试结果、当前待办，崩溃后可续跑。
- 长时间运行的工作流（审批流、数据处理管道）：中途需要人工审批时暂停并落盘状态，审批后恢复。
- 研究/调查型 Agent：并行发起多路检索，各子任务中间结果需要隔离存储再汇总。
- 客服/对话 Agent：跨会话维持用户任务进度（如订单处理到第几步），用户下次回来接着处理。
- 批量任务编排：一次处理成百上千条目，需按条目维护独立状态并支持部分失败重试。
- 需要审计与回溯的受监管场景：要求完整记录每一步状态变迁以备追责。

## 适用边界

**适合使用**

- 任务跨多步、单步耗时长、可能被中断，需要断点续跑的场景。
- 需要人工介入（暂停/审批/修正）后再继续的工作流。
- 长会话或长任务，上下文容易膨胀，需要显式裁剪与压缩。
- 多 Agent 协作或并发执行，需要清晰的状态边界与合并策略。
- 对可观测性、审计、可复现有要求的生产系统。

**不适合使用**

- 单轮、无状态的一次性问答，引入状态管理只会增加复杂度。
- 极低延迟、极简的工具调用，持久化开销得不偿失。
- 原型验证阶段，过早设计复杂状态 schema 会拖慢迭代。
- 任务本身天然幂等且廉价，重跑成本低于维护状态的成本时。

## 常见误区

- 把"对话历史"等同于"状态"：历史只是状态的一部分，真正的状态还包括计划、游标、控制位等结构化字段。
- 混淆 State / Context / Memory：误以为塞进模型窗口的就是全部状态，或把长期记忆和运行时状态混存。
- 以为做了持久化就能自动续跑：若工具调用不幂等、没有游标，恢复时会重复执行产生副作用。
- 全量追加永不裁剪：导致上下文爆炸和成本飙升，误以为"模型会自己忽略无关历史"。
- 忽略 schema 版本：状态结构演进后旧快照无法反序列化，升级即丢数据。
- 把不可序列化对象（文件句柄、网络连接）直接存进状态，恢复时崩溃。

## 我的结论

> 当任务是"多步、长时、可能中断、需要可恢复或可人工介入"时，就应该把状态当成一等公民来显式工程化：用结构化 schema 建模，配 Checkpointer 持久化，设计幂等的工具与清晰的恢复语义，并用摘要/外部化手段控制膨胀。
>
> 反过来，当任务是单轮、无状态、廉价且幂等时，就不该引入状态管理——它带来的序列化、存储、schema 演进成本会超过收益。判断标准很简单：**"崩溃后从头重跑的代价，是否高到值得为可恢复性付出持久化与复杂度成本？"** 答案为是，才做重状态设计；否则保持无状态、让重跑来兜底。
