# Reliability / 可靠性

> **状态**：🟢 已理解 ｜ **深度**：A 深入掌握 ｜ **更新**：2026-09-15
> **上级**：[08-Agent工程化](README.md) ｜ **依赖**：State Management、Observability

## 一句话定义

> Agent 可靠性是指在模型输出非确定、工具调用会失败、外部依赖会抖动的前提下，通过重试、超时、熔断、降级、幂等、预算与迭代上限等工程手段，让 Agent 以可预期的成功率、延迟和成本稳定完成任务（或可控地失败）的能力。

## 解决的问题

> 在没有系统性可靠性设计之前，Agent 应用普遍遇到这些麻烦：
> - LLM 输出非确定，同样输入时好时坏，偶发格式错误直接导致下游解析崩溃，难以复现和调试。
> - 工具/API 调用会超时、限流（429）、返回 5xx 或脏数据，单点失败就让整个任务中断，没有兜底。
> - Agent 陷入循环（反复调用同一工具、来回纠错）时无人止损，token 和费用无上限地飙升。
> - 任务中途失败后盲目重试，导致重复下单、重复发消息、重复写库等副作用（非幂等）。
> - 模型供应商宕机或某个模型质量下降时，没有切换/回退机制，整个服务跟着挂。
> 结果是：线上成功率低、成本不可控、故障难归因，无法达到生产级 SLA。

### 重试策略如何设计（哪些可重试）

核心原则：只重试**瞬时性、可恢复**的失败，不重试**确定性、业务性**的失败。

| 类型 | 典型错误 | 是否重试 |
| --- | --- | --- |
| 瞬时错误 | 网络超时、连接重置、429 限流、502/503/504 | 重试 |
| 服务端错误 | 500（部分幂等场景可重试） | 谨慎重试 |
| 客户端错误 | 400 参数错误、401/403 鉴权、404 | 不重试，直接失败 |
| 业务错误 | 余额不足、库存为零 | 不重试，交回决策逻辑 |

要点：

- 用**指数退避 + 抖动（jitter）**，避免大量请求同时重试引发惊群/雪崩；对 429 优先遵守 `Retry-After` 头。
- 设置**最大重试次数**（通常 2~3 次）和**总超时上限**，重试不能无限叠加延迟。
- 对 LLM 的**格式错误**是一类特殊可重试项：可带着错误信息回灌给模型让其自我纠正（self-correction），但要限次。
- 非幂等的写操作重试前必须有幂等保护（见幂等性问题），否则宁可不重试。

### 超时与熔断

- **超时（Timeout）**：每一层都要有独立超时——单个工具调用、单次 LLM 请求、整个 Agent 任务。超时值应基于 P99 延迟设定，而非平均值。LLM 流式场景可用"首 token 超时 + 整体超时"双阈值。缺少超时是 Agent 卡死、线程/连接耗尽的首要原因。
- **熔断（Circuit Breaker）**：当某个下游依赖（工具 API、模型供应商）错误率或延迟在滑动窗口内超过阈值时，熔断器打开，后续请求**快速失败**（fail-fast）而不再打到故障依赖，给其恢复时间；经过冷却期进入半开状态试探性放行少量请求，成功则闭合。熔断防止故障级联和重试风暴把下游彻底打死。
- 两者配合：超时触发失败计数，失败计数触发熔断；熔断打开时直接走降级逻辑。

### Tool Failure 的处理与降级

- **分层兜底**：工具失败 →（可重试则）重试 →（有备用则）切换备用工具/数据源 →（都不行则）降级返回。
- **降级（Fallback）策略**：返回缓存的旧结果、返回部分结果、使用更简单的默认值、或把失败信息结构化地告诉 LLM 让它换一条路径（例如换个搜索关键词或换个工具）。
- **错误信息回灌**：把工具的结构化错误（而非裸异常栈）喂回 Agent，使其能基于错误做决策，这是 Agent 相比传统系统独有的"自愈"能力，但要防止它反复撞同一堵墙（配合迭代上限）。
- **隔离**：对不稳定工具做舱壁隔离（bulkhead），用独立线程池/并发配额，避免一个慢工具拖垮整个 Agent。
- **校验**：工具返回后做 schema/数值合理性校验，脏数据按失败处理，不要污染后续推理。

### Model Failure 的处理与切换

- **供应商级故障**：主模型（如某供应商）宕机或限流时，自动**failover**到备用供应商或备用模型（如 GPT→Claude，或大模型→小模型）。通过统一网关/路由层（如 LiteLLM 一类抽象）屏蔽差异。
- **质量级故障**：输出不符合 schema、拒答、幻觉严重、置信度低时，可重试、换更强模型、或加约束（JSON mode / 结构化输出 / 更严格 prompt）。
- **成本/延迟权衡**：可做模型分级路由——简单请求走便宜小模型，失败或复杂请求升级到大模型。
- **一致性注意**：切换模型会改变输出风格和行为，降级到弱模型可能牺牲质量，需在降级与质量间明确取舍，并在可观测性里标记用了哪个模型。

### 非确定性如何影响可靠性设计

- LLM 即使 temperature=0 也不保证完全确定（浮点、并行、供应商实现差异），所以**不能假设可复现**，可靠性设计必须面向"分布"而非"单次结果"。
- 影响：不能用精确断言做测试，要用**基于规则/语义的评估 + 容忍区间**；要用**结构化输出 + 校验**把自由文本收敛成可判定的结果；要为"偶发错误"预留重试和兜底，而不是假设每次都对。
- 对关键决策引入**自洽性/多数投票（self-consistency）**、多次采样取共识，或加入确定性的验证步骤（如用代码/规则复核模型结论）。
- 可靠性指标应统计化：成功率、P50/P99 延迟、格式合规率，而非"能不能跑通"。

### 幂等性如何保证

- 核心手段是**幂等键（idempotency key）**：对每个有副作用的操作生成稳定唯一 ID（如基于任务 ID + 步骤 + 参数哈希），下游服务用它去重，重复提交返回首次结果而非再次执行。
- **去重表 / 乐观锁 / 唯一约束**：在数据库层用唯一索引挡住重复写入。
- **状态机 + 持久化**：把 Agent 执行过程落盘为可恢复的状态（checkpoint），崩溃重启后从上次成功步骤继续，而不是从头重放副作用。
- 读操作天然幂等；对不可幂等且不可去重的外部动作（如发邮件），要么前置幂等网关，要么用"先登记意图再执行"的两段式，宁可漏发也不重发或反之，取决于业务容忍度。
- 工具设计上尽量把动作设计成幂等（PUT 而非 POST 语义）。

### 如何设置最大迭代与成本上限

- **最大迭代/步数（max steps / max turns）**：硬性限制 Agent 的循环轮数（如 ≤10~25 步），到顶即停止并返回当前最佳结果或明确失败，防止死循环。
- **Token / 成本预算**：为单次任务设置 token 上限和金额上限，累计超限即熔断任务；可按用户/租户设配额。
- **墙钟时间上限**：整体任务 wall-clock 超时，防止长尾任务无限占用资源。
- **循环检测**：检测重复的 action/观察序列（如连续 N 次调用相同工具相同参数），提前判定陷入循环并中止或切换策略。
- 这些限制应作为**独立于 LLM 的外层守卫**（由编排框架强制，而非指望模型自觉），超限时走明确的失败/降级路径并记录原因。

## 核心内容

- **失败分类**：先区分瞬时 vs 永久、可重试 vs 不可重试、系统故障 vs 业务失败，这是一切策略的前提。
- **重试 + 退避 + 抖动**：针对瞬时失败的第一道防线，限次限时。
- **超时**：每层独立超时，基于 P99 设定，防卡死。
- **熔断 + 隔离（bulkhead）**：防止故障级联和重试风暴压垮下游。
- **降级 / Fallback**：工具级、模型级、结果级的多层兜底，保证"优雅失败"而非崩溃。
- **幂等 + 状态持久化（checkpoint）**：保证重试和崩溃恢复不产生重复副作用。
- **预算守卫**：最大迭代、token/成本上限、墙钟超时、循环检测，由外层编排强制。
- **结构化输出 + 校验**：把非确定的自由文本收敛为可判定结果。
- **可观测性闭环**：trace、指标、告警是可靠性的前提，没有观测就无法度量和改进可靠性。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | State Management、Observability | 可靠性依赖状态持久化/checkpoint 做崩溃恢复与幂等，依赖可观测性（trace/指标/告警）来度量成功率、延迟、成本并定位故障，没有观测就谈不上可靠 |
| 下游 | SLA/SLO 保障、Evaluation、生产部署与运维 | 可靠性工程直接支撑对外承诺的服务等级目标，并为评测体系提供"成功率/合规率"等稳定性指标，是 Agent 上生产的前置条件 |
| 易混淆 | 容错(Fault Tolerance) vs 鲁棒性(Robustness) vs 弹性(Resilience) | 容错=有故障仍可用（偏硬件/系统冗余）；鲁棒性=对异常/脏输入不崩（偏输入侧）；弹性=受冲击后能恢复（偏恢复能力）。可靠性是这些能力在"长期按预期运行"目标下的综合体现，三者是其手段而非同义词 |

## 典型工程场景

- 面向用户的生产级 Agent/Copilot，需要承诺可用性和响应延迟 SLA。
- 多工具/多 API 编排的 Agent：外部依赖多且不稳定，必须有重试、熔断、降级。
- 涉及写操作/交易的 Agent（下单、转账、发消息、工单处理）：必须幂等防重复。
- 长时间运行的自治任务（研究型 Agent、批处理 pipeline）：需要迭代/成本上限和断点续跑。
- 多租户 SaaS 平台：需要按租户的成本配额和故障隔离，防止单租户拖垮整体。
- 跨多个 LLM 供应商的网关：需要 failover 与模型路由应对供应商抖动。

## 适用边界

**适合使用**

- 生产环境、面向真实用户、有 SLA/成本约束的 Agent 系统。
- 依赖大量外部工具、API、数据库等不稳定资源的场景。
- 有副作用（写数据、花钱、发通知）的关键业务动作。
- 长周期、自治、无人值守运行的任务。

**不适合使用**

- 一次性脚本、原型验证、离线实验：过度做可靠性工程是过度设计，拖慢迭代。
- 纯只读、无副作用、人工全程盯着的交互式玩具 demo。
- 对正确性/实时性要求极高、根本不该用非确定 LLM 的硬实时控制场景——此时问题不是加可靠性补丁，而是不该用 Agent。

## 常见误区

- **把"加重试"当成可靠性全部**：不加熔断/退避的盲目重试会放大故障（重试风暴），把抖动变雪崩。
- **对非幂等操作直接重试**：导致重复下单/重复扣款等严重业务事故。
- **指望 LLM 自己控制循环和成本**：模型不会可靠地自我止损，上限必须由外层编排硬性强制。
- **缺少分层超时**：只有全局超时或根本没有超时，导致卡死和资源耗尽。
- **把业务失败当技术失败重试**：对 400/鉴权/余额不足反复重试，浪费资源还掩盖真实问题。
- **追求 LLM 输出完全确定**：temperature=0 ≠ 可复现，应面向分布设计而非单次结果。
- **降级即静默吞错**：降级要有标记、告警和可观测，而不是悄悄返回错误结果。

## 我的结论

> 可靠性不是上线前补的一个 feature，而是贯穿 Agent 架构的横切约束：只要 Agent 要面向真实用户、涉及副作用、或要承诺成本与延迟，就必须从一开始做失败分类、分层超时、带退避的限次重试、熔断隔离、多层降级、幂等保护和外层预算守卫这一整套。
> 判断是否该投入：**有 SLA、有副作用、有外部依赖、长时间无人值守** —— 命中任一就该认真做；反之，一次性脚本、只读 demo、人工全程盯着的原型则不必过度工程化，否则是用复杂度拖慢迭代。
> 一句话抓手：先把失败分类清楚（瞬时/永久、可重试/不可重试、技术/业务），再决定每类用重试、熔断、降级还是直接失败——分类错了，后面所有策略都会放大故障而不是抑制故障。
