## 一句话定义

> Agent Evaluation 是一套系统性度量方法：用可复现的数据集、指标和判定逻辑，衡量 Agent 在完成多步骤任务时的最终结果质量与中间决策过程质量，从而支撑迭代、回归和上线决策。

## 解决的问题

> 在 Agent 出现之前（或在没有评估体系时），人们面对这些麻烦：
>
> - **"看起来能用"陷阱**：单条 Demo 跑通不代表整体可靠。LLM 输出非确定性，同一输入多次运行结果可能不同，靠人工点开几个 case 根本无法覆盖真实分布。
> - **改动无法量化**：换了 prompt、换了模型、加了一个工具，到底是变好还是变差？没有基线和指标就只能靠感觉，极易"修一个 case 坏三个 case"。
> - **多步骤过程不透明**：Agent 会调用工具、循环推理，一个任务失败可能发生在规划、工具选择、参数构造、结果解析任何一环。只看最终答案无法定位问题。
> - **上线风险不可控**：没有量化的成功率、成本、延迟数据，无法判断是否满足 SLA，也无法向业务方交代。

### 如何判断 Agent 是否做得好

"做得好"必须拆成可度量的维度，不能用单一分数概括：

- **结果正确性（Outcome）**：任务是否达成了预期目标（答案正确、文件被正确修改、订单被正确创建）。这是第一位的。
- **过程合理性（Process/Trajectory）**：是否用了合理的步骤、是否调用了正确的工具、有没有多余循环或危险操作。
- **约束遵守**：是否遵守了安全边界、权限边界、输出格式、不越权删数据等。
- **效率成本**：完成任务消耗的 token、工具调用次数、端到端延迟、金钱成本。
- **稳健性**：对同一任务多次运行的结果一致性（pass^k / variance），以及对输入扰动的鲁棒性。

工程上的做法是：先定义**任务级的通过判据（success criteria）**，再在一个有代表性的数据集上批量跑，统计成功率与各维度分布，而不是看单条输出。

### Evaluation Dataset 如何构建

数据集质量决定评估可信度，构建要点：

| 要素 | 做法 |
| --- | --- |
| 来源 | 优先用**真实线上流量**采样（最贴近分布），辅以人工构造的边界/难例，必要时用 LLM 合成扩充 |
| 覆盖 | 按任务类型、难度、领域分层采样，保证覆盖长尾与失败模式，避免只测 happy path |
| 标注 | 每条样本带 **输入 + 期望结果 / 判定规则 / 参考轨迹**；判据可以是精确匹配、规则校验，或 rubric |
| 规模 | 从几十条冒烟集起步，逐步扩到几百~上千条；分成冒烟集（快）与全量集（全面） |
| 治理 | 版本化管理、防止数据泄漏进训练/few-shot、定期回填线上新发现的 bad case |

关键原则：数据集要能**区分出好坏系统**（有区分度），且判据要可自动执行、可复现。

### 自动评估与人工评估的分工

两者互补，按阶段和场景分工：

- **自动评估**：用于 CI 回归、快速迭代、大规模扫描。适合有客观判据的任务（代码能否编译/测试通过、API 返回是否匹配、是否包含必需字段）。优点是快、便宜、可复现。
- **人工评估**：用于主观质量（有用性、语气、创造性）、校准自动指标、审查高风险样本、建立"金标准"。优点是准、能发现自动指标漏掉的问题；缺点是慢、贵、有标注者间不一致。
- **LLM-as-judge**：介于两者之间，用模型模拟人工打分，覆盖主观维度的同时保持规模化，但需要用人工标注持续校准。

典型分工：**自动指标跑全量把关回归，人工抽样校准并处理 judge 存疑的样本**。

### 任务成功率之外还需要哪些指标

成功率是必要但远不充分的，还需要：

- **成本类**：平均/分位 token 消耗、工具调用次数、金钱成本。
- **延迟类**：端到端耗时、首 token 延迟、P50/P95/P99。
- **过程类**：步数、工具调用正确率、无效循环率、提前终止率。
- **稳健性**：pass@k（放宽，k 次中有一次成功）与 pass^k（收紧，k 次全部成功，衡量一致性）、方差。
- **安全/合规类**：越权操作率、有害输出率、拒答恰当性、幻觉率。
- **分维度细分**：按任务类型/难度拆分成功率，定位能力短板。

工程上常把这些指标做成仪表盘，关注的是**成功率与成本/延迟的权衡曲线**，而非单点。

### 轨迹评估（trajectory）与结果评估的区别

| 维度 | 结果评估（Outcome） | 轨迹评估（Trajectory） |
| --- | --- | --- |
| 评估对象 | 最终输出/状态是否正确 | 中间步骤序列：规划、工具调用、参数、推理 |
| 回答的问题 | "做对了吗" | "怎么做的、过程合理吗" |
| 优点 | 直接对齐业务目标、判据清晰 | 能定位失败环节、发现"蒙对"的脆弱路径 |
| 缺点 | 无法解释为什么失败、可能结果对但过程危险 | 没有唯一正确轨迹、标注与判定更难 |
| 典型方法 | 精确匹配、规则校验、单元测试 | 工具调用匹配、步骤 rubric、关键节点检查 |

实践建议：**结果为主，轨迹为辅**。结果判对错，轨迹用来诊断原因和防止"结果正确但过程不可接受"（如绕过权限、删了不该删的数据）。

### LLM-as-judge 的可靠性边界

LLM-as-judge 很实用但有明确的失效模式，必须知道边界：

- **已知偏置**：位置偏置（偏好靠前/靠后的候选）、长度偏置（偏好更长答案）、自我偏好（偏好同家族模型的输出）、措辞/格式偏置。
- **可靠的场景**：相对比较（A/B 二选一）比绝对打分更稳；有明确 rubric 和参考答案时更可靠；判据客观时更可靠。
- **不可靠的场景**：需要专业领域知识、精确事实核查、复杂数值/逻辑推理时容易误判，可能自信地判错。
- **缓解手段**：提供清晰 rubric、给参考答案、随机化候选顺序消除位置偏置、用更强模型做 judge、多次采样投票、链式思考后再打分、关键决策用人工复核。
- **底线**：judge 的分数必须用**人工标注集定期校准**（算一致性/相关性），否则它只是另一个未经验证的模型输出。

### 如何做回归测试，防止改动导致能力倒退

把评估接入工程流水线，像对待软件测试一样对待 Agent：

- **基线固定**：维护一个版本化的评估集和当前基线分数。
- **CI 门禁**：每次改动 prompt/模型/工具/代码，自动在冒烟集上跑，分数低于阈值则阻断合并。
- **分层测试**：快冒烟集（PR 级，秒~分钟）+ 全量集（合并/发版前，更全面）。
- **处理非确定性**：固定随机种子/温度、多次运行取统计量、设置容忍区间，避免因抖动误报。
- **bad case 回填**：线上发现的失败 case 固化成回归用例，确保"修过的 bug 不复发"。
- **对比报告**：输出新旧版本的逐 case diff，重点看**新增失败（regression）**而非只看总分，总分持平也可能是"好了一批坏了一批"。

## 核心内容

- **三层评估对象**：结果（outcome）、过程/轨迹（trajectory）、以及运行时特性（成本、延迟、安全）。
- **四类判定方法**：精确/规则匹配（客观、可自动）、代码执行校验（如跑测试）、LLM-as-judge（主观、规模化）、人工标注（金标准、校准用）。
- **评估数据集**：真实流量采样 + 边界难例 + 合成扩充，分层覆盖，带判据，版本化，防泄漏。
- **指标体系**：成功率、pass@k / pass^k、成本、延迟、步数/工具正确率、安全合规率，分维度细分。
- **流程闭环**：定义成功判据 → 建数据集 → 批量运行 → 聚合指标 → 定位失败 → 迭代 → CI 回归门禁 → 线上监控回填。
- **离线 vs 在线**：离线评估（固定数据集、迭代期）与在线评估（线上 A/B、真实用户反馈、监控）结合。
- **非确定性治理**：多次运行、统计分位、固定种子/温度、容忍区间。

## 典型工程场景

- **AI 编码助手/编程 Agent**：用一组真实代码任务（能否通过单元测试、能否正确修改仓库）评估成功率与回归。
- **客服/问答 Agent**：评估答案正确性、是否正确调用知识库/工单工具、是否越权、语气是否得体。
- **RAG 系统**：评估检索相关性、答案忠实度（faithfulness）、是否幻觉、引用是否正确。
- **浏览器/操作型 Agent**：评估多步操作任务完成率、步数效率、是否执行危险操作。
- **模型/Prompt 升级决策**：切换底座模型或改写 system prompt 前，用评估集量化收益与回退风险。
- **上线前门禁与线上监控**：发版前跑全量集，线上持续采样打分并回填 bad case。

## 适用边界

**适合使用**

- 任务有相对明确的成功判据，或能构造 rubric 的场景。
- 需要在迭代中量化对比不同版本（模型/prompt/工具）的收益与回退。
- 对可靠性、成本、安全有量化要求，需要上线门禁与持续监控的生产系统。
- 存在可采样的真实流量，能构建有代表性的数据集。

**不适合使用**

- 极早期原型探索阶段，需求与形态都在剧烈变动，建评估集的投入还不划算（先手动看 case）。
- 任务目标高度主观且无法形成稳定共识（纯开放创作），自动与 judge 评估都难给出可信分数时，应以人工为主并降低对自动分数的依赖。
- 样本极度稀缺或高度一次性、无法复现的任务，难以形成可复用的评估集。
- 把评估分数当成唯一真理：当分数与真实用户体验脱节时，评估体系本身需要先被重新校准。

## 常见误区

- **把 benchmark 分数当 Agent 质量**：模型在 HumanEval 高分 ≠ 你的编码 Agent 在你的仓库上好用。
- **只看最终结果不看轨迹**：结果蒙对掩盖了脆弱或危险的过程，换个 case 就崩。
- **只看平均成功率**：忽略分维度细分和方差，长尾/高风险场景被平均数掩盖。
- **盲信 LLM-as-judge**：不做人工校准、不处理位置/长度/自我偏好偏置，把 judge 分数当客观真理。
- **忽视非确定性**：只跑一次就下结论，被随机抖动误导（误报 regression 或误判改进）。
- **数据集泄漏/过拟合**：评估集进了 few-shot 或被反复针对性调优，分数虚高、失去区分度。
- **只有离线没有在线**：离线集跑得好，线上真实分布不一样，缺少监控与回填。
- **忽略成本/延迟**：只追成功率，上线才发现成本或延迟不可接受。

## 我的结论

> 一旦 Agent 要进入迭代和生产，评估不是可选项而是基础设施——它是你唯一能把"感觉变好了"变成"确实变好了"的手段。
>
> **该用**：当你需要反复改 prompt/模型/工具并判断收益、需要上线门禁防止能力倒退、或对可靠性与安全有量化要求时，必须先建哪怕只有几十条的评估集，并接入 CI。结果评估为主、轨迹评估定位问题、LLM-as-judge 规模化但要人工校准。
>
> **不该（过早）用**：在形态剧烈变动的早期原型阶段，重投入建评估集会拖慢探索，此时手动看 case 更划算；对纯主观开放任务，别迷信自动分数。
>
> 一句话判断：**只要这个 Agent 还会被继续改、且改坏了有代价，就值得为它建评估。** 评估的价值不在于得到一个漂亮的数字，而在于让每一次改动的好坏可被量化、可被回滚。
