> **上级**：[08-Agent工程化](README.md) ｜ **依赖**：Reliability、Security、Cost & Performance

## 一句话定义

> 生产架构是把一个能跑通的 Agent 原型，改造成能在真实流量下长期稳定、可观测、可控成本、可安全运维的线上系统所需的一整套工程结构与运行机制。

## 解决的问题

> 原型阶段的 Agent 往往是一段"能在我机器上跑通"的脚本：单请求、同步阻塞、无重试、无监控、Prompt 和密钥硬编码、没有并发与配额控制。一旦面对真实用户，就会暴露出一连串麻烦：LLM/工具调用超时和限流导致请求挂死；长任务拖垮同步接口、把线程池占满；一次 Prompt 或模型升级就线上行为突变却无法回滚；成本随 token 不受控地飙升；出问题后既看不到调用链也复现不了;多个租户互相争抢资源。生产架构就是为了系统性消除这些"从 demo 到线上"的落差而存在的。

### 从原型到生产的差距有哪些

核心差距可以分为几个维度，原型普遍只满足"功能跑通"，而生产要求"功能 + 非功能"同时成立：

| 维度 | 原型 | 生产 |
| --- | --- | --- |
| 可靠性 | 单次调用、无重试 | 超时/重试/退避/熔断/幂等/降级 |
| 可观测 | print 日志 | 结构化日志 + 指标 + 分布式追踪 + 回放 |
| 并发/负载 | 单请求串行 | 连接池、限流、背压、队列削峰 |
| 配置管理 | Prompt/模型硬编码 | 版本化、灰度、可回滚 |
| 安全 | 密钥明文 | 密钥托管、鉴权、输入输出过滤、工具权限边界 |
| 成本 | 不关心 | token 预算、缓存、模型分级路由 |
| 多租户 | 无隔离 | 配额、数据隔离、公平调度 |

关键认知：从原型到生产增加的工作量，绝大部分不在"智能"本身，而在上面这些非功能性需求上。

### 部署形态（同步 / 异步 / 队列）如何选择

选择依据主要是**任务时长**、**用户是否需要实时反馈**、**流量是否有尖峰**：

- **同步请求-响应**：适合单轮、秒级完成的任务（简单问答、单次工具调用）。实现简单，但长任务会占用连接、容易超时，不抗尖峰。
- **流式（SSE/WebSocket）**：仍是"在线"形态，但边生成边返回，改善长回复的首字延迟和体验，适合对话式交互。本质还是同步连接，不解决后端算力削峰问题。
- **异步任务 + 轮询/回调**：适合几十秒到数分钟的多步 Agent 任务。客户端提交后拿到 task_id，后端慢慢跑，通过轮询或 webhook 返回结果，连接不被长期占用。
- **消息队列 + Worker 池**：适合高并发、有尖峰、需要削峰填谷和重试的场景。队列解耦生产与消费，Worker 可独立扩缩容，天然支持重试、死信、优先级。

经验法则：**> 10 秒的任务不要放在同步接口里**；有突发流量或需要可靠重试，就上队列；需要实时字符级反馈才用流式。多数生产 Agent 是"流式对话 + 队列化后台任务"的混合形态。

### 灰度、回滚与版本管理

目标是让任何变更都"小步、可观测、可快速撤销"：

- **版本化一切**：Prompt、模型版本、工具 schema、Agent 配置都应有明确版本号并纳入制品管理，而不是直接改代码里的字符串。
- **灰度发布**：按百分比流量、用户分组或租户维度逐步放量（1% → 10% → 50% → 100%），期间对比新旧版本的质量指标与成本。
- **快速回滚**：回滚必须是"切配置/切路由"级别的秒级操作，而不是重新发版。因此配置与代码要解耦。
- **影子/双跑**：对关键变更，先让新版本在真实流量上"只计算不生效"，离线比对输出差异后再放量。
- **可审计**：每次变更记录谁、何时、改了什么、为什么，便于事故追溯。

### Prompt / 模型 / 工具的变更如何管理

这三者是 Agent 行为的"三个旋钮"，任何一个变动都可能让线上行为突变，因此要像管代码一样管它们：

- **Prompt**：集中存储在 Prompt 仓库/配置中心，带版本、变更评审、评测集回归。禁止散落在代码里直接改。
- **模型**：抽象出模型路由层，模型名/供应商/参数（温度、max_tokens）皆可配置；换模型前跑离线评测集，上线用灰度。注意不同模型对同一 Prompt 行为差异很大。
- **工具**：工具的入参 schema、权限、副作用需版本化；新增/变更工具要考虑向后兼容和权限边界；对有副作用（写库、付款、发消息）的工具必须幂等并加审批/限额。
- **统一机制**：三者都需要"离线评测集 + 回归测试 + 灰度 + 回滚"这条流水线来兜底，避免凭感觉上线。

### 监控告警体系如何建立

建议按"三大支柱 + Agent 特有指标"组织：

- **指标（Metrics）**：QPS、延迟分位（P50/P95/P99）、错误率、超时率、重试率、熔断次数；以及 Agent 特有的 token 消耗、每请求成本、工具调用次数/失败率、平均对话轮数。
- **日志（Logging）**：结构化日志，带 trace_id/request_id/tenant_id，记录每一步的输入输出摘要（注意脱敏）。
- **追踪（Tracing）**：分布式链路追踪贯穿"请求 → LLM 调用 → 各工具调用 → 子 Agent"，定位慢在哪、错在哪。
- **质量监控**：离线评测集定期回归 + 线上采样人工/模型评估 + 用户反馈（点赞/点踩）闭环。
- **告警**：基于错误率、延迟、成本突增、配额逼近等设阈值告警，区分 P1/P2，避免告警风暴；关键是成本和质量这两类"软故障"也要有告警，而不只是传统的宕机告警。

### 多租户与配额

目标是在共享一套服务的同时，保证租户之间**互不影响、数据隔离、成本可归属**：

- **数据隔离**：按租户隔离会话历史、向量库、知识库，防止跨租户泄露；强隔离场景可做物理/库级隔离，弱隔离用 tenant_id 行级过滤 + 严格校验。
- **配额与限流**：按租户设 QPS、并发、token/成本预算，超限则限流或排队，防止单租户耗尽资源（吵闹邻居问题）。
- **公平调度**：队列按租户加权或优先级调度，避免大租户饿死小租户。
- **成本归属**：按租户统计 token 与调用量，支持计费和成本分析。
- **配置隔离**：允许不同租户使用不同 Prompt/模型/工具集，但共享底层运行时。

## 核心内容

- **分层结构**：接入层（鉴权/限流/路由）→ 编排层（Agent 循环、规划、记忆）→ 模型与工具层（模型路由、工具执行、沙箱）→ 基础设施层（队列、存储、缓存、密钥管理、可观测）。
- **可靠性机制**：超时、重试与指数退避、熔断、降级、幂等、死信队列；对有副作用的操作尤其强调幂等与审批。
- **部署形态**：同步 / 流式 / 异步 / 队列-Worker，按任务时长与流量特征组合选择。
- **配置与发布**：Prompt/模型/工具版本化，灰度 + 回滚 + 影子双跑，配置与代码解耦。
- **可观测性**：指标 + 日志 + 追踪 + 质量评估的四位一体，并对成本与质量这类软故障告警。
- **成本控制**：token 预算、提示/结果缓存、模型分级路由（简单任务用小模型）、上下文裁剪。
- **安全与多租户**：密钥托管、工具权限边界、输入输出过滤、租户隔离与配额。

## 典型工程场景

- 面向 C 端的对话式 AI 助手：高并发、流式输出、需要成本与质量监控。
- 企业内多租户 SaaS Agent 平台：按客户隔离数据与配额、按用量计费。
- 长耗时自动化任务（代码库重构、数据批处理、报告生成）：异步 + 队列 + Worker 池。
- 客服/工单自动化：Agent 调用内部工具（下单、退款、查库存），强调幂等、审批和权限边界。
- RAG 知识问答服务：向量库多租户隔离、缓存命中优化、模型分级路由控制成本。

## 适用边界

**适合使用**

- 需要面向真实用户/业务持续提供服务，有稳定性、成本、安全要求的 Agent 系统。
- 存在并发、尖峰流量，或长耗时多步任务的场景。
- 多租户、需要配额与成本归属的平台型产品。
- 变更频繁（Prompt/模型/工具经常迭代），需要灰度与回滚保障的系统。

**不适合使用**

- 一次性探索、PoC、内部 demo，追求快速验证想法，上重型生产架构是过度工程。
- 单人、低频、离线批处理的小脚本，没有并发与多租户诉求。
- 需求和技术方案尚未稳定、还在频繁推翻重来的早期阶段，过早固化架构反而拖慢迭代。

## 常见误区

- 把"模型调通"当成"系统做完"，忽视了占大头的非功能性工作。
- 只做传统宕机/错误率告警，却不监控成本飙升和输出质量退化这两类"软故障"。
- 把长耗时 Agent 任务塞进同步接口，导致连接占满、频繁超时。
- Prompt/模型/密钥硬编码在代码里，变更要重新发版、无法快速回滚。
- 多租户只靠应用层 if 判断过滤，缺乏强隔离与配额，出现数据串租户或吵闹邻居。
- 迷信"换个更大的模型"解决问题，而不先补齐重试、缓存、评测、路由等工程手段。
- 没有离线评测集就凭感觉改 Prompt/换模型，线上行为悄悄劣化却无人察觉。

## 我的结论

> 生产架构的本质，是用成熟的分布式系统工程把 LLM 的不确定性、慢、贵、有副作用这几个特性"包起来"，让它可控、可观测、可回滚。
> **何时该用**：当 Agent 要服务真实流量、有稳定性/成本/安全/多租户诉求，或变更频繁需要灰度与回滚时——此时非功能性工程才是成败关键，必须系统性投入。
> **何时不该用**：在 PoC、内部 demo 或需求尚未稳定的探索期，优先用最简形态快速验证价值，不要被架构拖慢；等方向确定、要上真实用户时再分层补齐可靠性、可观测、成本与隔离能力。判断标准很简单：**有没有真实用户和真实后果**。
