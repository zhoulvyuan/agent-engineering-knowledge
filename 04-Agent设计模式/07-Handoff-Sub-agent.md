## 一句话定义

Handoff / Sub-agent 是一种让当前 Agent 把一段任务连同所需上下文「交棒」给另一个（通常更专精的）Agent，由后者接管、独立完成并返回结果的协作模式，核心动作是任务控制权与上下文在 Agent 之间的转移。

## 解决的问题

在它普及之前，人们通常用一个「全能大 Prompt」试图让单个 Agent 处理所有子任务：工具集庞杂、系统提示臃肿、上下文窗口被无关历史塞满，导致模型注意力分散、工具选择出错、角色串味。遇到需要不同专业能力（如先检索、再写代码、再审查）的流程时，单 Agent 要么反复切换人格、要么把所有领域知识硬塞进一个上下文，既贵又不稳定。Handoff 让每个子任务由边界清晰、提示精简、工具受限的专精 Agent 承担，用「分而治之 + 显式交接」替代「一个超大上下文硬扛」。

### Handoff 解决什么问题（任务与上下文转移）

核心是把「一个 Agent 做所有事」拆成「多个专精 Agent 各管一段，并在边界上显式交接」。它主要解决三类工程痛点：

1. **提示与工具膨胀**：单 Agent 要承载所有角色时，系统提示和工具列表无限增长，模型选工具、守角色的准确率下降。拆分后每个 Agent 只带自己需要的工具与指令。
2. **上下文污染**：无关的历史对话、中间产物会挤占窗口、干扰注意力。Handoff 时只传递下游真正需要的信息，相当于一次有目的的上下文裁剪。
3. **专业化与可维护性**：检索、编码、审查、客服分流等能力可以各自独立演进、独立评测、独立替换，而不必动一个巨型 Prompt。

交接的本质是两件东西同时转移：**控制权**（接下来由谁决策、调用工具、与用户/环境交互）和**上下文**（任务目标、约束、已有结论、必要的原始材料）。只转控制权不转上下文会「失忆」，只转上下文不转控制权就退化成普通的函数调用。

### 上下文如何在 Agent 间传递（隔离 vs 共享）

两种主流策略，工程上常混用：

| 维度 | 隔离式（Isolated / 消息摘要） | 共享式（Shared / 完整历史） |
|------|------------------------------|------------------------------|
| 传递内容 | 结构化任务说明 + 精炼摘要/必要片段 | 完整对话历史或共享内存/黑板 |
| 上下文窗口 | 小、省 token、注意力聚焦 | 大、易膨胀、可能污染 |
| 信息完整度 | 可能丢失隐含背景 | 完整但含噪声 |
| 下游独立性 | 强，像独立服务被调用 | 弱，耦合上游语境 |
| 典型实现 | 子任务 prompt、工具返回结构体、交接 payload | 共享 message 列表、全局 state、外部记忆库 |

工程取舍：**隔离式更可控、更省、更利于评测**，是默认推荐，但要求交接时主动把关键背景「写清楚」，否则下游缺信息；**共享式**适合强关联、需要完整语境推理的协作，但必须配合上下文压缩/摘要，否则很快撑爆窗口并引入干扰。常见折中是：共享一份只读的「任务目标 + 关键事实」，私有化各自的工作草稿，交接时附带结构化摘要而非整段原文。

### 与 Orchestrator-Worker 的区别

两者都属于多 Agent 协作，但控制流和权责不同：

| 维度 | Handoff（交接式） | Orchestrator-Worker（编排式） |
|------|-------------------|-------------------------------|
| 控制权 | 转移：交出去后由接棒者接管，上游可能退出 | 保留：Orchestrator 始终持有控制权 |
| 结构 | 对等/链式/路由，去中心化 | 中心化，一个协调者 + 多个被调工人 |
| 返回 | 不一定回到原 Agent（接力式推进） | Worker 结果汇总回 Orchestrator |
| 决策 | 决策权随任务流动 | 决策集中在 Orchestrator |
| 类比 | 接力赛 / 客服转接 | 项目经理派活并收活 |

一句话：Handoff 是「我把事和话筒都给你，你接着往下走」；Orchestrator-Worker 是「我派你去办这件事，办完回来向我汇报」。实践中二者可嵌套：Orchestrator 内部的某一步可以用 Handoff，Handoff 链路里的某个节点也可以是一个小型 Orchestrator。路由型 Agent（根据意图把请求 handoff 给专科 Agent）是 Handoff 的典型形态。

### 常见风险（上下文丢失、循环移交）

- **上下文丢失/失真**：隔离式交接若摘要不全或语义漂移，下游缺少关键约束，产出跑偏；这是最高频风险，需在交接 payload 里固化「目标、约束、已完成结论、禁止事项」。
- **循环移交（loop / ping-pong）**：A 交给 B，B 又交回 A，或多方互踢皮球，陷入死循环；需设最大交接深度、交接次数预算、环路检测与兜底 Agent。
- **职责边界模糊**：路由判断不准，任务被交给不胜任的 Agent，或多个 Agent 都认为「不该我管」。
- **成本与延迟放大**：每次交接都重放/重建上下文，token 和往返次数成倍增长。
- **错误传播与可观测性差**：没有统一 trace 时，跨 Agent 的失败难以定位；需要贯穿式的追踪 ID 和交接日志。
- **安全与权限扩散**：工具权限随交接传递，若不收敛会放大越权风险。

## 核心内容

**基本动作序列**

```
用户/上游 Agent
   │ 1. 识别子任务超出自身职责或需专精能力
   ▼
决定 Handoff ── 选择目标 Agent（按能力/意图路由）
   │ 2. 构造交接 payload：目标 + 约束 + 必要上下文 + 期望产出格式
   ▼
目标 Sub-agent 接管
   │ 3. 用自己的提示/工具独立执行（可再向下 handoff）
   ▼
返回：结果 + 状态
   ├─ 接力式：直接继续面向用户/下一环节
   └─ 回传式：把结果交回上游汇总
```

**关键构件**

- **交接 payload（contract）**：结构化的任务说明，至少含目标、输入材料、约束与边界、期望输出 schema。这是 Handoff 质量的决定因素。
- **路由/分诊器**：根据意图或规则选择接棒 Agent，可基于关键词、分类模型或 LLM 判断。
- **上下文策略**：隔离摘要 vs 共享历史（见上表），常配合压缩、裁剪、只读共享事实。
- **终止与护栏**：最大交接深度、循环检测、兜底/升级到人工（human handoff）。
- **可观测性**：统一 trace ID、交接日志、每跳的输入输出留痕，便于回放与评测。

**与工具调用的区别**：Handoff 把「决策与多轮自主行动」交给另一个 Agent（接棒者可自行规划、循环、调用工具）；而工具调用只是执行一个确定性函数、立即返回、控制权不转移。可把 Sub-agent 看作「会思考、能自主多步」的高级工具。

## 典型工程场景

- **客服分流**：前台 Agent 判断意图后，把退款、技术支持、投诉分别 handoff 给对应专科 Agent，必要时升级到人工坐席。
- **编码助手流水线**：规划 Agent → 编码 Agent → 测试/审查 Agent，逐棒推进，每个 Agent 工具与提示各不相同。
- **深度研究（deep research）**：主 Agent 把「检索某子主题」handoff 给检索子 Agent，收回结构化证据后再综合。
- **多语言 / 多领域路由**：按语言或专业领域把对话交给专门调优的 Agent。
- **分层审批与安全隔离**：高权限操作交给权限受限、审计严格的专用 Agent 执行。
- **IDE/CLI 智能体**：主 agent 把大规模代码搜索、独立实现任务 handoff 给 sub-agent，隔离上下文、避免污染主对话。

## 适用边界

**适合使用**

- 任务可清晰拆分为职责边界明确的子任务，且各子任务需要不同的提示/工具/专业能力。
- 单 Agent 的提示或工具列表已膨胀到影响准确率。
- 需要上下文隔离以控制窗口占用、避免历史噪声干扰。
- 存在天然的「分诊/路由」语义（客服、多领域问答）。
- 需要把特定能力独立评测、独立迭代或独立授权。

**不适合使用**

- 任务简单、单 Agent 足以胜任——引入交接只增加延迟、成本与故障点。
- 子任务间强耦合、需要频繁来回协商，交接开销会超过收益。
- 对延迟极敏感的实时场景，多跳往返不可接受。
- 缺乏可观测性与护栏时贸然使用，循环移交与上下文丢失难以排查。
- 子任务其实是确定性函数——用工具调用而非 Sub-agent 更简单可靠。

## 常见误区

- **把 Handoff 当成普通函数调用**：忽略了控制权转移和接棒者的自主性，设计出只传数据不传目标的「残缺交接」。
- **以为共享完整历史最安全**：直接把全部对话塞给下游，造成窗口膨胀与注意力污染，反而降低质量。
- **交接 payload 写得太随意**：只给一句话任务，缺约束与期望输出格式，导致下游产出不可控。
- **忽视循环与深度限制**：不设环路检测与最大跳数，系统可能陷入互相移交的死循环。
- **Agent 拆得过细**：为拆而拆，制造大量微型 Agent，交接成本和维护负担超过专业化收益。
- **混淆 Handoff 与 Orchestrator-Worker**：误以为只要有多个 Agent 就是编排，忽略了控制权是否转移这一本质区别。

## 我的结论

当任务存在清晰的职责边界、不同子任务需要不同的工具/提示/专业能力，或单 Agent 的上下文与工具已膨胀到损害可靠性时，应该用 Handoff，并默认采用隔离式上下文 + 结构化交接 payload，配齐环路检测、最大跳数和统一 trace。若需要集中汇总与全局决策，用 Orchestrator-Worker；若子任务是确定性操作，用工具调用。不该用的情形是：任务简单、子任务强耦合需频繁协商、或对延迟极敏感——此时多一跳交接只会放大成本、延迟与故障面，得不偿失。一句话：Handoff 的价值来自「专业化隔离」，当隔离带来的收益盖不过交接开销时就不要用。
