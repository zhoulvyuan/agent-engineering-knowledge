## 一句话定义

Reflexion 是一种让 Agent 在一次任务尝试失败（或得分不足）后，用自然语言把"哪里错了、下次怎么改"写成一段反思文本，存入记忆并在下一次重试时作为上下文注入，从而通过"语言化强化学习"迭代改进表现的闭环模式。

## 解决的问题

在 Reflexion 出现之前，基于大模型的 Agent 面对需要多步推理、工具调用或试错的任务时存在几个痛点：

- **一次性作答、不会从失败中学习**：ReAct 等模式能"边想边做"，但一轮跑完若结果错误，模型下一轮往往重复同样的错误，缺乏跨尝试的改进机制。
- **传统强化学习代价太高**：想让模型"从失败中学"，经典做法是用梯度更新权重（RLHF/PPO），需要大量样本、算力和训练流水线，无法在推理期即时生效。
- **稀疏/延迟奖励难以利用**：很多任务只有最终成败这一个标量信号（如单元测试是否通过），模型拿到这个 0/1 信号也不知道"具体哪一步该怎么改"。
- **错误信息转瞬即逝**：报错栈、测试失败详情、环境反馈在单轮内被用过就丢，没有被结构化沉淀下来指导后续尝试。

Reflexion 的核心主张是：不改权重，而是把失败的教训转成"文字经验"存进记忆，用提示工程的方式在重试时喂回去，等价于一次廉价的、推理期的策略改进。

### Reflexion 解决什么问题（失败后自我改进）

核心是让 Agent 具备**跨尝试的自我改进能力**，且不需要微调模型权重：

- **把稀疏奖励转成可操作的语言反馈**：环境只给"成功/失败"或一个分数，Reflexion 让模型自己生成一段诊断——"我上次假设了 X，但测试表明应该是 Y，下次应先验证边界条件"。这段话比裸标量信号信息量大得多。
- **用"语言化强化学习"代替梯度更新**：传统 RL 把经验压进参数；Reflexion 把经验压进 **上下文/记忆**。改进发生在 prompt 层，即时、便宜、可解释。
- **形成 行动→评估→反思→重试 的闭环**：论文在 ALFWorld（决策）、HotpotQA（推理）、HumanEval（编程）上显示，加入反思后多轮成功率显著提升（HumanEval pass@1 曾报到约 91%）。
- **收敛而非乱撞**：因为每次重试都带着上一次的具体教训，错误空间被不断缩小，而不是随机重来。

### 反思信息如何存储与复用

Reflexion 的记忆分**短期**与**长期**两层，职责不同：

| 记忆类型 | 存什么 | 生命周期 | 复用方式 |
|---|---|---|---|
| 短期记忆（轨迹） | 本次尝试的完整 行动-观察 轨迹（trajectory） | 单次尝试内 | 供 Evaluator 评估、供 Self-Reflection 生成反思时参考 |
| 长期记忆（反思） | Self-Reflection 生成的自然语言经验，逐条追加 | 跨尝试累积 | 作为上下文注入到下一次 Actor 的 prompt 中 |

典型流程：

1. **Actor** 执行任务，产出一条轨迹（短期记忆）。
2. **Evaluator** 对轨迹打分——可以是环境信号（测试是否通过）、启发式规则，或 LLM 自评。
3. **Self-Reflection 模型** 读取"轨迹 + 分数"，生成一段简短的文字反思。
4. 反思被 **追加** 到长期记忆（通常是一个有上限的滑动缓冲，如最近 1~3 条，避免上下文爆炸）。
5. 下一次尝试时，长期记忆中的反思被拼进 Actor 的 prompt，Actor 带着教训重试。

工程上记忆可以就是内存里的字符串列表；要跨会话持久或条目很多时，再引入向量库做检索式召回（只注入与当前子任务相关的反思）。

### 它和简单 retry、Evaluator-Optimizer 的区别

| 维度 | 简单 Retry | Evaluator-Optimizer（评估-优化） | Reflexion |
|---|---|---|---|
| 是否利用失败细节 | 否，原样或仅加温度重跑 | 是，评估反馈直接驱动下一版 | 是，且显式生成"语言化诊断" |
| 是否有持久记忆 | 无 | 通常单轮内循环，不强调跨尝试累积 | 有，长期记忆跨多次尝试累积经验 |
| 改进载体 | 随机性 | 评审意见 → 修订 | 自然语言反思 → 注入 prompt |
| 反思由谁产出 | 无反思 | 评估者给意见，优化者改 | Actor 对自己轨迹做自省（可自评也可借外部信号） |
| 典型循环结构 | 失败就重来 | 生成↔评审 两角色往返直到达标 | Actor + Evaluator + Self-Reflection 三要素，记忆驱动迭代 |

要点辨析：

- **vs 简单 retry**：retry 不改变策略，只是赌随机性或赌模型偶然答对；Reflexion 每次都带着具体教训，是有方向的收敛。
- **vs Evaluator-Optimizer**：两者都有"评估"这一步，概念高度重叠，Reflexion 可看作 Evaluator-Optimizer 的一个具体实例/变体。差异在于 Reflexion 强调（1）把反馈**显式转写成自然语言经验**，（2）用**跨尝试的长期记忆**沉淀这些经验。Evaluator-Optimizer 更泛指"评审改稿"回路，不一定强调语言化记忆的持久累积。

### 代价与适用边界

代价：

- **多次 LLM 调用**：每个任务要跑 执行 + 评估 + 反思 + 重试 N 轮，token 和延迟成倍上升。
- **需要可靠的评估信号**：Evaluator 质量决定上限。若用 LLM 自评，可能出现"自我感觉良好"的误判，反思方向跑偏。
- **上下文膨胀**：反思条目越积越多会挤占上下文窗口，必须设上限或做检索式召回。
- **可能收敛到局部最优或震荡**：反思不保证单调改进，设计不当会在两种错误间来回摇摆。

适用边界概述（详见后文"适用边界"）：适合有明确、可自动化验证信号且允许多次重试的任务（编程、带环境反馈的决策）；不适合一次性、低延迟、无可靠验证手段或极度成本敏感的场景。

## 核心内容

**三个核心组件 + 两层记忆**构成 Reflexion 的闭环：

- **Actor（执行者）**：通常基于 ReAct/CoT，负责产出"思考-行动-观察"轨迹，完成任务尝试。
- **Evaluator（评估者）**：对轨迹产出奖励/判定。来源可以是（1）环境真值信号——如编译/单测结果、游戏得分；（2）启发式规则；（3）LLM 自评。真值信号最可靠。
- **Self-Reflection（自省者）**：输入"轨迹 + 评估结果"，输出一段自然语言反思，指出失败原因与改进方向。这是 Reflexion 区别于其他回路的灵魂。
- **记忆**：短期（当前轨迹）+ 长期（历次反思，带容量上限）。

闭环流程图（文字版）：

```
          ┌─────────────────────────────────────────┐
          │                                           │
          ▼                                           │
   [Actor 执行] ──轨迹──► [Evaluator 评估] ──分数──► [Self-Reflection]
          ▲                                           │
          │                                        生成反思
          │                                           │
          └──── 长期记忆（历次反思，注入prompt）◄──追加─┘

   终止条件：评估通过 / 达到最大尝试次数 / 达到预算上限
```

关键设计点：

- **终止条件**要明确：成功即停、设 max_trials、设 token/时间预算，三者取其一先到。
- **记忆窗口**要有上限：常见保留最近 1~3 条反思；条目多时用向量检索只召回相关经验。
- **反思要具体**：好的反思是"下次应先运行边界用例再提交"，而不是"我要更仔细"。prompt 应引导模型给出可执行的改进项。
- **评估信号优先用客观真值**：能用单测/编译/校验器就不要只靠 LLM 自评。

## 典型工程场景

- **自动化编程 / 代码生成**：用单元测试或编译结果作 Evaluator，失败后反思"哪个用例没过、是边界还是逻辑错"，再生成修订版代码。信号客观、天然适配。
- **交互式决策 / 具身任务**：如 ALFWorld 类文本环境、网页/桌面操作 Agent，用环境成败或得分驱动反思，逐次减少无效动作。
- **多跳问答与检索推理**：如 HotpotQA，反思上次"检索关键词选错/跳步推理断链"，调整检索与推理策略。
- **工作流/数据处理任务**：有 schema 校验、规则校验等可自动判定正确性的任务，用校验失败信息驱动自改进。
- **带评测闭环的 Agent 评测/优化**：在已有自动评分器的场景，把 Reflexion 作为提升通过率的推理期手段。

## 适用边界

**适合使用**

- 存在**明确、可自动化**的成败/评分信号（单测、编译、校验器、环境奖励）。
- 任务允许**多次重试**，且重试成本可接受。
- 单次尝试易错、但错误**可通过经验收敛**（有迹可循，而非纯随机）。
- 对**可解释性**有要求——语言化反思本身就是改进日志。

**不适合使用**

- **一次性、低延迟**在线请求（聊天即时回复），没时间多轮迭代。
- **缺乏可靠评估信号**：既无真值又无靠谱校验，只能 LLM 自评且自评不准。
- **成本/预算极度敏感**：多轮调用的 token 开销不可接受。
- 任务**不可重试或副作用不可逆**（如已发生的真实交易、不可回滚的外部操作）。
- 失败模式**随机无规律**，反思无法提供有效方向。

## 常见误区

- **把 Reflexion 当成会改权重的"学习"**：它不更新模型参数，改进只存在于上下文/记忆中，换个新会话且不带记忆就"失忆"了。
- **以为 LLM 自评足够可靠**：缺少客观信号时，自评可能自我肯定导致反思跑偏，务必优先接入真值评估。
- **反思越多越好**：无上限累积反思会撑爆上下文、稀释关键信息，还增加成本，应设窗口或检索召回。
- **反思写得太空泛**：诸如"我要更认真"的反思无用，必须引导出具体、可执行的改进项。
- **和简单 retry 混为一谈**：retry 不带教训、不收敛；Reflexion 的价值正在于带着具体诊断有方向地迭代。
- **忽视不可逆副作用**：在真实环境里盲目重试可能造成重复的外部操作，需做幂等或沙箱保护。

## 我的结论

当任务**有客观可验证的评估信号、允许多次重试、且错误可通过经验收敛**时（最典型是带自动测试的代码生成、带环境奖励的决策任务），应优先考虑 Reflexion：它用推理期的"语言化经验"换取显著的成功率提升，成本远低于微调，且反思日志本身可解释、可审计。

反之，当面对**一次性低延迟请求、缺乏可靠评估信号、预算极度敏感，或操作不可逆**的场景时，不该用 Reflexion——此时多轮迭代带来的收益被延迟、成本或风险抵消，简单 retry、更好的单轮 prompt，或直接引入人工复核更合适。一句话：Reflexion 是"有裁判、能重来、错误有迹可循"场景下的性价比利器，离开这三个前提就要谨慎。
