# Plan-and-Execute

## 一句话定义

Plan-and-Execute 是一种 Agent 设计模式：先由一个规划器（Planner）一次性产出完成任务的完整多步计划，再由执行器（Executor）按计划逐步执行每个子任务，必要时根据执行结果触发重规划（Replan）。它把"想清楚整条路径"与"埋头走每一步"在结构上分离，而不是像 ReAct 那样每走一步都重新思考下一步。

## 解决的问题

在 Plan-and-Execute 出现（典型如 BabyAGI、LangChain Plan-and-Execute、Plan-and-Solve 论文）之前，主流的 ReAct 式 Agent 把"思考—行动—观察"揉在同一个循环里，每一步都调用一次大模型即兴决定下一步该做什么。这带来几类麻烦：

- **缺乏全局视野**：模型只盯着当前这一步，容易在复杂任务里"走一步看一步"，中途偏离目标、重复劳动或陷入局部循环，难以保证把一个长任务完整做完。
- **成本与延迟高**：每一步都用最强（最贵）的模型做完整推理，长任务步数多，token 消耗和响应时间都线性膨胀。
- **过程不可审查**：没有一份显式的、可供人类或程序事先检查的计划，无法在真正花钱执行前判断方向是否正确。
- **难以并行与复用**：步骤之间的依赖关系隐含在循环里，无法预先识别哪些子任务可以并行、哪些结果可以缓存。

Plan-and-Execute 用"先出完整计划、再逐步执行"的结构回应了这些问题。

### Plan-and-Execute 的两阶段结构是什么

它由两个在职责上分离的阶段组成，中间常常加入一个重规划环节，构成"规划 → 执行 →（必要时）重规划"的闭环。

- **规划阶段（Plan）**：规划器接收用户目标，一次性输出一个结构化的子任务序列（通常是有序列表或 DAG），每个子任务描述"做什么"而非"怎么调工具"。这一步通常用能力最强的模型，追求计划的正确性与完整性。
- **执行阶段（Execute）**：执行器按计划逐条取出子任务，调用工具/子 Agent 完成它，并把结果（观察）记录下来，供后续步骤使用。执行器可以用更小更快的模型，甚至每个子任务内部再跑一个小的 ReAct 循环。
- **状态与衔接**：两阶段之间通过一份共享的"任务列表 + 已完成结果"状态传递。执行完一步后，系统判断是继续下一步、还是因为出现偏差而回到规划器。

对比两阶段的分工：

| 维度 | 规划阶段 Planner | 执行阶段 Executor |
| --- | --- | --- |
| 关注点 | 全局路径、子任务拆分与排序 | 单个子任务的落地执行 |
| 输入 | 用户总目标 | 单个子任务 + 已有上下文 |
| 输出 | 完整步骤计划（list/DAG） | 该步骤的执行结果 |
| 模型选择 | 偏强模型，重推理 | 可用轻量模型，重执行 |
| 调用频率 | 少（任务开始/重规划时） | 多（每个子任务一次或多次） |

### 它相比 ReAct 的优势与代价

二者不是对立，而是不同粒度的权衡。可以把 ReAct 看作"每步都重新规划"，Plan-and-Execute 看作"先规划一次、再执行"。

| 维度 | ReAct | Plan-and-Execute |
| --- | --- | --- |
| 全局一致性 | 弱，易偏离/循环 | 强，有显式整体计划 |
| 长任务完成度 | 容易半途而废 | 更能跑完多步任务 |
| 成本/延迟 | 每步都用强模型，偏高 | 规划一次用强模型、执行用弱模型，整体更省 |
| 可审查性 | 过程隐式，难事前检查 | 计划可被人/程序事前审查、修改 |
| 适应突发变化 | 强，天然随观察调整 | 需显式重规划才能适应 |
| 实现复杂度 | 低，一个循环 | 高，需规划器+执行器+重规划+状态管理 |

**优势**：全局视野更好、长任务更可靠、成本可通过模型分层下降、计划显式可控。

**代价**：架构更复杂；若初始计划是在信息不足时制定的，可能一开始就错；对高度动态、无法预先规划的环境适应性不如 ReAct；重规划逻辑设计不当会退化成"每步都重规划"，丧失成本优势。

### 计划失效/中途出错时如何处理（重规划）

计划是基于执行前的信息做出的假设，执行中一定会遇到现实偏差，因此重规划（Replan）是该模式的核心而非附属。常见处理策略：

- **触发条件**：某子任务执行失败/工具报错；执行结果与预期严重不符；出现计划未预见的新信息；或所有步骤执行完但总目标仍未达成。
- **重规划粒度**：
  - *整体重规划*：把"原目标 + 已完成步骤及其结果 + 失败原因"喂回规划器，让它重新生成剩余计划（LangChain Plan-and-Execute 的典型做法）。
  - *局部修补*：只替换/插入出问题的那几步，保留其余计划，开销更小。
- **工程防护**：设置最大重规划次数与总步数上限，防止无限循环；对失败步骤做重试/退避；保留执行日志以便回溯；必要时将无法自动解决的分歧升级给人类（human-in-the-loop）。
- **状态管理**：重规划必须携带"已完成成果"，避免重复已做的工作，也避免遗漏依赖。

一个健壮实现的循环是：`执行一步 → 检查结果 → 若偏离则重规划，否则继续 → 直到完成或触达上限`。

### 适合什么规模/类型的任务

- **步数较多、路径较清晰的多步任务**：如"调研某主题并产出报告""跑一条数据处理流水线""多工具组合完成的运维脚本"。任务可被预先拆成相对确定的子目标时收益最大。
- **子任务间存在明确依赖/可并行结构**：显式计划（尤其 DAG 形态，如 LLMCompiler）能识别并行机会，缩短整体时延。
- **对成本/延迟敏感的长任务**：通过"强模型规划、弱模型执行"的分层显著降本。
- **需要事前审查或人工介入的高风险任务**：显式计划可在真正执行前被人类检查、批准或修改。

不太适合：单步或极短任务（规划开销不值得）、环境高度不可预测需每步临场反应的任务（ReAct 更合适）、以及目标在执行前根本无法拆解的探索型任务。

## 核心内容

**整体数据流**

```
用户目标
   │
   ▼
┌──────────┐   完整计划(有序步骤/DAG)   ┌──────────┐
│ Planner  │ ─────────────────────────▶ │  任务队列  │
└──────────┘                            └────┬─────┘
      ▲                                      │ 取出下一步
      │ 带着(目标+已完成结果+失败原因)         ▼
      │                                 ┌──────────┐  工具/子Agent
      │   需要调整时                     │ Executor  │ ───────────▶ 外部环境
   ┌──┴───────┐  是                     └────┬─────┘
   │ Replan?  │◀──── 结果偏离预期? ────────────┘
   └──┬───────┘  否 → 继续下一步 / 全部完成 → 输出
      ▼
   更新剩余计划
```

**关键机制**

- **计划的表示**：最简单是有序步骤列表；更进阶用 DAG 表达依赖，支持并行调度（代表作 LLMCompiler）。
- **模型分层**：Planner 用强模型保正确，Executor 用轻量模型保吞吐，是降本的主要来源。
- **状态/记忆**：维护"原目标、完整计划、已完成步骤及其结果"的共享状态，是衔接两阶段和重规划的基础。
- **执行器内部可嵌套**：每个子任务内部可以再跑一个小 ReAct 循环，形成"外层规划、内层反应"的分层结构。
- **收敛控制**：最大步数、最大重规划次数、超时与成本预算，防止发散。

**常见变体对比**

| 变体 | 计划形态 | 特点 |
| --- | --- | --- |
| Plan-and-Solve（论文） | 一次性文字计划 | 偏 prompt 技巧，引导模型先列计划再解题 |
| LangChain Plan-and-Execute | 步骤列表 + 显式 Replan | 规划器/执行器分离，带重规划节点 |
| BabyAGI | 动态任务列表 | 边执行边生成/排序新任务，重规划很频繁 |
| LLMCompiler | DAG | 识别依赖、并行执行多个工具，优化时延 |
| ReWOO | 先规划再无观察执行 | 规划阶段不看中间观察，减少 LLM 调用次数 |

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | ReAct | Plan-and-Execute 可视作把 ReAct 的"每步思考"上提为"一次全局规划"；执行器内部仍常复用 ReAct 循环处理单个子任务 |
| 上游 | Planning / Task Decomposition（任务分解） | 规划阶段的理论基础，决定如何把总目标拆成有序、可执行、依赖清晰的子任务 |
| 下游 | LLMCompiler / ReWOO | 在 Plan-and-Execute 基础上进一步演进：前者用 DAG 实现并行执行，后者去掉中间观察以减少调用，都是对该模式的优化 |
| 易混淆 | ReAct | ReAct 是"边想边做"的单循环、无显式整体计划；Plan-and-Execute 是"先想完再做"、有可审查的全局计划，两者常被混为一谈 |

## 典型工程场景

- **深度调研/报告生成**：先规划"检索→筛选→归纳→成文"等步骤，再逐步执行，保证不漏环节、过程可审查。
- **数据处理与分析流水线**：任务天然可拆为抽取、清洗、计算、可视化等有依赖的步骤，适合显式计划（尤其 DAG）调度。
- **运维/DevOps 自动化**：如"排查并修复某服务异常"，先规划检查项与修复步骤，高风险操作在执行前供人工审批。
- **多工具编排的复杂业务流**：如订单处理、合同审查，涉及多系统调用且步骤相对固定。
- **代码库级任务**：先规划"定位→修改→测试→验证"，再分步执行，避免 ReAct 式即兴修改导致的发散。

## 适用边界

**适合使用**

- 任务步数多、可被预先拆成相对确定的子目标。
- 子任务间有明确依赖或可并行结构，能从显式计划/DAG 获益。
- 对成本、延迟敏感，希望用"强模型规划 + 弱模型执行"降本。
- 高风险或合规场景，需要在执行前审查、批准或人工介入计划。

**不适合使用**

- 单步或极短任务，规划开销不划算。
- 环境高度动态、每步都要临场反应，初始计划很快失效（ReAct 更合适）。
- 目标在执行前根本无法拆解、需边探索边定义的开放型任务。
- 子任务高度耦合、无法清晰切分，强行规划反而制造错误假设。

## 常见误区

- **以为计划一次成型、不会变**：忽略重规划，是该模式最常见的失败来源；现实中计划几乎一定要迭代修正。
- **把它和 ReAct 对立**：实际上二者常组合使用——外层规划、内层用 ReAct 执行单步。
- **规划阶段过度追求细节**：把计划拆得过细、过早绑定具体工具调用，会在信息不足时写出错误假设，不如保留一定抽象度。
- **忘记传递已完成成果**：重规划时不带已有结果，导致重复劳动或丢失依赖。
- **缺少收敛护栏**：不设最大步数/重规划上限，遇到难题时无限循环、烧钱。
- **误以为一定更省钱**：若重规划过于频繁、或执行器也用强模型，成本优势会消失甚至反超 ReAct。

## 我的结论

当任务**步数较多、路径大体可预先拆解、且对可靠性或成本敏感**时，应该用 Plan-and-Execute：显式计划带来全局一致性、可审查性，模型分层带来成本优势，重规划提供必要的鲁棒性。尤其在调研、数据流水线、受监管的高风险操作等场景，它明显优于裸 ReAct。

反过来，当任务**极短、环境高度动态需要每步临场反应、或目标在执行前无法拆解**时，不该用它——此时 ReAct 的即兴适应更合适，强上规划只会增加复杂度并写出很快失效的假设。实践中最稳的做法往往是分层组合：用 Plan-and-Execute 管全局，用 ReAct 管单步；并务必配上重规划与收敛护栏，否则它既不够鲁棒也不够省。
