## 一句话定义

ReAct 是一种让大模型把「推理（Reasoning）」和「行动（Acting）」交错进行的 Agent 范式：模型在每一步先生成一段思考文字决定要做什么，再调用外部工具执行动作，然后把工具返回的观察（Observation）喂回上下文，循环「Reason → Act → Observe」直至得出最终答案。

## 解决的问题

在 ReAct 出现之前，用大模型完成需要外部信息或多步操作的任务存在两类典型困境：

- **纯推理（如 Chain-of-Thought）会"闭门造车"**：模型只能依赖参数里固化的知识一次性推理到底，无法获取实时信息，容易产生幻觉，且推理链一旦前段出错后面会一路错到底，没有纠偏机会。
- **纯行动（直接调工具）缺乏规划**：如果让模型机械地调用工具而不解释意图，它难以处理多步依赖、无法根据中间结果调整策略，遇到工具报错或返回意外结果时也不知道如何重新规划。

ReAct 的价值在于把二者缝合：推理为行动提供方向和可解释的意图，行动为推理提供真实世界的反馈，使模型能够在"想—做—看—再想"的闭环中动态修正，既减少幻觉又具备多步任务的执行能力。

### ReAct 的核心循环是什么（Reason→Act→Observe）

ReAct 把一次任务求解拆成若干个结构化步骤，每个步骤由三部分组成，形成一个显式的循环：

1. **Thought（Reason，推理）**：模型用自然语言写出当前的分析——"我现在知道什么、还缺什么、下一步该做什么"。这段思考不执行任何副作用，纯粹用来规划。
2. **Action（Act，行动）**：模型根据思考结果，输出一个结构化的动作调用，通常是「工具名 + 参数」，例如 `search("ReAct paper authors")` 或 `calculator("23*47")`。
3. **Observation（Observe，观察）**：运行时实际执行该动作，把工具/环境返回的结果拼接回上下文。

随后进入下一轮 Thought，模型基于新的观察继续推理，如此往复，直到某一步的 Action 是「Finish / Final Answer」，输出最终结果。关键点在于：**观察结果是动态注入的真实反馈**，不是模型自己想象的，这让后续推理建立在事实之上。整个循环本质上就是一个带工具调用的 Agent Loop，终止条件通常是产出终答、达到最大步数，或连续失败触发兜底。

### 它和纯 Chain-of-Thought、纯 Tool Calling 的区别

| 维度 | Chain-of-Thought | 纯 Tool Calling | ReAct |
|------|------------------|-----------------|-------|
| 是否有外部交互 | 无，只在内部推理 | 有，但缺少显式推理 | 有，推理与行动交错 |
| 信息来源 | 仅模型参数内知识 | 工具返回结果 | 参数知识 + 工具实时反馈 |
| 能否纠偏 | 几乎不能，错了一路错 | 弱，难根据结果重规划 | 强，可依据观察动态调整 |
| 可解释性 | 高（有思考文字） | 低（只见调用） | 高（思考 + 动作都可见） |
| 多步任务能力 | 弱 | 中 | 强 |
| 幻觉风险 | 高 | 中 | 较低（有事实锚定） |

一句话概括：CoT 是「只想不做」，纯 Tool Calling 是「只做不想」，ReAct 是「边想边做、以做验想」。需要补充的是，现代 LLM 的原生 Function/Tool Calling 已经隐含了部分规划能力，很多框架里的 ReAct 实际是「原生工具调用 + 显式思考字段」的融合形态，二者边界在工程上逐渐模糊。

### 什么任务适合 ReAct、什么不适合

**适合**：

- 需要外部实时/私有信息的任务：联网搜索问答、查数据库、读文档（RAG 检索增强）。
- 多步、有中间依赖的任务：先查 A 再根据 A 查 B，或需要计算、代码执行等工具协作。
- 需要试错和纠偏的任务：工具可能失败、结果可能不符合预期，需要重规划。
- 需要可审计、可解释执行轨迹的场景：思考文字便于调试和归因。

**不适合**：

- 纯知识性、单步即可回答的问题（如常识问答），引入循环只增加延迟和成本。
- 对延迟/成本极度敏感的高并发场景，ReAct 的多轮往返会放大 token 消耗和响应时间。
- 任务目标模糊、工具集设计不清晰时，容易陷入无效循环。
- 需要严格确定性输出的流程（如固定的 ETL 管道），用规则/工作流编排比让模型自由决策更可靠。

### ReAct 的常见失败模式与工程注意点

常见失败模式：

- **死循环 / 重复动作**：模型反复调用同一工具或在两个状态间来回震荡，常因观察结果没被有效利用或终止条件缺失。
- **格式违约**：模型输出的 Action 不符合解析器预期（工具名拼错、参数非法 JSON），导致解析失败。
- **幻觉工具调用**：调用不存在的工具或凭空捏造观察结果（尤其当 prompt 让模型自己续写 Observation 时）。
- **上下文爆炸**：步数一多，历史 Thought/Action/Observation 累积，超出上下文窗口或稀释关键信息。
- **错误传播**：某步观察有误但模型未识别，后续推理建立在错误事实上。

工程注意点：

- **强约束输出格式**：优先用原生 Function Calling 或 JSON 模式，而非靠文本正则解析；对解析失败做重试与纠错提示。
- **设置最大步数与超时**：防止死循环，超限时走兜底回答或人工介入。
- **严禁模型自行生成 Observation**：Observation 必须由运行时真实注入，在停止符/解析上做好隔离。
- **工具描述要清晰**：工具名、参数 schema、用途说明直接影响调用准确率。
- **上下文管理**：对长轨迹做摘要/截断，保留关键观察。
- **可观测性**：记录每一步的 Thought/Action/Observation 用于调试、评测和回放。

## 核心内容

ReAct 的核心是一个带结构化步骤的循环，可用如下流程表示：

```
用户问题
   │
   ▼
┌─────────────────────────────┐
│  Thought: 分析现状，决定下一步  │ ◄──────┐
└─────────────────────────────┘        │
   │                                    │
   ▼                                    │
┌─────────────────────────────┐        │
│  Action: 工具名(参数)          │        │ 把 Observation
└─────────────────────────────┘        │ 拼回上下文
   │                                    │
   ▼                                    │
┌─────────────────────────────┐        │
│  Observation: 运行时注入真实结果 │ ──────┘
└─────────────────────────────┘
   │（若 Action 为 Finish 则结束）
   ▼
最终答案
```

关键机制与结构：

- **三元组步骤（Thought / Action / Observation）**：这是 ReAct 的最小单元，缺一不可。Thought 提供规划，Action 产生副作用，Observation 提供反馈。
- **显式推理轨迹**：思考被写出来而非隐藏在模型内部，带来可解释性和可调试性，也让模型"自我监督"下一步。
- **工具抽象层**：Action 对应一组预定义工具（搜索、计算、代码执行、API 调用等），运行时负责路由、执行、异常处理。
- **终止控制**：由特殊 Action（Finish）、最大步数、超时或置信度阈值共同决定何时停止。
- **与 Reflexion 等的衔接**：ReAct 是很多更高级范式的基座，例如 Reflexion 在 ReAct 轨迹上叠加"自我反思"，Plan-and-Execute 把规划与执行分层，本质都是对 Reason/Act 比例和结构的调整。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
|------|--------|------|
| 上游 | Chain-of-Thought、Tool Calling / Function Calling | ReAct 把 CoT 的"显式推理"与工具调用的"外部行动"组合而成；原生 Function Calling 是其工程落地的首选实现方式。 |
| 下游 | Reflexion、Plan-and-Execute、多智能体编排 | 这些范式都以 ReAct 的"推理+行动"循环为基础，分别叠加自我反思、规划/执行分层、角色分工等机制。 |
| 易混淆 | 纯 CoT、纯 Tool Calling、Agent Loop | CoT 只想不做、Tool Calling 只做不想；Agent Loop 是更泛化的"感知-决策-行动"循环，ReAct 是其中一种具体的、带显式思考字段的实现模式。 |

## 典型工程场景

- **检索增强问答（RAG Agent）**：模型先推理需要查什么，调用检索工具拿回文档片段，再基于片段推理并作答，必要时多轮检索补全信息。
- **企业内助手 / 客服 Agent**：根据用户意图调用订单查询、知识库检索、工单创建等 API，多步串联完成一次服务。
- **数据分析 Agent**：推理分析思路 → 生成并执行 SQL/代码 → 观察结果 → 修正查询，直到得出结论。
- **自动化运维 / DevOps 助手**：诊断问题时查日志、查监控指标、执行诊断命令，根据观察逐步定位根因。
- **浏览器 / 网页操作 Agent**：在网页环境中边思考边点击、输入、读取页面状态，完成多步交互任务。

## 适用边界

**适合使用**：

- 任务需要外部实时或私有信息，模型参数内知识不足。
- 多步、有中间依赖、需要工具协作的任务。
- 工具可能失败或返回意外结果，需要动态纠偏与重规划。
- 需要可解释、可审计的执行轨迹用于调试或合规。

**不适合使用**：

- 单步、纯知识性问题，加循环只增成本与延迟。
- 对延迟和成本极敏感的高并发在线场景。
- 流程高度确定、可用规则/工作流固定编排的任务，无需让模型自由决策。
- 工具集设计不清晰、目标模糊，容易陷入无效循环的情况。

## 常见误区

- **"ReAct 就是让模型多想想（CoT）"**：错，核心区别在于有真实的外部行动与观察反馈，而非只加思考文字。
- **"把 Observation 也让模型一起生成"**：严重错误，Observation 必须由运行时真实执行工具产生，否则就是自编自演的幻觉。
- **"ReAct 一定比直接工具调用好"**：不一定，简单任务下显式思考反而增加 token、延迟和出错面；要按任务复杂度权衡。
- **"ReAct 必须靠文本解析 Thought/Action"**：这是早期论文的实现方式，现代工程更推荐用原生 Function Calling / 结构化输出，可靠性更高。
- **"步数越多越聪明"**：步数失控往往是死循环或规划失败的信号，而非能力强，必须设上限与兜底。

## 我的结论

当任务**需要外部信息、涉及多步工具协作、且中间结果可能需要纠偏**时，应该用 ReAct：它用"显式推理 + 真实观察"的闭环显著降低幻觉并提升多步任务成功率，同时留下可审计的轨迹。工程落地上，优先基于模型原生的 Tool/Function Calling 实现，而不要依赖脆弱的文本解析，并务必配上最大步数、超时和格式校验等护栏。

反过来，**单步可答的纯知识问题、延迟/成本敏感的高并发场景、以及流程高度确定可用规则编排的任务**，不该用 ReAct——此时它只会放大成本、延迟和失控风险。一句话：ReAct 是"复杂多步、需要事实锚定"任务的默认基座，但不是所有任务的银弹，用之前先问"这个任务真的需要模型边想边做吗"。
