# Router / 分发

> **上级**：[04-Agent设计模式](README.md) ｜ **依赖**：Agent Loop

## 一句话定义

Router（分发）是一种"先分类、再派发"的控制结构：系统在入口处对输入做一次归类判断，然后把该输入交给与之最匹配的下游处理者（专用提示、专用工具、专用子 Agent 或专用模型）去处理，而不是让单一通用处理者包揽所有情况。

## 解决的问题

在 Router 出现之前，构建对话或任务型系统时人们常把所有逻辑塞进一个"万能大 Prompt"或一个通用模型里。随之而来的麻烦：

- **提示臃肿、相互干扰**：退货规则、技术排障、闲聊、下单意图全写在一个 System Prompt 里，指令越堆越多，彼此冲突，模型顾此失彼。
- **成本与延迟失衡**：简单问题（如"你们几点关门"）和复杂问题（如多步排障）用同一个大模型、同一套长上下文处理，简单请求被迫承担昂贵算力。
- **难以针对性优化**：想提升退货场景的准确率，却因为逻辑耦合，改动会殃及其他场景，回归测试代价高。
- **工具/知识范围过宽**：给模型挂上全部工具与全部知识库，选错工具、检索到无关内容的概率上升。
- **难以扩展**：新增一个业务领域就得重写大 Prompt，无法像插件一样增量接入。

### Router 模式解决什么问题

核心是用"分而治之"替代"一揽子处理"，把一个异构的大问题拆成若干同质的小问题，再分别交给专精处理者。它带来的收益：

| 维度 | 没有 Router | 有 Router |
|------|------------|----------|
| 提示设计 | 单一超长 Prompt，指令互相打架 | 每个分支独立短 Prompt，职责单一 |
| 成本/延迟 | 简单请求也走大模型长上下文 | 简单请求可路由到小模型/规则，省钱提速 |
| 准确率 | 工具与知识范围过宽，易误选 | 每分支工具/知识聚焦，命中率高 |
| 可维护性 | 改一处影响全局 | 分支隔离，可独立迭代与评测 |
| 可扩展性 | 新领域需重写主干 | 新增分支即可，近似"插件化" |

一句话：Router 把"模型要同时既懂路又会开车"降级为"先看路牌、再上对的车道"，让每个下游只需在狭窄领域内做好一件事。

### 路由决策依据什么（意图分类/规则/模型）

路由本质是一个分类器，常见三类实现，工程上经常混合使用：

| 方式 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| 规则/关键词 | 正则、关键字、字段匹配、白名单 | 零延迟、零成本、确定可控、易审计 | 覆盖窄、脆弱、维护成本随规则膨胀 | 结构化输入、强合规、热路径兜底 |
| 嵌入/分类模型 | 文本向量化后用轻量分类器或最近邻判类 | 快、便宜、可离线训练、延迟低 | 需要训练数据、类目变动要重训 | 类目相对稳定、流量大 |
| LLM 判别 | 让一个（通常较小的）LLM 输出类别标签/结构化 JSON | 零/少样本即可、理解语义、灵活 | 有延迟和成本、可能输出不合法、需约束 | 意图多变、语义复杂、冷启动 |

工程要点：
- **约束输出**：让 LLM 路由时强制输出受限枚举（function calling / JSON schema / 约束解码），避免自由文本难解析。
- **分层决策**：先用廉价规则命中高频确定场景，未命中再降级到模型路由，兼顾成本与覆盖。
- **置信度**：路由器应给出置信分，低于阈值走澄清或兜底分支，而非强行归类。

### 与 Orchestrator-Worker 的区别

两者都把工作交给下游，但控制流与职责根本不同：

| 对比项 | Router / 分发 | Orchestrator-Worker |
|--------|--------------|---------------------|
| 决策性质 | 一次性"选择一条路" | 持续"规划—拆解—调度—汇总" |
| 下游数量 | 通常命中单一分支（1 选 1） | 常并行/串行调度多个 Worker |
| 是否聚合结果 | 一般不聚合，谁接手谁负责到底 | 需要把多个 Worker 结果整合为答案 |
| 复杂度 | 轻量、无状态为主 | 重，需维护任务图与中间状态 |
| 典型比喻 | 前台分诊/交换机 | 项目经理带团队 |

直观判断：如果问题是"这归谁管"，用 Router；如果问题是"要拆成几步、分给几个人干、再拼起来"，用 Orchestrator-Worker。Router 常作为 Orchestrator 的一个内部环节出现（编排器用路由决定把子任务派给哪个 Worker），二者可组合而非互斥。

### 路由错误如何兜底

路由器会错判，必须显式设计兜底，否则错误会被下游放大：

- **默认分支（default/fallback）**：所有未命中或低置信度的输入落到一个通用处理者或人工坐席，避免"无人接管"。
- **置信度阈值 + 澄清**：置信度低时不猜，而是反问用户澄清意图，或给出候选让用户选择。
- **可纠偏/可回退**：下游发现"这不该归我"时，能把请求退回路由器重判（re-route），或触发二次路由。
- **多路由器投票/校验**：关键场景用规则与模型双通道，结果不一致时升级处理。
- **监控与回放**：记录路由输入、判类、下游结果，离线评测路由准确率，用误判样本回灌训练/补规则。
- **幂等与可观测**：路由与下游调用保证幂等，便于安全重试；全链路打点便于定位错在分类还是执行。

设计原则：宁可路由到"更保守但正确的通用分支"，也不要高置信地路由到错误的专用分支——后者的错误更隐蔽、更难察觉。

## 核心内容

**基本结构**

```
          ┌─────────────┐
输入 ───▶ │   Router    │ 分类/判别（规则 or 模型 or LLM）
          └──────┬──────┘
                 │ 选择分支 + 置信度
     ┌───────────┼───────────┬──────────────┐
     ▼           ▼           ▼              ▼
 [退货处理]  [技术排障]   [下单助手]    [默认/人工兜底]
 专用Prompt  专用工具集   专用子Agent    低置信度落点
```

**关键机制**

- **分类器（Router 本体）**：输入 → 类别标签（+ 置信度）。可以无状态，也可参考少量上下文（如最近对话）。
- **分支注册表（Route Table）**：类别 → 处理者的映射。处理者可以是提示模板、工具子集、独立子 Agent、甚至不同规格的模型。
- **派发器（Dispatch）**：根据标签取出处理者并执行，必要时注入该分支专属的上下文/工具。
- **兜底与回退**：默认分支、低置信澄清、下游 re-route。

**选型维度（分支里"换的是什么"）**

| 换的对象 | 说明 | 典型目的 |
|---------|------|---------|
| Prompt | 同一模型，不同系统提示 | 职责隔离、减少干扰 |
| 工具集 | 不同分支挂不同工具 | 缩小工具选择面、降误用 |
| 子 Agent | 分支本身是独立 Agent | 领域能力解耦、独立迭代 |
| 模型 | 简单走小模型、难走大模型 | 成本/延迟/质量平衡（即 model routing） |
| 知识库 | 不同分支检索不同索引 | 提升 RAG 命中与相关性 |

**设计要点**

- 类目要**互斥、穷尽、稳定**：避免类别重叠导致摇摆，用默认分支覆盖长尾。
- 路由尽量**轻、快、便宜**：它在热路径上，重路由会抵消"省算力"的初衷。
- 输出**结构化、受约束**：枚举标签 + 置信度，便于程序判定与兜底。
- 可**组合与嵌套**：粗分类后在分支内再做细分类（分层路由）。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
|------|--------|------|
| 上游 | Agent Loop / 入口编排 | Router 通常挂在主循环入口，决定本轮请求进入哪条处理链路；它消费 Loop 提供的上下文并产出"走哪条分支"的决策。 |
| 下游 | 专用子 Agent / 工具子集 / RAG 检索器 | 被路由命中的处理者才是真正干活的单元；Router 只负责把活交到对的手上，执行质量取决于这些下游。 |
| 易混淆 | Orchestrator-Worker、Chaining（提示链）、Mixture-of-Experts | Orchestrator 是"规划+调度多步"，Router 是"一次选路"；Chaining 是"固定顺序接力"，无分类决策；MoE 是模型内部的门控路由，概念相近但发生在参数层而非应用编排层。 |

## 典型工程场景

- **客服/工单分诊**：按意图（退换货、账单、技术支持、投诉）路由到不同话术与知识库，低置信转人工。
- **多技能助手**：一个入口下挂"写代码、查数据、日程管理"等能力，按请求类型分发到对应工具/子 Agent。
- **成本敏感的模型路由**：闲聊/简单问答走小模型，复杂推理/代码走大模型，显著降本（如 FrugalGPT 思路）。
- **RAG 索引选择**：按问题领域路由到不同向量库/文档集，提升检索相关性。
- **合规与安全前置**：先路由出敏感/违规请求走专门的拒答或审核链路。
- **多语言分发**：按语种路由到对应语言的处理流程或翻译前置。

## 适用边界

**适合使用**

- 输入可被清晰划分为**少数几个互斥类别**，且各类处理方式差异明显。
- 存在**成本/延迟异构**需求（简单请求想省钱、复杂请求要质量）。
- 不同场景需要**不同工具、知识或话术**，耦合在一起会相互干扰。
- 需要**增量扩展**领域，希望以"加分支"方式演进。

**不适合使用**

- 类别**边界模糊、高度重叠**，分类本身比执行还难，强行路由反而引入错误。
- 任务需要**跨多个领域协同、拆解再汇总**——那是 Orchestrator-Worker 的活。
- 分支极少且处理高度相似，**单一处理者足矣**，加路由只增复杂度。
- 路由开销（延迟/成本）**接近或超过**所省收益，得不偿失。
- 对**误判零容忍**又缺乏兜底条件的强安全场景，需更保守的确定性设计。

## 常见误区

- **把 Router 当编排器**：以为它能规划多步、聚合多路结果；实际它只做"选一条路"，复杂协同要用 Orchestrator。
- **路由器过重**：用大模型 + 长上下文做路由，热路径被拖慢、成本不降反升，违背初衷。
- **类目不互斥/不穷尽**：类别重叠导致摇摆，长尾无落点报错；忘了设默认分支。
- **忽视置信度与兜底**：高置信地路由到错误分支，错误被下游执行放大且难察觉。
- **自由文本输出**：让路由 LLM 输出自然语言再去解析，脆弱易错；应约束为枚举/JSON。
- **只测端到端、不单测路由**：无法区分错在"分类"还是"执行"，优化无从下手。
- **静态规则一劳永逸**：业务意图会漂移，不做监控与回灌，规则/分类器会逐渐失准。

## 我的结论

当输入天然可切成少数几个边界清晰、处理方式差异明显的类别，且你希望按场景隔离提示/工具/知识或做成本分级时，就该上 Router——它用一次轻量分类换来职责解耦、成本下降和可维护性提升，是性价比极高的入口级模式。反之，当类别边界模糊、分类比执行还难，或任务需要跨域拆解与结果汇总时，不该用 Router：前者会把错误前置并放大，后者本质是编排问题。实践上，让路由器保持"轻、快、受约束、带置信度与默认兜底"，并对路由单独评测与监控；路由器可以、而且常常嵌在 Orchestrator 内部作为调度环节，二者是组合关系而非替代关系。
