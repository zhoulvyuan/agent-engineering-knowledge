# Evaluator-Optimizer

## 一句话定义

Evaluator-Optimizer 是一种双角色闭环工作流：一个「生成者（Optimizer/Generator）」负责产出候选答案，另一个独立的「评估者（Evaluator）」依据明确标准给出通过与否或打分与改进意见，二者循环对抗迭代，直到评估通过或触发停止条件后输出最终结果。

## 解决的问题

在它出现之前，单次生成（one-shot）是 LLM 应用的主流形态，由此带来一系列麻烦：

- 一次生成往往"差一口气"：结构基本对，但有事实错误、遗漏约束、格式不符或风格不达标，而模型自己在同一次输出里既当运动员又当裁判，很难发现自己的问题。
- 质量不可控、不可度量：没有显式的验收标准，输出好坏全凭下游人工抽查，无法形成"不达标就重做"的自动机制。
- 复杂任务（翻译、代码、长文写作、检索答案）需要多轮打磨，但人工 Review-Rewrite 成本高、不可规模化。
- 提高质量的常见做法是堆更强的模型或更长的提示词，边际收益递减且成本高，缺少一个"用迭代换质量"的结构化手段。

Evaluator-Optimizer 把"生成"与"验收"拆成两个职责分离的角色，用可重复的闭环把质量提升过程自动化、可度量化。

### 生成者-评估者对抗迭代如何工作

核心是一个带反馈的循环，而非单向流水线：

1. **生成**：Optimizer 根据任务输入产出候选结果 `v1`。
2. **评估**：Evaluator 依据预设标准（评分维度、硬约束、测试用例）对 `v1` 做判定，返回"通过/不通过"以及**结构化的改进反馈**（哪里错、为什么、怎么改）。
3. **优化**：若未通过，Optimizer 把原输出 + 评估反馈作为新上下文，产出 `v2`。
4. **循环**：重复 2–3，直到评估通过或命中停止条件（最大轮数、分数阈值、改进停滞）。

"对抗"的含义不是博弈论意义的零和，而是**职责对立**：评估者的目标是尽可能挑错并提出可操作意见，生成者的目标是针对意见修复。关键工程点在于反馈必须是**可执行的具体差异**（例如"第 3 条引用与原文不符"），而不是"再好一点"这类空泛评价，否则迭代会原地打转。

### 评估者从哪来（模型自评/规则/另一个模型）

评估者的来源决定了可靠性与成本，常见有三类，可组合使用：

| 评估者类型 | 实现方式 | 优点 | 局限 |
| --- | --- | --- | --- |
| 规则/程序化 | 单元测试、编译器、JSON Schema 校验、正则、业务校验函数 | 客观、确定、零幻觉、便宜 | 只能覆盖可形式化的标准，难评"好不好" |
| 另一个 LLM（LLM-as-a-Judge） | 独立提示词/独立模型按评分 rubric 打分 | 能评主观质量（流畅、相关、风格） | 有偏见与幻觉，可能被"看起来对"的输出骗过 |
| 外部真值/工具 | 检索比对、执行结果、API 返回、人工抽检 | 接近 ground truth，最可信 | 不一定可得，延迟与成本高 |

工程上的最佳实践：**能用规则就不用模型**（如代码先过编译和测试再让模型评风格）；用 LLM 评估时让评估者与生成者使用**不同的提示词甚至不同模型/温度**，降低"同源盲点"；对主观维度给出明确 rubric 和打分区间，避免评估漂移。注意"模型自评"（同一次对话里自我反思）严格说不是独立评估者，容易自洽式自我肯定，可靠性弱于独立评估者。

### 它和 Reflexion 的区别

二者都用"反馈驱动改进"，但层次不同：

| 维度 | Evaluator-Optimizer | Reflexion |
| --- | --- | --- |
| 本质 | 一种工作流/设计模式 | 一种具体的 Agent 学习算法（Shinn 等, 2023） |
| 反馈形式 | 评估者的评分/判定 + 改进意见 | 把环境反馈（成败信号）转成**语言化的自我反思**写入记忆 |
| 记忆 | 通常无跨任务长期记忆，循环在单任务内 | 维护一个 episodic memory，跨 trial 累积反思经验 |
| 评估来源 | 显式独立评估者（规则/模型/工具） | 多来自环境奖励或任务成败等外部信号 |
| 适用 | 单次任务内把质量迭代到达标 | 需要多次尝试、从失败中累积经验的交互式任务 |

简言之：Evaluator-Optimizer 是"生成—验收"的通用结构模式，强调评估者独立；Reflexion 是在此思想上更具体的方法，强调把反馈转为语言反思并存入记忆以指导后续尝试。可以认为 Reflexion 是 Reflection/Evaluator-Optimizer 思想的一个具体工程化实例。

### 收敛与成本如何控制、何时停止

迭代不收敛和成本失控是该模式最大的落地风险，常用控制手段：

- **最大轮数（hard cap）**：设 N（常见 2–4 轮），到顶即输出当前最优，避免无限循环。
- **分数阈值 / 质量门**：评估分达到阈值即停；对硬约束用"全部通过"作为门槛。
- **改进停滞检测**：若连续两轮分数不升或反馈重复，提前退出（防止来回震荡/原地打转）。
- **成本预算**：按累计 token 或调用次数设上限；评估用小模型、生成用大模型做分工以降本。
- **早停优先**：第一轮就通过则直接返回，不要为"迭代而迭代"。
- **防震荡**：把历次版本与反馈一并喂给生成者，避免"修了 A 又坏了 B"的回退循环。

一个经验法则：若任务**有清晰、可验证的成功标准**（能写出 rubric 或测试），迭代收益明显且可控；若标准模糊，评估者本身会漂移，再多轮也不收敛，此时应先把"什么叫达标"定义清楚。

## 核心内容

**结构（两角色 + 反馈环）**

```
输入 ──▶ [Optimizer 生成] ──▶ 候选结果
             ▲                    │
             │                    ▼
       改进反馈           [Evaluator 评估]
             │                    │
             └──── 未通过 ◀────────┤
                                  │ 通过/到顶
                                  ▼
                               最终输出
```

**关键机制要点**

- **职责分离**：生成与评估是两个独立角色，各自提示词/标准独立，评估者不负责生成，生成者不自我放水。
- **结构化反馈**：评估输出应是机器与模型都能消费的结构（通过标志 + 维度分 + 具体问题列表），而非自然语言含糊评语。
- **可验收标准先行**：先定义 rubric / 测试 / 约束，再跑循环；标准即"真值代理"。
- **停止条件显式化**：最大轮数、阈值、停滞检测三者至少配其一。
- **分工降本**：评估常比生成简单，可用更便宜模型或纯规则承担。

**与相邻模式对比**

| 模式 | 关系 |
| --- | --- |
| Reflection（反思） | Evaluator-Optimizer 是把反思"外置"为独立评估者的强化版 |
| Prompt Chaining | 单向链无反馈环；本模式是带回路的链 |
| Orchestrator-Workers | 关注任务拆分与并行；本模式关注质量迭代 |

## 典型工程场景

- **代码生成**：生成代码 → 编译器/单元测试做评估 → 按报错迭代修复，直到测试全绿。
- **机器翻译/本地化**：译文 → 评估者按忠实度、流畅度、术语一致性打分并指出问题句 → 重译。
- **结构化抽取/报告生成**：产出 JSON 或长文 → Schema 校验 + rubric 评审 → 补齐缺失字段、修正格式。
- **RAG 答案质量把关**：生成答案 → 评估者核对是否有检索依据、是否幻觉、是否答非所问 → 不达标则重写或重检索。
- **文案/营销内容**：生成稿 → 按品牌调性与合规清单评估 → 迭代到过审。
- **复杂搜索/研究综述**：初稿 → 评估覆盖度与引用准确性 → 补充检索与修订。

## 适用边界

**适合使用**

- 存在清晰、可验证的成功标准（可写测试、Schema 或明确 rubric）。
- 单次生成质量不稳定，但多迭代一两轮即可显著改善。
- 质量比延迟/成本更重要的离线或半实时任务。
- 评估比生成更容易、更便宜（验证比求解简单的场景收益最大）。

**不适合使用**

- 低延迟、强实时交互（多轮循环会显著增加响应时间）。
- 成功标准模糊、无法度量，评估者本身会漂移、无法收敛。
- 简单任务一次就能做好，加循环只是增加成本与复杂度。
- 评估和生成一样难甚至更难（验证无优势）时，收益可疑。

## 常见误区

- **把模型自评当独立评估**：同一上下文里让模型"自己检查"易自我肯定，不等于职责分离的评估者。
- **反馈空泛**："再好一点""不够准确"无法指导修复，必须给可执行的具体差异。
- **不设停止条件**：迷信"多迭代必更好"，导致无限循环、来回震荡或成本爆炸。
- **只用 LLM-as-a-Judge**：忽视能用规则/测试做客观评估的部分，既贵又引入评估幻觉。
- **评估者与生成者同源**：用完全相同的模型和提示词，盲点一致，等于没评。
- **误以为它等于 Reflexion**：把一个通用模式和一个具体算法画等号。

## 我的结论

当任务**有可形式化的验收标准、且验证比生成更容易**时，应该用 Evaluator-Optimizer：优先用规则/测试做评估，LLM-as-a-Judge 只补主观维度，设置 2–4 轮上限加停滞检测，用"迭代换质量"性价比很高（代码、翻译、结构化抽取、RAG 把关是典型受益场景）。当任务实时性要求高、成功标准模糊无法度量、或一次生成已足够好时，不该用它——此时迭代只增加延迟与成本却不收敛，更该先把"什么叫达标"定义清楚，或改用更强模型/更好提示的一次性生成。一句话：**它是用结构化闭环把"可验证的质量"自动迭代出来的工具，价值完全取决于你能否把"达标"写成可判定的标准。**
