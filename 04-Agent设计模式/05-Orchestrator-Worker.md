## 一句话定义

Orchestrator-Worker 是一种分层协作模式：由一个「编排者（Orchestrator）」在运行时动态把复杂任务拆解成若干子任务，分发给多个「执行者（Worker）」并行或串行完成，再由编排者收集、校验并综合各 Worker 的产出为最终结果。

## 解决的问题

在它出现之前，面对复杂且结构不固定的任务，工程上通常有两种糟糕选择：

- **单 Agent 硬扛**：让一个 Agent 在一个长上下文里完成所有事情（检索、分析、写作、校对……）。随着步骤变多，上下文被塞满、注意力被稀释，中间结论互相干扰，长链推理越走越偏，且无法并行，延迟线性累积。
- **预先写死的固定管道（static pipeline）**：人工把流程拆成固定的 N 步串成 DAG。它在任务形态可预测时有效，但一旦子任务的数量、类型、顺序要「看输入才知道」（例如"这份需求要改动几个文件"），固定管道就无法表达，只能保守地覆盖所有分支，臃肿且脆弱。

Orchestrator-Worker 的价值在于：**把"要拆成几个子任务、每个子任务是什么"这件事本身也交给 LLM 在运行时决定**，从而既获得分工带来的专注度与并行度，又保留了对未知任务结构的适应能力。

### 这个模式的结构与职责划分

整体是「一主多从」的两层（有时三层）结构，职责严格分离：

- **Orchestrator（编排者）**：负责"想"而非"做"。它接收原始任务，产出一个子任务计划（通常是结构化输出，如 JSON 列表），为每个子任务准备必要上下文，调度 Worker（决定并行度、顺序、依赖），接收回传结果，判断是否需要补充/重试，最后综合（synthesize）成最终答案。它持有全局视图，但**不直接执行细粒度工作**。
- **Worker（执行者）**：负责"做"而非"想全局"。每个 Worker 只拿到被隔离的、聚焦的子任务和最小必要上下文，独立完成（可以带自己的工具、短循环），把结果结构化回传。Worker 之间通常**彼此不感知、无共享状态**，这是并行与隔离的前提。

| 角色 | 关注点 | 典型输入 | 典型输出 | 是否持有全局上下文 |
|------|--------|----------|----------|--------------------|
| Orchestrator | 任务分解、调度、综合 | 原始任务 + 中间结果 | 子任务计划 / 最终答案 | 是 |
| Worker | 单个子任务的完成 | 隔离的子任务 + 最小上下文 | 子任务结果 | 否（仅局部） |

关键点：拆解在**运行时**由 Orchestrator（通常是 LLM）决定，这把它和"人工写死步骤"的固定工作流区分开来。

### 什么时候需要它而不是单 Agent

当任务满足以下特征时，收益显著，否则单 Agent 更简单划算：

- **子任务数量/类型事先未知**：必须先看输入才知道要做哪几件事（如"根据改动需求修改相关文件"，文件数不定）。
- **子任务之间弱耦合、可并行**：拆开后彼此独立，能并发执行以压缩总延迟（如同时检索多个信息源、同时分析多个模块）。
- **单一上下文容量/注意力成为瓶颈**：全部塞进一个 Agent 会超出有效上下文或导致推理退化，隔离到各 Worker 能保持每个子任务的高信噪比。
- **需要分工复用不同能力/工具**：不同 Worker 可配不同工具、提示词甚至不同模型（便宜模型做批量子任务，强模型做综合）。

反之，任务步骤固定、线性、短小，或子任务间强依赖必须严格串行时，Orchestrator-Worker 的额外编排开销（多轮 LLM 调用、调度复杂度、成本）得不偿失，应退回单 Agent 或固定管道。

### 子任务拆解与结果汇总的难点

这是本模式最核心也最难做好的两端：

- **拆解（decompose）难点**：
  - 粒度难把握——拆太细则子任务太多、调度/综合成本爆炸、Token 翻倍；拆太粗则又回到单 Agent 的注意力问题。
  - 边界重叠或遗漏——Orchestrator 可能生成互相重叠（重复劳动）或留有缝隙（遗漏覆盖）的子任务。
  - 上下文传递——每个 Worker 需要"刚好够用"的上下文，给少了 Worker 没法做，给多了又失去隔离的意义。
  - 依赖识别——有依赖的子任务不能盲目并行，Orchestrator 要正确识别并排序。
- **汇总（synthesize）难点**：
  - 结果冲突/不一致——不同 Worker 的产出可能矛盾、风格不一、接口对不上，综合时需裁决或二次协调。
  - 质量与完备性校验——Orchestrator 要判断"是否已经够好/够全"，否则需触发补充子任务，这本身是一个难以稳定的终止判断。
  - 累积误差——Worker 的小错误被综合放大；缺乏溯源会让最终结果难以调试。
  - 成本与延迟——综合阶段往往要把多个结果再喂给强模型，是成本大头；"扇出-扇入"的尾部延迟由最慢的 Worker 决定。

工程上常用对策：结构化输出（强约束 schema）、给 Worker 明确的产出契约、对拆解结果做校验/去重、设重试与超时、对综合阶段加评审（critic/verifier）。

### 与 Multi-Agent、Router 的关系与区别

三者容易混淆，用一张表对齐：

| 维度 | Router | Orchestrator-Worker | Multi-Agent（通用多智能体） |
|------|--------|---------------------|------------------------------|
| 核心动作 | 分类/选路，选一个处理者 | 拆解 + 分发 + 综合 | 多个自治 Agent 协作/协商 |
| 子任务数 | 通常选 1 条路径 | 运行时动态拆成 N 个 | N 个，可能长期存在 |
| 控制结构 | 单点分发（无汇总） | 中心化（一主多从，有汇总） | 可中心化也可去中心化/对等 |
| Worker 自治度 | — | 低（受编排者支配、无状态） | 高（有记忆、角色、可对话） |
| 典型关系 | 是 O-W 的"轻量特例" | 是 Multi-Agent 的一种**中心化编排拓扑** | 更宽的范畴，O-W 是其子集 |

- **与 Router 的区别**：Router 只做"选择一条路/一个专家"，它是**单选且不负责综合**；Orchestrator 是"拆成多份并最后合并"。可以认为 Router 是 Orchestrator 退化到"只拆出一个子任务、无汇总"时的特例。实践中 Orchestrator 内部也常先用 Router 式判断再决定怎么拆。
- **与 Multi-Agent 的区别**：Orchestrator-Worker 是 Multi-Agent 家族里的一种**中心化、层级化**的具体拓扑；Worker 通常是无状态、受支配、彼此不通信的。而广义 Multi-Agent 还包含去中心化、对等协商、Agent 之间直接对话、长期有记忆与角色的形态（如辩论、群聊、市场机制）。换句话说：所有 Orchestrator-Worker 都是 Multi-Agent，但多数 Multi-Agent 不是严格的 Orchestrator-Worker。

## 核心内容

典型执行流程（扇出-扇入 / fan-out, fan-in）：

```
原始任务
   │
   ▼
┌──────────────┐   ① 分解：LLM 产出结构化子任务计划
│ Orchestrator │   ② 为每个子任务准备最小上下文
└──────┬───────┘
       │ fan-out（并行/串行分发）
   ┌───┼───┬───────┐
   ▼   ▼   ▼       ▼
 [W1][W2][W3] ... [Wn]   ③ 各 Worker 独立执行（可带工具）
   └───┼───┴───────┘
       │ fan-in（回传结构化结果）
       ▼
┌──────────────┐   ④ 校验/去重/判断是否补充子任务（可循环）
│ Orchestrator │   ⑤ synthesize：综合为最终答案
└──────┬───────┘
       ▼
   最终结果
```

关键机制要点：

- **动态拆解**：子任务的数量和内容由 Orchestrator 在运行时生成，而非预先写死——这是它区别于固定工作流（prompt chaining / 静态 DAG）的根本标志。
- **上下文隔离**：每个 Worker 只见自己的子任务，天然避免长上下文污染，提升单任务信噪比。
- **结构化契约**：Orchestrator↔Worker 之间用结构化输出（JSON/schema）约定子任务与结果格式，保证可调度、可汇总、可校验。
- **异构配置**：不同 Worker 可用不同模型/工具/提示词；常见做法是"强模型做编排与综合、弱模型做批量 Worker"以平衡成本。
- **综合阶段是重心**：最终质量取决于 synthesize，常再叠加 critic/verifier 做评审或触发补做。
- **循环与终止**：Orchestrator 可根据汇总质量决定是否追加子任务，需要明确的终止条件/预算上限防止无限扩张。

对比：固定工作流 vs Orchestrator-Worker

| 维度 | 固定工作流（静态管道） | Orchestrator-Worker |
|------|------------------------|---------------------|
| 子任务结构 | 开发期写死 | 运行时由 LLM 决定 |
| 适应未知输入 | 弱 | 强 |
| 可预测性/可测试性 | 高 | 较低（需额外护栏） |
| 成本/延迟可控性 | 高 | 需主动约束 |
| 适用任务 | 结构稳定 | 结构随输入变化 |

| 关系 | 知识点 | 说明 |

| 上游 | Router / 任务分解（Decomposition）/ 结构化输出 | Orchestrator 的拆解依赖"分类选路 + 任务分解"思想，并用结构化输出把子任务计划落成可执行的 schema；Router 可视为其退化特例。 |
| 下游 | 并行工具调用、Reflection/Critic 评审、Map-Reduce 式综合 | 分发阶段落到并行工具/子 Agent 调用；综合阶段常接评审或 reduce 式归并来保证质量。 |
| 易混淆 | Multi-Agent（去中心化协商）、固定 Prompt Chaining | 前者 Worker 自治且可对等协商，O-W 是中心化层级；后者步骤写死，O-W 的步骤运行时动态生成。 |

## 典型工程场景

- **编码 Agent 改多文件**：需求下来后先由 Orchestrator 判断要改哪些文件、各自改什么，分发给 Worker 并行修改，再综合成一次提交（Anthropic 博客给出的经典例子）。
- **深度研究 / Research Agent**：把一个研究问题拆成多个子查询，多个 Worker 并行检索不同信息源，Orchestrator 汇总去重、交叉验证后撰写报告。
- **多源信息聚合**：如竞品分析、尽调，拆成"按维度/按对象"的子任务并行收集，再统一成表格或结论。
- **复杂文档生成**：长报告按章节拆给不同 Worker 起草，Orchestrator 统一风格、消除重复、串成全文。
- **批量数据处理/标注**：对一批条目动态分片，Worker 并行处理，Orchestrator 聚合统计与异常复核。

## 适用边界

**适合使用：**
- 子任务数量/类型需看输入才能确定，无法预先写死流程。
- 子任务弱耦合、可并行，能用并发显著降低总延迟。
- 单上下文装不下或会导致推理退化，需要上下文隔离。
- 需要异构能力/模型分工，或综合多路结果才能得到答案。

**不适合使用：**
- 任务步骤固定、线性、短小——固定管道或单 Agent 更简单可靠。
- 子任务强依赖、必须严格串行——并行收益为零，徒增编排开销。
- 对成本/延迟/可预测性极敏感的场景——动态拆解带来额外 LLM 调用与不确定性。
- 子任务无法清晰界定边界或无法隔离上下文——拆了反而增加协调成本与出错面。

## 常见误区

- **以为拆得越细越好**：过度拆解会让子任务爆炸、Token 与综合成本飙升，还放大累积误差；粒度要匹配任务。
- **把它等同于 Multi-Agent**：它只是 Multi-Agent 的中心化层级特例，Worker 通常无状态、不互相通信，不等于对等协商的多智能体。
- **忽视综合阶段**：以为难点在拆解，实际最终质量更多由 synthesize 决定，冲突裁决与完备性校验最容易被忽略。
- **让 Worker 共享状态/互相感知**：这会破坏并行与隔离前提，引入竞态与上下文污染。
- **不设终止与预算**：Orchestrator 循环追加子任务却无上限，导致成本失控或不收敛。
- **误用于固定流程**：任务结构其实稳定，却套用动态编排，白白牺牲可预测性与可测试性。

## 我的结论

**该用**：当"要做哪几件事"必须在运行时看输入才知道、且这些事弱耦合可并行、单上下文又装不下时——Orchestrator-Worker 是性价比最高的结构。它用一次"拆解+综合"的额外开销，换来适应性、并行度和每个子任务的高信噪比。工程落地要点是：强约束结构化契约、给 Worker 最小必要上下文、把成本花在综合与评审上、设明确的终止与预算。

**不该用**：当流程本就固定、线性、短，或子任务强依赖必须串行时，不要为了"看起来智能"而引入动态编排；此时固定管道或单 Agent 更便宜、更可预测、更好测。一句话——**结构不确定才编排，结构确定就写死**。
