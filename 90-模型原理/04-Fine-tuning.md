# Fine-tuning / 微调

> **状态**：🟢 已理解 ｜ **深度**：C 理解概念 ｜ **更新**：2026-09-15
> **上级**：[90-模型原理](README.md) ｜ **依赖**：Pre-training

## 一句话定义

> 微调是在一个已完成预训练的模型基础上，用规模更小、更贴合目标任务的数据继续训练，从而更新模型权重、让模型适配特定任务、领域或风格的过程。

## 解决的问题

> 预训练模型虽然掌握了通用语言能力，但对特定领域术语、企业私有知识、固定输出格式或特定任务（分类、抽取、风格模仿）往往表现不稳定。
> 在微调出现之前，要让模型做好某个专门任务，只能从头训练一个专用模型——数据和算力成本极高，而且难以复用通用模型已学到的世界知识。微调让人们可以"站在巨人肩膀上"，用少量标注数据和相对低的算力，把通用能力迁移到具体任务上。

### 微调与 Prompt / RAG 的取舍

三者解决的问题层次不同，常常组合使用而非互斥：

| 手段 | 改变什么 | 擅长 | 不擅长 |
| --- | --- | --- | --- |
| Prompt / 上下文工程 | 不改权重，只改输入 | 快速迭代、零训练成本、通用任务 | 复杂稳定行为、超长知识注入、严格格式 |
| RAG（检索增强） | 不改权重，运行时注入外部知识 | 时效性强、可更新的事实性知识、可溯源 | 改变模型的"能力/风格"、推理模式 |
| 微调 | 更新模型权重 | 固化行为/风格/格式、领域语感、压缩长提示 | 注入频繁变动的事实、需要可追溯来源 |

工程判断顺序通常是：先 Prompt，再 RAG，最后才考虑微调。原则是"知识问题用 RAG，行为/风格/格式问题用微调"。事实会频繁更新时优先 RAG，因为微调把知识写死进权重后更新成本高且容易过期。

### 什么场景下必须微调

- 需要稳定、可复现的输出格式或行为，Prompt 反复调仍不稳定（如严格 JSON schema、固定话术）。
- 领域语言分布与通用语料差异大（医疗、法律、金融、代码特定框架），模型缺乏"语感"。
- 希望大幅压缩提示长度、降低每次推理的 token 成本（把冗长指令固化进权重）。
- 蒸馏场景：用大模型的输出训练小模型，在特定任务上以更低延迟/成本接近大模型效果。
- 对延迟和隐私敏感、必须本地部署小模型并保证专项质量时。
- 反例：如果任务本质是"需要最新/可变事实"，这不是必须微调的场景，RAG 更合适。

### 微调的成本与风险

- **数据成本**：高质量标注数据是主要瓶颈，数据质量比数量更关键，脏数据会直接污染模型行为。
- **算力成本**：全量微调需要与模型规模相当的显存和训练时间；参数高效方法（LoRA 等）可显著降低。
- **灾难性遗忘**：过度微调会损害模型原有的通用能力，需控制学习率、步数并保留部分通用数据。
- **过拟合**：小数据集上容易记住训练样本而非学到规律，需要验证集和早停。
- **维护成本**：底座模型升级、业务需求变化都可能要求重新微调，形成长期负担。
- **评估风险**：微调效果需要可靠的离线评估集 + 线上监控，否则"感觉变好"难以证实。
- **安全/对齐风险**：不当微调可能破坏原模型的安全对齐（越狱、有害输出）。

### LoRA 等参数高效方法的基本思想

PEFT（Parameter-Efficient Fine-Tuning）的核心思想是：冻结原始模型的绝大部分权重，只训练少量新增或选中的参数，从而大幅降低显存与存储成本。

- **LoRA（Low-Rank Adaptation）**：假设权重更新量 ΔW 是低秩的，于是不直接更新原权重 W，而是在旁路学习两个小矩阵 A、B（ΔW = B·A，秩 r 远小于原维度）。推理时 W + BA 等价于微调后的权重。只需训练和保存这对小矩阵，参数量常只占原模型的 0.1%~1%。
- **QLoRA**：在 LoRA 基础上把底座模型量化到 4-bit 存储，进一步把微调所需显存压到单张消费级显卡可承受的范围。
- **其他**：Adapter（插入小型瓶颈层）、Prefix/Prompt Tuning（只学习少量可训练的前缀向量）等。
- 工程优势：一个底座可挂载多个 LoRA 适配器按需切换；适配器文件小、便于分发和版本管理。

## 核心内容

- **定位**：迁移学习的一种，位于预训练之后、部署之前，是把通用模型"收窄"到具体任务的手段。
- **主流方式**：
  - 全量微调（Full Fine-tuning）：更新全部权重，效果上限高但成本大、易遗忘。
  - 参数高效微调（PEFT / LoRA、QLoRA、Adapter、Prefix Tuning）：只训练少量参数，成本低、可插拔。
- **按目标分**：
  - SFT（监督微调）：用「输入—期望输出」对，教模型遵循指令、模仿风格/格式。
  - 偏好对齐（RLHF / DPO 等）：用人类偏好数据进一步对齐"好/坏回答"。
- **关键流程**：明确目标 → 构造高质量数据集 → 选择底座与方法 → 设定超参（学习率、epoch、batch）→ 训练 → 在独立验证集评估 → 迭代 → 部署与监控。
- **数据原则**：质量 > 数量；覆盖目标分布；格式一致；留出验证集防过拟合。
- **典型超参注意点**：微调学习率通常远小于预训练；epoch 过多会过拟合与遗忘。

## 典型工程场景

- 企业客服/话术机器人：固化统一的回复风格与品牌话术。
- 结构化信息抽取：让模型稳定输出符合业务 schema 的 JSON（订单、合同、病历字段）。
- 垂直领域问答与写作：法律、医疗、金融等领域语感和术语适配。
- 代码助手定制：适配企业内部框架、API、编码规范。
- 文本分类/意图识别：工单路由、情感分析、内容审核等高吞吐任务。
- 模型蒸馏/小模型替代：用大模型数据微调小模型，降低线上延迟与成本。
- 多语言/小语种适配：增强模型在特定语言上的表现。

## 适用边界

**适合使用**

- 需要稳定、可复现的输出格式或固定行为/风格。
- 领域语言分布与通用语料差异明显，Prompt+RAG 仍不达标。
- 有足够量、高质量且可持续维护的标注数据。
- 想压缩长提示、降低单次推理成本，或需本地化小模型。
- 任务目标相对稳定，不会频繁变化。

**不适合使用**

- 核心诉求是注入频繁更新或需溯源的事实知识（优先 RAG）。
- 数据量少、质量差或无法持续维护。
- 需求尚未稳定、仍在快速探索阶段（先用 Prompt 迭代）。
- 缺乏可靠评估集，无法衡量微调是否真的变好。
- 一次性/低频小任务，微调的投入产出不划算。

## 常见误区

- **"效果不好就先微调"**：多数问题应先用 Prompt 和 RAG 解决，微调是成本更高的最后手段。
- **"微调能让模型记住最新知识"**：微调擅长改变行为/风格，不适合注入高频变动的事实，事实注入应交给 RAG。
- **"数据越多越好"**：少量高质量、分布正确的数据往往优于海量脏数据；质量优先。
- **"微调只增不减"**：过度微调会导致灾难性遗忘，损害原有通用能力。
- **"LoRA 就是打折版全量微调"**：PEFT 是不同范式，很多任务上效果接近全量且更易维护，并非一味"更差"。
- **"微调完就一劳永逸"**：底座升级、业务变化、数据漂移都需要重新评估甚至重训。
- **"微调一定提升安全性"**：不当数据反而可能破坏原模型的安全对齐。

## 我的结论

> 微调是把"行为、风格、格式、领域语感"固化进模型权重的手段，而不是注入事实知识的手段。
> **该用的时候**：Prompt 和 RAG 都试过仍无法稳定达到目标行为/格式，且手上有足够量、高质量、可持续维护的标注数据，任务目标也相对稳定——此时微调（优先 LoRA 这类参数高效方法）能带来稳定收益并可能降低长期推理成本。
> **不该用的时候**：核心需求是最新或可溯源的事实知识、数据不足或易变、需求尚不稳定、缺乏可靠评估——这些情况下微调投入大、风险高（遗忘、过拟合、维护负担），应退回到 Prompt + RAG。
> 一句话：**知识问题用 RAG，行为问题用微调；能不改权重就先不改。**
