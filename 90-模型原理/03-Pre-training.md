# Pre-training / 预训练

> **上级**：[90-模型原理](README.md) ｜ **依赖**：无

## 一句话定义

> 预训练是在海量无标注（或弱标注）文本/多模态语料上，用自监督目标（如预测下一个 token）大规模训练一个基础模型，使其习得语言、世界知识与通用表征，作为后续微调与对齐的底座。

## 解决的问题

> 在预训练范式之前，NLP 任务普遍依赖针对单一任务的监督学习：每个任务都要人工标注大量数据、单独设计模型并从零训练。这导致标注成本高、样本利用率低、模型无法迁移、小数据任务效果差。预训练把"从数据中学习通用知识"和"适配具体任务"解耦——先用近乎免费的无标注语料学到可复用的表征，再用少量标注数据微调，大幅降低了单任务的数据和工程门槛，并带来了跨任务的泛化与涌现能力。

### 预训练的目标是什么

- 工程目标：得到一个具备通用语言理解/生成能力、广泛世界知识和良好表征的**基础模型（base model）**，作为后续 SFT、RLHF、领域微调的底座，而不是直接解决某个具体任务。
- 训练目标函数：主流是**自监督**，用数据自身构造标签，无需人工标注。
  - 自回归语言建模（GPT 系）：给定前文预测下一个 token，最小化交叉熵（等价于最小化困惑度 perplexity）。
  - 掩码语言建模（BERT 系）：随机掩盖部分 token 并还原，适合理解类任务。
  - 多模态/其他：图文对比（CLIP）、去噪、span 预测（T5）等。
- 本质：通过"预测被遮住的内容"这一简单目标，逼迫模型压缩语料中的统计规律、语法、事实和推理模式，从而在参数里隐式存储知识。

### 数据和算力如何影响能力

- **Scaling Law（扩展律）**：模型能力（以 loss/perplexity 衡量）随参数量 N、数据量 D、计算量 C 呈平滑的幂律下降。能力提升是可预测的，而非偶然。
- **三者需协同**：Chinchilla（DeepMind, 2022）指出，在固定算力预算下，参数量与训练 token 数应**近似等比例增长**（约 20 tokens/参数），早期大模型普遍"参数过大、数据不足"而训练不充分。

| 因素 | 影响 |
| --- | --- |
| 数据规模 | token 越多，覆盖的知识/语言现象越全，loss 越低；但受限于高质量语料总量 |
| 数据质量 | 去重、清洗、过滤低质内容比单纯堆量更关键；污染/重复会损害泛化 |
| 数据多样性 | 代码、多语言、数学等配比直接决定下游特定能力 |
| 算力/参数 | 决定模型容量上限与能承载的数据量；不足则欠拟合、浪费数据 |

- 工程含义：算力和高质量数据是硬约束。盲目加大模型而不配套数据，或数据脏乱，都会使实际效果偏离 scaling law 的理论曲线。

### 为什么预训练决定了模型的能力上限

- **知识在预训练阶段注入**：模型的世界知识、语言能力、推理模式几乎全部来自预训练语料。后续 SFT/RLHF 主要是**对齐与激发**已有能力（让它按指令、按人类偏好输出），而非注入大量新知识。
- **能力的"天花板"由底座决定**：如果某类知识/能力在预训练中几乎没出现（如某冷门领域、某种推理），微调很难凭空造出来；微调更多是"解锁"而非"扩容"。
- **缺陷会被继承**：预训练数据的偏见、知识截止日期、事实错误会沉淀进参数，下游阶段难以彻底消除。
- **工程推论**：想显著提升模型天花板，通常要回到预训练/继续预训练（continued pre-training）层面补数据、补算力；只靠 prompt 或少量微调无法突破底座限制。

## 核心内容

- **自监督目标**：从无标注数据自动构造预测任务（下一 token / 掩码还原），避免人工标注瓶颈。
- **Transformer 架构**：几乎所有现代预训练模型的骨架，依赖注意力机制并行处理长序列。
- **Tokenization**：用 BPE/BBPE/SentencePiece 等把文本切成子词单元，是模型的输入基本单位。
- **数据管道**：抓取 → 清洗/去重 → 质量过滤 → 配比混合 → 分片，是决定效果的核心工程。
- **大规模分布式训练**：数据并行 / 张量并行 / 流水线并行 + 混合精度 + 梯度检查点，支撑千亿参数训练。
- **优化**：AdamW、学习率 warmup + 余弦衰减、长时间单/少 epoch 训练（高质量数据往往只过 1~2 遍）。
- **评估**：以验证集 loss/perplexity 为主，辅以下游基准（MMLU、HellaSwag 等）判断能力。
- **产物**：base model（基础模型），后续进入对齐流程。

## 典型工程场景

- 大厂/研究机构从零训练通用大模型（如构建自研基础模型）。
- 针对特定领域（医疗、法律、金融、代码）在开源 base 上做**继续预训练**，注入领域知识。
- 多语言/小语种模型构建，通过调整语料配比提升目标语言能力。
- 代码大模型：在通用语料中加大高质量代码配比以增强编程能力。
- 评估与选型：根据 scaling law 和基准结果，判断用多大参数、多少数据训练才划算。

## 适用边界

**适合使用**

- 需要一个具备广泛通用能力、可服务多任务的基础模型时。
- 拥有海量语料 + 大规模算力，且目标是长期可复用的底座。
- 需要注入大量新知识/新语言/新领域（继续预训练比微调更合适）。

**不适合使用**

- 只有少量标注数据、只解决单一具体任务——直接用现成模型微调或 prompt 更高效。
- 算力/数据不足：从零预训练成本极高（数百万美元级），绝大多数团队应复用开源 base。
- 只想改变输出风格、遵循指令或对齐偏好——那是 SFT/RLHF 的职责，不该用预训练解决。

## 常见误区

- 误以为"微调能给模型注入大量新知识"——实际上知识主要来自预训练，微调以激发/对齐为主。
- 误以为"参数越大越好"——忽视 Chinchilla 结论，数据不足会导致训练不充分、算力浪费。
- 混淆预训练与微调/对齐，把 base model 当成能直接听指令的助手（base model 往往不擅长遵循指令）。
- 认为"数据越多越好"而忽视质量与去重——脏数据、重复、测试集污染会显著损害效果。
- 把 perplexity 下降直接等同于下游任务一定变好——相关但不完全等价，需配合基准评估。

## 我的结论

> 预训练是模型能力的"地基"：它决定了知识广度、推理潜力和能力天花板，而对齐只是在这个地基上装修。**该用预训练（或继续预训练）的时机**：当你要构建长期复用的通用/领域底座，且确实有海量高质量数据和足够算力，或需要注入靠微调无法实现的大规模新知识。**不该用的时机**：数据/算力有限、只解决单一任务、只需改风格或对齐行为时——这些场景应优先复用开源 base + 微调/RAG/prompt，从零预训练在经济性上几乎总是错误选择。工程上先问"能力缺口是知识层（找预训练）还是行为层（找对齐）"，再决定投入方向。
