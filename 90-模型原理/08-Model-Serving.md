## 一句话定义

> 模型服务（Model Serving）是把训练好的模型包装成一个可持续运行、可被并发调用的在线服务，负责接收请求、调度算力执行推理、并在延迟与吞吐约束下稳定返回结果。

## 解决的问题

> 在它出现之前，模型往往只以"离线脚本 + 本地加载权重"的方式运行：每来一个请求就临时加载一次模型、单条串行执行、无法并发、无法扩缩容、没有限流和监控。工程上面临几类麻烦：
> - 冷启动慢、显存/内存被反复占用，资源利用率极低。
> - 无法应对突发流量，延迟抖动大，缺乏排队、超时、重试、降级等保护。
> - 模型与业务代码耦合，升级/回滚/多版本灰度困难。
> - 缺乏统一的接口协议、鉴权、计量和可观测性，难以作为稳定的生产依赖被其他系统调用。

### 模型服务的部署形态

主要分为几种形态，按"谁持有模型、运行在哪里"划分：

| 形态 | 说明 | 典型场景 |
| --- | --- | --- |
| 托管 API（Serverless/SaaS） | 调用厂商提供的 HTTP 接口，按量计费，无需管理 GPU | 快速接入 GPT/Claude/文心等通用大模型 |
| 自建在线服务（常驻进程 + GPU 池） | 自己拉起推理服务（vLLM、TGI、Triton 等），常驻加载权重 | 对数据合规、成本、定制化有要求的中大规模场景 |
| 边缘/端侧部署 | 模型量化后跑在终端或边缘节点 | 低延迟、离线、隐私敏感（手机、车机、IoT） |
| 批量/离线推理 | 非在线，走任务队列批处理 | 大规模数据打标、Embedding 预计算 |

关键工程要素：权重常驻（避免反复加载）、多副本 + 负载均衡、健康检查与自动扩缩容、模型多版本管理与灰度、GPU 显存与 KV Cache 管理。

### 吞吐与延迟的权衡（batching）

吞吐（throughput，单位时间处理的 token/请求数）和延迟（latency，单条请求的响应时间）通常是此消彼长的关系，batching 是核心调节手段：

- **静态 batching**：攒够 N 条或等待 T 毫秒再一起算。batch 越大，GPU 利用率和吞吐越高，但队首请求等待时间变长，尾延迟升高。
- **动态/连续 batching（continuous batching）**：LLM 推理的主流做法（vLLM 等）。在 token 级别而非请求级别调度，已完成的序列立即退出、新请求随时插入，显著提升 GPU 利用率而不必等整个 batch 结束。
- **关键指标**：对话类场景更关注 TTFT（首 token 延迟）和 TPOT（每个输出 token 的间隔）；批处理场景更关注整体吞吐和单位成本。
- **权衡取舍**：面向交互的在线场景应限制最大 batch 和最大等待时间以保尾延迟；面向离线/批量的场景可放大 batch 换吞吐。配合 PagedAttention、KV Cache 复用、量化等进一步提升。

### 自建 vs 调用 API 的取舍

| 维度 | 调用托管 API | 自建服务 |
| --- | --- | --- |
| 上手速度 | 快，几行代码即可 | 慢，需搭建 GPU、推理框架、运维 |
| 成本结构 | 按 token/调用量付费，低量省钱、高量可能更贵 | 前期固定投入高，规模化后单位成本可摊薄 |
| 数据合规 | 数据出域，受厂商条款约束 | 数据可留在内网，合规可控 |
| 定制能力 | 受限于厂商开放的参数与模型 | 可用自有/微调模型，可深度优化 |
| 稳定性/限流 | 依赖厂商 SLA 与配额 | 自己掌控，但要自己保障可用性 |

一般判断：原型验证、流量不确定、无运维能力时优先用 API；当调用量大且稳定、有强合规要求、需要自有微调模型或要压成本时，自建更划算。常见折中是混合部署——通用能力走 API，核心/敏感/高频链路自建。

## 核心内容

- **接口层**：统一的 HTTP/gRPC 接口与协议（如 OpenAI 兼容接口、Triton 的 KServe 协议），负责鉴权、限流、参数校验、流式返回（SSE）。
- **调度与批处理**：请求排队、动态/连续 batching、优先级与超时控制，是吞吐与延迟权衡的核心。
- **推理执行引擎**：加载权重并执行前向计算，涉及算子优化、算子融合、CUDA Graph、量化（INT8/FP8/GPTQ/AWQ）。
- **显存与缓存管理**：KV Cache、PagedAttention、Prefix Cache 复用，决定并发上限与成本。
- **扩缩容与路由**：多副本、负载均衡、按队列长度/GPU 利用率自动扩缩容。
- **模型版本治理**：多版本共存、灰度/金丝雀发布、A/B、快速回滚。
- **可观测性与保护**：延迟/吞吐/错误率/GPU 利用率监控，限流、熔断、降级、重试、超时。

## 典型工程场景

- 对话/Copilot 类产品：高并发、强调首 token 延迟与流式输出。
- RAG 问答与检索增强应用：模型服务 + 向量检索组合，需稳定低延迟。
- 批量文本处理：离线打标、摘要、Embedding 预计算，追求吞吐与单位成本。
- 多租户 AI 平台：统一网关 + 多模型多版本，按团队限流计量。
- 私有化/合规部署：金融、政务、医疗等要求数据不出域的自建推理服务。

## 适用边界

**适合使用**

- 模型需要被多个系统/用户长期、并发调用，且对延迟和可用性有要求。
- 需要统一的鉴权、限流、计量、监控与多版本灰度治理。
- 流量较大、需要通过 batching/缓存/扩缩容来优化吞吐与成本。

**不适合使用**

- 一次性离线实验或极低频调用，直接本地加载脚本运行即可，无需服务化。
- 团队无 GPU/运维能力且流量小又不确定，直接用托管 API 更划算（无需自建 Serving）。
- 端侧/离线场景更适合把模型量化后嵌入应用，而非常驻在线服务。

## 常见误区

- 把"推理"等同于"模型服务"：只跑通一次前向，不代表能稳定承载并发生产流量。
- 盲目加大 batch 以为能普遍提速：会抬高尾延迟，交互场景反而伤体验。
- 忽视 KV Cache/显存管理：并发上限和成本很大程度由显存与缓存策略决定，而非单纯算力。
- 认为自建一定更便宜：低流量或流量不稳时，自建的固定成本与运维投入往往高于按量付费的 API。
- 缺少限流/降级/超时等保护：突发流量下服务被打垮，缺乏优雅降级。
- 不做版本治理：模型升级直接覆盖，出问题无法快速回滚、无法 A/B 对比。

## 我的结论

> 当模型要成为被多方长期并发调用的"生产依赖"、且对延迟、可用性、成本或合规有明确要求时，就应该做模型服务化；此时 batching、KV Cache、扩缩容、版本治理和可观测性是绕不开的工程内核。
> 反过来，若只是一次性实验、极低频调用，或团队无 GPU/运维能力且流量小又不稳定，就不该自建 Serving——直接本地脚本或调用托管 API 更省心省钱。实践上最稳妥的路径是先用 API 验证需求与流量，待调用量稳定、成本或合规压力显现后，再迁移到自建或混合部署。
