> **上级**：[07-Workflow编排](README.md) ｜ **依赖**：Workflow、Agent Loop

## 一句话定义

> Human-in-the-loop（HITL，人在回路）是一种在 Agent/Workflow 自动执行流程中，于特定节点主动暂停、把控制权交回给人类做确认、修改或决策，再根据人的输入继续执行的编排机制。

## 解决的问题

> 在纯自动化的 Agent Loop 中，模型可能产生幻觉、误判意图或在不可逆操作上出错，而这些错误往往要到造成实际后果（误删数据、错误支付、对外发错消息）后才被发现。
> 此前的做法要么是全自动（风险不可控、用户不敢授权高权限操作），要么是全人工（每一步都要人盯着，失去了自动化价值）。HITL 在两者之间提供了一个可调节的"信任边界"：只在关键/高风险/低置信度节点请求人工介入，其余步骤仍自动完成。它同时解决了合规审计（谁批准了什么）与可控授权（人类保留最终决定权）的问题。

### 哪些节点必须引入人工确认

判断是否需要人工确认，核心看三个维度：**不可逆性、影响范围、置信度**。

- **不可逆/高代价操作**：删除数据、支付转账、发布上线、对外发送邮件/消息、修改生产配置、授予权限——一旦执行无法轻易回滚。
- **高影响范围操作**：批量操作（影响大量记录/用户）、涉及资金或法律后果、触及敏感数据（PII、密钥、财务）。
- **低置信度决策点**：模型自评置信度低、工具调用参数来自不可信输入、意图存在歧义、检索证据不足。
- **策略/合规要求**：行业监管或企业内控明确要求人工审批的环节（如大额支出、合同签署）。

工程实践上通常用一张"动作风险矩阵"来声明哪些工具/动作需要确认，而不是让模型临时决定——确认点应是**系统强制的策略**，而非依赖模型自觉。

### 审批的粒度与体验如何平衡

粒度过细会造成"确认疲劳"（用户机械点同意，失去把关意义），过粗又会漏掉关键风险。平衡手段：

| 手段 | 说明 |
| --- | --- |
| 分级确认 | 按风险分级：低风险自动放行、中风险轻确认、高风险强确认（甚至多人审批） |
| 批量/计划确认 | 把多步操作汇总成一个"执行计划"让人一次性审阅批准，而非逐步打断 |
| 自动批准阈值 | 金额/数量低于阈值自动执行，超过才升级到人工 |
| 预览与 diff | 展示操作前后差异、受影响对象清单，降低审阅成本 |
| 可配置信任 | 允许用户对某类操作"记住选择/本会话免确认"，逐步放宽 |
| 超时与默认值 | 设置审批超时策略（超时默认拒绝/升级），避免流程无限挂起 |

核心原则：**让人在正确的时刻看到足够的上下文做出高质量决策**，而不是频繁打断。

### 人工介入如何影响 Agent 状态与恢复

人工确认意味着流程会被**长时间挂起**（人可能几秒也可能几天后才响应），这对执行引擎提出了状态持久化要求：

- **状态必须外部化持久化**：暂停时需把 Agent 的完整上下文（对话历史、中间变量、待执行动作、工具调用栈）序列化到持久存储（DB/状态快照），不能只靠内存。
- **可恢复/可续跑**：收到人工输入后，引擎按持久化的 checkpoint 恢复执行，而非从头重跑。LangGraph 的 `interrupt` + checkpointer、Temporal 的持久化工作流是典型实现。
- **人的输入作为新事件注入**：批准/拒绝/修改后的参数作为一个事件写回状态，Agent 据此决定下一步（继续、改参数重试、放弃分支）。
- **幂等与并发**：挂起期间外部世界可能变化，恢复前需校验前置条件是否仍成立；回调要幂等，防止重复提交导致重复执行。
- **超时与补偿**：长时间无响应需有超时与补偿/回滚策略，避免资源长期锁定。

### 高风险操作（删除 / 支付 / 对外发送）的确认机制

对这类操作，确认不是"弹个框点确定"那么简单，推荐一套纵深防御：

- **显式确认 + 结构化预览**：展示将要执行的确切操作（删除哪些记录、付给谁多少钱、给谁发什么内容），而非自然语言概述。
- **人类重述/二次输入**：高危操作要求人工输入确认码、重新键入金额或勾选逐项，防止条件反射式点同意。
- **白名单与限额**：收款方白名单、单笔/每日限额、删除范围上限等硬约束，即便人批准也不能越界。
- **Dry-run / 可回滚**：先执行模拟（预估影响），或采用软删除、延迟发送（可撤回窗口）、事务+回滚。
- **双人复核（4-eyes）**：极高风险（大额支付、生产删库）要求第二人独立批准。
- **完整审计日志**：记录谁、何时、基于什么上下文批准了什么，满足合规与事后追溯。
- **最小权限**：Agent 本身持有的凭证应最小化，关键凭证的使用由人类网关放行。

## 核心内容

- **信任边界（trust boundary）**：在自动流程中显式划定"哪里需要人"，其余自动化，是 HITL 的本质。
- **三类人类角色**：审批者（approve/reject）、修正者（edit 中间结果或参数）、决策者（在多个分支间选择）。
- **中断原语（interrupt）**：执行引擎在节点处暂停、抛出中断、把待决请求推给人、等待回填。
- **状态持久化与恢复**：checkpoint 快照 + 事件回填 + 续跑，支撑长时间异步等待。
- **风险策略层**：动作风险分级、自动批准阈值、限额/白名单等声明式策略，决定何时触发人工。
- **交互通道**：确认 UI、聊天内按钮、工单/审批系统、邮件回调等承载人机交互。
- **审计与可观测**：对每一次人工决策留痕，支持回放与合规审查。
- **反馈闭环**：人工修正数据可回流用于评估、提示优化乃至后续训练（HITL 在数据标注语境下的另一层含义）。

## 典型工程场景

- **AI 编码助手**：Agent 生成代码/执行命令前，让开发者审阅 diff、批准运行终端命令或写文件（如各类编码 Agent 的"确认执行"）。
- **企业自动化/RPA + Agent**：自动处理工单，但退款、合同、权限变更等关键步骤转人工审批。
- **金融/支付**：Agent 发起转账、报销、交易前的多级审批与限额确认。
- **客服与对外沟通**：AI 起草回复，坐席审核后再发送给客户；对外邮件/公告发布前人工把关。
- **数据运维**：Agent 执行数据库变更、删除、迁移脚本前要求 DBA 确认。
- **内容发布/营销**：自动生成文案，发布到社媒/官网前经人工审核。
- **医疗/法律等高风险领域**：模型给出建议，最终由专业人员确认后才生效。

## 适用边界

**适合使用**

- 操作不可逆或代价高（删除、支付、发布、对外发送）。
- 受监管/合规要求必须有人工审批的环节。
- 模型置信度低、输入不可信或意图有歧义的决策点。
- 需要积累人类反馈以持续改进系统的场景。
- 用户尚未建立对 Agent 的充分信任、需要渐进放权的早期阶段。

**不适合使用**

- 高频、低风险、可逆的操作（如只读查询、内部草稿生成），加确认只会拖慢并造成确认疲劳。
- 要求极低延迟的实时自动化场景（人工介入的等待不可接受）。
- 人工无法在合理时间内响应、或人工判断并不比模型更可靠的环节。
- 把 HITL 当成掩盖模型质量差的创可贴——根因应通过改进模型/护栏解决。

## 常见误区

- **以为加了确认弹窗就安全**：若预览信息不足或用户习惯性点同意，确认形同虚设。
- **让模型自行决定是否需要确认**：确认点应是系统强制策略，否则模型可能跳过关键确认。
- **忽视状态持久化**：把挂起状态只放内存，进程重启或超时后无法恢复，流程丢失。
- **粒度一刀切**：对所有操作统一确认，导致确认疲劳或该拦的没拦住。
- **混淆 HITL 与 human-on-the-loop**：前者需主动批准，后者只是监控可叫停，安全模型不同。
- **忽略超时与并发**：挂起期间不校验前置条件、回调不幂等，恢复后执行到过期/重复的操作。
- **把人工确认当免责**：缺乏审计留痕时，事后无法追溯谁批准了什么。

## 我的结论

> HITL 的本质是**用一个可配置的信任边界，在自动化效率与风险可控之间做权衡**。
> **该用它**：当动作不可逆、影响范围大、涉及合规，或模型置信度不足时——在这些节点强制人工确认，并配套结构化预览、限额/白名单、状态持久化与审计。
> **不该用它**：在高频、可逆、低风险的操作上，或在延迟敏感的实时链路里；此时应靠自动化护栏和模型质量而非人工打断来保证正确性。
> 判断准则一句话：**把人放在"错一次就很贵、或法规要求有人负责"的那几个点上，其余交给自动化**；并随着信任建立逐步放宽确认粒度。
