# Workflow vs Agent

> **状态**：🟢 已理解 ｜ **深度**：A 深入掌握 ｜ **更新**：2026-09-15
> **上级**：[07-Workflow编排](README.md) ｜ **依赖**：Workflow、Agent 是什么

## 一句话定义

> Workflow 是由人预先编排好步骤与跳转的"确定性控制流"，Agent 是把控制流交给模型、让它在运行时自主决定下一步做什么的"动态控制流"；二者的本质区别在于**由谁来决定执行路径**。

## 解决的问题

> 在二者被明确区分之前，工程上常把所有 LLM 任务一股脑塞进一个"大 prompt + 自由循环"的 Agent 里：结果是简单任务也要靠模型反复推理，带来高延迟、高成本、不可复现和难以调试的问题；反过来，用纯脚本流水线又无法处理需要语义理解、动态分支和开放式决策的任务。把"确定性编排"和"自主决策"拆成两种范式，让团队能按任务特征选择成本/可控性/灵活性的平衡点。

### 什么信号说明该用 Workflow 而不是 Agent

- **路径可枚举**：任务步骤和分支条件在设计期就能写清楚（如"抽取字段 → 校验 → 入库 → 通知"），不需要运行时才知道下一步。
- **强确定性/可复现要求**：同样输入必须得到同样流程，便于审计、回放、单元测试。
- **低容错预算**：金融、合规、支付等场景不接受模型"自由发挥"带来的不确定跳转。
- **成本/延迟敏感**：Workflow 每一步只在需要语义能力的节点调用 LLM，其余用普通代码，调用次数可控。
- **信号速记**：如果你能画出一张稳定的流程图，就应该用 Workflow 把它固化下来，而不是让 Agent 每次重新"推理出"这张图。

### 什么信号说明必须用 Agent

- **路径不可预先枚举**：下一步依赖中间结果，分支空间大或开放（如"排查这个线上故障"、"根据代码库完成这个需求"）。
- **需要动态使用工具并对结果做反思**：模型要根据工具返回决定继续、重试还是换策略（ReAct / plan-act-observe 循环）。
- **目标导向而非步骤导向**：用户给的是目标（"把测试修绿"），而不是明确步骤。
- **环境高度不确定**：输入形态多变、无法穷举规则，用规则引擎会写不完。
- **信号速记**：当"该走哪条路"本身就需要智能判断时，才把控制权交给模型。

### 两者结合的边界在哪里（Agentic Workflow）

实践中最稳健的架构往往是**用 Workflow 做骨架、在局部节点嵌入 Agent**，或反过来**让 Agent 调用一批被封装成"确定性工具"的 Workflow**。划分边界的原则：

| 维度 | 交给 Workflow | 交给 Agent |
| --- | --- | --- |
| 控制流 | 整体编排、关键跳转、重试/超时/回退策略 | 单个开放子任务内部的决策 |
| 可靠性 | 需要审计、幂等、事务的环节 | 容忍试错、可观测兜底的环节 |
| 边界划法 | 把"稳定、可枚举"的部分固化成流程 | 把"开放、需推理"的部分圈成一个受限 Agent |

边界的核心是**收敛 Agent 的自主度**：给它有限工具集、步数上限、明确的成功判定和外层守卫，让不确定性被关在一个可控的盒子里，而盒子之间用确定性 Workflow 连接。

### 选错的代价分别是什么

- **该用 Workflow 却用了 Agent**：延迟和 token 成本成倍上升；结果不可复现、难以回归测试；偶发的"离谱决策"进入生产；调试要读一长串推理轨迹而非确定日志。
- **该用 Agent 却用了 Workflow**：规则和分支越写越多、维护成本爆炸（"if 地狱"）；无法覆盖长尾输入，一遇到没预设的情况就失败；需求一变就要重写流程图，交付变慢。
- **共性教训**：选错的本质是把"决策权"放错了位置——要么让模型承担了本该由代码保证的确定性，要么让代码去模拟本该由模型完成的开放推理。

## 核心内容

- **控制流归属**：Workflow 的下一步由代码/配置决定；Agent 的下一步由模型在循环中决定（感知→决策→行动→观察）。
- **Workflow 构成**：节点（含 LLM 节点与普通代码节点）、有向边/条件分支、状态传递、重试与超时、人工介入点；本质是一张可视化/可声明的 DAG 或状态机。
- **Agent 构成**：目标、上下文/记忆、工具集（function calling）、决策循环、停止条件（成功判定或步数上限）、守卫与回退。
- **自主度是一条光谱**，不是二选一：从纯脚本 → 条件分支 Workflow → 带 LLM 路由的 Workflow → 受限 Agent → 完全自主 Agent，自主度递增、可控性递减。
- **常见组合模式**：Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer（多为 Workflow 模式），以及把这些模式作为工具供 Agent 调度。
- **工程取舍三角**：灵活性 ↔ 可控性/可复现 ↔ 成本/延迟，范式选择就是在这个三角里取点。

## 典型工程场景

- **文档/工单处理流水线**：抽取 → 分类 → 校验 → 入库 → 通知，用 Workflow；仅在"分类/抽取"节点调用 LLM。
- **客服与问答路由**：先用 Routing Workflow 判断意图，再把开放式"疑难问题排查"交给一个受限 Agent。
- **编码助手 / 自动修复**：面对"实现这个需求 / 修复这个 bug"这类开放目标，用 Agent 做探索-编辑-运行测试的循环。
- **数据/报表 ETL 与定时任务**：强调幂等、可复现、可审计，天然属于 Workflow。
- **研究型/调查型任务**（深度检索、竞品分析、故障根因定位）：路径不可预设，适合 Agent，外层用 Workflow 管控阶段与预算。
- **营销内容批量生成**：Prompt Chaining / Parallelization 等 Workflow 模式即可满足，无需 Agent 自主度。

## 适用边界

**适合使用（指倾向 Workflow）**

- 步骤、分支在设计期可枚举，流程稳定且很少变。
- 需要可复现、可审计、可单测，容错预算低。
- 成本/延迟敏感，希望精确控制 LLM 调用次数。
- 团队需要清晰的可视化编排与明确的责任边界。

**不适合使用（指此时应转向 Agent 或 Agentic Workflow）**

- 下一步依赖运行时中间结果，路径无法预先穷举。
- 目标开放、输入长尾、规则写不完。
- 需要模型反思工具结果并自主调整策略。
- 任务探索性强、允许试错且有可观测兜底。

## 常见误区

- **"Agent 更先进，所以都应该用 Agent"**：Agent 不是升级版 Workflow，而是另一种取舍；多数生产任务用 Workflow 更稳更省。
- **"带 LLM 的流程就是 Agent"**：只要路径由代码决定，哪怕每个节点都调模型，它仍是 Workflow。
- **"Agent 等于一个大 prompt + while 循环"**：真正可用的 Agent 需要工具约束、停止条件、守卫和可观测性，否则极易发散、死循环或烧钱。
- **"二选一"思维**：现实多是 Agentic Workflow 的混合体，自主度是连续光谱而非开关。
- **忽视失败模式差异**：Workflow 的风险是"覆盖不全/僵化"，Agent 的风险是"不可预测/不可复现"，二者需要不同的测试与监控手段。

## 我的结论

> 默认先用 Workflow，只有当"该走哪条路"本身需要智能判断、且路径无法预先枚举时，才把那一段控制权交给 Agent。
>
> 判断口诀：**能画出稳定流程图的，固化成 Workflow；画不出、要靠运行时推理才知道下一步的，交给受限 Agent。** 最佳工程形态通常是"Workflow 做骨架、Agent 做局部"，并始终给 Agent 加上工具白名单、步数上限、成功判定与外层兜底——把不确定性关进可控的盒子，而不是让它蔓延到整个系统。
