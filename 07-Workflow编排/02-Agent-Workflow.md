## 一句话定义

> Agent Workflow 是一种以 LLM 为决策核心、由模型在运行时自主规划步骤并调用工具来逼近目标的任务编排范式——流程走向由模型根据中间结果动态决定，而非由开发者预先写死的固定路径。

## 解决的问题

> 传统的固定 Workflow（DAG / 状态机）要求开发者在编码期就穷举所有分支和步骤顺序，这在面对以下场景时力不从心：
>
> - **路径不可预先枚举**：任务步骤数量、顺序依赖输入内容（如"排查这个线上故障"），无法用静态流程图表达。
> - **需要边做边看**：下一步该做什么取决于上一步工具返回的结果（搜索到什么、报错是什么），固定流程无法根据中间产物改变走向。
> - **长尾分支爆炸**：业务规则的异常分支极多，硬编码会让流程图不可维护。
>
> Agent Workflow 把"决定下一步做什么"这件事从开发期推迟到运行期，交给模型基于当前上下文判断，从而用一套机制覆盖高度动态、开放式的任务。

### Agent Workflow 的构成

一个典型的 Agent Workflow 由以下要素闭环构成：

| 组成 | 作用 |
| --- | --- |
| **目标 / 任务（Goal）** | 用户意图，Agent 要逼近的终态或验收标准 |
| **模型（LLM 决策核心）** | 读取上下文，决定下一步是推理、调用工具还是结束 |
| **上下文 / 记忆（Context & Memory）** | 系统提示、历史消息、工具返回、长期记忆，构成模型每一步的输入 |
| **工具 / 行动（Tools / Actions）** | 模型可调用的外部能力（检索、执行代码、读写文件、调 API） |
| **观察（Observation）** | 工具执行后的结果，回填进上下文供下一轮决策 |
| **控制循环（Agent Loop）** | "思考→行动→观察"反复迭代，直到满足终止条件 |
| **终止 / 验收条件** | 达成目标、步数上限、预算上限或人工介入等停机条件 |

核心运行形态是一个 **Reason–Act–Observe 循环**（ReAct 范式），每一轮模型基于累积上下文产出一个动作，环境返回观察，循环推进直到收敛。

### 哪些环节该固定、哪些该交给模型决策

工程上的黄金原则是：**把"确定性、合规性、安全性"相关的环节固定下来，把"开放式判断、路径选择"交给模型**。

应当固定（代码/编排层控制）：
- 工具的输入输出 schema、参数校验、权限与配额。
- 高风险动作的审批与护栏（删除数据、发邮件、支付、生产变更）。
- 终止条件、最大步数/token/时间预算、重试与回退策略。
- 关键业务规则中不可妥协的部分（如风控红线、幂等性保证）。

可交给模型决策：
- 下一步调用哪个工具、以什么参数、按什么顺序。
- 如何拆解子任务、何时需要澄清、何时判定任务完成。
- 对非结构化中间结果的理解与综合。

实践中更常见的是**混合编排**：外层用固定 Workflow 划定阶段（如"检索→生成→校验"三段），每段内部再嵌入一个受约束的 Agent 子循环。这样兼顾可控性与灵活性。

### 如何为 Agent 的自主性设置边界

自主性边界应从多个维度叠加设置，而非单点控制：

- **工具白名单与能力分级**：只暴露任务所需的最小工具集；高危工具单独走审批或人工确认（Human-in-the-loop）。
- **预算与停机**：设置最大迭代步数、token 预算、墙钟时间、单工具调用超时，防止无限循环与成本失控。
- **权限最小化**：工具在执行层做鉴权与范围隔离（如只读 vs 读写、沙箱执行、目录/网络白名单），不依赖模型"自觉"。
- **结构化约束**：用 schema 校验、函数签名、受限动作空间约束模型输出，拒绝不合法动作。
- **可观测与可中断**：全程记录思考/动作/观察日志，支持运行中人工打断、纠偏、接管。
- **验收闭环**：引入独立的校验步骤（规则校验或 critic 模型）判断结果是否达标，不达标才允许继续或回退。

一句话：**模型负责"选择做什么"，但"能做什么、做多少、谁来兜底"必须由系统硬约束。**

## 核心内容

- **决策核心是模型**：与固定 Workflow 最大的区别在于，流程图不在代码里，而是在运行时由模型逐步生成。
- **Agent Loop（ReAct 循环）**：思考（Reason）→ 行动（Act，调用工具）→ 观察（Observe，读取结果）→ 再思考，迭代至终止。
- **工具调用（Tool / Function Calling）**：模型通过结构化输出触发外部能力，是 Agent 与真实世界交互的手段。
- **上下文工程**：每一步决策质量取决于喂给模型的上下文（提示、历史、记忆、检索结果），上下文管理是 Agent 质量的关键变量。
- **规划机制**：可以是隐式（模型边走边想）或显式（先产出计划再执行，如 Plan-and-Execute、Tree/Graph of Thoughts）。
- **多 Agent 协作**：复杂任务可拆为多个专职 Agent（规划者/执行者/评审者）协同，通过消息或共享状态通信。
- **终止与护栏**：步数/预算上限、审批点、校验器共同决定何时停、能不能做某个动作。
- **错误恢复**：工具失败、幻觉、死循环需要重试、回退、自我反思（Reflexion）等机制兜底。

| 关系 | 知识点 | 说明 |

| 上游 | 固定 Workflow（DAG / 状态机编排） | Agent Workflow 是对固定编排的放松：把静态路径替换为运行时模型决策；二者常混合使用，外层固定、内层自治 |
| 下游 | 多 Agent 系统 / Agent 平台（如 LangGraph、AutoGPT、CrewAI 类） | Agent Workflow 是单 Agent 的基础运行范式，多 Agent 协作与具体框架在其之上构建调度、通信与状态管理 |
| 易混淆 | 纯 Prompt Chaining / RAG Pipeline | 这类是预先写死的线性/固定流程，模型只在节点内生成文本，不决定流程走向；Agent Workflow 的关键区别是模型能在运行时自主选择下一步动作 |

## 典型工程场景

- **AI 编码助手 / Agent**：在代码库中自主读文件、搜索、改代码、跑测试、看报错、再修复的闭环。
- **故障排查 / 运维 Agent**：根据告警动态查日志、查指标、关联分析、给出或执行修复动作。
- **深度研究 / 调研 Agent**：围绕一个问题反复检索、交叉验证、综合，产出带引用的报告。
- **客服 / 工单自动化**：理解诉求后决定查订单、查物流、调退款接口等不同动作组合。
- **数据分析 Agent**：根据自然语言问题自主写 SQL/代码、执行、看结果、迭代直至回答。
- **浏览器 / GUI 自动化**：根据页面观察动态决定点击、输入、翻页等操作序列。

## 适用边界

**适合使用**

- 任务路径高度动态、无法预先枚举所有分支。
- 下一步强依赖上一步的中间结果（需要边做边看）。
- 任务开放式、探索性强（研究、排查、调试）。
- 需要灵活组合多种工具且组合方式因输入而异。

**不适合使用**

- 流程固定、步骤明确且稳定——直接写固定 Workflow 更可靠、更便宜、更快。
- 对延迟、成本、确定性要求极高的高频在线链路（多轮模型调用成本和时延高）。
- 对正确性零容忍且难以事后校验的高危操作（除非配强护栏与人工确认）。
- 可用一次结构化输出或简单 Prompt Chaining 解决的任务——用 Agent 属于过度设计。

## 常见误区

- **"Agent 越自主越好"**：自主性与可控性是权衡，过度放权导致不可预测、难调试、成本失控；多数生产系统是"受约束的 Agent"。
- **"有了 Agent 就不需要固定流程"**：恰恰相反，优秀系统往往是固定骨架 + 局部 Agent 的混合体。
- **"把所有工具都给模型"**：工具越多模型越容易选错、幻觉参数；应最小化可用动作空间。
- **"循环会自己停"**：若不设步数/预算/终止条件，Agent 很容易陷入死循环或反复兜圈。
- **"模型会自己保证安全"**：安全与权限必须在执行层硬约束，不能依赖提示词或模型自律。
- **"Agent = 多 Agent"**：多数任务单 Agent 加好工具就够，盲目堆多 Agent 增加协调成本与故障面。

## 我的结论

> 该用的时候：任务路径无法预先枚举、强依赖中间结果、探索性强（代码修复、故障排查、深度研究这类），且你能接受多轮模型调用的成本和不确定性，并愿意为它配上工具白名单、预算上限、校验器和审批点等护栏。
>
> 不该用的时候：流程本身是确定的、可枚举的，用固定 Workflow 或 Prompt Chaining 就能稳定解决；或者是对确定性、延迟、成本极敏感的高频链路。此时上 Agent 只会带来更高成本、更难调试和更不可控的结果。
>
> 核心判断：**Agent 的价值在于"运行时决策"，只有当决策确实无法在开发期做出时，这份灵活性才值回它在成本、延迟和可控性上的代价。** 现实中最稳妥的姿势是"固定骨架 + 受约束的局部自治"，而不是全盘交给模型。
