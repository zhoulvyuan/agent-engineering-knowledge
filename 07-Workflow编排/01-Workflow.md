## 一句话定义

> Workflow（工作流）是把一个业务目标拆解为若干有明确先后与依赖关系的步骤（节点），再由一个编排引擎按预先定义好的控制流（顺序、分支、并行、循环）自动驱动这些步骤执行、传递数据并处理异常的机制。

## 解决的问题

> 在没有工作流编排之前，多步骤业务逻辑往往以"胶水代码"的形式散落在各处：步骤之间的调用、状态保存、失败重试、超时、补偿、并发控制都由开发者手写在业务代码里。这带来几个麻烦：

- 流程不可见：业务流程只存在于代码调用链中，无法直观看到"一共有哪些步骤、现在走到哪一步"。
- 状态与可靠性难保证：进程崩溃、机器重启后，长流程的中间状态容易丢失，重试和幂等要逐个手写。
- 变更成本高：调整步骤顺序、加一个审批分支，往往要改动大量代码并重新测试。
- 跨系统协调困难：涉及多个服务/人工审批/定时等待时，缺乏统一的协调者，容易出现状态不一致。

### Workflow 的定义与基本形态

Workflow 的本质是"**把流程显式建模为数据/配置，再由引擎解释执行**"，而不是把流程隐含在命令式代码里。

- 基本构成：**节点/任务（Task）**（一个可执行单元）、**边/依赖（Edge）**（节点间的先后与数据流）、**控制流**（决定下一步走向）、**上下文/状态（State）**（在节点间传递的数据）、**触发器（Trigger）**（启动流程的事件或定时）。
- 常见形态：**DAG（有向无环图）**，适合数据管道这类无环流程（如 Airflow）；**状态机 / 状态图**，适合有回退、循环、长等待的业务流程（如 AWS Step Functions、Temporal）；**流程图/BPMN**，面向业务审批与人工节点（如 Camunda、Activiti）。
- 定义方式：声明式（YAML/JSON/DSL/可视化拖拽）或代码即工作流（Code-as-Workflow，如 Temporal 用普通代码写流程，引擎负责持久化与重放）。

### Workflow 引擎的编排能力（顺序 / 分支 / 并行 / 循环）

这是工作流引擎相对于裸调用的核心价值——提供标准化的控制流原语：

| 能力 | 含义 | 典型用途 |
| --- | --- | --- |
| 顺序 | A 完成后才执行 B，B 依赖 A 的输出 | 线性管道、步骤串联 |
| 分支（条件） | 根据上下文/返回值选择不同路径（if/switch） | 风控放行/拒绝、审批通过与否 |
| 并行（fan-out/fan-in） | 多个无依赖节点同时执行，再汇聚结果 | 多路数据抓取、批量调用后聚合 |
| 循环/迭代 | 对集合逐项处理，或满足条件前反复执行 | 批处理、轮询等待、重试循环 |

除控制流外，引擎通常还内建：**重试与退避、超时、幂等、补偿/回滚（Saga）、人工任务与审批、定时与延迟等待、子流程嵌套、并发度限制、持久化与断点续跑**。

### Workflow 的确定性带来的工程优势

这里的"确定性"指：**给定相同的输入和流程定义，执行路径和结果可预期、可复现**。

- 可观测：每一步的状态、输入输出、耗时、失败原因都被记录，流程进展一目了然，便于排障。
- 可靠性强：引擎负责持久化中间状态，崩溃后可从断点续跑；重试/超时/补偿是声明的能力而非手写逻辑。
- 可测试、可审计：路径有限且可枚举，便于编写用例覆盖；每次执行留痕，满足合规审计。
- 易维护与演进：流程以配置/图呈现，调整顺序或增加分支的改动局部且直观，降低回归风险。
- 可控的成本与安全：步骤明确意味着调用次数、权限边界、资源用量都可预估和限制。

### AI 时代 Workflow 的新形态

AI（尤其是 LLM/Agent）给工作流带来两种明显演化：

- **AI 作为节点**：把"LLM 调用、向量检索、工具调用、文档解析"等封装成工作流中的标准节点，用确定性的编排把不确定的模型能力"框"起来。代表：LangGraph、Dify、Coze、n8n、腾讯元器等编排平台。
- **Workflow 与 Agent 的光谱**：一端是**纯 Workflow**（路径人工预定义，确定性高、可控）；另一端是**纯 Agent**（由模型自主决定下一步，灵活但不确定）。工程实践常取中间：**用 Workflow 固定骨架与护栏，在局部节点让 Agent/模型做决策**，兼顾可控性与灵活性。
- 新增关注点：对非确定性节点需要**结构化输出校验、重试/降级、幻觉与越权防护、成本与延迟预算、评测（eval）**，这些都成为 AI 工作流编排的一等公民。

## 核心内容

- **三要素**：节点（任务）、依赖（边/控制流）、状态（上下文数据）。流程 = 显式建模的"图/状态机"+ 解释执行的引擎。
- **控制流原语**：顺序、条件分支、并行汇聚、循环迭代；是编排区别于普通函数调用的核心。
- **可靠性机制**：持久化状态、断点续跑、重试与退避、超时、幂等、补偿/Saga。
- **交互与时间维度**：人工审批节点、定时触发、延迟等待、长流程（可运行数天/数月）。
- **定义范式**：声明式（YAML/DSL/可视化）vs 代码即工作流；DAG vs 状态机 vs BPMN 各有侧重。
- **可观测性**：执行历史、步骤级日志、指标与追踪，是运维与审计的基础。

## 典型工程场景

- 数据/ETL 管道：定时抽取、清洗、转换、入库，节点间有明确依赖（Airflow 典型场景）。
- 订单/交易履约：下单→库存扣减→支付→发货→通知，涉及跨服务协调与失败补偿（Saga）。
- 审批与 BPM：请假、报销、合同审批等含人工节点和条件分支的业务流程。
- CI/CD 流水线：构建→测试→安全扫描→部署，带并行与条件门禁。
- AI 应用编排：RAG 问答（检索→重排→生成→校验）、文档批处理、多工具 Agent 任务、内容审核流水线。
- 定时与长流程：对账、报表生成、营销触达、需等待数天的回访/续费流程。

## 适用边界

**适合使用**

- 流程由多个步骤组成、步骤间有明确依赖或需要跨服务/跨人协调。
- 需要可靠性保证：失败重试、断点续跑、补偿回滚、长时间运行。
- 对可观测、可审计、可复现有要求（合规、金融、运维场景）。
- 流程会频繁调整，希望把流程与业务代码解耦、便于演进。

**不适合使用**

- 单步或极简逻辑：一次函数调用就能完成，引入引擎只是过度设计。
- 超低延迟、超高吞吐的同步请求路径：引擎的持久化与调度开销可能成为瓶颈。
- 路径高度动态、无法预先建模、需模型实时自主决策的任务：更适合 Agent 范式（或 Workflow+Agent 混合）。
- 纯事件解耦、不需要控制流与状态管理的场景：用消息队列即可。

## 常见误区

- 把 Workflow 等同于"定时任务/cron"：定时只是触发方式之一，工作流的核心是控制流与状态管理。
- 认为引擎能让流程自动变可靠：重试/幂等/补偿仍需正确设计，节点自身必须幂等，否则重试会造成重复副作用。
- 把所有逻辑都塞进工作流：细粒度步骤过多会让流程臃肿、调度开销上升，应保持节点粒度适中。
- 混淆 Workflow 与 Agent：以为加了 LLM 节点就是 Agent；只要路径是人预先定义的，它仍是 Workflow。
- 忽视可视化/声明式的隐性成本：复杂逻辑用拖拽式表达反而更难维护，有时代码即工作流更清晰。

## 我的结论

> 当一个目标需要"多步骤 + 明确依赖 + 可靠性/可观测性"时，就应该用 Workflow：它用预定义的确定性路径换来可控、可复现、可演进，特别适合履约、审批、ETL、CI/CD 以及需要护栏的 AI 应用骨架。反过来，单步逻辑、极致低延迟的同步链路、或路径必须由模型实时自主决定的任务，就不该硬套工作流——前两者是过度设计，后者更适合 Agent。实践中最稳妥的做法是"**Workflow 定骨架与护栏，Agent/模型管局部决策**"，在可控与灵活之间取平衡。
