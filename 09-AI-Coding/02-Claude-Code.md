## 一句话定义

> Claude Code 是 Anthropic 推出的、运行在终端里的 Agentic 编码工具：它以 Claude 模型为大脑，通过"读写文件 / 执行命令 / 调用工具"的自主循环，直接在你的真实代码仓库里完成理解、修改、测试、提交等工程任务。

## 解决的问题

> 它出现之前，人们遇到了什么麻烦？

- 传统补全式 AI（如早期 Copilot）只能在编辑器里逐行建议，缺乏对整个仓库的理解，无法跨文件、多步骤地完成一个完整任务。
- 聊天式 AI（网页版对话）与代码库隔离：模型看不到真实文件、跑不了测试、改不了代码，用户要在"复制粘贴—回贴报错—再问"之间反复搬运上下文。
- 多步工程任务（定位 bug → 改多个文件 → 跑测试 → 修复 → 提交）需要人把每一步拆开喂给模型，模型没有自主执行与自我验证能力。
- 缺少统一、可脚本化、可嵌入 CI/CD 的命令行入口，难以把 LLM 能力接进既有工程流水线。

### Agent Loop 的实现方式

Claude Code 的核心是一个"模型自主决策 + 工具执行"的循环：

- 模型收到用户任务后，不直接给最终答案，而是输出"下一步要调用哪个工具"（tool_use）。
- 工具执行后，结果（tool_result，如文件内容、命令 stdout/stderr、退出码）被回填进对话，模型据此决定下一步。
- 这个"思考 → 调用工具 → 观察结果 → 再思考"的循环持续进行，直到模型判断任务完成或需要用户确认。
- 循环中模型会主动做自我验证：改完代码后跑构建/测试，看到报错再回到循环修复。
- 停止条件由模型自身判断（任务达成）、用户介入或权限/错误边界触发。本质上是一个 ReAct 式 Agent，但紧密绑定文件系统与 shell。

### Tools 的设计与权限模型

工具是模型与真实环境交互的唯一通道，设计上追求"小而正交"：

| 类别 | 典型工具 | 说明 |
| --- | --- | --- |
| 文件读写 | read / write / edit | 读取、创建、精确替换文件内容 |
| 搜索 | glob / grep | 按路径模式或内容检索，优于裸 find/grep |
| 执行 | bash | 跑命令、构建、测试，返回 stdout/stderr 与退出码 |
| 扩展 | MCP 工具、子任务 | 接入外部系统或委派子 Agent |

权限模型要点：

- 默认采取"最小权限 + 人类确认"：读文件、跑测试等低风险操作可自动执行；写文件、删文件、`git push`、改生产配置等高风险/不可逆操作需用户批准。
- 支持权限分级与白名单（允许的命令/目录），可在非交互或 CI 场景预先授权以减少打断。
- 把外部内容（文件、命令输出、网页）视为不可信数据，防止提示注入；对可能含密钥的文件谨慎读取。

### Skills 的加载机制

Skills 是"可复用的任务专用指令包"，用于按需扩展 Agent 的领域能力：

- 会话启动时只注入 Skill 的"目录/摘要"（名称 + 何时使用），不加载完整指令，避免一次性撑爆上下文。
- 当用户点名某个 Skill、或任务明显匹配其描述时，Agent 才调用 `skill` 工具按确切名称加载该 Skill 的完整指令（`<skill_content>`）。
- 加载后 Agent 遵循其中的流程（例如处理 .docx/.pptx/.xlsx 的 Office skill、腾讯文档 skill），完成任务。
- 这是一种"渐进式披露 / 懒加载"策略：既让能力可插拔、可组合，又把 token 成本控制在实际用到时才付出。

### MCP 的接入方式

MCP（Model Context Protocol）是 Anthropic 提出的开放协议，用于把外部工具和数据源标准化地接入 Agent：

- 以 Client-Server 架构：Claude Code 作为 MCP Client，连接各类 MCP Server（数据库、Jira、浏览器、内部 API 等）。
- Server 向 Client 声明自己提供的 tools / resources / prompts，Client 把这些工具并入模型可调用的工具集。
- 传输方式常见有 stdio（本地进程）与 HTTP/SSE（远程服务）；通过配置文件登记服务器及其启动命令、鉴权。
- 价值在于"写一次接入、处处可用"：无需为每个外部系统硬编码集成，Agent 就能统一调用；接入的外部数据同样应按不可信处理。

### Context 管理策略（压缩 / 子任务隔离）

长任务会不断积累对话、文件、命令输出，必须主动管理有限的上下文窗口：

- 自动压缩（compaction）：接近窗口上限时，把早期历史摘要化保留关键结论，释放空间继续工作；压缩后应通过重读文件状态而非记忆来确认当前进度。
- 子任务 / 子 Agent 隔离：把独立的研究、审查、批量检索委派给子 Agent，子 Agent 在自己的上下文里工作，只把最终结果返回主循环，从而不污染主上下文。
- 工具的"按需读取"也是上下文策略：用 offset/limit 分段读大文件，用 grep/glob 精确检索而非整仓塞入。
- 项目级记忆文件（如 CLAUDE.md）承载长期约定与背景，跨轮次复用。

### Coding Workflow 的组织方式

Claude Code 把编码组织成"探索 → 计划 → 实现 → 验证"的工程化流程：

- 探索：先读相关代码、配置文件（package.json、Makefile 等），弄清项目使用的构建/测试/lint 工具与既有风格，而非凭空假设。
- 计划：对多文件或不熟悉的改动先列计划（可用 plan 模式与 todo 列表），得到确认后再动手；小而明确的改动则直接执行。
- 实现：遵循仓库既有约定与依赖，优先做小步、可逆的修改。
- 验证：改完跑构建与相关测试，有报错先修复再交付；新功能/修 bug 时补测试；清理临时文件。
- 协作面：可创建分支、提交、发 PR，但默认不直接推 main、破坏性 git 操作需显式授权。

## 核心内容

- 定位：终端里的 Agentic 编码工具，以 Claude 模型为核心，直连本地仓库与 shell。
- 核心机制：模型自主的 Agent Loop（思考—调用工具—观察—再思考），直到任务完成或需人确认。
- 工具体系：read/write/edit、glob/grep、bash 等正交工具，配合最小权限与高风险操作人工确认。
- 可扩展性：Skills（按需加载的任务指令包）+ MCP（标准化接入外部工具/数据）+ 子 Agent 委派。
- 上下文工程：自动压缩、子任务隔离、按需读取、项目记忆文件（CLAUDE.md）共同支撑长任务。
- 工程流程：探索—计划—实现—验证闭环，内建自我验证（跑测试、读报错、再修复）。
- 接入形态：可交互使用，也可非交互/脚本化嵌入 CI/CD。

## 典型工程场景

- 跨文件重构：统一重命名、抽取公共逻辑、迁移 API 用法，并自动改动所有引用。
- 定位并修复 bug：从报错出发检索代码、改多个文件、跑测试直到通过。
- 为既有代码补测试：识别测试框架、生成用例并运行。
- 新功能实现：读懂现有模式后按既有架构落地一个完整特性。
- 代码库问答与导航：快速解释大型陌生仓库的结构与关键流程。
- 工程自动化：依赖升级、批量脚本化改码、生成/维护文档，或嵌入 CI 做自动检查与修复。
- 通过 MCP 打通内部系统（数据库、工单、知识库）完成端到端任务。

## 适用边界

**适合使用**

- 有明确验收标准、可通过构建/测试自动验证的工程任务。
- 多步骤、跨文件、需要在真实仓库里读写与执行的任务。
- 重复性高、可脚本化的工程自动化。
- 需要接入外部工具/数据（经 MCP）的集成型任务。

**不适合使用**

- 目标模糊、缺乏可验证标准的开放式探索（需人先定清楚需求）。
- 高风险不可逆操作在无人监督下自动执行（生产部署、删库、强制推送）。
- 对正确性要求极高且难以自动验证的安全/合规核心逻辑，仍需人工把关。
- 受限或离线、无法提供模型 API 访问的环境。

## 常见误区

- 以为它只是"更强的代码补全"：实际是能自主多步执行并自我验证的 Agent。
- 以为它会无脑自动完成一切：高风险操作需人工确认，复杂任务仍需人给清晰目标与边界。
- 把工具输出/外部内容当成可信指令：应按不可信数据处理，警惕提示注入。
- 以为上下文无限：窗口有限，长任务靠压缩与子任务隔离管理，可能遗漏早期细节。
- 盲目信任生成结果不做验证：必须跑测试、审查 diff，尤其是安全/数据相关改动。
- 把 Skills/MCP 当成"自动全加载"：Skills 按需加载，MCP 需显式配置接入。

## 我的结论

> **何时该用**：当任务是真实仓库里的多步、可验证的工程工作——跨文件重构、修 bug、补测试、实现有明确标准的特性，或可脚本化的自动化流程时，Claude Code 能显著提升吞吐，让人专注在设计与决策上。前提是你能给出清晰目标与验收标准，并对高风险步骤保留人工确认。
>
> **何时不该用**：目标尚不清晰、正确性难以自动验证、或涉及不可逆的生产/数据操作而又无人监督时，不要让它全自动跑。此时它应退化为"结对的加速器"而非"无人驾驶"：先用它探索与出方案，关键改动由人复核后再落地。
