## 一句话定义

> AI Coding 基本模式指的是大模型辅助软件开发时的几种人机协作形态——以"行内补全""对话问答""自主 Agent"为代表，按 AI 承担工作量与自主程度从低到高递进。

## 解决的问题

> 在 AI Coding 出现之前，开发者的产出几乎完全受限于个人的记忆、打字速度和查资料效率：写样板代码、查 API 用法、读陌生代码、写单测、改 bug 都要手工完成，大量时间消耗在"低创造性但不可省略"的机械劳动上。知识散落在文档、Stack Overflow、代码库各处，上下文切换成本高。AI Coding 把"编写"这一环节部分自动化，让人更多地做设计、决策与审查，而把重复性的生成、检索、改写交给模型。

### 代码补全 / 对话 / Agent 三种模式的差异

三种模式的本质差异在于 **AI 的自主程度** 与 **交互粒度**：

| 维度 | 代码补全（Completion） | 对话（Chat） | Agent（自主体） |
| --- | --- | --- | --- |
| 触发方式 | 边敲边补，输入即触发 | 用户主动提问/下指令 | 用户给目标，Agent 自主拆解执行 |
| 上下文范围 | 当前文件 + 少量相邻文件 | 选中片段 / 手动贴入 / 工程检索 | 全仓库 + 工具（文件读写、终端、测试）|
| 产出粒度 | 行/块级代码 | 片段、解释、方案 | 跨文件改动、可运行的完整任务 |
| 人介入频率 | 极高（每行都在决策接受与否）| 中（按轮次审查）| 低（事后审查 diff，或分阶段确认）|
| 自主程度 | 无规划，纯预测下一段 | 无执行能力，只生成文本 | 有规划-执行-观察的闭环 |

- **补全**：本质是条件语言模型对"下一段代码"的概率预测，不理解任务目标，只续写上下文。延迟要求极低（百毫秒级）。
- **对话**：引入了显式意图和多轮上下文，模型能解释、重构、生成方案，但自身不动代码库，执行靠人复制粘贴。
- **Agent**：在对话基础上接入工具调用与反馈循环（读文件、跑测试、看报错、再修改），能独立完成"实现某功能并通过测试"这类端到端任务。

### 各自的适用场景

- **代码补全**：适合高频、低风险、上下文明确的场景——写样板/CRUD、补全函数体、重复结构、测试用例骨架、注释与类型标注。开发者保持在"驾驶座"，心流不被打断。
- **对话**：适合需要解释与权衡的场景——理解陌生代码、设计方案讨论、定位 bug、生成正则/SQL、翻译语言、Code Review 建议、学习新 API。适合"我知道要什么但不确定怎么写"。
- **Agent**：适合目标清晰、步骤繁琐、可验证的场景——按 issue 修复 bug、批量重构/迁移、补全测试覆盖、脚手架搭建、依赖升级。前提是有明确的验收信号（能编译、测试能跑），否则 Agent 会"自信地跑偏"。

### AI Coding 对研发流程的实际影响

1. **工作重心上移**：开发者从"写代码"更多转向"描述意图 + 审查结果"，Code Review 的重要性和工作量显著上升。
2. **初稿速度提升、但审查成为新瓶颈**：生成快了，但正确性、安全性、风格一致性仍需人把关，净收益取决于审查效率。
3. **知识门槛变化**：降低了语法/API 层面的门槛，但抬高了"判断生成结果是否正确、是否符合架构"的门槛——资深者收益放大，新手易被误导。
4. **流程工具化**：催生 PR 自动生成、测试自动补全、规格驱动（spec-driven）等新工作流；对代码规范、测试覆盖、CI 门禁的依赖加强（它们是约束 AI 产出的"护栏"）。
5. **不改变工程本质**：需求理解、架构设计、系统边界、责任归属仍是人的工作；AI 放大的是执行效率，不是替代判断。

## 核心内容

- **三种基本模式按自主度递进**：补全（预测续写）→ 对话（意图驱动的生成/解释）→ Agent（规划-执行-观察闭环）。三者常在同一工具内共存、互补，而非互斥。
- **补全的机制**：基于当前光标前后上下文（FIM，Fill-in-the-Middle）做低延迟预测，关键在上下文窗口裁剪与相关文件召回。
- **对话的机制**：多轮上下文 + 可选的工程检索（RAG/符号索引），输出文本，不直接改动代码。
- **Agent 的机制**：目标分解 → 工具调用（读写文件、执行命令、跑测试）→ 观察结果 → 迭代修正，直到满足验收条件或达到步数上限。核心是"反馈闭环"与"工具使用"。
- **共性要素**：上下文工程（给模型喂对信息）、提示/指令质量、验收信号（测试/编译/类型检查）、人类审查环节。
- **风险要素**：幻觉（编造 API）、上下文不足导致的偏差、安全漏洞、与既有架构/规范不一致。

## 典型工程场景

- 日常编码时的行内补全，加速样板、CRUD、测试骨架编写。
- 接手陌生/遗留代码库时，用对话快速理解模块职责与调用关系。
- 按 Jira/GitHub issue 让 Agent 自主修复 bug 并提交带测试的 PR。
- 框架或语言版本大版本迁移、API 批量替换等重复性重构。
- 为缺乏测试的历史代码补全单元测试、提升覆盖率。
- 生成/优化复杂 SQL、正则、Shell 脚本、配置文件等"写起来烦但逻辑不深"的内容。

## 适用边界

**适合使用**

- 任务目标明确、可被机器验证（能编译、测试能通过、有明确输入输出）。
- 重复性高、模式化强、低创造性的工作（样板、迁移、测试补全）。
- 上下文可被模型获取（代码在仓库内、规范有文档）。
- 结果有人审查，且团队有测试/CI/规范等"护栏"。

**不适合使用**

- 需求本身模糊、需要与业务方反复澄清的早期阶段。
- 高风险且难验证的变更（核心算法正确性、分布式一致性、安全关键逻辑）而缺乏测试覆盖时。
- 强依赖团队隐性知识、特定架构约定而这些未被显式记录时。
- 对延迟/成本极度敏感、或代码不允许外传的保密环境（需评估私有化部署）。

## 常见误区

- **"AI 能替代开发者"**：它替代的是部分编写劳动，不是需求理解、架构决策与责任承担。
- **"生成了就等于对了"**：模型会自信地产生看似合理实则错误的代码（幻觉），审查不可省。
- **"Agent 越自主越好"**：自主度越高，跑偏时的损失越大；缺乏验收信号的任务不该交给 Agent 放手去做。
- **"补全和对话是同一回事"**：补全无意图、无执行；对话有意图、无执行；混用会误判工具能力。
- **"用了 AI 就一定更快"**：若审查、修正、来回澄清的成本高于手写，净收益可能为负，尤其对不熟悉的领域。
- **"护栏可以省"**：恰恰相反，AI 产出越多，测试、类型检查、规范、Code Review 这些约束越关键。

## 我的结论

> 把三种模式理解为一条"自主度光谱"，按任务的**可验证性**和**风险**来选用，而不是追新：
> - **补全**在任何编码场景都值得常开，它低风险、不打断心流、净收益稳定。
> - **对话**在"我需要理解或权衡"时用，它是最安全的"放大镜"和"陪练"。
> - **Agent** 只在"目标清晰 + 有自动验收信号 + 改动可被 diff 审查"三者同时满足时才放手，否则它的自主性会变成风险。
>
> 一句话：AI Coding 放大的是执行效率，不是判断力；它越强，越要把人的精力投入到定义问题和审查结果上，并用测试与规范为它建好护栏。
