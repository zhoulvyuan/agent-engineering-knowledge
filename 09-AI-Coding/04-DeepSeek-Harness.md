## 一句话定义

> DeepSeek Harness（DSH）是围绕大模型构建的「Agent 运行时与脚手架」——它把模型、工具调用、上下文管理、子代理编排、技能与插件、以及面向用户的交互层封装成一套可运行的编码智能体系统，让模型能在真实环境里读写文件、执行命令并完成多步工程任务。

## 解决的问题

> 裸调用一个 LLM 只能产出文本，无法真正"干活"：它看不到用户的代码仓库、不能执行命令、没有记忆、也无法把一个大任务拆成多步可验证的动作。开发者若要把模型落地成一个能自主完成编码任务的智能体，就必须自己拼接"调用模型 → 解析输出 → 执行工具 → 把结果喂回模型"的循环，并处理上下文超限、工具权限、安全护栏、错误恢复等一堆工程细节。Harness 把这些共性的脚手架沉淀下来，开发者只需关注任务本身，而不必每次重造一遍 Agent 的运行底座。

### Harness 的基本定位

"Harness"（马具/挽具）这个比喻很贴切：模型是"马"，Harness 是套在模型外面、让它能拉动真实世界负载的那套装置。它本身不产生智能，而是为智能提供可执行的躯干。

- 它处于**模型之上、应用之下**：向下对接一个或多个 LLM，向上提供 CLI / Web GUI 等交互入口。
- 核心职责包括：维护 Agent Loop、暴露工具（文件读写、命令执行、搜索、Web 访问等）、管理上下文窗口、承载技能（Skill）与插件（Plugin）、编排子代理（Subagent）与工作流（Workflow）。
- 它是**产品形态与框架形态的结合体**：既是一个可直接用的编码助手，也是一套可被二次开发扩展的运行时。

### Agent / Coding Agent 的运行模式

典型运行模式是一个"感知—决策—行动"的闭环（Agent Loop）：

1. 接收用户消息与系统上下文（操作系统、工作目录、可用技能等）。
2. 模型决定是直接回答，还是调用一个或多个工具。
3. Harness 执行工具调用（如 read / edit / bash / grep），把结果作为观察回灌给模型。
4. 循环往复，直到任务完成或达到停止条件。

Coding Agent 的特化之处在于：工具集围绕"读代码—改代码—验证"展开，强调在修改后运行构建/测试来闭环验证；并引入**安全护栏**（破坏性操作需确认）、**权限沙箱**（如 workspace-write 限制可写范围）、以及**上下文自动压缩**以支撑长任务。独立子任务可通过 subagent 并行外包，避免污染主上下文。

### Plugin 能力与扩展点

Harness 通常提供多层扩展点，让能力可以被组合与定制：

| 扩展点 | 作用 |
| --- | --- |
| Tool（工具） | 定义 Agent 可执行的原子动作（文件、命令、搜索、网络等） |
| Skill（技能） | 按需加载的任务专用指令集（如 office-docx、tencent-docs），只有命中任务时才注入，节省上下文 |
| Plugin（插件） | 更重的扩展单元，可挂接新能力、UI、或后端服务；客户端插件支持 HMR 热更新 |
| Subagent / Workflow | 把工作外包给独立子代理，或用脚本在多个子代理间大规模编排（fan-out） |

关键设计是**按需加载**：技能目录里只放摘要，真正命中时才加载完整指令，用上下文预算换取能力广度。

### 与 Claude Code CLI 的关系

DSH 与 Claude Code CLI 是**同一类产品的不同实现**——都是面向终端/编辑器的"编码智能体脚手架"。相似点：都提供 Agent Loop、文件与命令工具、子代理、技能/插件机制、安全确认护栏。

区别主要在实现与生态：DSH 由 DeepSeek 侧实现并可绑定自家模型（如本会话运行于 claude-opus 类模型，说明 Harness 与模型是解耦的），自带 Web GUI 与基于 Electron（app.asar）的分发形态，以及 workflow 等多代理编排原语。可以把 Claude Code 理解为同一设计范式的另一参照系，而非上下游依赖关系。

### AI Coding 工具的架构抽象

把这类工具抽象成分层模型，有助于横向对比（Cursor、Claude Code、Aider、DSH 等）：

- **交互层**：CLI / IDE 插件 / Web GUI，负责输入输出与结果呈现。
- **编排层（Harness 核心）**：Agent Loop、上下文/记忆管理、子代理与工作流调度、权限与安全护栏。
- **能力层**：工具集、技能、插件——决定 Agent"能做什么"。
- **模型层**：可插拔的一个或多个 LLM，提供推理与决策。
- **环境层**：文件系统、shell、沙箱、版本控制等真实执行底座。

这套抽象的价值在于：模型可替换、能力可扩展、交互可多端，而编排层是沉淀工程价值的核心。

### 自身使用经验如何反哺 Agent 设计

一个有意思的闭环是：用 Harness 本身来开发和改进 Harness（dogfooding）。DSH 把自己的实现 checkout 暴露给 Agent，Agent 可以读、改、扩展自身代码。这带来几点反哺：

- **真实痛点驱动工具设计**：Agent 在自用中频繁遇到的问题（如上下文溢出、工具粒度不对），会直接推动工具与护栏的迭代。
- **提示词与规则的实证打磨**：系统提示里的大量细则（何时用 read 而非 cat、如何引用文件路径、后台 job 管理）往往来自真实失败案例的沉淀。
- **交互契约的收敛**：把"默认沉默、少叙述""改动后必须验证"等经验固化为规则，提升可预期性。

本质上，这是把"运维/使用反馈"转化为"产品规则与工具契约"的持续工程过程。

## 核心内容

- **Agent Loop**：感知—决策—行动的闭环，是整个 Harness 的心脏。
- **工具系统**：文件读写（read/edit/write）、命令执行（bash）、搜索（glob/grep）、网络（web_search/web_fetch）等原子动作；强调用专用工具而非裸 shell，以提升可观测性。
- **上下文管理**：维护系统上下文与对话历史，接近窗口上限时自动压缩，支撑长任务。
- **子代理与工作流**：subagent（独立上下文外包）、subagent_fork（继承当前对话）、workflow（脚本化多代理 fan-out 编排）。
- **技能与插件**：按需加载的能力扩展；技能目录仅存摘要，命中才加载完整指令。
- **安全与权限**：破坏性操作需确认、权限沙箱（如 workspace-write）、把外部内容一律当作不可信数据。
- **验证闭环**：改动后运行构建/测试，失败先修复再交付，并清理临时文件。
- **多端交互**：CLI（kiro-cli chat 等）与 Web GUI 并存，模型层可插拔。

## 典型工程场景

- 在真实仓库中自主完成多文件的功能开发、重构或 bug 修复，并自动跑测试验证。
- 批量化工程任务：审计大量文件、跨仓库迁移、多角度研究——用子代理/工作流 fan-out 并行处理。
- 文档与办公自动化：通过技能生成/编辑 Word、PPT、Excel 或在线云文档。
- CI/运维辅助：读日志、定位问题、生成修复补丁与 PR（遵守 git 安全规则）。
- 作为团队内部的可扩展 Agent 平台底座，承载自研工具与插件。

## 适用边界

**适合使用**

- 需要在真实文件系统/命令行环境中执行的多步编码与工程任务。
- 任务可被拆成"动作—观察—验证"的闭环，且有明确的成功判据（构建通过、测试绿）。
- 需要并行处理大量独立子任务，或需要可扩展的技能/插件生态。

**不适合使用**

- 纯粹的一次性问答或创意写作，用不上工具与环境，Harness 的开销反而是负担。
- 高风险、不可逆且无法人工把关的生产操作（直接改生产库、强制 push）——需人在环路。
- 环境缺失依赖/沙箱过紧导致无法执行与验证时，Agent 只能给建议而非落地。

## 常见误区

- 以为 Harness 自带"智能"：它只是脚手架，智能来自模型；换模型会显著改变表现。
- 把 Harness 等同于某个具体 CLI 工具：它是运行时/框架层，CLI 只是其交互入口之一。
- 认为给了工具就能自动安全：破坏性操作、权限边界、不可信外部内容仍需护栏与人工确认。
- 迷信"全自动"：长任务需要上下文管理、验证闭环与失败恢复，否则会累积错误或陷入死循环。
- 把子代理当免费资源无脑并行：fan-out 有成本与协调开销，独立性不足反而更慢更乱。

## 我的结论

> 当任务是"在真实代码/文件环境里完成多步、可验证的工程工作"时，应该用 Harness：它把 Agent Loop、工具、上下文管理、安全护栏这些共性脚手架做好了，让我专注任务本身，并能通过子代理/技能横向扩展。
> 反过来，如果只是单轮问答、创意写作，或是高风险不可逆的生产操作，就不该把它当"全自动"来用——前者是杀鸡用牛刀，后者必须保留人在环路。判断标准很简单：任务能不能拆成"动作—观察—验证"的闭环，并且有没有明确的成功判据；两者都满足，Harness 才真正发力。
