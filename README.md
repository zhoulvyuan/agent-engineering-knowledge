# Agent 工程能力知识库

> 一个持续演进的 Agent 应用开发知识库。
>
> **起点**：已有的 Java 软件工程能力。
> **目标**：面对真实业务问题时，能判断 AI 是否适合、该用什么能力、如何组合、如何工程化落地。

---

## 这是什么

这不是技术名词清单，也不是学习笔记的堆放处。

它是一张**可执行的知识地图**，负责回答四个问题：

1. 我现在的知识版图是什么样？
2. 哪些地方是缺口？
3. 下一步该学什么？
4. 各知识点之间是什么关系？

**核心原则**：不走"数学 → 机器学习 → 深度学习 → Transformer"的学院派路线。
优先从**使用和工程问题**出发，在真正需要时才补充原理。

## 总分三层的组织方式

```text
第1层（总）   知识地图.md
              └ 唯一索引：能力全景、状态看板、学习路线、优先级

第2层（分·域） 编号目录 + README.md
              └ 该域定位、知识点清单、学习顺序、已识别缺口

第3层（层·知识点）  单个知识点文件
              └ 按统一模板沉淀
```

**关键机制**：`知识地图.md` 的状态看板是全库**唯一的进度视图**。
不需要打开所有文件就能知道学到哪了。

## 知识状态与深度

**状态**（用于识别缺口）：

| 标记 | 含义 |
| --- | --- |
| ⚪ | 未开始 |
| 🔴 | 不理解 |
| 🟡 | 理解中 |
| 🟢 | 已掌握 |
| 🔵 | 已实践 |

**深度**（用于决定投入程度）：

| 级别 | 含义 |
| --- | --- |
| A | 深入掌握 |
| B | 能够应用 |
| C | 理解概念 |
| D | 当前阶段暂不投入 |

## 沉淀流程

```text
知识地图发现缺口
   ↓
在对应域开一个专题会话（聊天负责探索）
   ↓
理解 / 对比 / 实践
   ↓
形成结论，回填知识点文件（文件负责沉淀）
   ↓
更新知识地图的状态看板
   ↓
继续发现新的知识缺口
```

> **聊天负责探索，文件负责沉淀。**
> 不要把所有聊天内容直接复制到文件里。

## 三条写作原则

1. **写判断，不写定义。** 每个知识点文件的「我的结论」一节是核心价值所在。
2. **写边界。** "什么时候不该用它"比"它是什么"更重要。
3. **写缺口。** 不懂的地方明确写出来，这比假装懂了有价值得多。

## 维护约定

### 新增知识点

1. 先判断它**属于哪个域**。归属不明确，说明分类需要调整，先改分类再建文件。
2. 复制 [`99-附录/模板-知识点.md`](99-附录/模板-知识点.md) 到目标域，按 `序号-名称.md` 命名。
3. 在**域 README 的清单表**、**知识地图的状态看板**都加上一行。

### 修改状态

需要**同时**改两处：

- 知识点文件头部的 `> **状态**：`
- `知识地图.md` 第 2 节的看板

### 允许重构

当发现原有分类不合理时，**调整整个知识地图**，而不是为了保持旧结构强行添加新节点。
但要在 `知识地图.md` 的「结构决策记录」中写下理由，避免以后重新纠结同一个问题。
