# Reflection / 反思

> **上级**：[03-Agent核心](README.md) ｜ **依赖**：Agent Loop、Memory

## 一句话定义

> Reflection（反思）是让 Agent 在产出结果后，再用一轮或多轮 LLM 调用对自己的输出进行审查、批评并据此修订的机制，把"一次性生成"变成"生成—自评—改进"的迭代闭环。

## 解决的问题

> 在 Reflection 出现之前，LLM 一次性（zero-shot / single-pass）生成的结果存在几类顽固问题：代码跑不通但模型不自知、推理链中途出错却一路错到底、输出遗漏需求点、格式或约束不满足。因为模型是自回归逐 token 生成的，一旦前面走偏就难以回头，而人类专家写完草稿后往往会复查修改，单次生成缺的正是这个"复查"环节。Reflection 把这一步显式补上，用额外的推理算力换取更高的正确率和完成度。

### Reflection 解决什么问题

- 核心是弥补 LLM "单次前向生成不可回退" 的结构性缺陷：生成时无法像人一样停下来复查，Reflection 用额外一轮调用补上复查与修订。
- 典型可修复的错误类型：代码语法/运行错误、推理算错或逻辑跳步、需求点遗漏、输出不满足格式与约束、事实性疏漏（在有外部反馈时）。
- 本质是"用推理时的额外算力换质量"（test-time compute），把一次性采样的随机失误通过第二眼审查过滤掉。
- 注意边界：它主要纠正模型"能看出来但第一遍没做好"的错误；对于模型知识盲区或系统性错误（它压根不知道对错）帮助有限，甚至可能自我强化错误。

### 自我批评如何提升结果质量

- 机制上把生成与评判拆成两个认知步骤：生成关注"产出"，批评关注"挑错"，分开后批评阶段的注意力集中于找缺陷，比边写边检查更有效。
- 批评 prompt 通常引导模型逐条对照要求/测试用例/评分标准（rubric）审查，产出结构化的"问题清单 + 修改建议"，再喂回生成阶段定向修订。
- 反馈质量决定提升幅度，从弱到强大致是：纯模型自评 < 带 rubric/检查清单的自评 < 外部可验证信号（编译器、单元测试、linter、检索结果）驱动的反思。有客观反馈时提升最明显。
- 关键风险：无外部信号的纯自评会受"模型既当运动员又当裁判"的偏差影响——它可能对错误过度自信，也可能把本来对的答案改坏。因此工程上优先接入可验证反馈，并限制迭代轮数（常见 1~3 轮）防止发散或成本失控。

### Reflection 与 Evaluator-Optimizer 模式的关系

- Evaluator-Optimizer 是 Anthropic 等总结的一种 Agent 工作流模式：一个 LLM 做 Optimizer（生成），另一个 LLM 做 Evaluator（按标准打分并给反馈），循环直到评估通过。
- 关系：Reflection 是这一模式的思想内核与最小实现——当"评估者"和"生成者"是同一个模型（自我批评）时就是经典 Reflection；Evaluator-Optimizer 把评估者显式独立出来，职责更清晰、可用不同模型或可验证器充当评估者。

| 维度 | Reflection（自我反思） | Evaluator-Optimizer |
| --- | --- | --- |
| 评判者 | 通常是生成模型自己 | 独立的评估者（可另一个模型/规则/验证器） |
| 停止条件 | 固定轮数或自认为满意 | 评估者给出的明确通过标准 |
| 适用前提 | 评判难以外部化时 | 存在清晰、可迭代反馈的评价标准 |
| 关系 | 更基础、更通用的技术 | Reflection 的一种结构化、职责分离的工作流实例 |

## 核心内容

- **基本循环**：生成（draft）→ 反思/批评（critique）→ 修订（refine），可迭代多轮；每轮把上一轮输出与批评意见一起作为上下文。
- **两种角色**：生成者（actor）与批评者（critic）。二者可同模型不同 prompt，也可拆成不同模型/工具。
- **反馈来源（由弱到强）**：
  - 内部自评：仅凭模型自身判断。
  - 启发式/规则：格式校验、长度、关键字检查。
  - 外部可验证信号：编译器、单元测试、linter、类型检查、检索到的事实、运行结果。
- **记忆机制**：进阶做法（如 Reflexion）把每次失败的反思总结成"经验教训"写入记忆，供后续尝试参考，实现跨轮次学习。
- **终止控制**：设最大轮数、评估通过阈值、或"连续两轮无改进即停"，避免无限循环与成本膨胀。
- **代价**：每轮反思都是额外的 LLM 调用，延迟与 token 成本成倍增加，需按价值权衡。

## 典型工程场景

- 代码生成 Agent：生成代码 → 跑测试/编译 → 根据报错反思并修复（最成功的落地场景，因为有客观反馈）。
- 复杂推理/数学题：第一遍解答后自查步骤，纠正算错或逻辑漏洞。
- 长文写作与报告：对照需求清单检查是否覆盖所有要点、风格与结构是否达标后改稿。
- RAG 问答：对初答做事实核查，发现证据不足则重新检索再回答。
- 结构化输出校验：生成 JSON/SQL 后校验 schema 或语法，不合规则自我修正。
- 多步骤任务规划：执行前反思计划是否可行，执行后反思是否达成目标。

## 适用边界

**适合使用**

- 存在客观、可自动化的反馈信号（测试、编译器、校验器、检索）。
- 任务有明确的质量标准或检查清单可对照。
- 错误是"模型能识别但第一遍没做好"的类型，且单次正确率中等（有改进空间）。
- 质量比延迟/成本更重要的离线或高价值场景。

**不适合使用**

- 对延迟和成本极度敏感的高并发在线场景。
- 任务超出模型能力边界、无外部真值时——纯自评可能把对的改错、对错的更自信。
- 简单任务，单次已足够正确，反思只增加开销甚至引入噪声。
- 缺乏任何可验证反馈且对正确性要求高的场景（易自我强化错误）。

## 常见误区

- 以为"反思越多轮越好"：收益通常快速递减，2~3 轮后常无改进甚至变差，还成倍增加成本。
- 以为纯自我批评一定能提高质量：缺少外部信号时，模型可能对错误过度自信或把正确答案改坏。
- 把 Reflection 当银弹：它纠正不了模型知识盲区和系统性偏差。
- 混淆 Reflection 与 CoT：前者是生成后审查修订，后者是生成时展开推理。
- 不设终止条件导致死循环或成本失控。
- 批评 prompt 过于笼统（"检查一下有没有问题"），缺乏 rubric 和具体对照项，反思流于形式。

## 我的结论

> 该用 Reflection 的判断标准不是"任务难不难"，而是"有没有廉价可靠的反馈信号 + 单次正确率是否有提升空间"。当我能接上编译器、单元测试、校验器或检索等客观反馈时，Reflection 几乎总是划算的，尤其是代码类任务——用一两轮额外调用换显著的正确率提升。反之，当只能靠模型自己当裁判、又没有外部真值时，我会非常谨慎：此时它很可能把对的改错或强化错误，不如用 Self-Consistency 多采样投票或换更强模型。实践上我默认限制 1~3 轮、设"无改进即停"，并把精力花在设计高质量的批评 prompt（带明确 rubric）和接入可验证反馈上，而不是盲目堆迭代轮数。
