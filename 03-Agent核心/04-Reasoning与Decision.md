> **上级**：[03-Agent核心](README.md) ｜ **依赖**：Agent Loop

## 一句话定义

> Reasoning/Decision 是 Agent 在每一步循环中，基于当前目标、历史轨迹和环境观测，判断"下一步做什么"的认知过程——它把模型的语言生成能力转化为可执行的行动选择（调用哪个工具、给什么参数、还是直接作答或终止）。

## 解决的问题

> 在 Reasoning/Decision 作为显式环节出现之前，LLM 的使用方式是"一问一答"：用户给一个 prompt，模型直接吐出最终答案。这带来几个麻烦：
> - 复杂任务无法分解，模型容易在一次生成里"跳步"，中间逻辑错了也无从纠正。
> - 模型只能依赖参数里的知识，无法在作答过程中查资料、算数、调 API，导致事实性错误和幻觉。
> - 没有"决策点"，就无法根据中间结果动态改变路径，所有行为都是一次性静态输出。
>
> 把推理与决策显式拆成循环中的一步后，模型可以"想一步、做一步、看结果、再想"，从而处理多步骤、需要外部信息、需要纠错的任务。

### 模型推理在 Agent 中承担什么角色

模型推理是 Agent 的"决策中枢"，在 Agent Loop 中承担以下职责：

- **目标理解与分解**：把用户的高层意图拆解为可执行的子目标和步骤。
- **状态评估**：读取当前轨迹（历史动作 + 观测结果），判断距离目标还有多远、上一步是否成功。
- **动作选择**：决定下一步是调用工具、继续推理、向用户追问，还是终止并给出最终答案。
- **参数构造**：为选定的工具/API 生成结构化的调用参数。
- **纠错与反思**：当观测结果与预期不符时，重新规划路径（如 ReAct、Reflexion 中的反思步骤）。

需要强调的是：模型本身**不执行**动作，它只产出"决策意图"（通常是一段文本或结构化的 tool call）；真正的执行由外层的 Agent 框架/工具运行时完成。推理是"大脑"，执行环境是"手脚"。

### Reasoning 与 Action 的关系

两者是交替耦合的闭环关系，经典范式是 ReAct（Reasoning + Acting）：

| 维度 | Reasoning（推理） | Action（行动） |
| --- | --- | --- |
| 产出 | 对局势的分析、下一步计划（思维链/thought） | 对环境的实际操作（tool call、API 调用） |
| 作用对象 | 模型内部的"思考" | 外部环境 |
| 是否产生副作用 | 否（纯文本） | 是（改变环境、获取新信息） |
| 结果 | 指导下一个 Action | 产生 Observation，反哺下一轮 Reasoning |

关系要点：

- **Reasoning 为 Action 提供依据**：先想清楚"为什么做、做什么"，再发出动作，避免盲目调用。
- **Action 为 Reasoning 提供新证据**：工具返回的 Observation 补充了模型参数里没有的实时/私有信息，纠正推理方向。
- **二者交替形成循环**：Thought → Action → Observation → Thought … 直到任务完成。只有 Reasoning 没有 Action 会退化为纯 CoT 问答；只有 Action 没有 Reasoning 会变成无脑的工具堆砌。

### 为什么 Agent 的行为具有不确定性

不确定性来自多个叠加的来源：

- **采样随机性**：LLM 解码时通常使用带 temperature/top-p 的采样，同样的输入会产生不同的输出；即使 temperature=0 也可能因浮点、批处理、硬件差异产生非完全确定的结果。
- **路径分叉放大**：Agent 是多步循环，每一步的微小差异会在后续步骤中被级联放大，最终轨迹可能完全不同（蝴蝶效应）。
- **环境非确定性**：工具/API 返回的结果本身会变（网络、时间、第三方数据、搜索排序），同一决策在不同时刻得到不同 Observation。
- **上下文敏感**：模型对 prompt 措辞、历史顺序、token 位置高度敏感，轻微扰动即可改变决策。
- **长程规划的模糊性**：开放式任务没有唯一正确路径，模型可能选择多条合理但不同的解法。

工程含义：Agent 不能当作确定性函数来测试，需要用评测集 + 多次采样统计成功率、设置护栏（约束、校验、重试上限）、并通过结构化输出和确定性工具来收敛不确定性。

### 推理模型（reasoning model）对 Agent 设计的影响

推理模型（如 OpenAI o 系列、DeepSeek-R1 等，在作答前生成大量内部思考 token）改变了 Agent 的设计权衡：

- **规划下沉到模型内部**：以往需要靠外部框架（显式 CoT prompt、规划器）编排的多步推理，现在很大一部分可以由模型在一次调用内完成，Agent 编排层可以更薄。
- **延迟与成本上升**：推理模型会消耗大量思考 token，单步变慢、变贵；需要重新权衡"模型内部多想" vs "多轮循环 + 工具"的分工，并对何时启用深度推理做路由。
- **提示工程策略变化**：对推理模型，过度的 few-shot 和手写 CoT 提示反而可能有害，官方建议给清晰目标、少干预其思考过程。
- **可观测性下降**：内部思考常被隐藏或摘要，调试和审计 Agent 决策链变难，需要依赖外部日志记录 tool call 与 observation。
- **分工重新划分**：常见做法是用推理模型做"规划/难决策"，用更快更便宜的模型做"执行/格式化"，形成分层架构。

> 注：具体模型的参数、是否暴露思维链、定价等细节更新频繁，相关不确定点见「待解决问题」。

## 核心内容

- **循环中的决策步**：Reasoning/Decision 是 Agent Loop（感知→推理→行动→观测）中的"推理+决策"环节，输入是目标与轨迹，输出是下一步动作。
- **三类决策产物**：① 继续推理（thought）② 发起行动（tool/function call）③ 终止并给出最终答案。
- **主流范式**：
  - ReAct：思考与行动交替。
  - Plan-and-Execute / Plan-and-Solve：先整体规划再逐步执行。
  - Reflexion / Self-Refine：引入反思步骤对失败轨迹进行自我批评和重试。
  - Tree-of-Thoughts / 多路径搜索：探索多条推理分支再择优。
- **决策依据**：系统提示（角色/约束）、可用工具描述、历史轨迹、当前观测、以及可选的记忆/检索内容。
- **结构化输出**：现代实现多用 function calling / tool use，让模型以 JSON 结构表达决策，便于程序解析与执行。
- **护栏与控制**：步数上限、超时、工具白名单、参数校验、人类确认（human-in-the-loop）用于约束决策的风险。

## 典型工程场景

- **AI 编码助手 / 编码 Agent**：决定读哪个文件、改哪行、运行什么命令、是否重试。
- **检索增强问答（Agentic RAG）**：决定是否需要检索、检索什么、检索到的内容是否足够、要不要再查一次。
- **客服 / 工单自动化**：判断用户意图、调用订单/库存 API、决定是否转人工。
- **数据分析 Agent**：决定写什么 SQL/脚本、看到结果后下一步分析方向。
- **浏览器 / GUI 自动化**：根据当前页面观测决定点击、输入、翻页等操作。
- **运维 / SRE 助手**：根据告警和日志决定执行哪些排查命令、是否需要人工确认高危操作。

## 适用边界

**适合使用**

- 任务需要**多步骤、动态路径**，中间结果会影响后续走向。
- 需要在作答过程中调用**外部工具/实时信息**（检索、计算、API）。
- 问题开放、无固定流程，难以用确定性 workflow 穷举分支。
- 允许一定失败率并能通过观测纠错、重试的场景。

**不适合使用**

- 流程**固定且已知**：用确定性 workflow / 状态机更可靠、更便宜、更可测。
- 对**延迟和成本极度敏感**的高频在线请求（多轮推理开销大）。
- 要求**强确定性和可审计**的高危操作（金融交易、生产变更）——至少要加人工确认与硬约束。
- 单步、简单、无需外部信息的问答——直接一次 LLM 调用即可，无需 Agent 决策循环。

## 常见误区

- **把 Reasoning 当成答案本身**：思维链是决策依据，不是对外交付物，不应直接把 thought 返回给用户或当作最终结果。
- **"推理越多越好"**：盲目堆叠思考步骤会增加成本、延迟和跑偏概率；很多任务简单的 workflow 更合适。
- **误以为 temperature=0 就确定**：采样只是不确定性来源之一，环境返回和级联放大仍会导致行为漂移。
- **让模型自由决策却不设护栏**：缺少步数上限、工具白名单、参数校验，容易出现死循环、乱调工具、越权操作。
- **混淆 Agent 与 Workflow**：把固定流程硬塞给模型"自由决策"，既不稳定又浪费 token；该写死的就写死。
- **用单次结果评判 Agent**：应基于多次采样的成功率/统计指标评测，而非一次 demo。

## 我的结论

> 当任务路径不确定、需要边做边查边纠错时，才值得引入 Reasoning/Decision 循环——它的价值在于"动态性"，代价是不确定性、延迟和成本。
> 反过来，只要流程是已知且固定的，就应该用确定性的 workflow/状态机，把模型只用在真正需要判断的"决策点"上，并用结构化输出、工具白名单、步数上限和（高危场景的）人工确认把不确定性关进笼子里。
> 实践上倾向"分层"：用强推理模型做少数关键决策，用快而便宜的模型做执行与格式化，既控成本又保质量。
