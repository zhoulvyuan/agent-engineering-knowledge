# Agent 是什么

> **上级**：[03-Agent核心](README.md) ｜ **依赖**：Tool Calling

## 一句话定义

> Agent 是一类以大语言模型（LLM）为决策核心、能在「感知环境 → 规划 → 调用工具行动 → 观察反馈」的循环中自主推进，直到完成目标的软件系统。

## 解决的问题

在 Agent 范式出现之前，LLM 应用普遍是「一问一答」的单轮管线：

- 模型只能基于训练知识生成文本，无法读取实时数据、无法执行外部动作（查数据库、调 API、运行代码），知识会过期、也做不了副作用操作。
- 复杂任务需要人把问题拆成固定步骤、手工编排 Prompt 链（Chain），流程写死、无法根据中间结果动态调整；一旦某步出错，整条链就断了。
- 没有记忆与状态，模型无法跨多步累积上下文、无法从失败中重试修正。

Agent 把「让人编排流程」变成「让模型自己决定下一步做什么」，用工具打通了模型与真实世界，用循环实现了多步、可纠错的任务执行。

### Agent 与普通 LLM Application 的区别

核心区别在于**控制流由谁决定**。普通 LLM 应用（含固定 Prompt、固定 RAG、固定 Chain）的执行路径由开发者在代码里写死，模型只负责在某一步生成文本；Agent 则把「下一步做什么、是否调用工具、是否结束」交给模型基于当前观察动态决定。

| 维度 | 普通 LLM 应用 | Agent |
| --- | --- | --- |
| 控制流 | 开发者预先编排、路径固定 | 模型运行时动态决策 |
| 轮次 | 多为单轮或固定步数 | 多轮循环，步数不定 |
| 工具 | 可无，或固定调用 | 按需选择并调用工具 |
| 状态/记忆 | 通常无状态 | 维护对话历史、中间结果、工作记忆 |
| 纠错 | 出错即失败 | 可观察错误并重试/换策略 |

需要注意：两者是连续谱系而非非黑即白。固定流水线 + 一次工具调用更偏「应用」；赋予模型自主决策与循环能力才更接近「Agent」。

### Agent 的自主性来自哪里

自主性不是模型「有意识」，而是由以下工程要素叠加涌现：

1. **决策循环**：外层代码反复把「当前状态 + 可用工具」喂给模型，让它在每一步选择动作，而不是只跑一次。
2. **工具调用（Tool/Function Calling）**：模型能输出结构化的动作指令，由运行时执行并把结果回填，使模型的「想法」能作用于环境。
3. **反馈闭环**：工具返回结果（含报错）重新进入上下文，模型据此调整后续决策，实现观察—修正。
4. **目标导向的终止判断**：模型自己判断任务是否完成、何时停止。

因此自主性本质是「模型的语言决策能力」被「循环 + 工具 + 反馈」这套脚手架放大后的结果，边界由开发者给定的工具集、权限和终止条件约束。

### Agent 的基本组成（模型 / 工具 / 状态 / 循环）

- **模型（Model / 决策核心）**：负责推理、规划和决定下一步动作，是 Agent 的「大脑」。能力上限基本决定 Agent 的上限。
- **工具（Tools / Actions）**：模型可调用的外部能力集合，如检索、代码执行、API 调用、文件读写。每个工具有名称、参数 schema 和描述，供模型选择。
- **状态与记忆（State / Memory）**：短期记忆（对话历史、本轮中间结果、scratchpad）与长期记忆（向量库、持久存储），为多步决策提供上下文。
- **循环（Loop / Orchestration）**：驱动「模型决策 → 执行工具 → 观察结果 → 再决策」反复进行的控制器，并负责终止条件、步数上限、异常处理。ReAct 的「Thought–Action–Observation」是最典型的循环形态。

四者缺一不可：缺工具则无法行动，缺状态则无法累积，缺循环则退化为单轮应用，缺好模型则决策不可靠。

## 核心内容

- **决策循环是本质**：Agent = LLM + 工具 + 在循环中反复决策。最经典的范式是 ReAct（推理 Reasoning 与行动 Acting 交替）。
- **工具是手脚**：通过 Function/Tool Calling 让模型以结构化方式请求外部能力，运行时执行后把 Observation 回填上下文。
- **上下文工程**：每一步把目标、历史、工具结果、约束组织进上下文窗口，是 Agent 工程的核心难点（受窗口大小、噪声、成本约束）。
- **规划能力**：简单任务靠单步决策；复杂任务可引入显式规划（任务分解、计划—执行、树/图搜索如 ToT）。
- **终止与护栏**：需设置最大步数、超时、权限边界、人工确认（human-in-the-loop）防止死循环与越权。
- **多 Agent 可选**：复杂系统可拆成多个专职 Agent 协作（如 Planner/Worker/Reviewer），但会引入编排与一致性成本。

## 典型工程场景

- **AI 编码助手**：读代码库、运行测试、改文件、看报错再修（Cursor、Claude Code、各类 coding agent）。
- **自动化运维/数据分析**：根据告警自主查日志、查指标、定位问题并给出或执行修复。
- **复杂客服与业务助理**：跨多个内部系统（查订单、改状态、发工单）完成一个用户诉求。
- **深度研究/信息聚合**：多轮搜索—阅读—归纳，产出带引用的研究报告。
- **RPA 升级版/浏览器自动化**：在网页或桌面环境中完成多步操作任务。

## 适用边界

**适合使用**

- 任务步骤不确定、需根据中间结果动态决策的开放性问题。
- 需要调用多种外部工具/系统，且调用顺序因情况而异。
- 允许一定延迟和成本以换取自动化程度（多轮调用意味着更高 token 与时延）。
- 结果可验证、可回退，或有人工确认兜底的场景。

**不适合使用**

- 流程固定、步骤明确的任务——直接写确定性代码或固定 Chain 更快、更省、更可控。
- 对延迟/成本/确定性要求极高的在线核心链路（多轮推理不可控）。
- 高风险且不可逆的操作（资金转账、生产删库）且缺乏护栏与人工确认时。
- 单次问答即可解决、无需工具与多步的简单任务。

## 常见误区

- **「接了工具就是 Agent」**：固定调用一次工具的流水线仍是应用，关键在模型是否在循环中自主决策。
- **「Agent 越自主越好」**：自主性越高越难预测和调试，工程上常刻意收窄权限、固化部分流程以换取可靠性。
- **「Agent 能自己想清楚一切」**：Agent 能力上限受模型推理能力限制，复杂规划仍易出错、绕圈、幻觉调用。
- **「多 Agent 一定比单 Agent 强」**：多数任务单 Agent + 好工具已足够，盲目多智能体会放大协调成本与错误传播。
- **「Agent 不需要确定性代码」**：成熟系统往往是 Agent 决策 + 确定性代码护栏的混合体，而非纯 LLM 驱动。

## 我的结论

Agent 的价值在于「把运行时控制权交给模型」，所以它只在**任务路径不确定、需要动态决策和多工具协作**时才划算。当流程可以预先写死时，用确定性代码或固定 Chain 几乎总是更快、更便宜、更可控——不要为了用 Agent 而用 Agent。

落地时的判断线：先问「这个任务能不能写成固定流程？」能，就别上 Agent；不能，再评估是否值得为自主性付出 token、时延和不确定性的代价。即便决定用 Agent，也应尽量收窄工具权限、设置步数/超时上限、对高风险动作加人工确认，用确定性护栏包住不确定的决策核心。
