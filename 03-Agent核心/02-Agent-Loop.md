## 一句话定义

> Agent Loop 是"观察环境 → 用模型推理决策 → 执行动作（含工具调用）→ 把结果再喂回模型"反复迭代、直到任务完成或触发终止条件的运行时控制循环，是 LLM 从"一次性回答"升级为"自主完成多步任务"的执行骨架。

## 解决的问题

> 单次 LLM 调用是无状态、一步到位的：模型只能基于已有上下文生成一段文本，无法在生成后获取新信息、无法执行真实动作、也无法根据动作结果纠正自己。于是遇到需要多步推理、调用外部工具、与环境交互、根据反馈修正的任务时，开发者只能手工串接 prompt、人工把中间结果拼回去，既不可扩展也无法自主纠错。Agent Loop 把"决策—执行—反馈"固化成一个自动迭代的运行时，让模型可以分步骤、带反馈地推进任务。

### Loop 为什么是 Agent 的核心

- 它是"自主性"的来源：没有循环，LLM 只能一问一答；有了循环，模型才能在拿到新证据后改变计划，表现出"自己把任务做完"的行为。
- 它把"思考"与"行动"解耦并串联：每一轮产生一个决策（继续思考 / 调工具 / 结束），每一轮的结果又成为下一轮的输入，形成闭环反馈。
- 其他 Agent 要素（记忆、工具、规划、反思）本质都是挂在这个循环上的插件：记忆决定每轮喂什么上下文，工具是每轮可选的动作，规划/反思是对循环节奏的调制。
- 换句话说，Agent = LLM（决策器）+ Loop（控制流）+ Tools（执行器）+ State（记忆），其中 Loop 是把其余三者组织起来的中枢。

### State 在 Loop 中的作用

- State（状态/上下文）是循环的"记忆载体"，典型包括：原始目标、历史消息、已执行的工具调用及其返回、中间结论、剩余预算（步数/token）等。
- 它保证循环的连续性：每一轮推理都要基于累积状态，否则模型会"失忆"、重复已做过的动作或忘记目标。
- 它是上下文窗口压力的主要来源：状态随循环增长，需要用截断、摘要、向量检索、滚动窗口等策略压缩，否则会撑爆 token 限制或稀释关键信息。
- 工程上常把 State 分层：短期（本轮对话消息）、工作记忆（当前任务的 scratchpad）、长期记忆（跨会话、落库或向量库），循环只在需要时把相关片段"召回"进上下文。

### Tool Calling 如何进入 Loop

| 环节 | 做了什么 |
| --- | --- |
| 声明 | 把可用工具的名称、描述、参数 schema（如 JSON Schema）随请求发给模型 |
| 决策 | 模型在推理这一轮输出"要调用哪个工具 + 结构化参数"，而不是直接回答 |
| 执行 | 运行时解析该结构化调用，真正执行函数/API，拿到返回结果 |
| 回灌 | 把工具返回（成功结果或错误）作为新的 observation 追加进 State |
| 迭代 | 带着新结果进入下一轮推理，模型据此决定继续调用、换工具还是给出最终答案 |

- 关键点：模型本身不执行工具，它只"请求"调用；真正的执行与结果回灌由循环的运行时负责，这一来一回正是循环推进的驱动力。
- 一轮可支持并行多工具调用（并行 tool calls），运行时需全部执行完再把结果一并回灌。

### 循环的终止条件如何设计（自然终止 / 迭代上限 / 外部中断）

- 自然终止：模型判断任务完成，输出不含工具调用的最终答案（或显式调用 `finish`/`submit` 这类终止工具）——这是最理想的收敛方式。
- 硬性上限：设置最大迭代步数、最大工具调用次数、最大 token / 时间 / 成本预算，达到即强制停止，防止失控。
- 外部中断：用户取消、上游超时、人工介入（human-in-the-loop）审批被拒、或检测到危险动作时由运行时主动打断。
- 异常终止：连续工具报错、无法恢复的错误、或进入已知无效状态时提前退出并返回部分结果或错误说明。
- 工程建议：多种条件叠加使用，且终止时要有优雅的收尾（返回当前最佳结果 + 说明为何停止），而不是静默失败。

### 如何防止死循环与无限工具调用

- 预算约束：对步数、工具调用次数、总 token / 时间 / 费用设硬上限，是最后一道兜底防线。
- 循环检测：记录动作指纹（工具名 + 参数），若短时间内重复出现相同或高度相似调用则判定为"打转"并干预。
- 进展度量：跟踪任务是否在推进（如新信息增量、子目标完成数），长时间无进展则强制反思或终止。
- 提示与结构约束：在系统提示中明确"不要重复无效调用""每步要说明是否更接近目标"，并要求结构化输出便于校验。
- 错误处理回路：工具报错要把清晰的错误信息回灌给模型让其纠正，而不是让它盲目重试同样的调用；对重试本身也要限次数。
- 必要时人工介入：高风险或长时间卡住的循环升级给人工决策。

## 核心内容

- 基本节拍：Observe（获取环境/工具反馈）→ Reason/Decide（模型推理下一步）→ Act（执行动作，常为工具调用）→ 将结果 Observe 回灌 → 迭代，直到 Terminate。
- 四大构成：决策器（LLM）、控制流（循环逻辑与终止判断）、执行器（工具/环境）、状态（上下文与记忆）。
- 决策形态：每轮模型要么产出"工具调用请求 + 参数"，要么产出"最终答案"（即隐式结束循环）。
- 典型实现范式：ReAct（推理与行动交替、显式写出 Thought/Action/Observation）、Function/Tool Calling（结构化调用）、Plan-and-Execute（先规划后分步执行）、Reflexion（引入自我反思修正）。
- 必备的工程护栏：迭代上限、预算控制、循环/重复检测、错误回灌与重试限制、超时与中断、可观测性（trace 每一轮的输入输出）。
- 状态管理：上下文累积与压缩（截断/摘要/检索召回）、短期与长期记忆分层。
- 可观测性与可恢复性：对每一轮打点记录，支持回放、调试，必要时可从中间状态续跑。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | LLM 推理与 Function/Tool Calling | 循环的每一轮决策都依赖模型的推理能力和结构化工具调用能力；没有可靠的工具调用，循环无法驱动真实动作 |
| 下游 | 多 Agent 协作 / 规划与反思（Planning、Reflexion）/ 具体 Agent 框架（LangGraph、AutoGPT 等） | 这些都建立在单个 Agent Loop 之上：多 Agent 是多个循环的编排，规划/反思是对循环节奏的增强 |
| 易混淆 | Chain（固定流水线，如 LangChain Chain）、RAG 的检索-生成、工作流引擎 | Chain/工作流是预先编排、步数固定的有向流程；Agent Loop 的步数与路径由模型在运行时动态决定，具备自主分支与循环能力，这是本质区别 |

## 典型工程场景

- 编码助手 / 自主编程 Agent：读文件 → 运行命令 → 看报错 → 改代码 → 再运行，循环直到测试通过。
- 深度研究 / 问答 Agent：多轮检索、交叉比对、调用多个数据源后综合成答案。
- 运维 / SRE 自动化：观察告警与指标 → 诊断 → 执行修复脚本 → 验证是否恢复。
- 浏览器 / GUI 操作 Agent：根据页面状态循环决定点击、输入、导航，完成下单、填表等任务。
- 数据分析 Agent：生成查询/代码 → 执行 → 看结果 → 迭代修正分析口径。
- 客服 / 流程自动化：多步调用业务 API（查单、改单、退款）直至完成用户诉求。

## 适用边界

**适合使用**

- 任务需要多步推理、且中间步骤依赖外部信息或工具返回。
- 执行路径无法预先确定，需要根据反馈动态分支或重试。
- 需要与环境交互并根据结果自我纠错（如编码、运维、研究）。
- 容忍一定延迟与成本，换取自主完成度。

**不适合使用**

- 任务是单步、确定性的（简单问答、翻译、分类）——直接一次调用更快更省。
- 流程固定、步骤已知——用 Chain / 工作流引擎更可控、可预测、可审计。
- 对延迟/成本极敏感或要求强确定性的场景——循环的不确定性和多次调用是负担。
- 高风险且不可逆的动作且无人工审批——自主循环的失控风险不可接受。

## 常见误区

- 把 Agent Loop 等同于"套个 while 循环"：真正难点在状态管理、终止判断、错误回灌与护栏，而非循环语法本身。
- 以为步数越多越聪明：过长循环常是模型在打转或迷失目标，反而消耗成本、放大错误累积。
- 混淆 Chain 与 Agent：固定编排的流水线不是 Agent Loop，缺少运行时的动态决策与自主分支。
- 忽视终止与预算设计，导致死循环、费用飙升或无限工具调用。
- 认为模型自己会执行工具：模型只产出调用请求，执行和结果回灌必须由运行时实现。
- 不做可观测性：没有逐轮 trace，循环一旦出错极难调试和复现。

## 我的结论

> 当任务是"多步、路径不固定、依赖外部反馈并需要自我纠错"时，才该上 Agent Loop——它的价值正是用运行时的动态决策换取自主完成度。反之，若流程固定、步骤已知，就用 Chain / 工作流；若任务单步确定，就直接一次 LLM 调用。决定用它之后，工程成败不在"会不会写循环"，而在三件事：状态怎么管（上下文压缩与记忆分层）、什么时候停（自然终止 + 预算上限 + 中断）、怎么防失控（循环检测、错误回灌、可观测性）。把这三件事做扎实，Agent Loop 才是可靠的生产力，而不是烧钱的黑盒。
