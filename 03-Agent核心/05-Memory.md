# Memory / 记忆

> **状态**：🟢 已理解 ｜ **深度**：A 深入掌握 ｜ **更新**：2026-09-15
> **上级**：[03-Agent核心](README.md) ｜ **依赖**：Context / 上下文、Agent Loop

## 一句话定义

> Memory 是 Agent 在"当前上下文窗口之外"持久化、组织并按需召回信息的机制，让 Agent 能跨越单次调用、单轮对话甚至多次会话保持连续性与经验积累。

## 解决的问题

> LLM 本身是无状态的：每次推理只能看到被塞进上下文窗口的内容，窗口一关闭，之前的交互、用户偏好、任务进展就全部丢失。上下文窗口还有长度上限和成本约束，无法把历史全部堆进去。于是出现几类麻烦：对话多轮后 Agent "失忆"、反复询问已知信息；跨会话无法记住用户习惯；长任务中间状态无处存放；检索到的知识用完即弃、无法沉淀为经验。Memory 就是为了把"需要跨越窗口边界存活的信息"从易失的上下文里剥离出来，单独管理。

### Memory 为什么需要存在

- 根因是 LLM 的**无状态性 + 有限上下文窗口**：模型每次只处理当次输入，不自带跨调用的持久状态。
- 窗口有物理上限（token 数）与经济上限（长上下文推理慢且贵），无法把全部历史无脑拼接。
- 长程任务（多步骤规划、多日协作）需要中间状态、决策理由、已完成项的存档，否则无法恢复或续作。
- 个性化要求 Agent 跨会话记住用户是谁、偏好什么、之前约定过什么，这类信息天然要存在窗口之外。
- 一句话：Memory 把"该长期存活的信息"与"当前这次推理要看的信息"解耦，前者归 Memory，后者归 Context。

### 短期记忆 / 长期记忆的划分

| 维度 | 短期记忆（Short-term） | 长期记忆（Long-term） |
| --- | --- | --- |
| 生命周期 | 单次会话/任务内有效 | 跨会话、持久存在 |
| 载体 | 多数直接等同于上下文窗口 + 临时缓冲 | 外部存储：向量库、KV、文档库、关系库 |
| 典型内容 | 本轮对话历史、当前任务中间状态、刚检索的片段 | 用户画像/偏好、历史事实、沉淀的经验与教训 |
| 访问方式 | 直接读取（已在窗口里） | 需要显式检索/召回后再注入窗口 |
| 写入成本 | 几乎为零（就在上下文里） | 需要抽取、嵌入、落库，有延迟与成本 |

- 工程上常再细分：**工作记忆（working memory）**约等于当前窗口；**情景记忆（episodic）**记"发生过什么事/交互轨迹"；**语义记忆（semantic）**记"稳定的事实与知识"；**程序记忆（procedural）**记"怎么做某事的流程/技能"。
- 短期与长期之间需要"**固化（consolidation）**"通道：把短期中值得保留的内容抽取、摘要后写入长期。

### Memory 与 Context 的区别

- Context 是**当前这次模型调用实际看到的 token 集合**（system prompt、对话历史、工具结果、检索片段等），是"此刻在模型眼前的东西"。
- Memory 是**信息的持久仓库与管理机制**，大部分内容平时不在窗口里，只有被召回时才临时注入 Context。
- 关系：Memory 是"仓库"，Context 是"工作台"；Context Engineering 决定每一步从 Memory 里取什么、放多少、怎么排布进窗口。
- 易错点：短期记忆常和 Context 重叠（都在窗口内），但 Context 还包含 prompt、工具 schema 等非记忆内容；而长期记忆绝大多数时间根本不在 Context 中。
- 一句话：所有在窗口里的都是 Context，但只有"需要跨步骤/跨会话存活的信息"才算 Memory。

### Memory 的工程实现方式（存储 / 检索 / 写入时机）

- **存储**：
  - 向量库（如 FAISS/pgvector/Milvus）存可做语义检索的文本片段；
  - KV / 文档库（Redis、MongoDB）存结构化画像、键值偏好、会话状态；
  - 关系库 / 知识图谱存实体关系；
  - 原始对话日志单独归档以便审计与再加工。
- **检索/召回**：常见为语义相似度检索（embedding + top-k）、关键词/元数据过滤、时间衰减与重要性加权（如近因 + 频次 + 重要度评分），以及基于当前任务的查询改写；召回后还需去重、重排、压缩再注入。
- **写入时机**：
  - 轮末/回合结束触发抽取（从本轮对话抽事实与偏好）；
  - 窗口将满时做摘要固化（把旧历史压缩成记忆条目）；
  - 显式信号触发（用户说"记住……"、任务里程碑达成）；
  - 后台异步固化（避免阻塞主回路）。
- **治理**：需要更新/纠错（新事实覆盖旧事实）、去重、过期清理（TTL）、冲突消解与版本管理。

### 什么该记、什么不该记

- **该记**：用户稳定偏好与身份约束、长期有效的事实、任务目标与关键决策及其理由、重要的失败教训与成功经验、跨会话需要延续的状态。
- **不该记**：一次性的闲聊、容易过期的瞬时信息（如"现在几点"）、可随时重新计算或重新检索得到的内容、与未来任务无关的噪声。
- **谨慎记**：敏感/隐私数据（PII、凭证）——若非必要不存；必须存时要加密、脱敏、最小化并遵循留存与删除合规（如用户要求遗忘）。
- 判断准则：三问——未来会不会再用到？能否廉价重算而不必存？存了是否带来隐私/合规风险？只有"会复用、重算不划算、风险可控"才值得写入长期记忆。

## 核心内容

- **本质**：对抗 LLM 无状态性与窗口有限性的持久化信息层。
- **分层**：工作记忆 / 短期记忆（≈窗口）与长期记忆（外部存储），长期内再分情景 / 语义 / 程序记忆。
- **读写回路**：抽取（从交互中提炼）→ 固化/写入（落库、嵌入、摘要）→ 检索/召回（语义+元数据+重要性）→ 注入（重排、压缩进 Context）→ 更新/遗忘（纠错、去重、过期）。
- **关键机制**：摘要压缩、重要性评分、近因加权、冲突消解、TTL 过期、异步后台固化。
- **与检索的衔接**：RAG 是面向外部知识库的检索增强，Memory 则偏向 Agent 自身交互产生的、可增量写入的个性化状态；两者技术栈高度重叠但语义目的不同。

## 典型工程场景

- 个人助理/客服 Agent：记住用户姓名、偏好、历史工单，跨会话不重复询问。
- 长程编码 Agent：记录项目约定、已做的架构决策与失败尝试，避免重复踩坑。
- 多轮对话压缩：会话变长时把旧历史摘要成记忆条目，腾出窗口。
- 多 Agent 协作：共享任务状态与中间产物作为团队"黑板"。
- 自我改进/反思循环：把成功与失败经验固化为可召回的教训，提升后续决策质量。

## 适用边界

**适合使用**

- 需要跨多轮或跨会话保持连续性、个性化的应用。
- 长程、多步骤、状态复杂、单窗口装不下的任务。
- 需要沉淀经验、让 Agent 随使用变"更懂你"的场景。

**不适合使用**

- 一问一答、无状态的单次调用（直接用 Context 即可，加 Memory 是过度设计）。
- 信息可随时廉价重算或实时检索、无需持久化的场景。
- 强隐私/合规约束下、不允许留存用户数据的场景（需极度克制或禁用长期记忆）。

## 常见误区

- 把 Memory 等同于"更大的上下文窗口"——加长窗口不解决跨会话持久化与成本问题。
- 以为"全存下来"就好——无节制写入会带来噪声、召回质量下降、隐私与成本风险。
- 把 Memory 和 RAG 混为一谈——两者技术栈重叠，但目的（自产增量状态 vs 外部静态知识）不同。
- 忽视"遗忘与更新"——只写不删会让旧事实、冲突信息污染召回，必须有纠错/过期机制。
- 认为检索召回总是准确——召回是概率性的，可能漏召或召回无关内容，需重排与验证。
- 忽略敏感信息治理——把 PII/凭证直接写入向量库是常见安全隐患。

## 我的结论

> 当应用需要**跨越单次上下文窗口的连续性**（多轮个性化、跨会话记忆、长程任务状态、经验沉淀）时，就该引入 Memory，并按"短期≈窗口、长期入外部存储"分层，配齐抽取—固化—召回—更新—遗忘的完整回路。
> 当任务是无状态的单次问答、信息可廉价重算、或处于严格隐私约束下时，就**不该**上长期记忆——它会带来噪声、成本与合规负担。核心判断不是"能不能记"，而是"这条信息未来会复用、重算不划算、且风险可控"——三者同时成立才值得写入。
