## 一句话定义

> Multi-Agent 是把一个复杂任务拆给多个各自拥有独立上下文、角色和工具权限的 Agent，通过显式的消息传递与协调机制协作完成的系统架构。

## 解决的问题

> 单个 Agent 在面对复杂任务时会遇到几类硬约束：（1）上下文窗口被长流程、海量工具描述和中间结果塞满，导致注意力稀释、指令遵循下降；（2）一个 Agent 既要做规划、又要做检索、又要做写代码、又要做审查，角色混杂使得 prompt 难以同时优化，表现趋于平庸；（3）工具数量一多，模型选错工具的概率上升；（4）缺乏天然的并行能力，串行处理慢。Multi-Agent 通过"分工 + 上下文隔离 + 并行"来缓解这些问题：每个子 Agent 只看自己该看的信息、只持有自己该用的工具、只被一段专门的指令驱动。

### 为什么需要多个 Agent

核心动机不是"多就是好"，而是三条可量化的收益：

- **上下文隔离**：主 Agent 的上下文是稀缺资源。把一次需要读 20 个文件的调研丢给子 Agent，子 Agent 只把结论（而非 20 个文件的原文）返回主上下文，主 Agent 的 token 预算被显著节省，长程任务更稳。
- **角色专精**：规划、检索、编码、审查对 prompt 和模型的要求不同。拆成独立角色后，每个角色的系统提示、工具集、甚至底层模型都能单独调优（如审查用更强模型、检索用更便宜模型）。
- **并行吞吐**：相互独立的子任务（扫描多个目录、多角度搜索、对多个候选方案打分）可以同时跑，墙钟时间从 O(n) 降到接近 O(1)。
- **权限最小化**：不同 Agent 持有不同工具权限，便于把高危操作（写文件、执行命令）限制在特定角色，降低风险面。

反过来，如果任务本身是线性、短、单一技能的，多 Agent 带来的收益为零，只剩开销。

### Multi-Agent 与 Workflow 的关系

两者是"自主程度"光谱的两端，常被混用，但工程语义不同：

| 维度 | Workflow（工作流） | Multi-Agent（多智能体） |
| --- | --- | --- |
| 控制流 | 由开发者预先编排、固定（DAG/状态机） | 由 LLM 在运行时动态决定调用谁、调几次 |
| 可预测性 | 高，路径确定、易测试 | 低，路径随输入变化 |
| 适用场景 | 步骤明确、重复性高的流程 | 任务开放、路径难以预先枚举 |
| 成本/延迟 | 可控 | 波动大，可能发散 |

实践中二者常嵌套：用 Workflow 做骨架（保证可控与可观测），在某个节点内放一个自主 Agent 处理开放子问题；或反过来，Orchestrator Agent 在编排层调用若干被固定成 Workflow 的子流程。先问"路径能不能提前画出来"——能就用 Workflow，不能才上 Agent 自主编排。

### Multi-Agent 是否真的比单 Agent 更好

不一定，取决于任务结构，不能一概而论：

- **更好的情形**：任务可清晰并行拆分、子任务间耦合低、每个子任务产出可压缩成简短结论（典型如"广度搜索/调研"）。Anthropic 公开过其研究系统在这类任务上多 Agent 显著优于单 Agent，但也指出其 token 消耗约为普通对话的 15 倍。
- **更差的情形**：任务高度耦合、需要共享大量中间状态、或要求前后一致性（如一次性重构一大段相互依赖的代码）。此时跨 Agent 传递状态的损耗、以及各 Agent 对全局缺乏统一认知，反而制造冲突和返工。
- **工程结论**：多 Agent 用 token 和架构复杂度换上下文容量与并行度。只有当"被省下的上下文/被并行的时间"价值 > "额外 token + 协调开销 + 调试难度"时才划算。默认先把单 Agent 做到极致，遇到明确瓶颈再拆。

### 多 Agent 的通信成本与上下文隔离问题

这是 Multi-Agent 最被低估的工程难点：

- **通信即丢信息**：子 Agent 之间只能通过文本消息传递，等于每次协作都经过一次"有损压缩"。主 Agent 的意图、约束、隐含上下文很难完整传给子 Agent，子 Agent 的发现也会在汇总时被压缩，容易产生误解和返工。
- **隔离与共享的张力**：隔离省 token、防污染，但也意味着子 Agent 看不到彼此的工作，可能重复劳动或得出互相矛盾的结论。需要一个汇总/仲裁角色或共享的外部记忆（如共享文件、黑板）来兜底。
- **成本放大**：每个 Agent 都要带自己的系统提示、工具描述和历史，token 随 Agent 数量和轮次近似相乘增长；并行还会放大瞬时并发成本。
- **可观测性与调试**：失败可能发生在任意子 Agent 或某次传递中，非确定性让问题难以复现。工程上需要全链路 trace、给每个 Agent 的输入输出打标、并对单个 Agent 设超时与轮次上限防止发散。
- **缓解手段**：把协议写死（规定返回的结构化字段）、让主 Agent 下发任务时明确边界与期望产出、用结构化输出而非自由文本做跨 Agent 接口、对子 Agent 结果做校验与去重。

## 核心内容

- **基本构成**：Orchestrator（主/编排 Agent）+ 若干 Worker（子 Agent）+ 共享或各自的 Memory + 消息/协调机制。
- **常见协作拓扑**：
  - *Orchestrator-Worker（主从/分派）*：主 Agent 拆任务、派发、汇总，最常用、最可控。
  - *并行扇出（Fan-out/Fan-in）*：同时跑多个独立子 Agent，再聚合结果。
  - *流水线（Pipeline）*：Agent A 的输出作为 Agent B 的输入，串联处理（如 生成→审查→修订）。
  - *辩论/评审（Debate/Critic）*：一个生成、一个批判，用对抗提升质量。
  - *群聊/去中心化*：多个 Agent 在共享对话里自由发言，灵活但易失控。
- **三个关键机制**：
  - *任务分解*：由谁、按什么粒度拆分，直接决定并行度和耦合度。
  - *通信协议*：消息格式（自由文本 vs 结构化字段）、共享记忆（黑板模式）、同步/异步。
  - *终止与仲裁*：谁判断任务完成、如何合并冲突结论、如何设轮次/超时上限防发散。
- **角色设计原则**：单一职责、最小工具权限、明确的输入契约与产出契约。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | Agent Loop（单 Agent 的感知-规划-行动-观察循环） | 每个子 Agent 本质仍是一个独立的 Agent Loop，Multi-Agent 是在其之上做编排 |
| 上游 | Memory（短期/长期记忆、共享记忆） | 跨 Agent 的状态共享依赖外部记忆（黑板、共享文件），是协作的基础设施 |
| 下游 | Agent 应用框架（LangGraph、AutoGen、CrewAI 等） | 这些框架把 Multi-Agent 的拓扑、消息、状态管理工程化落地 |
| 易混淆 | Workflow / Pipeline（固定编排） | Workflow 是开发者写死控制流，Multi-Agent 让 LLM 运行时决定协作路径；二者可嵌套 |

## 典型工程场景

- **深度调研/研究助手**：主 Agent 拆解问题，多个子 Agent 并行从不同角度检索、各自读大量资料，最后汇总成报告（广度优先、天然并行）。
- **大型代码库任务**：一个子 Agent 做跨文件审计/检索，把结论回传，主 Agent 保留上下文做实现；或"实现 Agent + 审查 Agent"做对抗式质量把控。
- **复杂数据处理/迁移**：对成百上千个文件/记录做同一处理，用并行子 Agent 扇出。
- **多角色模拟**：客服、产品、法务等多视角评审一份方案。
- **工具/权限隔离**：把高危操作（部署、删库）隔离给专门且权限受限的 Agent。

## 适用边界

**适合使用**

- 任务可清晰拆分为低耦合、可并行的子任务。
- 子任务产出能被压缩成简短结论，适合"读得多、带回来的少"的调研型工作。
- 需要上下文隔离以避免主 Agent 被海量中间信息污染。
- 需要多角色专精（不同系统提示/模型/工具权限）或角色间对抗评审。

**不适合使用**

- 任务线性、短、单一技能——单 Agent 甚至直接函数调用即可。
- 子任务高度耦合、需要频繁共享大量中间状态或保证全局强一致（如一体化重构）。
- 对延迟、成本、可预测性要求高——此时优先固定 Workflow。
- 团队尚未把单 Agent 的可观测性与评测做扎实，贸然上多 Agent 只会放大调试难度。

## 常见误区

- **"Agent 越多越聪明"**：多 Agent 主要换取上下文容量与并行度，不直接提升单步推理质量；拆得不好反而更差。
- **把 Workflow 当 Multi-Agent**：很多"多 Agent"其实是开发者写死的流水线，并没有运行时自主编排，混淆了二者的可预测性与成本特征。
- **忽视 token 成本**：多 Agent 的 token 消耗可能是单对话的十余倍，没有成本/收益核算就上线。
- **幻想无损通信**：以为子 Agent 能完整理解主 Agent 的意图，实际上每次消息传递都是有损压缩，需要靠结构化协议和明确契约兜底。
- **缺少终止与仲裁**：不设轮次/超时上限、不处理结论冲突，系统容易发散或自相矛盾。
- **无可观测性**：没有全链路 trace 就上多 Agent，故障几乎无法复现和定位。

## 我的结论

> **默认不用，证明必要再用。** 先把单 Agent（配合长上下文、好的工具设计和记忆）做到瓶颈，再考虑拆分。
> **该用的信号**：任务能并行拆分、子任务低耦合、产出可压缩成简短结论、或主上下文被中间信息严重污染——典型就是"广度调研"和"隔离高危/重活"。此时多 Agent 用 token 换容量与速度，划算。
> **不该用的信号**：任务线性或高度耦合、要求强一致、对成本和延迟敏感、或可观测性尚未建好。这些场景下固定 Workflow 或单 Agent 更稳、更便宜、更好调。一句话：Multi-Agent 是扩展上下文和并行度的架构手段，不是提升智能的魔法。
