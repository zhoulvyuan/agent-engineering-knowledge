# Planning / 规划

> **状态**：🟢 已理解 ｜ **深度**：A 深入掌握 ｜ **更新**：2026-09-15
> **上级**：[03-Agent核心](README.md) ｜ **依赖**：Agent Loop

## 一句话定义

> Planning 是 Agent 把一个高层目标拆解成一组有序、可执行的子任务，并在执行过程中根据反馈动态调整这组任务序列的能力。

## 解决的问题

> 在没有 Planning 之前，LLM 只能"一问一答"或靠一次性 prompt 完成任务，面对需要多步骤、跨工具、有依赖关系的复杂目标时会失败：模型要么试图一步到位导致中间步骤出错且无法纠正，要么被硬编码的固定流程束缚，无法应对任务的多样性和运行时的意外情况。Planning 让 Agent 能够先想清楚"分几步做、先做什么后做什么"，再逐步推进，并在偏离目标时重新组织步骤。

### Agent 为什么需要 Planning

- 复杂目标无法由单次推理直接完成：真实任务往往包含多个相互依赖的子步骤（如"调研—分析—撰写—校对"），需要显式拆解才能逐步推进。
- 单步推理缺乏全局视角：LLM 逐 token 生成，容易"走一步看一步"而陷入局部，Planning 提供一个全局骨架，约束后续动作朝目标收敛。
- 工具调用需要编排：多工具、多数据源的任务存在顺序和依赖（先查询再汇总再写入），Planning 负责确定调用顺序与数据流。
- 可控性与可解释性：显式的计划让人类可以在执行前审查、在执行中干预，也便于失败时定位是哪一步出了问题。
- 降低错误累积：把大任务切成可验证的小步，每步可以单独检查和纠错，避免错误在长链条中被放大。

### Planning 与普通 Workflow 的区别

| 维度 | 普通 Workflow | Agent Planning |
| --- | --- | --- |
| 流程来源 | 开发者预先编排、硬编码 | 由模型在运行时根据目标生成 |
| 灵活性 | 固定路径，分支需提前写死 | 可按输入和中间结果动态生成步骤 |
| 适应性 | 遇到未预期情况会卡住或报错 | 可感知失败并重新规划 |
| 可预测性 | 高，行为确定可复现 | 较低，存在不确定性 |
| 典型代价 | 覆盖面受限、维护成本高 | token/延迟成本高、可能跑偏 |

一句话：Workflow 是"人把路线画好让 Agent 走"，Planning 是"Agent 自己找路"。两者常混合使用——用 Workflow 固定可靠的骨架，在需要灵活性的节点交给 Planning。

### 动态规划与预定义流程的取舍

- 任务结构稳定、分支有限、对可靠性/合规性要求高 → 优先预定义流程（确定、可测试、可审计、成本低）。
- 任务开放、输入多变、无法穷举路径 → 需要动态规划（灵活、泛化好，但不确定、成本高、难调试）。
- 实践中的折中：外层用预定义流程保证边界与安全，内层在特定节点启用动态规划；或先让模型规划、再由规则校验计划合法性后执行。
- 取舍本质是在"可靠性/成本 ↔ 灵活性/覆盖面"之间权衡，应由任务的变异度和错误代价来决定，而非默认用最"智能"的方案。

### 计划何时应该被重新规划（replan）

- 某步执行失败或工具返回错误，且重试无法解决时。
- 执行结果与预期显著偏离（如检索为空、数据与假设矛盾）。
- 获得了规划时未知的新信息，使原计划的前提失效。
- 外部环境或用户目标发生变化（用户补充/修改需求）。
- 检测到循环或无进展（反复执行相似步骤却不接近目标）。
- 工程实现上通常有两种触发方式：按固定节奏周期性 replan（如每 N 步重估一次），或由显式的失败/偏差信号事件驱动 replan；同时需设置最大重规划次数以防死循环。

## 核心内容

- 任务分解（Task Decomposition）：把目标拆成子任务，常见方式有链式分解（CoT）、树状搜索（ToT）、以及按依赖关系构造 DAG。
- 规划范式：
  - 一次性规划（Plan-and-Execute / Plan-and-Solve）：先生成完整计划再执行，适合结构清晰的任务。
  - 交错式规划（ReAct 类）：推理与行动交替，走一步看一步，适合高度动态的任务。
  - 带反思的规划（Reflexion / self-critique）：执行后对结果反思并修正计划。
- 计划表示：自然语言步骤列表、结构化 JSON、代码（如 CodeAct/程序化计划）、或任务图。
- 反馈与重规划闭环：执行 → 观察结果 → 评估是否偏离 → 必要时 replan，构成 Agent Loop 的核心。
- 记忆配合：计划的中间状态、已完成/待办步骤需要在上下文或外部记忆中维护（如 todo 列表、scratchpad）。
- 终止与护栏：步数上限、重规划上限、成功判据，避免无限循环与成本失控。

| 上游 | Agent Loop / ReAct | Planning 嵌在"推理-行动-观察"循环中，Loop 提供执行与反馈的框架，是 Planning 运转的载体 |

| 易混淆 | Workflow 编排、Prompt Chaining | 后者是开发者预先固定的步骤链；Planning 强调由模型在运行时动态生成并可重规划 |

## 典型工程场景

- 深度研究 / 调研助手：拆解为"检索—筛选—交叉验证—综述"的多步流程。
- 编码 Agent：把需求拆成"定位文件—修改—编译—测试—修复"的计划并按反馈迭代。
- 复杂数据分析：多表联查、清洗、聚合、出图的步骤编排。
- 运维/自动化：故障诊断时按"查日志—定位—假设—验证—修复"分步推进。
- 多工具/多 API 任务：如差旅规划（查航班+酒店+日程），需要确定调用顺序与依赖。
- 需要人类审查的高风险操作：先出计划交人审批，再执行。

## 适用边界

**适合使用**

- 目标需要多步、跨工具、有依赖关系才能完成。
- 输入多变、路径无法事先穷举，需要运行时自适应。
- 任务允许一定不确定性，且可以用验证/反思来纠错。
- 需要可解释的执行轨迹（计划可供人审查）。

**不适合使用**

- 单步或固定流程即可完成的任务（直接 Workflow 更可靠、更省成本）。
- 对延迟/成本极敏感的高频在线场景。
- 对确定性、合规性要求极高、不容许模型自由发挥的流程。
- 缺乏可靠反馈信号、无法判断步骤成败的环境（Planning 难以收敛）。

## 常见误区

- 认为"计划越细越好"：过度分解会放大每步的误差并增加成本，粒度应与可验证性匹配。
- 把 Planning 等同于一次性生成完整计划：忽略 replan 闭环，遇到意外就卡死。
- 认为有了 Planning 就不需要固定流程：实际工程常是 Workflow + Planning 混合最稳。
- 混淆"规划能力"与"模型会不会用工具"：计划再好，工具调用/反馈不可靠一样失败。
- 不设护栏：缺少步数/重规划上限，导致死循环和成本爆炸。
- 盲信模型生成的计划：计划需要被校验（合法性、依赖、安全性）后才执行。

## 我的结论

> 当任务是"多步骤 + 有依赖 + 路径不可预先穷举 + 有可用的成败反馈"时，才真正值得上 Planning；此时它带来的灵活性和纠错能力能抵消其成本与不确定性。
> 反之，若流程稳定、分支有限、对确定性和成本敏感，就用预定义 Workflow，不要为了"显得智能"而让模型自由规划。
> 最务实的做法是分层：外层用确定的 Workflow 兜住边界与安全，在确有必要的节点启用动态规划，并始终配上重规划触发条件、步数/次数上限和计划校验这三类护栏。
