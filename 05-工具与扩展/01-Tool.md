# Tool / 工具

## 一句话定义

> Tool 是暴露给大模型调用的一个带结构化参数契约（schema）的外部能力单元：模型通过生成一次符合 schema 的调用请求，让宿主程序执行真实世界的动作（查数据、算数、改状态），并把结果回灌给模型继续推理。

## 解决的问题

> 在没有工具之前，LLM 只是一个"闭卷"的文本生成器，它的能力被三个硬边界卡死：
>
> - **知识截止与不可更新**：训练数据有时间上限，无法回答实时信息（天气、股价、工单状态）。
> - **不能产生副作用**：模型只能"说"，不能"做"——无法真正发邮件、下单、写数据库、调用内部系统。
> - **不擅长确定性计算**：精确算术、日期运算、代码执行、检索海量私有数据，用概率生成的方式既不可靠也不经济。
>
> Tool 把这些"模型不该自己硬扛的事"外包给确定性的程序，让模型专注于理解意图与编排，从而把语言模型从"问答玩具"变成能接入真实业务系统的 Agent 执行引擎。

### Tool 的定义

Tool 是对"一个可被模型按需触发的外部能力"的封装，通常由四部分构成：

- **name**：唯一标识，模型用它来指定调用哪个工具。
- **description**：自然语言说明"做什么、什么时候用、什么时候不用"，这是模型做选择的首要依据。
- **parameters schema**：一般为 JSON Schema，声明入参的字段、类型、枚举、必填项与约束。
- **执行体（handler）**：真正运行的代码，由宿主程序而非模型执行，返回结构化结果。

关键点：模型本身**不执行**工具，它只负责"产出一个结构化的调用意图"；执行与结果回传由 Agent 运行时（宿主）完成。工具因此是"模型意图"与"真实副作用"之间的受控边界。

### Tool 的输入输出契约

| 环节 | 内容 | 说明 |
| --- | --- | --- |
| 输入 | 模型生成的 `arguments`（JSON） | 必须满足 parameters schema；运行时应先校验再执行 |
| 执行 | 宿主调用 handler | 可能涉及网络、DB、文件、子进程等副作用 |
| 输出 | 结构化结果 + 状态 | 成功时返回数据，失败时返回错误对象，均作为新一轮上下文回灌给模型 |

契约要点：

- 入参应是**自描述、可校验**的；运行时需做 schema 校验、类型转换与边界检查，不能盲目信任模型输出。
- 返回值最好是**结构化且简洁**的（JSON 优于长文本），并显式携带成功/失败标志，便于模型判断下一步。
- 输出要控制体积：大结果应分页、截断或摘要，避免一次把上下文窗口撑爆。

### Tool 与传统 API / Function 的关系

- **底层同构**：一个 Tool 的 handler 本质上就是一次函数调用或一次 API 请求，技术栈完全复用。
- **差别在"消费者"**：传统 API/Function 的调用者是确定性代码（参数固定、调用时机由程序逻辑决定）；Tool 的调用者是概率性的模型（是否调用、何时调用、传什么参数由模型"决定"）。
- **因此多了一层契约语义**：Tool 需要面向模型的 `description` 和自然语言可理解的 schema，而普通 API 只需面向开发者的文档。
- **工程含义**：不能把任意内部 API 原样暴露成 Tool。要做收敛、鉴权、幂等、参数裁剪，把"给人/给代码用的接口"重新包装成"给模型用的、意图清晰且防呆的接口"。

### 工具 schema 如何设计才不容易被误用

- **描述即规格**：`description` 要写清适用场景、不适用场景、与相邻工具的区别，必要时给正反例，减少模型选错工具。
- **约束前移**：能用 `enum`、`type`、`required`、取值范围、正则限制的就写进 schema，让非法输入在校验阶段就被挡住，而不是靠 handler 兜底。
- **参数最小化**：只暴露模型真正需要填的字段；内部可推导、可从上下文注入的字段（如租户 ID、鉴权信息）不要交给模型填。
- **语义明确、避免歧义命名**：字段名要自解释（用 `start_date` 而非 `d1`），单位/格式写进描述（如 ISO 8601）。
- **一个工具只做一件事**：功能正交、粒度合适；避免"万能工具 + mode 参数"，那会让模型更难选对分支。
- **防危险操作**：高风险动作（删除、支付、群发）应拆出独立工具、加确认参数或二次校验，不要和低风险读操作混在一起。

### 工具执行失败时如何把错误反馈给模型

- **结构化错误而非抛异常**：handler 捕获异常后，返回带 `error`/`code`/`message` 的结构化结果作为工具输出回灌，让模型"看见"失败并自行决策，而不是直接让整条链路崩溃。
- **错误信息要可操作**：告诉模型"为什么失败、如何修正"（如"参数 date 格式应为 YYYY-MM-DD"），而不是只给一个栈信息或 500。
- **区分错误类型**：
  - 可重试（超时、限流）→ 提示模型稍后重试或退避。
  - 参数错误 → 提示具体字段，引导模型重新生成调用。
  - 不可恢复（权限不足、资源不存在）→ 明确告知，让模型放弃或走降级路径。
- **防循环**：对同一工具的连续失败设重试上限，避免模型陷入"失败→重试→再失败"的死循环，必要时上抛给用户。
- **安全脱敏**：错误里不要把内部堆栈、密钥、SQL 原文等敏感信息直接回灌进上下文。

### 工具数量增多后如何保证选择准确率

- **工具检索/路由（RAG over tools）**：工具很多时不要全量塞进 prompt，先用向量检索或分类器按当前意图召回 Top-K 相关工具，只把候选集交给模型。
- **分层/分组**：按领域分组或用"父工具 → 子工具"两级结构，先选大类再选具体工具，降低单次选择空间。
- **描述质量治理**：工具选错往往源于描述含糊或多个工具描述重叠；要定期审查、去重、明确边界。
- **命名空间与数量控制**：单层暴露的工具数量建议控制在十几个量级以内；超出就引入路由。
- **评测驱动**：建立"意图→应调用工具"的评测集，持续回归工具选择准确率，发现系统性误选再针对性优化描述或路由。
- **约束解码/强制 schema**：用 function-calling 的结构化输出能力，保证产出的调用在格式上一定合法，减少"调用名拼错、参数缺失"类错误。

## 核心内容

- **四要素**：name（标识）、description（选择依据）、parameters schema（输入契约）、handler（执行体）。
- **调用闭环**：模型发起调用意图 → 运行时校验参数 → 执行 handler → 结构化结果回灌 → 模型基于结果继续推理，可多轮迭代。
- **职责分离**：模型负责"要不要调、调哪个、传什么参数"（概率/语义层）；运行时负责"校验、执行、鉴权、错误处理"（确定性/安全层）。
- **结构化优先**：输入输出都用 JSON Schema/JSON，便于校验、约束解码与可观测。
- **可观测与可控**：工具调用是 Agent 行为的审计点，应记录每次调用的参数、结果、耗时、成败，用于调试、评测与安全管控。
- **与推理循环耦合**：Tool 常与 ReAct / Function Calling / Agent Loop 配合，形成"思考—行动—观察"的循环。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | Tool Calling / Function Calling | 模型侧产出"调用哪个工具、传什么参数"的能力，是 Tool 得以被触发的前提机制 |
| 下游 | Agent / ReAct 循环、MCP（Model Context Protocol） | Tool 是 Agent 执行动作的基本单元；MCP 则把 Tool 的发现、描述、调用标准化为跨系统协议 |
| 易混淆 | 传统 API / RPC、Plugin、RAG 检索 | 底层都是函数/接口调用，但 Tool 的"调用者是模型且需面向模型的契约"；RAG 是把知识塞进上下文，Tool 是执行动作，二者目的不同（检索工具是 Tool 的一种特例） |

## 典型工程场景

- **实时信息查询**：天气、航班、股价、内部工单/订单状态等需要最新数据的问答。
- **企业系统集成**：让 Agent 读写 CRM、ERP、数据库、工单系统，完成下单、改状态、建工单等操作。
- **精确计算与代码执行**：调用计算器、SQL 查询、Python 沙箱做数据分析与可靠计算。
- **检索增强**：把向量库/搜索引擎封装成检索工具，为问答提供私有知识。
- **办公自动化**：发邮件、建日程、生成/修改文档、调用文件系统与命令行（如本会话中的编码 Agent）。
- **多系统编排**：一个任务串联多个工具（查库存→下单→发通知），由模型按结果动态决定下一步。

## 适用边界

**适合使用**

- 需要**实时、私有或外部**数据，模型知识无法覆盖。
- 需要产生**真实副作用**（写数据、改状态、触发流程）。
- 需要**确定性、可验证**的结果（精确计算、代码执行、结构化查询）。
- 动作可被清晰定义为"输入 → 输出"且参数可枚举/可校验。

**不适合使用**

- 纯语言任务（改写、总结、翻译、风格润色），模型自身即可完成，加工具反而增加延迟和出错面。
- 动作边界模糊、无法用 schema 清晰约束参数的任务。
- 高频、低延迟、确定性的流程——这类用传统硬编码管道比让模型"决定调不调"更可靠、更便宜。
- 极高危操作且无法加防护（无确认、无回滚）时，不应直接交给模型自主调用。

## 常见误区

- **"把所有内部 API 原样暴露给模型就行"**：会导致选择困难、参数误用、权限与安全风险；需做收敛、裁剪与包装。
- **"工具越多越强"**：工具过多显著降低选择准确率并撑爆上下文，需要路由/检索与数量控制。
- **"模型会自己执行工具"**：模型只产出调用意图，执行、鉴权、校验都在运行时，安全责任在宿主侧。
- **"schema 写个大概就行"**：描述含糊、约束缺失是误调用的头号来源；描述与约束就是工具的"规格"。
- **"失败就抛异常"**：异常应被捕获并转成结构化错误回灌给模型，否则模型无法自我修正。
- **"工具输出可以无脑回灌"**：大体积/敏感输出需截断、摘要、脱敏，否则污染上下文或泄露信息。

## 我的结论

> 当任务需要"模型做不了或不该做的确定性动作"——实时数据、真实副作用、精确计算——时，就应该用 Tool，把这部分能力外包给确定性程序，让模型只做意图理解与编排。反之，纯语言生成任务、能用固定管道硬编码的确定性高频流程、以及无法用 schema 清晰约束的模糊动作，不应该套 Tool：那只会增加延迟、成本和出错面。
>
> 判断口诀：**"模型能可靠地直接给出答案"就别加工具；"必须碰外部世界或要确定性结果"才加工具，且每个工具都要像设计公共 API 一样认真设计它面向模型的契约（描述 + schema + 错误语义）。** 工具的工程重点从来不在"能不能调通"，而在"模型能不能稳定地选对、填对、从失败中恢复"。
