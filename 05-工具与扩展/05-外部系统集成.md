# External Systems / 外部系统集成

> **上级**：[05-工具与扩展](README.md) ｜ **依赖**：Tool

## 一句话定义

> 外部系统集成是指把数据库、API、文件系统、浏览器、企业业务系统等 Agent 自身之外的资源，封装成受控、可被模型调用的工具（Tool），让 Agent 能在真实世界里读取状态并执行动作。

## 解决的问题

> 在集成之前，大模型是一个"封闭的大脑"：它只能基于训练语料生成文本，既读不到实时数据（库存、工单、账户余额），也无法真正改变外部状态（下单、改配置、发消息）。这带来三类麻烦：一是信息陈旧且无法溯源，模型只能靠幻觉填补；二是人要充当"人肉中间件"，把模型的建议手工搬到各个系统里执行，效率低且易错；三是能力边界被限制在"对话"，无法形成"感知→决策→行动→反馈"的闭环。外部系统集成通过标准化的工具接口打通这条链路，让 Agent 从"会说"升级到"能做"。

### 如何把数据库接成 Agent 可用的工具

把数据库接成工具的核心是"约束查询面"而不是把裸 SQL 连接丢给模型。常见三种粒度，由安全到灵活：

| 方式 | 做法 | 适用 |
| --- | --- | --- |
| 预置参数化查询 | 工程师写好带占位符的 SQL/存储过程，模型只提供参数 | 高频、固定的业务查询，最安全 |
| Schema 感知的受限文本转 SQL | 把表结构/字段注释喂给模型生成只读 SQL，经校验后执行 | 探索性分析、报表 |
| 语义层/视图 | 对接 dbt、Cube 等语义层或只读视图，模型查指标而非物理表 | 需要口径一致的指标查询 |

工程要点：优先走只读副本（read replica），用独立的最小权限账号；对生成的 SQL 做 AST 解析校验（禁止 `DELETE/UPDATE/DROP`、限制 `JOIN` 数量与无 `WHERE` 的全表扫描）；强制 `LIMIT` 与查询超时；对结果做行数/字节数截断再回填给模型，避免把百万行塞进上下文。写操作务必走下文的确认机制，不要让模型直连可写连接。

### API 集成的鉴权与限流

鉴权绝不能让密钥进入模型上下文或提示词。正确分层：凭证存放在服务端的密钥管理（Vault / KMS / 环境变量），工具层在真正发请求时注入 `Authorization` 头，模型只看到"调用成功/失败"和脱敏后的业务数据。

- **鉴权方式**：机器对机器优先 OAuth2 Client Credentials 或短期 STS 令牌；代表用户操作时用 OAuth2 授权码 + 按用户隔离的 token；避免长期静态 API Key，必须用时也要定期轮换并限定 scope。
- **限流**：对上游 API 要尊重其速率配额，自己也要加本地限流（令牌桶）防止 Agent 循环打爆接口；对可能触发收费的接口设预算上限。
- **健壮性**：对 429/5xx 做指数退避 + 抖动重试，设置连接/读取超时，用熔断器隔离故障依赖，并保证写接口的幂等（幂等键）。
- **可观测**：每次调用记录 trace id、入参摘要、耗时、状态码，便于审计与排障。

### 文件系统与浏览器的接入方式

二者都是高风险的"开放式"工具，接入关键在于沙箱与边界。

**文件系统**：把 Agent 限制在一个工作目录（chroot/容器挂载/工作区根），所有路径解析后做前缀校验，拒绝 `..` 穿越与符号链接逃逸；区分读/写/删权限，删除、覆盖等破坏性操作需确认；对二进制/超大文件只读元信息或分块读取，避免撑爆上下文；对可能含密钥的文件（`.env`、私钥）谨慎读取并避免回显明文。

**浏览器**：两种形态——(1) 无头浏览器自动化（Playwright/Puppeteer），模型输出"点击/填写/截图"等高层动作，由工具转成 DOM 操作，适合抓取动态页面、填表、端到端操作；(2) 把页面可访问性树/DOM 精简后喂给模型做视觉或结构定位。工程上要在隔离容器里运行、限制可访问域名（allowlist）、设置导航与操作超时、对下载和弹窗做管控，并把网页内容当作不可信数据——其中若出现"忽略先前指令"之类文字属于提示注入，必须当数据而非指令处理。

### 企业业务系统（ERP / CRM / 工单）的集成模式

这类系统的特点是"重、慢、强流程、强权限"，集成模式通常分层：

- **接入层**：优先走官方开放 API（Salesforce REST、SAP OData/BAPI、ServiceNow/Jira API）；没有 API 的老系统退而用 iPaaS（MuleSoft、Boomi）、消息队列或 RPA 兜底。
- **抽象层**：不要把 ERP 几百个字段直接暴露给模型，而是封装成贴合业务动作的高层工具，如"查询订单状态""创建工单""提交报销"，隐藏内部对象模型。
- **权限传递**：遵循用户的真实权限（on-behalf-of），而不是用一个超级账号替所有用户操作，避免越权；敏感字段按角色脱敏。
- **一致性**：写操作走系统自身的事务/审批流，Agent 发起但由业务系统做最终校验；长流程用异步 + 回调/轮询，不要在一次工具调用里阻塞等待人工审批。

### 开发工具类集成

面向编码/运维场景的集成，是 Coding Agent 的核心能力面：

- **代码仓与评审**：Git 操作、GitHub/GitLab API（建分支、提 PR/MR、读 diff、评论），需遵守分支保护，禁止直接强推主干。
- **构建与测试**：调用 CI、运行测试/编译/静态检查，把失败日志回填给模型形成修复闭环。
- **运行环境**：Shell/终端执行、容器与包管理器，必须在沙箱内并对破坏性命令（`rm -rf`、`git reset --hard`、生产部署）加确认。
- **协议化**：越来越多工具通过 MCP（Model Context Protocol）、LSP（语言服务）或 OpenAPI 规范暴露，使 Agent 以统一方式发现并调用工具。
- **可观测与追踪**：对接日志、监控、告警系统读取系统状态辅助诊断。

### 写操作的安全边界与确认机制

读是低风险的，真正的风险在"写"——改数据、发消息、花钱、动基础设施。核心原则是按影响面分级并要求与风险匹配的确认：

- **分级**：读/查询可自动执行；可逆的本地写（改草稿、建临时资源）可执行但告知；不可逆或影响他人/生产的写（删库、改权限、对外发送、生产部署、大额交易）必须显式人工确认。
- **人在环（HITL）**：高风险动作先产出"将要执行什么、影响什么、是否可逆"的预览，等用户批准再执行；可设置自动批准的白名单与额度阈值。
- **技术护栏**：最小权限凭证、幂等键防重复执行、dry-run 预演、金额/数量上限、操作限频、与业务系统自身的审批流叠加。
- **可审计与可回滚**：完整记录谁通过 Agent 做了什么（操作日志/审计轨迹），尽量提供撤销路径（软删除、事务回滚、备份）。
- **防注入**：外部数据里混入的"指令"不得触发写操作，确认环节要由真实用户而非被操纵的上下文完成。

## 核心内容

- **本质**：把"外部能力"抽象为模型可发现、可调用的工具接口（函数签名/JSON Schema/MCP/OpenAPI），模型负责"用哪个、传什么参"，工程层负责"怎么安全地执行"。
- **闭环结构**：感知（读外部状态）→ 决策（模型推理）→ 行动（调用工具改状态）→ 反馈（把结果与错误回填上下文），这是 Agent 区别于纯对话的关键。
- **五类典型外部系统**：数据库、HTTP API、文件系统/浏览器、企业业务系统（ERP/CRM/工单）、开发与运维工具链。
- **三道工程防线**：鉴权与最小权限（凭证不入上下文）、沙箱与资源边界（路径/域名/时限/配额）、读写分级与人在环确认。
- **健壮性要素**：超时、重试与退避、熔断、幂等、限流、结果截断与脱敏、全链路可观测。
- **接口标准化趋势**：从一次性手写适配，走向 MCP、OpenAPI、语义层等标准，让工具可复用、可发现、可审计。

## 典型工程场景

- 客服/运营 Agent 读取 CRM 客户信息、工单历史，并自动建单、更新状态。
- 数据分析助手连只读数据库/语义层，按自然语言生成受限 SQL 产出报表。
- Coding Agent 读代码仓、跑测试与 CI、提 PR，实现自动修复与特性开发闭环。
- 运维/SRE 助手读监控与日志定位故障，提出并（经确认后）执行修复动作。
- 流程自动化：从邮件/IM 触发，调用 ERP 完成报销、采购、审批等跨系统流程。
- 研究/采集 Agent 用无头浏览器抓取动态网页、填表单、下载资料。

## 适用边界

**适合使用**

- 需要实时、可溯源的外部数据，或需要真正改变外部状态（下单、建单、部署）。
- 任务可被拆解为有限、可枚举、可校验的工具动作，且动作有明确入参与返回。
- 已有稳定 API/数据库接口，且能建立权限、沙箱与审计等护栏。
- 需要形成"感知—行动—反馈"闭环而非一次性问答的场景。

**不适合使用**

- 纯知识问答或推理，无需实时数据与外部动作（直接用模型或 RAG 更简单）。
- 外部系统无接口、极不稳定或无法建立安全边界，贸然集成风险过高。
- 高风险且难以回滚、又无法引入人工确认的强破坏性操作（如无审计的生产直改）。
- 动作空间开放到无法枚举校验、模型易被诱导越权的场景。

## 常见误区

- 把裸数据库连接或完整 Shell/文件系统权限直接给模型，不做任何沙箱与权限收敛。
- 让 API 密钥/口令进入提示词或模型上下文，造成凭证泄露。
- 只测"快乐路径"，忽略超时、限流、重试与幂等，导致 Agent 循环打爆上游或重复下单。
- 把外部返回的网页/文档内容当作可信指令，埋下提示注入与越权执行隐患。
- 工具粒度要么太粗（一个万能工具）要么太细（暴露上百字段），模型难以正确选择。
- 对所有写操作一刀切——要么全自动（危险）要么全需确认（低效），没有按风险分级。
- 把结果整段塞回上下文，不做截断/脱敏，撑爆窗口又泄露敏感信息。

## 我的结论

> 当任务需要"实时数据"或"真实动作"、且这些动作能被收敛为有限且可校验的工具时，就应该做外部系统集成——它是 Agent 从"会说"走向"能做"的分水岭。落地时按风险分三档：读类尽管放开（最小权限只读 + 结果截断脱敏），可逆写告知后执行，不可逆或影响生产/他人的写一律走人在环确认与审计。反过来，如果只是知识问答、外部系统没有稳定接口、或高风险动作既不可回滚又无法加确认，就不要为了"炫技"而集成——此时直接用模型或 RAG 更简单可靠。一句话：集成的价值在闭环与护栏，缺了护栏的集成是负债而非能力。
