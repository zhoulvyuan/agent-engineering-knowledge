# Skill / 技能

> **状态**：🟢 已理解 ｜ **深度**：A 深入掌握 ｜ **更新**：2026-09-15
> **上级**：[05-工具与扩展](README.md) ｜ **依赖**：Tool、Context Engineering

## 一句话定义

> Skill 是一份"按需加载的任务说明书"——把某类任务的操作流程、约定、脚本和参考资料打包成一个可复用单元，Agent 在遇到匹配的任务时才把它读进上下文，从而在不长期占用上下文的前提下获得专项能力。

## 解决的问题

> 在 Skill 出现之前，让 Agent 掌握一类专项任务（如"生成规范的 Word 报告""调用某内部系统的固定流程"）只有两条路：要么把全部操作说明和示例一股脑塞进系统提示词，导致上下文被长期占用、与任务无关时也在消耗 token、还相互干扰；要么把能力硬编码成工具/代码，灵活性差、迭代要改程序、非工程人员无法维护。结果是提示词越堆越臃肿、能力难以沉淀和复用、团队间无法共享最佳实践。Skill 用"可插拔的说明文档 + 按需加载"把专项知识从提示词里解耦出来，解决了上下文膨胀与能力复用这两个核心矛盾。

### Skill 解决什么问题

- 核心是**上下文经济性**与**能力复用**两件事。专项任务的详细说明如果常驻系统提示词，会在 99% 不相关的对话里白白占用上下文窗口，并稀释模型对当前任务的注意力。
- Skill 把这些说明外置为独立文件，平时只在目录里保留一行"摘要/触发条件"，真正命中任务时才加载完整内容，用极小的常驻成本换取专项能力。
- 它还解决**沉淀与共享**问题：最佳实践、企业内部规范、特定格式要求可以写成 Skill 文件，像文档一样被版本管理、评审、跨团队/跨 Agent 复用，而不必改动程序代码。
- 对非工程人员友好——用自然语言 + 少量脚本就能编写和维护，降低了"教会 Agent 做某类事"的门槛。

### Skill 与 Tool 的区别

| 维度 | Tool（工具） | Skill（技能） |
| --- | --- | --- |
| 本质 | 一个可被模型调用的函数/接口（有名字、参数、返回值） | 一份任务说明书（指令 + 流程 + 可选脚本/资源） |
| 作用 | 让 Agent 执行一个**原子动作**（读文件、发请求、查数据库） | 教 Agent **如何编排一连串动作完成一类任务** |
| 加载方式 | 工具的 schema 通常常驻上下文供模型选择 | 元信息常驻、正文按需加载 |
| 粒度 | 细（单次操作） | 粗（多步骤的完整工作流） |
| 内容 | 代码实现 + 结构化参数定义 | 自然语言为主，可内嵌命令/代码片段 |

一句话：**Tool 是"能做什么"的能力原语，Skill 是"遇到这类任务该怎么用这些能力把事做对"的方法论**。Skill 往往会在其正文里指挥 Agent 调用若干 Tool。

### Skill 与 Agent 的关系

- Agent 是执行主体（具备推理、规划、调用工具的循环）；Skill 是 Agent 可以挂载的"可插拔专长包"。二者是**宿主与插件**的关系。
- 一个 Agent 可以挂载多个 Skill，运行时根据任务动态选用其中一个或几个；同一个 Skill 也可以被不同 Agent 复用。
- Skill 不改变 Agent 的底层架构，只在上下文层面注入"针对某类任务的额外指令与资源"，相当于给通用 Agent 临时装上一套专业 SOP。
- 边界：Skill 本身不具备自主性，它不会主动决策，是否加载、何时加载由 Agent（或其调度框架）根据任务匹配来决定。

### Skill 如何按需加载以节省上下文

- **两级结构**：平时只在上下文里保留每个 Skill 的"名称 + 一句话描述 + 触发条件"（极少 token），完整正文存放在外部文件中。
- **触发匹配**：Agent 读取用户任务后，把任务意图与各 Skill 的描述做匹配（关键词命中或模型语义判断），命中才通过加载动作把该 Skill 正文读入上下文。
- **渐进式披露（progressive disclosure）**：Skill 内部还可进一步分层——正文先给概览和主流程，附带的大段参考资料/示例/脚本只在真正需要那一步时再读取，避免一次性灌满。
- **用完即弃的边界**：加载进来的只是完成当前任务所需的那一个 Skill，任务结束后不会污染后续无关对话。
- 这样常驻成本从"所有 Skill 的全文"降为"所有 Skill 的目录摘要"，上下文占用从 O(全部能力) 降到 O(当前任务)。

## 核心内容

- **构成**：一个 Skill 通常是一个目录/文件，含元信息（名称、描述、触发场景）、正文指令（步骤、约定、注意事项）、以及可选的附属资源（脚本、模板、示例数据、参考文档）。
- **元信息层**：供 Agent 做匹配与路由，必须精准概括"这个 Skill 管什么、什么时候用"，是常驻上下文的唯一部分。
- **指令层**：用自然语言写清工作流——前置检查、主流程、输出格式、错误处理与边界条件；可内嵌具体命令行或代码片段。
- **资源层**：模板文件、脚本、长参考资料，遵循渐进式披露，用到才加载。
- **生命周期**：注册 → 任务到来 → 匹配触发 → 加载正文 → 按指令执行（期间调用 Tool）→ 任务完成后释放。
- **可维护性**：以文件形式存在，天然支持版本管理、评审、跨 Agent 共享，迭代无需改动 Agent 代码。

## 与其他知识的关系

| 关系 | 知识点 | 说明 |
| --- | --- | --- |
| 上游 | Tool / 函数调用 | Skill 正文在执行时依赖底层 Tool 作为原子动作；没有工具，Skill 的流程无法落地。 |
| 下游 | Agent 任务编排 / 多步工作流 | Skill 被 Agent 加载后，驱动一次具体的多步骤任务执行，是 Agent 完成专项任务的直接依据。 |
| 易混淆 | System Prompt（系统提示词） | 两者都是"给模型的文字指令"，但系统提示词常驻且全局生效，Skill 按需加载且针对特定任务；把 Skill 内容堆进系统提示词恰恰是 Skill 要解决的反模式。 |

## 典型工程场景

- 生成符合企业规范的办公文档（如固定模板的 Word 报告、PPT、Excel 分析），把格式约定与操作步骤封装成 Skill。
- 对接内部系统的固定操作流程（如工单创建、合规审批、特定 API 的调用序列），用 Skill 固化 SOP。
- 代码仓库的专项任务（按团队规范发起 PR、运行特定测试与发布流程、按约定写 commit）。
- 领域专项能力（法律合同条款审查、财报结构化提取、特定数据管道的清洗规则）作为可复用技能包分发。
- 多 Agent 平台上沉淀和共享"最佳实践库"，让不同 Agent 复用同一套经过验证的流程。

## 适用边界

**适合使用**

- 任务是**可复用、有稳定流程**的一类（而非一次性临时需求）。
- 专项说明较长、但只在部分场景才用到——用 Skill 避免长期占用上下文。
- 需要跨团队/跨 Agent 共享、需要版本管理和评审的操作规范。
- 以自然语言 + 少量脚本即可描述清楚的工作流，便于非工程人员维护。

**不适合使用**

- 单次原子操作——直接做成 Tool 更干净，无需包一层 Skill。
- 需要严格确定性、低延迟或强安全校验的核心逻辑——应固化为程序代码而非自然语言指令。
- 任务流程高度动态、每次都不同，没有可复用模式时，封装成 Skill 反而增加维护负担。
- 内容极短、放进系统提示词成本可忽略时，拆成 Skill 属于过度设计。

## 常见误区

- 把 Skill 当成 Tool 的同义词——实际上 Skill 是编排层方法论，Tool 是能力原语，二者分工不同。
- 以为 Skill 全文会一直在上下文里——恰恰相反，节省上下文正是其设计目的，正文应按需加载。
- 元信息/描述写得含糊，导致触发匹配不准（该加载时没加载，或无关时误加载）。
- 把一个 Skill 写成包罗万象的大杂烩，违背"单一任务、职责清晰"原则，既难匹配又难维护。
- 把需要强确定性的核心逻辑也用自然语言写进 Skill，牺牲了可靠性，这类逻辑应落到代码。
- 忽视渐进式披露，把超长示例和参考资料全塞进正文，使"按需加载"又退化成上下文膨胀。

## 我的结论

> 当一类任务**反复出现、有稳定可复用的流程、且说明较长但并非每次对话都需要**时，就该用 Skill：它用极小的常驻成本（一行描述）换取专项能力，并让流程以文档形式沉淀、共享、迭代。反之，若是单次动作（做成 Tool）、需要强确定性的核心逻辑（写成代码）、或流程每次都不同无规律可循，就不该硬套 Skill。判断口诀：**原子动作交给 Tool，稳定流程沉淀为 Skill，核心可靠性逻辑交给代码。**
